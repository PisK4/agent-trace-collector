# Agent Note: 一致前缀发布

Status: implemented

## Problem

组派生把整组重算一次，落库前用 CAS 检查输入修订。CAS 不命中就整轮丢弃：计算了 3.7 秒，一行都不留，回到队列从头再来。生产热组实测约 40% 的轮次这样丢掉（330 秒内 461 次丢弃）。

丢弃的代价之所以是全有或全无，是因为读侧只有一条判据：组 `clean` 且发布修订等于输入修订。于是"组没算完"等于"页面什么都不能读"，落库段也就没有写半组的意义。

可这一轮的结论并非全部作废。链关系只依赖祖先，标题与摘要只依赖本行输入。输入在算完之后变过，改动落在某一笔之后时，它之前的行仍按本轮的输入算出来，结论仍然成立。只有链角色（按整组选主干）、工具配对与后台作业（可能被后来的请求补全）依赖整组。

## Decision

`derive_queue.from_sort` 承担边界。它从"一个没写全的排序键"改成一个定宽位置串：脏标记写入时记下最早受影响那一笔的 `started_ms`（16 位补零）。落库段把它当边界：

- 输入没变（`input_revision` 仍相等）：整组落库，清脏，`from_sort` 置 `~`。
- 输入变过且边界已知：只写位置严格小于边界的行。链关系与展示列写前缀，`chain_role`、工具行、后台作业一律不写。组保持 `dirty`。
- 输入变过但边界未知（空串，历史脏标记）：整轮抛 `derive_input_changed`，与旧口径同义。

位置相等一律排除：同一毫秒分不出先后。

写侧边界后来改为独立列 `claim_from_sort`，每轮认领重新起算，`from_sort` 退为已发布边界并由前缀轮推进——见[认领边界](2026-11-03-derive-claim-boundary.md)。

**可写集合按库里此刻的 `started_ms` 取，不按计划里的位置。** 迟到账本会改写 `started_ms`，计划算时的位置可能已经过期；结论来自计划，可写范围必须来自库。

**读侧按同一判据放行。** `derivedStateOf` 仍返回 `dirty`，但 `projectRow` 增加 `derived_prefix`：位置严格小于组 `from_sort` 的行，关系、标题、摘要、回复形状、上下文事件按落库值返回。`chain_role` 仍是 `unknown`，因为它是整组产物。`derivationOf` 把这种行记成 `chain_state='prefix'`，前端把它当作可读关系与可标新增的一档。

`from_sort` 的取值集合是三个互不重叠的形态：空串（未知，历史行与来源没给位置的标记）、`~`（无待处理变化）、16 位数字串（边界）。SQL 侧的 `rowPrefixSql` 与 JS 侧的 `prefixValid` 是同一判据的两处实现，只比较 `started_ms` 一列，不引入第二套排序键。

脏标记的写入点全部改为带位置：`markRequestGroupsTx` 与 `markOwnershipChangeTx` 取请求自身位置，`markKnownGroup`（用途判定）取该请求位置，hook 合并取源行与被移动行的位置，purge 取被删请求的最早位置。`rebuildDerived` 与显式用途升级仍然传空串——它们影响整组，没有可用的前缀。

## Alternatives considered

**只改落库，不动读侧。** 前缀写进去了，页面依旧只认 `clean`，全部落库成果在组完成前不可见。这条是原方案的默认形态，实测结论是收益为零。

**前缀发布包含 `chain_role`。** 角色按整组根的时间顺序选主干，再按后继数传播；只算到前缀时主干可能还没到齐，写下去等于给未算部分猜一个角色。读侧若放行它，一个后来独立重跑的会话会把真正的开头挤成分支。

**用完整排序键（`started_ms` + `sort_source` + `sort_key`）当边界。** 边界判定要在 SQL 与 JS 两处都成立。完整键需要拼 JSON 再比字节序，SQL 侧要复刻同一个序列化；只比 `started_ms` 让两边都只有一次比较。代价是同毫秒的相邻行一律不参与前缀，这只损失极端场景下的收益。

**沿用 `from_sort` 原来的 `MIN()` 语义，让边界自己往前走。** 前缀轮不清脏，`from_sort` 若继续 `MIN()` 会停在最初的值，下一轮的可写集合永远覆盖不到新落库的部分。改为"整组完成时置 `~`"，边界在每轮开头重新由脏标记写入。

**解冻切片路径来解决同一问题。** 切片路径已有分页计算与发布代，但它同样卡在读侧不认识代际当前性。那是同一件读侧工作的另一条实现，先做它等于把这次的可验证收益推迟。

## Consequences

- 冲突轮不再全丢：边界之前的行按本轮结论落库，页面在组完成前就能读到这些行。
- 组完成前页面能看到的东西变多，也变复杂：同一组里前缀行有摘要、边界之后的行没有。`derived_prefix` 与 `chain_state='prefix'` 把这件事显式化，前端按它决定是否标新增。
- 链角色与工具配对仍然要等整组完成。这是有意保留的：它们不是行级事实。
- 每轮多一次组内位置查询（前缀轮才执行）。组规模与一次组读同量级。
- `from_sort` 的三种形态成为持久格式的一部分：`~` 与空串不是同一个意思，读侧与写入点都必须按它区分。历史库里的空串不会被回填，它表现为"这一组不支持前缀"，行为与改动前一致。
- 前缀轮只写行级列，`derive_version` 因此只在真正变化的行上加一——与 [派生落库只写实际变化的行](../simplification/2026-11-02-derive-apply-diff.md) 的口径一致。
