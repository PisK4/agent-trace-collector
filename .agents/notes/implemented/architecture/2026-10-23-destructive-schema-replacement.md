# Agent Note: 旧库删除重建，不做 v4→v5 迁移

Status: implemented

## Problem

首版发布前的架构重构会改存储结构、来源映射与派生口径。v4 库里的派生结果按旧规则算出，补列能让新代码读得下去，却不会让结果变对；要在旧库上得到正确结果，必须重写派生并逐项核对守恒。与此同时，旧库的正文只在本机这一份，设计迁移时曾把它当成必须保住的事实。

这个前提现在不成立：本次重构之后，本地旧数据可以直接删除。再维护一条可续跑的迁移路径，就要长期保留两套读口径、一组只在旧库上触发的阶段与验收，成本高于它能保护的数据。

## Decision

v4→v5 没有迁移路径。普通 `openStore` 只接受两种状态：空数据目录（建到 v5）或已经是 v5 的库。低版本报 `schema_rebuild_required`，高版本报 `schema_version_unsupported`，空目录以外的零散表报 `schema_unknown`。没有 `migration:v5` 完成标记，也没有"结构已升级、数据未迁移"的中间态。

旧库的处理是显式动作：停采集器，把数据目录整体移走或删除，让新版本建新库；旧库里的正文与派生结果一起丢弃。需要留档时在升级前用旧版本导出，不依赖本仓库的工具读取旧结构。

源码随之删除：`V5_DELTA`、`initializeV5`、迁移状态机、守恒摘要与 `src/conservation.ts`，以及恢复时的迁移标记校验和 `--allow-incomplete-migration`。`scripts/backfill-fingerprint.ts` 保留为 v3/v4 时代的列补齐工具，它不会把旧库带到 v5；文档不再把它描述成升级到当前版本的路径。

## Alternatives considered

**显式可续跑迁移。** 曾经按阶段与游标推进、以守恒摘要验收、用不可变只读连接做 preview。它保护的是旧库里的正文与证据；前提变成"旧数据可以删除"之后，它只是在为首版前不存在的兼容需求付费。保留它还会让读模型与写入者多出一组只在旧库上成立的分支。

**只保留完成标记，不实现迁移。** 没有生产者就不会出现未完成标记，校验与恢复检查都是死路径。一个永远为真的门不值得存在。

**保留旧库只读挂载。** 读模型没有版本标记区分新旧口径，混合读取会把旧结果当成现行事实；要区分就得再引入一层版本适配，回到迁移的成本。

**在 `openStore` 里自动重建。** 启动时删库是隐式破坏，失败时无法区分"用户想重建"与"路径写错"；拒绝打开并把删除留给运维，破坏性与可解释性都更好。

## Consequences

- 升级代码前必须显式处理旧数据目录；忘记时启动被 `schema_rebuild_required` 拒绝，不会带着半套结构运行。
- 旧库里的正文无法通过本仓库工具读取；保留需求必须在升级前用旧版本导出。
- 备份与恢复只接受白名单版本、且包内 `user_version` 与清单一致的 bundle；不存在半迁移包。
- 回滚要同时恢复旧代码与旧数据目录，不能只回滚代码。
- 首次发布后若需要跨结构保留事实，重新引入迁移必须以那时的真实保留需求为依据，重新写一份提案。

## Testing

`tests/store.test.ts` 的「低版本库拒绝打开，空库建到当前版本」锁定 `schema_rebuild_required` 与新建库的 `user_version=5`，「拒绝未知的高版本 schema」保持；`tests/maintenance.test.ts` 的 bundle 回归只覆盖完整库的备份与恢复，不再有半迁移包用例。
