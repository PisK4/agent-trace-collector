# Agent Note: 认领边界

Status: implemented

## Problem

[一致前缀发布](../architecture/2026-11-02-derive-prefix-publish.md) 把 `from_sort` 用作边界，但它同时承担两件事：写侧可写范围与读侧可见范围。它的更新规则是「上次整组发布以来的最小值」，组长期算不完时就会冻住。

冻结的代价是每轮算出来的成果继续丢弃。一轮算完 3.7 秒，计划读到的是最新输入，落库却只写第一笔变化之前的行。按约 5 秒一笔的到达间隔，10 分钟的 dirty 期约 120 行停在边界之后，页面没有标题与关系，落库每轮重算后丢掉。

部署前遗留的空串边界同样卡在这里：它要等一次整组发布才会换成数字边界。本机 4,026 行的活跃组因此在窗口内持续整轮丢弃。

## Decision

队列新增 `claim_from_sort` 作为写侧边界，`from_sort` 退为读侧边界（已发布到哪儿）。两者取值形态相同：空串未知、`~` 无待处理、16 位补零的 `started_ms`。

认领是计算快照之前的一次单条 UPDATE，把 `claim_from_sort` 重置成 `~`。此后的脏标记两列一起取最小值；组从 `clean` 重新变脏时两列都从这次标记重新起算，上一版的已发布边界不与新边界取最小值。落库段：

- 修订没变：整组发布，两列一起清成 `~`。
- 修订变过且写侧边界是位置串：只写小于它的行，并把 `from_sort` 推进到它。组保持 dirty。
- 写侧边界是空串或 `~`：整轮作废。修订变过却没有任何认领后变化，说明有别的路径推进了修订，不能认任何行。

认领早于计算快照，写侧边界因此比真实快照更保守，只会少写。读侧只看 `from_sort`，所以计算期间页面不会失去已发布前缀。

迟到账本会把 `started_ms` 改小，写侧边界可能比已发布边界更早。`from_sort` 跟着退回，已发布前缀暂时缩小，那一轮不读还没按新位置重算的行；下一轮按新位置重算后再前进。宁可暂时少读，不读错的。

列是 `ALTER TABLE ADD COLUMN` 加常量默认值，存量行取空串。加列脚本自带列存在性判断：SQLite 没有 `IF NOT EXISTS`，一次失败的启动会让下次重试报 `duplicate column`，库卡在打不开的状态。

## Alternatives considered

**让 `from_sort` 自己前进，不新增列。** 读侧与写侧共用一列时，认领重置成 `~` 会让页面在整轮计算期间看不到已发布前缀。分开两列才能让写侧每轮重新起算，同时读侧保持上一轮的位置。

**只按本轮计划里的位置判前缀，不读库。** 迟到账本会改写 `started_ms`，计划里的位置可能已经过期。可写集合必须来自库，这一点上一轮已经定过。

**认领时不重置，改成记下认领时刻。** 时刻只能与 `started_ms` 比大小，而脏标记记的是受影响那一笔的位置；两者语义不同，混在一列里判不出边界。重置成 `~` 再取最小值最省。

**为遗留空串组做一次性回填。** 回填要替历史标记猜一个位置，猜错会放出没重算的行。认领路径让空串在第一次冲突轮自然失效，不需要猜。

## Consequences

- 组长期算不完时，已发布前缀逐轮前进，页面新增行不再等整组发布。收益上限是边界冻住期间新增与变化的行数，不是整组。
- 很快完成的组几乎不受影响：整组发布本来就频繁，边界总是新值。
- 部署前的空串组在第一次认领后进入前缀路径，不必再等整组发布。
- 计算成本不变，整组仍算一遍；落库写量不变，仍只写差异行。
- 每轮多一次单条 UPDATE 的认领写事务（`derive-claim`）。热组约每 5 秒一次。
- 维护脚本与在线进程同时跑派生时认领会互相覆盖，后果是多丢弃，不会写错。
- 切片路径不参与前缀发布；它发布时两列一起清成 `~`，语义与同步路径一致。
- `derive_queue` 的可恢复备份白名单扩展到 v9；旧包恢复后首次打开原地升级。
