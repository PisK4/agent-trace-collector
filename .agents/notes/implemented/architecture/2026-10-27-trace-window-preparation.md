# Agent Note: 中栏窗口读取的准备流水线

Status: implemented

## Problem

旧路径 `loadWindowReads` 按四笔一批读详情与最多两片可信增量，每批整栏重绘。组内步骤直接按缓存已装载到哪一步投影：同一批请求的步骤数量取决于响应先后，先到的组先长出几行、后到的再补；System 与前驱的比较、工具结果到调用方的摘要也取决于调用方是否恰好先读完。正在读的组会随批次增删行，读者的位置、选择与文字选择被反复打断。

还有一处并发空转：`loadDelta` 在 `state.loading` 为真时直接返回当前快照，准备阶段若按「未完成就再消费两片」循环，会立刻拿到未变化的结果反复打转。

## Decision

准备单元改成请求组，准备与提交分开。详情、显示依赖与增量预算都到位后，页面才把这笔记为可提交（[app.js](../../../../web/app.js) 的 `readyRequests`），提交时才按当前读取生成完整投影。

**显示依赖**（`settleDependencies`）：已确认前驱的元信息（System 比较）与已配对结果所属调用方的元信息（工具摘要）。依赖只读详情与元信息，不消费增量；只补窗口内的依赖，不扩大缓存边界；失败降级显示，不阻塞本组。

**增量预算**：每组在准备阶段自动消费至多 `DELTA_PIECE_BUDGET = 20` 片，每片跨度小于 40 条消息，沿用 store 的 `loadDelta(id, 2)`。出错即停，剩余缺口留在组内的增量事件行，由「点击续读」显式继续。预算有界，长请求不会把整条历史正文拉进缓存。

**窗口顺序**（`prepareWindow`）：首载时目标组单独先准备并提交，其余按窗口顺序四笔一组；整窗准备完成后才把 `state.revealed` 置位，此前的提交一直以选中组为锚。加载更早只准备新进窗口的组。作废项不参与批次，归 store 的自动重读；失败项随下一次窗口导航重试。

**三态投影**（`stepsOf`）：已备齐的组用当前读取投影，并更新保留投影；未备齐但有保留投影的组显示旧投影加 `data-stale`；两者都没有时显示一条 `preparingStep` 记录行「正在读取请求…」，组上带 `data-placeholder`。准备行是占位，不是证据：提交层对占位组不用步骤锚，改锚组本身，备齐替换时组顶不动。点中准备行会触发该组准备，行随占位一起消失，选中也一并清掉，不留一个指向已消失步骤的高亮。失败与作废的组不退回占位行，缺口原因与重试入口照旧可见。

**变化通知按影响面响应**（`onStoreChange`、`affectsRail`）：作废把该笔撤出可提交集；自动重读换新后，仅当该笔未登记且仍在窗口内时才重新备齐，已登记的组不因通知自动扩量。右栏只在变化落在当前请求、工具配对调用方或选中轮次两端时重绘，其余组的准备完成只提交中栏。

**增量消费去重**（[reader-store.js](../../../../web/reader-store.js) 的 `loadDelta`）：同一记录同一时刻只跑一条增量任务，并发调用共享同一任务与同一份页数预算；任务结束后释放。预算循环因此不会空转，存储层也不会被两个消费者各自推进消费位置。切换会话或重置阅读版本时释放对应的任务登记，旧任务不能被新快照复用。actor 未知时首片原文的读取及其证据边界见[孤立请求的正文与来源报告](../bug-fix/2026-10-27-unassigned-request-reading.md)。

窗口内点击走同一条准备路径（`ensureRead` → `prepareGroup`），已登记的组不因点击重新扩量；窗口外请求保持旧深度：详情、元信息与两片增量。

## Alternatives considered

**保留批次重绘，只加大批次。** 步骤数量仍由缓存进度决定，先到的组先长行；批越大，单次阻塞越久，没有改变「按响应顺序长出来」的语义。

**用会话级 `userMoved` 闩锁取消过期补偿。** 闩锁把「用户是否移动过」摊成整场状态，滚过一次之后所有批次永久停止补偿。捕获与恢复同在一次同步提交里完成，锚点只认提交瞬间的首条可见步骤，过期补偿不存在，闩锁没有必要。

**先显示读取事件行，再逐批替换成真实步骤。** 这是旧路径的形状：同一组的行会随读取进度增删，锚点节点频繁消失。准备行只占一行、只在组首次可提交前存在，替换一次完成。

**每组自动排空全部增量。** 预算无界，单笔超大请求会把整段历史正文读进页面缓存；增量事件行与显式续读本就是这条路径的诚实表达，不需要在准备阶段抹平。

**页面另存一份可写读取缓存供准备阶段使用。** store 仍是唯一读取缓存；页面只持有显示投影（`retainedSteps`）与准备结论（`readyRequests`），不复制正文。

## Consequences

收益：组一旦提交就带着完整步骤集，或带明确的续读入口；步骤不再随响应顺序增删改序，System 抑制与工具摘要不再依赖缓存命中顺序。准备期间每组只有一行占位，锚点落在组上，备齐替换不动组顶。右栏不再随每批读取重建。

代价：提交次数从「四笔一批」变为「一组一次」，同一窗口准备的模型生成与比较次数与组数同阶，比较本身不碰未变节点。失败是准备结论：失败的组在下一次窗口导航或点击重试前不自动重试，作废仍归 store 的自动重读。预算耗尽的组会显示增量续读行，这是明确的未完成输入，不是半份投影。

## Testing

`bun test tests/reader-store.test.ts tests/trace-view.test.ts tests/web.test.ts tests/trace-commit.test.ts tests/http.test.ts` 共 105 项通过（2026-10-27），新增并发增量消费去重测试：两个消费者共享同一任务、只发一条增量请求，任务结束后释放。`bun run typecheck` 通过。

合成浏览器验收（ego lite，`prototypes/synthetic-server.ts` 端口 8770，生产采集器未动）逐项断言：首屏出现占位组，全部备齐后占位为零、无旧版本标记、无增量续读行；准备完成后选中步骤只改高亮，70 个步骤节点全部保留；视口内点选前后滚动位置与锚点像素不变；「加载更早」从 30 组增到 52 组后，同一步骤的视口位置 78.125 → 78.078；换会话与显式刷新后无残留占位、无旧版本标记；网络延迟下点中占位行会就地备齐该组（另 29 组仍在准备）；注入一次工具结果 409 后，该组保留 3 条旧步骤并显示「旧版本 · 重读中」，自动重读换新后标记消失、仍为 3 步。像素截图本轮未采集，视觉项以 DOM 几何与属性断言代替。真实流量验收未执行，需单独授权。
