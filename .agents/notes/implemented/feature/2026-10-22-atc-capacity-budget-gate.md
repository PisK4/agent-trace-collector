# Agent Note: 容量预算从计划刻度冻结，未达成的目标留在预算里

Status: implemented

## Problem

报告能跑出来了，但"这一版能不能收"没有判据。阈值散在计划的正文里，改动之后只能靠人重读一遍数字，既没法自动判，也没法说明某个数字是从哪来的。更要紧的是负载端与采集器的关系。如果下限取自"这一轮实际发出多少"，采集器跟不上时它就把自己的缺口冻成标准，越跑越"通过"。

## Decision

`scripts/capacity-gate.ts` 持有报告、预算与门槛三者的形状与判定。预算从 `all` 的汇总报告冻结，`source_report_sha256` 对整个文件计算；每个场景一份 `ScenarioBudget`，每个上/下限都带 `basis`，取值为 `code-constant`、`product-target`、`baseline-envelope` 或 `proposed`。

上限分两类。有目标值的指标（hook 与 page 读时延、事件循环 p99、写事务）直接用目标或提案值当上限，不拿单轮包络去收紧。同一个 1 rps 场景两次跑，page 读 p95 是 33 ms 与 153 ms，差出四倍多，比"一成半余量"大得多；用单轮包络当上限，只会造出抖动红门。单调量（rss、存储字节、拒绝计数）没有目标值，取实测包络留一成半余量。写事务上限、积压年龄与排空上限标 `proposed`（900 ms 只说明"其它连接最多等写锁 1000 ms"，推不出成功上界）。

**速率场景的下限取自 `client.ticks_scheduled`（即 `durationMs × rps`，由 `scheduledTicks` 算出），不取自 `client.accepted`。** 长组不发 HTTP，行数下限直接钉 `config.requests`。只有 burst 这类既无速率也无笔数的场景，才退回实测接受数的 99%。`max.ticks_dropped` 为 0，标 `product-target`。丢刻度不是"跑得慢"，是这一档根本没测到。

冻结时用同一套判定跑一遍源报告，把失败项按场景写进 `unmet`。门槛脚本只认已冻结的预算，缺预算、缺报告或形状不符一律退出 2，通过退出 0，越界退出 1。只测到过的指标才进预算。长组的时延样本为 0 时不给它设时延上限，否则预算会变成"永远失败"。`backlog_max_age_ms` 为 null 表示整轮没见过脏组，按 0 读；`drain_ms` 为 null 表示超时未收敛，两者区别对待。

## Alternatives considered

**时延上限取"包络与目标里更紧的那个"。** 试过并放弃。单轮包络的方差大于余量本身，1 rps 的 page 读 p95 在两轮里是 33 ms 与 153 ms。抖动红门比放宽的阈值更糟，它会教人忽略门槛。要收紧到时延层面，得先有多轮跑出的稳定包络，那时再改这条规则。

**所有上限都取实测包络。** 产品目标会只剩注释的作用，实测再差也不会被判红。

**下限取实测接受数的 99%。** `baseline-5rps` 只发出 2,031 笔时下限会冻成 2,010，等于承认"采集器跟不上"是新标准。取计划刻度后，同一份报告的下限是 2,970，红门来自事实，与立场无关。

**把未达成的场景从预算里删掉，或把它的目标下调到实测值。** 两者都等于宣布目标已达成，与"产品目标未达成"这个记录直接冲突。

**门槛从单场景报告生成预算。** 单场景报告生成不出"全部场景"的预算，用它冒充全部会把没跑到的场景静默漏掉。

## Consequences

- 冻结出的预算里带着 `unmet`：`baseline-5rps` 的 `ticks_dropped`、`accepted`、`request_rows` 与 `event_loop_p99_ms` 都在其中。这份预算从第一天起就让门槛退出 1，这是记录，不是待修的配置项。
- `proposed` 的三个上限（`max_write_tx_ms`、`backlog_max_age_ms`、`drain_ms`）是没有证据支持的提案值，最终报告必须与"已验证"分开写。
- 预算不因某次优化结果改写，只有重新测量并重新冻结才变。
- 门槛对汇总与单场景两种输入都判，且两边缺项都算失败。判定不读 `notes`，只读指标。
- 时长与解释的权威在 [docs/architecture-design.md](../../../../docs/architecture-design.md) 的容量一节。本 note 只写为什么这样冻结。

## Testing

`bun test tests/capacity-gate.test.ts` 覆盖：预算缺失与形状不符（含哈希长度与缺 `basis`）都拒绝；报告缺失、非法与汇总形状都拒绝读取；有目标值的指标用目标本身、包络只用于单调量（fixture 的 200 ms p95 得上限 2000、90 ms 的 p99 得 100、rss 300 MB 得 375,000,001）；速率场景下限来自计划刻度（3,000 刻度丢弃 984 笔的报告下限为 2,970，且 `ticks_dropped` 越界）；长组按计划笔数取行数下限且不要求接受数；超上限、低于下限与 null 指标都记失败并给出 `-1`；报告与预算互相缺场景都记失败；汇总冻结把源报告已越过的门槛写进 `unmet`；扁平化把队列与存储读数一并交给判定。`bun run typecheck` 覆盖两个脚本的共享类型。
