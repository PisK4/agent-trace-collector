# Agent Note: 活跃区的沉降窗口

Status: implemented

## Problem

活跃会话分区（提案笔记 2026-11-03-live-session-activity-and-navigation）把活跃区提到顶部，但行在 `live_until` 到期的瞬间就下沉。列表本身不轮询，重排只发生在到期定时器和用户动作（首屏、加载更多）两处，所以抖动集中在到期那一刻：12 个活跃会话在约 11 秒内逐个过期，就成了 12 次重排、每次行位置移动一行。读列表或正要点击时被抽走一行，是这类抖动最难受的形态。

## Decision

- **保留期 60 秒 + 提交点对齐 30 秒**。`live_until` 过期后不立即沉降，等到它过期满 60 秒、且落在下一个整 30 秒边界时再移出活跃区。额外等待因此是 60–90 秒；同一段内过期的会话共享同一个提交点，只移动一次。
- **在途行豁免**。`inflight === true` 的行进区不等窗口，撤下也不等；它不进入「上一帧因最近活跃进区」的集合，在途结束后若没有最近活动就立刻回全部会话。在途是硬事实，不是估算。
- **到期基点改成提交点**。`liveCommitAt(row)` 给出 `ceil((live_until + 60s) / 30s)`，`nextCommitAt` 取代原来的 `nextLiveExpiry`；定时器仍只有一个，到点重排一次。继续沿用 `live_until` 会先在到期处空转一次，画面上什么也没发生。
- **状态跨渲染保留**。`createLivePartition()` 持有保留期中的 key 与上一帧靠「最近活跃」进区的 key。同一份快照内 `last_ms` 不变，所以保留期不依赖轮询，也不新增任何查询；服务端与 HTTP 返回结构零改动。
- **不引入动画**。整块 `innerHTML` 重排，节点被替换；沉降靠「位置变化」本身表达，`prefers-reduced-motion` 下与常态完全一致。

## Consequences

- 合成 12 行场景（快照静止、无重取）：活跃集合变化 13 次 → 2 次；跨区移动的行次 24 → 24（每行仍只动一次，但集中在同一提交点）。
- 合成单会话场景（t=0 与 t=80s 各更新一次、每 20s 重取）：变化 4 次 → 2 次，60s 处的「先下沉再回活跃」消失。
- 代价：活跃区最多多留 90 秒。时间格显示的仍是真实 `last_ms`，不伪造「刚更新」，所以只影响分区位置，不影响时间语义。
- 首次加载时已经过期的会话不会因为窗口被误判为活跃：没有上一帧的进区记录就没有保留资格。

## Alternatives considered

- **纯 90 秒保留、不对齐提交点**：额外等待固定 90 秒，但逐个到期仍是逐个移动，抖动次数不减，只是整体推迟。
- **按行去抖（debounce）而非共享提交点**：每行有自己的提交时刻，互不合并；实现更碎，收益反而更少。
- **后端 `activity_state` 投影或 `/api/activity` 长轮询**：能真正推送新会话，但要新增对外接口与常驻连接，超出本次「只改前端分区」的范围；评估结论是不做。
- **增量 DOM 更新 + 过渡**：无 DOM 测试环境，且实测 40 行重排没有 longtask；为不可见的过渡改渲染架构不划算。
