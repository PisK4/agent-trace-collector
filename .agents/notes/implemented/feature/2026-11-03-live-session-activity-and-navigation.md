# Agent Note: 活跃会话监控与导航异步顺序统一

Status: implemented

## Problem

会话栏需要显示哪些会话正在产生请求，并按最后活动时间排序，方便在多个会话之间找到正在推进的工作。现有[会话查询](../../../../src/queries/sessions.ts)按 `MAX(started_ms)` 倒序排列，但[页面](../../../../web/app.js)只在首屏和加载更多时读取列表。打开页面后，活动会话与新会话不会自动出现在正确位置。数据库的 `updated_at` 又会被费用回填等维护操作修改，不能直接用作活动时间。

会话切换、显式刷新、切窗与 URL 定位的异步顺序仍由 `app.js` 中多个入口分别安排。它们需要依次清理准备结果、读取窗口、核对导航是否过期、保护等待期间的新选择，再执行默认选择和定位。加入后台活动更新后，还会出现列表重排、活动通知与用户点击同时发生的情况；各入口继续自行维护这些顺序，会增加迟到任务覆盖新选择的机会。

未来桌面 APP 也要呈现这些活动。窗口关闭、睡眠唤醒和采集器重启都可能中断连接，界面需要恢复当前状态，不能把断线前的执行标记当作仍然有效。这份记录把活动监控与导航整理作为同一项功能规划：活动事实与活跃分区已交付，导航整理与桌面端仍在 `## Deferred`。

## Decision

会话栏的活动事实、顶部独立活跃分区与 60 秒沉降窗口已交付并合入 master：`49ac7bf`（摄入增量维护在途集合、按 60 秒窗口判定活跃）、`4cd6179`（活跃会话提升为顶部独立分区，全部会话不再重复）、`33870c5`（时间格定宽右对齐与分组计数样式）、`2178e79`（活跃判定、在途撤回、启动恢复与分区渲染测试）、`a16ed4c`（基准输出补 p95/p99）、`7291f66`（归属升级时迁移在途标记，并按 500 分块查询），经 `57491a4` 合并；随后 `68312d8` 把活跃区沉降改为保留期 + 整 30 秒提交点，经 `868882f` 合并。

后台更新只改变活动事实和列表内容；用户选择、URL 导航与主动定位始终通过现有页面入口处理。活动更新不得直接调用整窗刷新、改写选择或重置正文阅读位置。

导航异步顺序的集中管理**不在**本次交付内，仍由 `web/app.js` 的多个入口持有，见 `## Deferred`。本次也只增加会话栏的活动发现与更新，不包含正文自动追尾、整场历史自动排空或工具进程监控。切会话仍沿用现有默认开头窗口；查看最新内容使用明确的导航动作。

## 活动事实与排序

活动状态与数据是否可信分别表达。收到新记录可以证明最近有活动；只有可信的实时快照中存在该会话的未结束请求，才能显示模型请求中。

| 事实 | 可以表达什么 | 不能推出什么 |
| --- | --- | --- |
| 可确认归属的实时请求尚未结束 | 该会话有模型请求在途，范围含选路与重试 | 模型一定正在输出，或工具一定正在运行 |
| 收到新的请求或完成记录 | 会话最近发生过活动 | 此刻仍有请求执行 |
| 当前可信快照没有在途请求 | 当前没有观测到该来源的在途请求 | 会话已结束、工具已结束或正在等用户 |
| 接口断连、快照失效或来源不支持实时信息 | 当前运行状态待确认 | 会话空闲或执行成功 |

会话按最后一次已知活动发生时间倒序排列，同一时刻按稳定会话键排序。请求开始和明确的完成时间可以参与计算；完成时间缺失时不补造。工具或子代理的独立进展只有在时间与会话归属均可确认后才能纳入，首版不把它们作为已有能力。

费用回填、派生重算、页面轮询、心跳和历史记录补入均不算新活动。历史补入采用原事件时间；上游 `seq` 只用于识别变化，不当作时间戳，也不把每次元数据变更解释为工作进展。实时活动与完成记录汇合后，不能把同一请求重复计数或再次伪造一次新活动。

明确的 session 按现有规则对应 `conv_key`；缺失或歧义不能靠相近时间、标题或 Agent 名强行合并。新会话的首个请求可能尚未形成持久请求记录，活动区仍应能显示可确认归属的会话；在正式 trace 产生前，不制造可点击的假请求 ID。多个 actor 的已确认活动汇总到同一会话，但请求、工具与子代理各自的身份不混用。

全局默认排序是最后活动倒序，不额外把所有在途会话强制置顶。2026-11-03 评审已定为独立活跃分区：活跃区在上、全部会话在下，两区互斥，同一会话不占两行；分区不改变全局排序本身（`4cd6179`）。现有搜索、Agent 筛选、探针与旁路会话折叠规则继续生效。

## 采集、变化等待与桌面端

> 交付状态：本节的长轮询、游标恢复与桌面端**均未落地**。实际交付的是摄入增量维护的在途集合、`/api/sessions` 一次性快照，以及前端的 60 秒沉降窗口。保留本节作为未交付部分的设计依据，现状描述见 `## Decision` 与 `## 技术方案`。

ATC 后端统一取得实时活动，所有浏览器和桌面窗口共享这份事实。窗口读取 ATC，不各自连接 magpie。现有账本、路由文件与 hook 继续承担持久证据；实时入口用于补充正在发生的活动，不被当作完整历史队列。

推荐首版采用带游标的 HTTP 长轮询：窗口等待上次游标之后的变化；有变化时返回有限结果，没有变化时等待超时。响应包含变化会话的身份、必要活动摘要与后续游标，正文仍按需走现有读取。等待到期不重扫全部历史；连续变化合并通知，客户端合并同一会话的待更新项，避免逐事件触发完整列表查询。

首次活动快照与游标必须对应同一状态版本。游标区分采集器启动代次与变化位置；近期变化记录有上限，游标过旧、服务重启或来源重置时，明确要求重取快照。重新确认前，旧运行标记只能作为历史信息，不能继续宣称正在执行。记录移出上游内存缓冲也不能直接当作完成。

变化等待归页面或桌面窗口，不归当前选中的会话。切会话不停止会话栏监控；窗口销毁取消该窗口的等待。普通页面隐藏时暂停页面等待，恢复可见时校准；后端采集继续运行。桌面后台通知、菜单栏常驻和系统唤醒策略不在本轮范围，不能把网页可见性规则直接解释为桌面进程退出规则。

每个窗口最多一个后台等待请求，继续通过现有 HTTP adapter 和统一调度，等待发生在数据库事务之外。现有调度默认有 4 个活动槽，长轮询会占用一个；超时、退避、合并通知和读取预算需在实施时集中定义，并验证不饿死交互读取。HTTP 等待耗时与实际查询耗时分别计量，不把长等待当作慢 SQL，也不宣称它不占并发容量。

WebView 可复用现有 JS；原生界面复用序列化事实、错误和恢复规则，自行实现读取与界面。桌面端独立发布时再落实应用协议版本协商，活动游标不代替应用协议版本或正文阅读身份。连接配置和身份由宿主注入，沿用本机监听与读取权限约束。当前不预选桌面框架、不引入 IPC、不开放生产 SQLite 给 UI。

## 导航如何处理活动更新

> 交付状态：导航模块的集中管理**未落地**。进入会话、刷新、切窗、URL 定位与退出仍分别由 `web/app.js` 的多个入口安排顺序。本节保留交错的验收要求，供后续实现使用。

导航模块持有导航代次，并核对等待期间是否出现更晚的用户选择。用户选择代次、reader-store 的会话缓存代次、准备任务代次和活动游标分别回答不同问题，不能合并成一个全局计数。业务转换仍走现有选择意图，不新增第二个选择写者。

| 交错场景 | 要求 |
| --- | --- |
| 会话 A 的读取晚于切换到 B 返回 | A 的收尾不能恢复旧选择、URL、焦点或滚动 |
| 刷新或切窗期间选择另一笔请求 | 新选择优先；旧默认选择和自动定位作废 |
| 活动通知让其他会话上移 | 当前会话、请求与正文锚点保持不变 |
| 当前会话产生窗口外的新请求 | 更新活动事实，不自动切窗或滚到底部 |
| 列表重排时正在键盘选择 | 按 `conv_key` 保留行身份与焦点，不按数组位置选另一行 |
| 返回无会话的 URL | 清理当前会话阅读，页级活动监控仍可继续 |
| 窗口销毁后等待结果迟到 | 不再写入缓存、选择或 DOM |

导航整理先保持现有行为，让进入会话、刷新、切窗、URL 定位和退出经过同一套过期检查与收尾规则。`reader-store` 接纳证据，显示准备安排预算，页面执行 DOM 与 URL 效果；导航不另存正文，也不拥有排序事实。

如果仅把几个函数搬到新文件，调用者仍需记住清理、等待和过期检查顺序，就没有完成这次整理。测试应直接调用导航模块的生产入口，用可控的延迟读取制造交错，观察最终选择与效果；不能只测试内部小函数再由页面手工拼回完整流程。

## 样式设计交接

下一位 Agent 先设计会话栏中的活动表达，覆盖浅色、深色与窄栏。可以比较行内标记和会话栏内活跃分区，但保持会话身份、选择和现有读取行为一致，不以视觉稿暗中决定新的导航默认值。

| 必画场景 | 样式需要说明的内容 |
| --- | --- |
| 一个会话有在途请求，包含未选中与已选中两态 | 活动标记与当前选择能同时辨认，不混用为同一状态 |
| 多个会话同时活动，标题过长 | 标题、归属、活动与时间的优先级；不靠增加副标签解释结构 |
| 会话刚更新但没有已知在途请求 | 最近活动与请求中的表达可以区分；不设计成未读状态 |
| 新会话首个请求尚未落库、标题未就绪 | 有限占位与可进入范围，不制造笔数或详情 |
| 当前会话的新请求位于当前窗口外 | 现有最新窗口入口如何承载明确的查看动作 |
| 断连、重连或实时来源不支持 | 数据仍可阅读，运行状态不冒充已确认 |
| 列表排序变化、搜索与筛选、加载更多 | 焦点与滚动连续，已加载历史不消失，不改变筛选含义 |
| 减少动态效果、键盘和辅助技术 | 活动不能仅靠动画或颜色表达，取消动画后仍可辨认 |

普通历史会话不增加常驻运行标签。请求中的文字、图形与动画形式、是否单设活跃分区、时间用绝对值还是相对值，都属于样式评审内容；事实含义、排序与用户选择优先级由本记录约束。最近活动不引入未读计数、已读状态或跨窗口同步的阅读进度。

样式提案沿用现有中性色与主题 token，关注会话栏，不扩展到顶栏、正文、工具页或全套视觉语言。若需要可运行样张，按[prototype 入口](../../../../prototypes/README.md)复用同一份生产页面与合成数据，不另建一套长期维护的会话 UI。交接先交语义与设计稿，不以设计任务顺带实施后端或重启生产服务。

### 最终形态

两区顺序固定：`活跃` 在上、`全部会话` 在下，都用现有 `.group-label`，活跃区计数随集合变化。一个 `conv_key` 同一时刻只属于一区，归属由读模型给出的判定决定，渲染层不做二次推断。分区之间不重叠、不复制。

行结构只改一格：标题、logo、归属、笔数、失败与缺正文标记全部原位不动；活跃行的 `请求中` 落在原有时间格里，右对齐不动，占位宽度不变，因此列表不会因为出现或撤下这个词而重排。非活跃行仍是现在的绝对时钟。

两种状态并存靠两个互不占用的通道：选中态维持 `.sess[aria-current="true"]` 的 `--hover` 底色，全栏唯一；活跃态只出现在文字层，不借底色、不借左边线、不加形状。同一行可以同时被选中与活跃，也可以「被选中但已不在活跃区」——后者仍留在全部会话里高亮，活跃区里没有它。焦点与滚动按 `conv_key` 承载，不按行位置。

本形态不需要任何位移动画。唯一的时间性变化是 `请求中` 的出现与撤下，用 160ms 透明度过渡；`prefers-reduced-motion` 下直接切换。列表重排一律不设过渡。

### 技术方案：60 秒判活不阻塞主线程

以下先记录实施前的现状判断，再给出交付后的实际取舍；未落地的等待方式随 `## Deferred` 保留。

实施前，表里五项只有时间戳是现成的，其余四项都没有。

| 问题 | 现状 |
| --- | --- |
| 前端有没有轮询 | 没有。[web/app.js](../../../../web/app.js) 只在首屏、显式刷新与加载更多时读 `/api/sessions`，列表没有 `setInterval` 驱动 |
| 有没有 SSE 或长轮询 | 没有。[src/http.ts](../../../../src/http.ts) 只有一次性 JSON 路由，无 `text/event-stream`，也没有等待参数 |
| 有没有可复用的时间戳 | 有。会话 `last_ms` 就是 `MAX(started_ms)`（[src/queries/sessions.ts](../../../../src/queries/sessions.ts)），且已有索引 `i_req_time (started_ms DESC, req_id DESC)` 与 `i_req_session_time (conv_key, started_ms DESC, req_id DESC)` |
| 有没有在途事实 | 没有投影到读模型。`done` 只在 `raw_route`（[src/schema.sql](../../../../src/schema.sql) 第 64 行），`request` 表没有这一列 |
| 采集有没有实时入口 | 没有。[src/main.ts](../../../../src/main.ts) 的 `routeTick` 读 `routingDir` 的文件增量，不是对 magpie trace 的等待式读取 |

因此把三件事分开归属，谁也不放在主线程上。

**一、谁判「60 秒内有更新」——服务端，按时间窗，不按表。**

```sql
SELECT conv_key, MAX(started_ms) AS last_ms
FROM request
WHERE started_ms >= ?          -- now - 60000
  AND conv_key IS NOT NULL
GROUP BY conv_key
```

走 `i_req_time` 做范围裁剪，代价是**窗口内的行数**，与会话总数和历史总量无关；60 秒内没有新请求时是 0 行，成本近似一次索引定位。它不是周期性任务，只在会话列表被读取时随查询执行。判活口径用 `started_ms` 而不是 `updated_at`，理由与 Alternatives 里「从 `request.updated_at` 推断活动」那条一致：后者会被费用回填与派生重算改写，读出来的是维护动作不是工作进展。

**二、谁判「有在途请求」——交付后由摄入增量维护内存集合，不改 schema。**

`request` 没有完成状态，本次也没有在读模型加列、没有在查询里 JOIN `raw_route`。实际做法是 [src/activity.ts](../../../../src/activity.ts) 维护一张 `conv_key → req_id 集合` 的内存表：摄入批次提交后，把本批改动过的 req_id 交给 `observe`，只按这些 id 回查 `raw_route`（`done=0` 进集合、`done=1` 移出），大批次按 500 条分块（`7291f66`）。进程启动时用 60 秒窗口、`LIMIT 1000` 做一次有界恢复；窗口外仍未完成的请求不再宣称在途，等下一次事实到达再确认。归属从请求级会话升级到真实会话时，`convByReq` 迁移旧的 `conv_key`，避免留下撤不掉的 `请求中`（`7291f66`）。因此 `请求中` 与 60 秒判活不是两个字段：在途判断来自内存集合，最近活动来自读模型每行的 `last_ms`。

**三、谁承担等待与计时——服务端给快照，前端按沉降窗口提交。**

- 快照：没有 `/api/activity` 长轮询，也没有游标。[src/http.ts](../../../../src/http.ts) 的 `/api/sessions` 仍是一次性 JSON；页面只在首屏、显式刷新、加载更多与沉降提交点时读取，活跃快照随会话列表一起返回。
- 沉降：[web/session-view.js](../../../../web/session-view.js) 用 `LIVE_RECENT_MS = 60_000` 判最近活动、`LIVE_SETTLE_MS = 60_000` 作为保留期，`createLivePartition()` 负责分区；提交点对齐到整 30 秒（`68312d8`）。`inflight` 为真的会话豁免沉降，「请求中」不被提交点撤下。
- 提交：主线程在提交点改变化行的分区归属与时间格文案，不逐事件重建列表；列表重排一律不做过渡动画。
- 代价量级：每次提交只处理活跃集合，不扫会话表；确实没有主线程 `setInterval`，但也没有服务端挂起与唤醒。

### 仍未决

1. 活跃区内部按 `last_ms` 倒序；新请求到达时立刻上移，还是每 60–90 秒提交一次。这决定点击位置会不会跑。
2. 窄栏形态：250px 下 `笔数` 与 `请求中` 是否都保留。只留图形就必须新增一枚 16px 图标，与「词表封闭」冲突，需要单独拍板。
3. 断连或快照失效时 `请求中` 撤下意味着「结束了」还是「不知道了」。`## Verification` 与 `## Consequences` 都要求不能把未知写成已结束，这里需要一句确定的降级文案。
4. `活跃 · N` 是否常驻，N 为 0 时隐藏分区还是显示空区。

- 桌面 APP、后台通知、菜单栏常驻与系统唤醒策略。
- 真实流量验收：请求从在途到完成的观察，以及导航、恢复与桌面端的自动化测试。

## Alternatives considered

**先独立整理全部导航，再开始活动功能。** 两者可以分开实现，但活动功能会新增等待、列表更新与用户点击的交错，正好给导航规则提供真实验证场景。采用同一功能规划，按可核对的步骤推进，不扩大为整个页面的通用导航重写。

**只给会话行加标记，并定时调用整窗刷新。** 现有 hook 到完成后才送达，单靠它不能证明请求在途；整窗刷新还会清理准备和阅读状态。补充实时事实，只更新会话栏，保留用户明确发起的刷新语义。

**把活动采集、选择、正文缓存与 DOM 放进一个导航模块。** 这些任务有不同生命周期，切会话也不应停止页级活动监控。保留既有所有者，集中异步顺序即可。

**立即采用 SSE 或 WebSocket。** SSE 能承载单向变化，但持续流需要现有有限 JSON 读取之外的契约和容量管理。当前没有持续双向交互需求，桌面端本身也不要求 WebSocket。首版推荐长轮询；若以后出现持续双向操作，再独立评估。

**让每个窗口直接读取 magpie，或从 request.updated_at 推断活动。** 前者使会话关联与重启恢复重复出现在每个宿主；后者会把维护动作当作工作进展。ATC 统一解释活动，窗口消费相同事实。

## Consequences

收益：打开页面即可看到活跃会话，并稳定落在顶部独立分区；`请求中` 只依赖可确认的在途事实，不会把「最近有更新」误写成正在执行；沉降提交点让列表重排不追着每次变更跑。

代价：活跃集合只在会话读取和摄入提交时更新，停止读取列表的窗口看不到新活动；活跃区在保留期内最多多留约 90 秒；启动恢复只覆盖 60 秒窗口，窗口外仍未完成的请求退回「未知」而不再宣称在途；活跃会话跨过分页边界时，旧游标仍可能遗漏或重复行；导航仍由 `web/app.js` 多入口安排，交错风险没有因本次交付降低；分区的 4 条样式取舍仍未决，见 `### 仍未决`。

实时入口有容量、重启和覆盖范围限制。通过其他通道进入 ATC 的请求可能没有实时开始信号；界面必须区分未知与无已知在途，不能承诺所有 Agent、工具和子任务均受完整监控。

分区布局、活动动画和相对时间仍待样式评审。它们不能把网关请求未结束扩展为整个会话正在执行，也不能把无实时证据设计成确定的空闲、等待用户或完成态。
