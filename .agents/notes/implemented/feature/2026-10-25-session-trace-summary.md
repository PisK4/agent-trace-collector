# Agent Note: 会话信息汇总:会话事实与证据回溯

Status: implemented

## Problem

打开一个长会话,「这次 agent 干了什么」没有汇聚点。中栏轨迹按请求粒度投影,320 笔请求的会话里想数出动过哪些文件、用过哪些工具、失败几次、用户打断几次,只能人工翻完整条时间线。右栏读数是单请求作用域;session-head 的合计只有 token 与费用,而且是「已加载窗口」口径,不是会话口径。

2026-10-25 讨论的需求原话:为每一条 Session trace 增加信息汇总,先想到四类——工具调用次数(失败数、各工具次数)、用户中断次数、核心修改文件(Edit/Write 统计)与参考文件(Read 统计)、引用的 Skill。随后的扩展讨论把范围放宽:凡库里已有证据、聚合即可得的会话级信号都进候选。

证据大多已经在库里,缺的是汇聚点与三个尚未持久化的事实。生产库 2026-10-25 实测(31 会话 / 3,775 笔请求 / 3,595 次工具调用):

- `tool_call` 表有全部调用与配对状态,但没有参数、没有失败位。`is_error` 在正文块里,只在展开消息时按需读取——[来源投影与字段保真](../architecture/2026-10-22-source-projection-and-field-fidelity.md)当时为此否决了长期列,理由是「首版前没有证据表明需要」。
- 中断标记的形状已确证:真实中断以**用户消息文本块开头**的 `[Request interrupted by user for tool use]` 出现。目标会话 1,053 个去重块里 65 处含这个短语,只有 2 处是真实标记,其余 63 处是压缩摘要的引用;全库 tool_result 里 0 处。全文搜索会误报三十倍,判定必须按消息开头的位置前缀做。
- 参数键全库统一:Edit/Write/Read 用 `file_path`,Skill 用 `skill`——与 trace 视图 `toolSummary` 已认的键名同一套词汇。
- 会话结构信号全部现成:`req_kind` 已派生;部分会话有子代理;`attempt_count>1` 共 16 笔。

需求与社区证据经[独立评审](../../../docs/session-trace-summary-review.md)核实,两条口径警示写进定位:

- OpenTelemetry GenAI 的 `tool_calls` 指标按单次 agent invocation 计客户端执行的调用,与本提案「模型发出的调用、全会话累计」是不同口径,不混称一致。
- HITL 语境的人介入包括批准、改参、拒绝、补充回答,中断只是其中一小类,本功能不把中断计数称为人介入率。

首批定位是**辅助人工评估的会话事实汇总**:计数回答不了任务是否完成、工具是否选对,验收锚定三项阅读任务——快速盘点操作范围、找到值得复核的异常、回到对应原始证据。

## Decision

会话口径的汇总落在中栏 session-head:合计行就地升级为会话口径并带缓存命中,其下挂一个折叠区承载工具、路径、Skill 与结构四组事实;每个数字经定位元数据回到支撑记录。三个此前未持久化的事实(调用参数、结果失败位、中断计数)进派生管线,单源提取,两条派生路径双写。

### 范围:第一梯队六项,延后项不因可提取就先做

1. **工具调用**:总数、各工具分布、已判定失败数、未知结果覆盖。
2. **涉及路径**:写入尝试(Edit/Write 的 `arg_path`)与读取请求(Read 的 `arg_path`)按原始路径分组,各默认前三、可展开。
3. **显式 Skill 调用**:`arg_skill`,展开区,默认前三、可展开;没有显式调用的会话整区不渲染。
4. **已识别用户中断**:事件计数。
5. **全会话 token、费用与缓存命中**:session-head 既有合计行就地升级为会话口径,不在折叠区另立第二处;缓存命中并入该行尾部,分母口径与缺值进悬停。
6. **结构详情**(展开区):主链/旁路笔数、子代理 actor 数与请求数、网关重试笔数、上下文占用峰值、模型足迹(多于一个才显示)。

延后到第二梯队(需要先定义口径):stop 原因分布、TTFT 分位、时长密度。缓存比例、上下文峰值与模型足迹原在此列,样张评审时按用户决定并入第一梯队。第三梯队:Bash 命令统计(提取函数留了键名位)、会话列表行微缩。自动评分、轨迹匹配、数据集对比是独立选型,本仓不为此提前引入依赖。

### 口径定义

- **会话口径**:按 `conv_key` 全量请求,含子代理与归属未知的行,与轨迹视图同一导航范围。token 与费用的唯一表达点是 session-head 既有的合计行,就地替换「已加载相加」;窗口信息由「已加载 N 笔」承载。facts 行原有的「N 笔失败」后缀移出可见文案:失败读数由折叠区承载(工具级),请求级失败在轨迹行已有红色边界;「N 笔未取得费用」进合计行悬停。折叠区不重复任何已表达的信息——同一数字一个家。
- **工具调用计数**:`tool_call` 行数,一行一次调用(发出方唯一,天然不跨请求重复计)。按 `state` 分列 resolved / pending / ambiguous。**失败数 = 已判定结果里 `is_error=true` 的次数**;ambiguous 与未判定既不算失败也不算成功,进覆盖度字段,沿用「缺失不等于成功」的既有立场。
- **失败位读法**:Anthropic `tool_result` 块只有显式 `is_error:true` 才记 1,显式 false 与字段缺席按协议缺省读成 0;chat 的 `role=tool` 消息没有失败通道,同读 0。生产库实测:目标会话 365 个 resolved 结果里 139 个带显式布尔、226 个缺席,真值恰好 13——缺席按缺省读才能让「未判定」落在真正没拿到结果的调用上。这条与[来源投影与字段保真](../architecture/2026-10-22-source-projection-and-field-fidelity.md)按需读取路径的严格三态分工:那边回答「这一块有没有明确报告失败」,这边回答「这次调用有没有失败」。
- **涉及路径**:发出的调用不解释成执行或产物——Edit 发出后可能匹配失败或被权限拒绝,Read 的路径可能不存在。所以命名是「写入尝试」「读取请求」,不称修改/参考成果;top N 是**高频路径**,不称核心文件。分组按原始路径(次数降序、并列路径字典序,保证确定性);显示层 basename 折算与悬停全路径沿用轨迹行惯例,同名 basename 并列时显示更多路径段。两组独立统计,同一文件两边都出现是正常形态。
- **显式 Skill 调用**:按 `arg_skill` 分组,键在 `skill`。技能可以经 system 声明进入上下文而不发生 `Skill` 调用,该计数不暗示技能使用的全貌。
- **已识别用户中断**:派生解释确定增量里的用户消息时,文本块 trim 后以 `[Request interrupted by user for tool use]` 开头计 1(大小写不敏感),落 request 级 `interrupt_count`,会话 SUM。**按 delta 归属**:中断标记随上下文延续出现在后续每笔请求里,只在首次落入某笔确定增量的那笔计一次;分支与关系未知的请求没有「新增」可言,不计数。摘要引用、tool_result 内文、块中段短语都不算。**排除用途按规则贡献 0,写 0 不留 NULL**——排除是判定不是缺口,用途改判的行也不保留过期计数;关系未知与正文不可读的参与行才是覆盖缺口。界面文案「已识别用户中断」;无法判定的请求计进覆盖度,不冒充 0,也不外推为人介入率。
- **全会话 token 与费用**:SUM(`in_tok`/`out_tok`/`cost`) over 会话全部请求;费用四态沿用,`cost_state='absent'` 的笔数进悬停——unpriced 是另一态,不混入「未取得费用」。
- **缓存命中**:Σ(`cache_read`) ÷ Σ(`in_tok + cache_read`),只计两个读数都在的请求;并入会话合计行尾部,分母口径与缺值进悬停,分母为空不给数,不给 0。
- **上下文峰值与模型足迹**:峰值取 max(`prompt_tokens` / `prompt_window`) 的整百分点,悬停给公式;模型足迹数 distinct `model_requested`(NULL 不计),多于一个才显示,完整清单进悬停。
- **主链/旁路**:主链 = `purpose_chain='participate'` 的笔数,旁路 = `'exclude'`(分类器与标题生成等排除请求);旁路解释请求总数与主链的差。不是 `chain_role`——那是组内的 main/branch 角色,与这里「对话请求 vs 旁路请求」的分工不同。

### 提取:三个事实进派生,单源双写

- 调用参数与失败位的提取只有一份实现,住在 `derive/decision.ts`。`anthropicReplyCalls` 顺带读 input 的 `file_path`/`skill`(chat 形状的 `arguments` 字符串与对象都认,坏 JSON 落 NULL 不抛错);`anthropicRequestResults` 顺带读 `is_error`。键缺失落 NULL,不猜近邻键——`path`、`command` 之类的近邻键不提取。
- `tool_call`(同步模式)与 `derive_tool_result`(切片模式)各加三列 `arg_path`/`arg_skill`/`is_error`。切片路径经 `derive_call_work` 与 `derive_result_work` 暂存转写,配对阶段不重读正文;同步路径在工具配对重建时直写。
- 中断判定只有一份实现:`isUserInterruptMessage` 住在 `input-interpretation.ts`,计数函数 `interruptCountOf` 住在 `derive/decision.ts`,DB 适配 `interruptCountTx` 住在 `derive/read.ts`。同步路径在链阶段 delta 结算后计数,随摘要写进 `request.interrupt_count`。切片路径在摘要阶段按暂存的 `delta_ordinals` 计数,写进 `derive_request_result.interrupt_count`。正文不可读或 delta 不在手时保留旧值,与回复形状位同一套保留语义。
- 正文回收后:已提取的事实随配对行保留(`retention_state='retained'` 照旧),没有提取到的行留 NULL。汇总端点不读正文,回收会话的计数与明细照常返回,覆盖度反映缺口。
- backfill 走既有路径:算法号 bump(GROUP 2→3、DERIVE 6→7)→ 全组标 dirty → drain 重算即回填。提取不到的行不阻塞组完成。

### 结构变更:跟随回复形状位的先例,不 bump 结构版本

十个可空列直接进 `schema.sql` 与 `schema-v6.sql`,新库建库即有:-request 一列、tool_call 三列、derive_request_result 一列、derive_tool_result 三列、derive_call_work 两列、derive_result_work 一列。`published_derive_request` 与 `effective_request` 两个视图带上 `interrupt_count`。

存量 v6 库由 `scripts/backfill-summary-facts.ts` 幂等补列、重建视图、全组标脏重算——与[回复形状位](../feature/2026-10-25-turn-pair-reading.md)落地时确立的路线一致。脚本的边界沿用提案当时写死的约束:仅可空加列、不搬既有数据、值全部由派生重算。部署顺序:停采集器 → 跑脚本 → 起新代码。`SCHEMA_VERSION` 保持 6,首版前「不提供跨结构升级」的立场没有被这次变更打开。

### 端点:查询时聚合与证据回溯

`GET /api/sessions/:key/summary`,只读快照内完成,不物化会话级表。理由:单会话聚合量级很小,物化要跨组协调代际发布,复杂度买不来收益。响应字段:

- `tools[]`:name/count/paired/error_known/errors
- `paths{written,read}`
- `skills[]`
- `interrupts{count,requests,unknown}`
- `totals{in_tok,out_tok,cost,cost_absent,cache_hit}`
- `structure{requests_total,main,bypass,subagent_actors,subagent_requests,retries,context_peak_pct,models}`
- `coverage{calls_total,calls_paired,calls_error_known,calls_fact_known}`
- `failures[]`:失败的 req_id+ord 集合,上限 200,超出置 `failures_truncated`
- `dirty`

行存在即计数;组 dirty 时返回已发布代或同步旧列的事实加 dirty 标志,不猜未完成的派生。

`GET /api/sessions/:key/summary/entries` 承担点击后的按组查询,上限 1000。`kind=tool/written/read/skill` 按组返回调用列表(req_id+ord);`kind=interrupts` 返回中断请求与各自次数。参数不合法显式 400,不静默回退。有效工具行的选源与 `getRequest` 同一条规则:发布代有该请求的工具行用发布代,否则回退同步旧表。`calls_fact_known` 按算法号判——发布代行看 `derive_tool_result.algorithm_version`,同步行看 `tool_call.algorithm_version`;保留行带着旧算法号,参数事实不算已知。

**证据回溯是首批验收,不是附加项**:

- 失败数直接给出失败调用集合,收起行里的失败数可点击、当场打开失败调用列表
- 工具、路径与 Skill 条目点击后经 entries 查询打开右栏条目列表,逐项跳配对页(配对页已支持调用方在窗口外时按需读取该请求)
- 复用工具配对页与窗口外请求详情的既有导航(新增 `open-offpage` 选择意图承载「定位窗口外请求」这一步)
- 正文已回收的行展示仍有的定位元数据并注明覆盖缺口

唯一成功标准:能从任一数字回到支撑它的记录。

### 前端:session-head 折叠区与读数页精简

折叠区在 session-head 内部、轮次带之上,做成 `rail-fold` 语言的折叠行。收起时一行核心数(路径用去重条数):`366 次工具 · 13 失败 · 2 次中断 · 写入尝试 44 / 读取请求 24 条路径`,失败数只在非零时出现,覆盖缺口进悬停。展开后四个分区,靠分组与明度差解释结构:

- **工具**:六色 tint 的 chip 行(Read 蓝/Edit 橙/Write 紫/Bash 玫红/Skill 黄/Agent 绿,其余中性青灰),chip 内「工具名 次数」。失败数只在非零时以 warn 色出现在对应 chip;未配对与未判定进 chip 悬停。点击 chip 打开条目列表。
- **涉及路径**:单行流式 chip,写入=橙、读取=蓝,颜色承担分组语义,不设两列与列头,两色之间只留一条细分隔;各前三加同色 `+N` 二级展开。chip 内 basename 加次数,悬停给全路径与计数,同名 basename 并列时显示更多路径段;点击打开条目列表。
- **显式 Skill 调用**:黄色系 chip,前三加二级展开;没有显式调用的会话整区不渲染,不留空位。
- **结构**:一行式文本,主链/旁路与上下文峰值常驻(峰值没有可用分母时该项不出现),子代理、重试非零才出现,模型多于一个才显示。不加括号注释,词义说明进悬停。

组 dirty 时折叠区顶部出现一条 warn note——派生没追上输入是异常态,标签只在这里出现。展开状态按稳定键记忆(既有约定)。打开会话即拉一次汇总,不懒加载;汇总端点不可用时合计行回退窗口口径,折叠区不渲染。

**随本功能落地的既有界面精简。** 命中率是现状里唯一两处表达的同类比例:读数页「用量与上下文」的请求级「命中 X%」行与摘要命中已退役——搬家在同一次变更里完成,不出现空窗;缓存读数行的悬停指向会话头合计行。保留项与理由:入/出/缓读/缓写/费用是请求级原始读数,构成条与图例回答「这笔的上下文被什么占满」,计时四行是时延诊断,窗口外请求详情复用同一函数自动一致;它们与会话汇总回答的是不同问题,不裁。

## Alternatives considered

**直接用 claude-devtools 或 ccusage。** 两者读客户端本地日志(`~/.claude` 等),与本仓以 magpie 请求为单位、三路证据对账的边界不同;正文回收覆盖度、路由尝试、派生代不在它们的输入里;会话阅读主界面在本仓,汇总离开阅读界面就变成第二个工具。会话成本速查可先用 ccusage 交叉验证需求,实现留在本仓。

**读时解压全部正文聚合,不动 schema。** 打开会话时解压该会话全部消息块、现场提取参数与 `is_error`。否决:本库当前最大会话 378 笔、千余消息块,magpie 账本实测单会话到过 1,825 笔,读时解压的量级只会涨,且每次打开都重算;正文已回收的会话整段算不出,汇总从「有缺口」变成「没有」;中断前缀判定还要重跑消息解释,与「读模型不重解读正文」的既有口径冲突。

**物化会话级汇总表,派生完成时写。** 查询零成本,但要跨组协调:一个 conv_key 下多个 actor 组各自重算、各自发布代,任何一组变化都要重算会话行;单会话聚合本身量级很小,物化买不来收益。轮次提案「不落表」的理由是判据未定型,这里的理由是成本不成立——都指向读时聚合。

**中断用全文搜索(`LIKE '%interrupted%'`)。** 实测误报三十倍(65 处命中里 63 处是压缩摘要引用)。位置前缀判定是唯一可靠口径。

**`is_error` 不落列,汇总端点按需读结果正文。** 即读时解压方案的子集,同样被 evicted 与性能否决。这条是对[来源投影与字段保真](../architecture/2026-10-22-source-projection-and-field-fidelity.md)否决项的反转:当时的理由是「首版前没有证据表明需要长期列」,会话级聚合就是新证据——不读全部正文就数不出失败数。该 note 的 is_error 段落已随本变更交叉链接更新,它保持活跃(其余决策不受影响)。

**结构版本 bump v7 + 一次性加列迁移。** 提案初稿的方案:v6 生产库已承载真实记录、hook 通路无保留,整库重建等于永久丢正文,所以为加列开一次升级例外。落实施时[回复形状位](../feature/2026-10-25-turn-pair-reading.md)已用「不 bump 版本、脚本幂等补列、全组重派生」的路线先行交付同类变更——加列的内容与那次完全同构(可空、可重算、不搬数据),脚本本身就是迁移,再开 v7 等于为同一条路维护两套入口,还坐实了「每个结构变更都会引用升级先例」的风险。改为跟随先例,`SCHEMA_VERSION` 不动;「仅可空加列、失败拒绝启动、任何数据搬动类变更不享受此路」的边界由脚本与「破坏式替换」总立场继续守住。

**arg 提取做成独立回填脚本。** 与既有「派生阶段顺带产出 + 算法号 bump + drain 重算」路径重复,还要自己处理增量与重算触发。否决。

**Bash `command` 提取进第一梯队。** 机制上顺路,但命令的展示口径(规范化、去重、是否分类)没有需求边界,先不做;提取函数留键名位,第三梯队再启用。

**会话列表行加微缩指标。** 左栏会变成仪表盘,违背降噪立场。否决,需要时随第二梯队再评估。

**缓存比例与 stop 分布进第一梯队。** 初稿包含,评审指出:缓存比例的分母要处理混合协议与缺值,单出一个百分比会被读成 Agent 好坏评价;`tool_use` 收尾不是任务轮次,stop 分布的语义没定义就上线是数字堆砌。降级后样张评审时用户要求更宽:缓存命中以并入资源合计行、分母进悬停的形态回到第一梯队,上下文峰值与模型足迹随结构行进第一梯队——「孤立百分比被当评价」的顾虑由呈现语境解决。stop 分布维持延后。

**把中断计数叫人介入率。** 初稿借用了社区指标名,评审纠正:HITL 的 approve/edit/reject/respond 我们一项都观察不到,中断只是取消类事件,同名会误导。改称已识别用户中断。

**称「核心修改文件」。** 初稿沿用需求原话的「核心修改」,评审指出按调用次数排出的只是高频路径,核心程度需要调用之外的评价依据;且发出的调用不证明改动落地。改为写入尝试/读取请求。

## Testing

合成数据口径由 `tests/session-summary.test.ts` 锁定:

- anthropic、chat 与 responses 三种协议形状的参数提取、缺键 NULL 不猜近邻键
- 失败位显式 true 才记 1、缺席按缺省读
- 中断判定只认用户消息第一个文本块的开头前缀,摘要引用与 tool_result 内文不算,计数按 delta 归属
- 排除用途的中断贡献按规则计 0、不算覆盖缺口
- ambiguous 不计失败、pending 不冒充零失败、coverage 如实
- 保留行计数与明细列保留、从未提取的行进覆盖缺口;中断未判定不冒充 0
- token 与费用缺值进覆盖度、不给 0;缓存分母为空不给数;峰值取 max 比值;路径按原始路径分组
- dirty 组返回已发布事实加标志
- 失败集合与工具/路径/Skill 条目都带 req_id+ord 定位
- `migrateSummaryFacts` 对缺列旧库幂等补列、重建视图、既有行不动

`tests/protocols.test.ts` 锁定 chat 调用提取的既有判据不漂移;`tests/web.test.ts` 锁定读数页无请求级命中行、缓存读数悬停指向会话头。

真实库验收以目标会话 `98da290b-7df1-4759-9dd4-d7d6482ea858` 的人工核对为准,锚点全部实测核对(2026-10-25):

- 调用 366 次:Edit 156 / Bash 138 / Read 57 / Write 15;失败 13(Bash 11 + Read 2),Bash 另 1 次结果未判定
- 写入尝试 44 条路径、读取请求 24 条;主链 256 / 旁路 64
- 缓存命中 94.9%、上下文峰值 24%、模型 3 个
- 会话合计 1.8M 提示 / 205K 输出 / $1.0290,cost_absent 13 笔;子代理与重试为零不出现

两处锚点在实施核对时修正:

- **中断是 1 次,不是提案阶段估的 2 次。** 「2」来自块级计数:同一条中断消息存在两个字节变体块(后续请求重新携带时序列化字节不同),块级去重把它数成 2。按 delta 归属,标记只在首次出现的 req 4925 计 1,其余 113 次出现都是上下文延续。
- **app.js 写入是 48 次,不是样张里的 96 次。** 96 来自对消息块的扫描式统计,同一 tool_use 被数成两次;按 tool_call 行计一行一次,与[数据形状](#口径定义)节「块级扫描会数成 2」的警告一致。

交付后观察(不阻塞):实际复盘中记录哪些数字触发了检查、是否成功找到证据;只被看总数、没有后续动作的指标列为删除候选。

## Consequences

- **反转了一个既有否决。** `is_error` 落列推翻了来源投影 note 的一个 alternatives 结论,依据是聚合需求这个新证据;失败位读法同时在提取层引入「缺席按协议缺省读」的口径,与按需读取路径的严格三态并存,两条路径的分工写进了 Decision。
- **定位边界是这个功能最大的失败方式。** 计数回答不了任务是否完成、工具是否选对、某个 Skill 是否改善结果;首批只服务三项阅读任务,文案与命名不得外推成评价结论。超出的评估诉求走独立选型。
- **前缀判定的脆弱性。** 客户端措辞变化会漏计。实测全库只有带括号的一种形状;漏计不误计,新形状出现时扩展判定并 bump 算法号即可。
- **回收中间请求会让中断重算出第二次计数。** 同一条标记按 delta 归属只计一次,靠的是前驱链上的指纹证据;承载它的中间请求被回收后,后续请求的前驱退到更早的可比祖先,标记落进新的确定增量,会被再计一次。这是「回收后按可证证据重算」的诚实结果——不冒充 0,也不为去重引入指纹表;窗口测试锁定了常规场景。
- **同毫秒分叉的 branch 双计窗口仍在。** 同一条中断消息若同时出现在两个分支的确定新增里,`interrupt_count` 会加两次;窗口极小(需要上下文重写后分叉),接受为已知边界,真要做指纹去重要等独立需求。
- **不 bump 版本是一次跟随,不是常设通道。** 加列类变更的脚本路线依赖「列可空、值可重算」这个前提;任何数据搬动类变更仍走破坏式替换的总立场,首个 tag 之后同样如此。
- **数字堆砌的反噬没有完全解除。** 收窄后首屏一行,但展开区仍有四组信息;交付后观察里「没有后续动作的指标删掉」要真执行,否则汇总区自己会变成降噪对象。
