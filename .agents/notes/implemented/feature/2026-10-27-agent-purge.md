# Agent Note: 按 agent 拆除对话数据

Status: implemented

## Problem

采集器把多个 harness 的请求写进同一个库。某个 harness 的集成被弃用后，它的历史对话仍留在 `request`、证据、正文块与来源层里，需要按来源整体清掉，而不是等保留期到期。

现有的 `purge-metadata` 只按天选目标。Hermes 的行与 claude、omp、zcode、codex 的同日请求混在相邻日期里，按天删除会连带删掉无关 agent 的对话；按日期截断没有表达「这个来源不要了」的能力，所以需要以 `agent` 列作为目标键的新命令。

## Decision

新增 `maintain purge-agent --agent <name>`，与 `purge-metadata` 共用同一个删除主干。主干从原 `purgeMetadata` 里抽成 `purgeTargetsTx`：目标固定、费用观测、墓碑与事件、行级级联、路由摘要回收、受影响组结算都在一处，两个命令只负责填目标集合与各自的来源层清理。删除顺序的事实因此只有一个家。命令的预览字段、错误码与执行前提见[运维手册](../../../docs/operations.md#purge-agent)。

范围包括请求侧全部依赖，以及来源层的 `raw_ledger`、`raw_route`、`raw_hook`、对应的 `pending_hook`、指向被删请求的 `bg_job` 与 `otlp_body_ref`、派生快照里属于这些请求的逐行结果。来源层必须一起删：原始账本与路由行仍带会话、模型与目录归属，只删请求行等于把同样的信息留在另一张表。正文块经 `request_block` 引用删除后按孤儿回收，共享块不受影响。

共享守卫按证据键判断而不是按 agent 列一刀切：原始行、路由或摘要仍被删除集合之外的请求引用时保留，避免拆掉另一个 agent 仍在使用的证据。事件记 `action=purge_agent`、`reason=agent_removal:<agent>`，把被拆的 agent 写进长期审计记录，同时不改表结构。墓碑按证据键写入，与元数据淘汰同义。受影响组沿用既有结算：还有成员的组重新标脏，空组同步成 clean。

## Alternatives considered

**用 `purge-metadata` 按天删除。** 不成立：目标 agent 的行与其它 agent 同日，按天删除无法区分来源，会删掉不在拆除范围内的对话。

**删库重建。** 不成立：其它 agent 的正文、派生结果与脱敏盐绑定一起丢掉，换来的是一个未请求的副作用。拆除只应影响目标来源。

**只删请求侧，把原始层留给 7 天保留期。** 不成立：请求行删除后原始行仍能读出来源归属与请求摘要，满足不了「历史对话直接删除」；把回收推给保留期也把一个显式动作变成了延后生效。

**给 `retention_event` 加 `agent` 列。** 为一条审计记录升结构版本不划算，本版本的墓碑与事件都按证据键与自由文本承载来源信息。将来查询需要按列过滤时再单独立项。

**让 route 与 hook 摄入也查墓碑。** route 重放只把路由应用到已存在的请求，不为删除的请求建行；hook 是上游一次性投递，历史回调不会重来。收紧摄入门控是行为变化，超出拆除本身的需要，先不混进来。

## Consequences

账本墓碑按物理身份记录（文件代际 + 偏移），文件换代后旧键不匹配，重放按新证据处理，删除的请求可能重建；这与元数据淘汰是同一边界，不假装墓碑能跨代际生效。hook 重投仍会按新请求落库，因为 hook 摄入本来就不查墓碑；历史 hook 不会被重投，风险窗口只在投递失败重试的当下。

共享守卫会让「按 agent 删除」在有跨 agent 引用时少删几行原始证据。宁可留下可解释的残留，也不删别的 agent 的依据；预览里的 `raw` 计数已按同一组守卫统计。

空掉的组保留 clean 完成记录，与元数据淘汰一致。派生代际若存在，旧代里属于被删请求的行一起删除，但代本身的计数列不重算：空组不会再发布，脏组重建时整代退役，不会把半代当结果读出来。
