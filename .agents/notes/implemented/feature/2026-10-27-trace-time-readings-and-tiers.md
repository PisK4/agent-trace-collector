# Agent Note: 轨迹时间读数与时长分级配色

Status: implemented

中栏每行右端新增一个定宽读数槽：文本行挂推理段，工具调用行挂执行段，数值按耗时落三档着色。同一次改动把时长的格式化、档位阈值与工具类别收进 `web/duration.js`，改写工具概览页的旧尾注，并删掉从未渲染过的「排队」读数。

本篇是读模型与显示层的事实记录，不改 schema，也不新增采集字段。它改写[pretty-trace 工具行摘要与工具强调色](2026-10-24-pretty-trace-tool-summary-and-tint.md)的行内构成——在工具身份 chip 之后多一个执行读数，工具身份的着色语义不变；行结构与稳定步骤键仍归[单行步骤投影](2026-10-24-trace-step-projection.md)。中栏三档颜色是对[前端降噪常备规则](../process/2026-10-24-frontend-denoise-standing-rule.md)的一次有意例外，右栏仍只在异常时着色。术语见 [GLOSSARY.md](../../../../GLOSSARY.md) 的「推理段」与「执行段」。

## Problem

评估 Agent 设计时，看不出工具执行和对话轮次的时间花在哪里。中栏每行只有角色、工具身份和内容，时间信息集中在右栏读数页，而且只在点开某一笔请求后才可见。读者无法在扫读轨迹时发现「这次 Read 卡了 15 秒」「这段推理思考了 40 秒」这类异常，改进内置工具、Skills 和对话轮次缺少直接的观察入口。

### 讨论中确认的需求

- 时间读数放在中栏行右端，与正文同一行，不新开二级面板。
- 分推理段与执行段两种读数：文本行挂推理段，工具调用行挂执行段。
- 每条文本行都显示推理段，一条回复有多条文本行也不省略。
- 时长按档位变色：短为绿、稍长为橙、特别长为红，用于快速分辨是否需要看。
- User 行不挂读数与颜色。
- 读数形态用 tag 包裹，与工具身份 chip 同一套几何；图标形态因可辨识性不足被否决。

## Decision

### 推理段：差值加一个守卫

推理段 = `first_text_ms − ttft_ms`。首个内容事件在有可见推理时就是推理起点，因此差值即可见推理时长。

差值大于零不构成证据。实施时快照里 1,995 笔差值为正，其中 1,778 笔的末次尝试报告了 `firstReasoning`：只有这 1,778 笔的首个内容确实是推理。其余差值来自文本块之间被隐藏的内容（如工具调用前的空转），不是可见推理。

守卫不新增 schema。`route_summary` 属长期保留层，列表与详情共用同一段 SQL（`src/queries/requests.ts` 的 `LAST_FIRST_REASONING_COL`）：先从 `tries_json` 取末次尝试的 `firstReasoning`，再用 `json_valid` 短路——非法 JSON 下 `json_extract` 会抛错，而 `$[#-1]` 对非数组（空数组、对象、标量）返回 NULL 不抛错。摘要层缺行、非法 JSON 与非数组都读成 NULL，读者拿到的就是留空。快照里 18,435 条摘要行没有一条是非法的，3,535 笔带双时长的请求全部有摘要行，取数代价是列表查询里一条按主键的关联子查询。

投影层把它落成 `RequestRow.reasoning_span_ms`：守卫通过且差值为正才给数，零值与负值同样留空。读不出就留白，不写「—」，也不写 0——纯工具请求没有文本块，没有文本行可挂读数。

### 执行段：两笔请求相减

执行段 = `result_req.started_ms − (call_req.started_ms + call_req.ms)`。这是工具耗时的上界：包含客户端处理、权限确认与会话中断，不是纯执行时间。Read 超过 10 秒多半卡在确认，不是读取慢。

窗口在 `getRequest` 里算：工具行查询连一次调用方 `request`、再 LEFT JOIN 结果请求，两笔时长都在且窗口非负才出 `exec_ms`，负值是时钟或结算异常，折成 NULL 而不是画一个负数。快照里 13,186 次已结算调用全部可算，负值 6 次，待定 267 次（`result_req` 为空，自然留空）。未配对与待定调用不补采集：推算已经覆盖了已结算调用，补采集要新增一轮采集与派生改动，只为多覆盖少数行。

非 `current` 时 `exec_ms` 与配对位置一起收起。配对是组的结果，旧读数跟着旧配对走，不外露。

### 档位

推理段按 5 s / 30 s；执行段按工具类别分档，避免把工具身份染成颜色：

| 类别 | 覆盖工具 | 绿 ≤ | 橙 ≤ | 红 > |
| --- | --- | --- | --- | --- |
| 读·写 | Read / Edit / Write | 1 s | 10 s | 10 s |
| 命令 | Bash / Skill / terminal | 5 s | 30 s | 30 s |
| 联网 | WebFetch / WebSearch | 15 s | 60 s | 60 s |
| 子代理 | Agent / SendMessage / SubagentHandback | 30 s | 120 s | 120 s |
| 思考 | 推理段 | 5 s | 30 s | 30 s |

阈值边界闭区间：等于第一档仍是绿，超过第二档才红。类别按工具名小写查表（`web/duration.js` 的 `toolCategory`），未登记的工具归命令档——通用阈值好过没有信号，MCP 形态的工具以后补表即可。

样本落档（提案期同日采样）：读写 4,665 次 72.6/13.7/13.8，命令 7,854 次 63.8/22.2/14.0，子代理 128 次 79.7/14.1/6.3，联网 115 次 14.8/66.1/19.1，推理段 1,985 笔 53.4/35.7/10.9。联网档绿区只有 14.8%，是这套阈值的已知代价：WebFetch 中位 31.8 s，收窄会让它长期落在橙区，放宽则失去提示作用。

等待型工具不上色：等人回答的 AskUserQuestion 与等后台条件的 wait、Monitor，长窗口来自等待本身，不是工具开销。读数照常显示，整枚标签退成中性色。

超过 10 分钟的窗口按红档显示，但它在样本里多半是会话中断而不是慢工具（本机库有 873 s 的 Read）。读数不区分这两者，读者需要自己辨认。

### 中栏读数槽

读数整体是一个 chip，沿用 `.row-tint` 的几何（2px 5px 内距、3px 圆角、9.5px 等宽），底色继承角色色：推理段用 Assistant 的琥珀，执行段用 Tool 的青。只有数字按档位换色，标签色始终表达角色。两个颜色通道各管一件事，不互相解释。

槽是定宽的，右对齐，每行都占位——没有读数的行留空槽，整列的右边缘因此是一条竖线，滚动时读数不左右跳。数字用等宽数字右对齐。调用行因此会同时出现两个 chip：左侧是工具身份，右侧是执行读数。这是本方案唯一的密度代价，也是选择 tag 形态而非纯文字前缀的代价。

实测：400 px 宽下中栏不出现横向滚动，最宽读数（`执行 14m 33s`）实测 66 px，完整落在槽内；亮暗两套主题下，绿橙红与角色底色都保持正文可读的对比度。

### 右栏只在异常时着色

中栏是扫读焦点，需要三档；右栏是详情阅读，整屏发绿反而看不出哪一条要读。所以右栏只在异常时着色，正常态保持正文色。

尝试链的单次 `ms` 按 30 s / 60 s 上档，只有橙与红两档有颜色。依据是全部尝试的分布（p80 27 s、p95 80 s），以及真正渲染出尝试链的那 984 条链里 182 次成功尝试基本落在 30 s 内——这条读数在异常链里出现，长窗口多半就是超时。首 token、首个推理、首个文本保持纯数字：它们随模型与输出量变化，统一阈值会让颜色变成模型身份的说明。

以下读数不上色，因为它们没有「快慢」或不该由颜色判断：时间戳与「刷新于」；会话头的首字 p50、平均时长这类聚合值；生成速度 `tok/s`——快是好事，绿橙红要反过来解释，会破坏整套直觉。首 token 与总时长同样保持纯数字。

背景作业的配对时延（中栏结果行的 `bg_x 已配对 · 2.31 s`）也不上色。它的窗口是发起请求到通知请求的 `started_ms` 差，量的是「多久之后 Agent 才回来看到结果」，不是后台作业跑了多久；快照里 7 次跨请求配对从 4.5 s 到 383 s，任何一档阈值都会把它们几乎全染成红色，颜色不再有区分度。这条读数保留纯文字。

「排队」读数整条删除。当日 1.8 万余条尝试项里没有一条带 `queued`，这一行从未渲染；读模型里的 `queued_ms` 一并去掉，不在白名单里留一个永远为 null 的字段。

### 口径只有一处

`web/duration.js` 是时长的唯一口径：`TIER_LIMITS`（阈值表）、`tierOf`（落档）、`toolCategory`（工具到类别）、`secs` 与 `compact`（两种密度）。原来 `web/rail-facts.js` 的 `secs` 与 `web/trace-view.js` 的 `bgSecs` 是两份相同的实现，现在只有 `secs` 一份，`bgSecs` 删除，导入方直接指向新模块。

两种密度不是重复实现：右栏读数固定用两位小数秒（`2.31 s`），与相邻的毫秒读数同屏；中栏槽要在 78 px 里放下 14 分钟，按量级换单位（`180ms` / `4.2s` / `14m 33s`）。两者住在同一个模块里，与阈值同进同出。

工具概览页尾注「工具执行时长未采集」不再成立，改写为实际口径：执行段按结果请求开始减调用请求结束推算，含客户端处理与人工确认，是上界。

## Alternatives considered

**全站一套阈值，不做类别区分。** 实现最省，但 Read 与 WebFetch 的耗时分布相差两个数量级（中位 179 ms 对 31,756 ms）。单套阈值下 WebFetch 永久红，颜色退化为工具身份，不再是异常信号。

**只显示数字、不着色。** 最安静，符合既有降噪倾向；但用户要的正是「快速分辨这些数据是否有问题」，纯数字仍需逐个读。降噪规则约束的是装饰性状态，不是数据本身的异常提示。

**图标代替文字前缀（大脑表示思考、终端表示执行）。** 11 px 下轮廓糊成一团，需要先建立符号到含义的记忆，学习成本高于直接读两个字。图标唯一优势是安静，而当前问题是太安静。

**纯文字前缀，不做 chip 包裹。** 9.5 px 灰字紧贴数字，视觉上是数字的附属说明而非独立对象，扫读时仍要逐字辨认。tag 形态让它成为一个可识别对象，代价是调用行出现两个 chip。

**首 token 与总时长按模型自身 p50/p90 做基线着色。** 能让颜色表达能力，但需要新读模型；8 个长尾模型样本不足 200，会有一批请求永远没有基线；且 17 个模型各一套基线的维护成本与「同一读数同一套档位」的直觉冲突。

**生成速度也上色。** 速度快是优点，绿橙红需要反向解释，与其余读数的语义冲突，读者要在两种直觉间切换。

**右栏与中栏一致使用三档。** 统一好看，但右栏是详情阅读区，正常态大面积绿色违反[前端降噪常备规则](../process/2026-10-24-frontend-denoise-standing-rule.md)的「正常态不带装饰性状态」。

**推理段只挂在回复的第一条文本行。** 每条回复只出现一次读数，不重复，行内更安静。落选原因是正文可能很长，第一条文本行常在视口之外，读当前位置时看不到读数。用户明确要求每条文本行都显示，宁可重复。

**为执行段新增采集字段，而不从请求配对推算。** 推算已经把已结算调用的窗口全部算出来了，未配对的长尾补采集要新增一轮采集与派生改动，收益只是多覆盖少数行，不划算。

**守卫在派生阶段落列，而不是查询时现读。** 读路径更便宜，但要带 schema 变更与 backfill，或在摘要层变化时留一条拒绝路径。现读的代价只是列表查询里一条按主键的关联子查询，快照实测 200 行 13 ms，不值得为它动 schema。

## Consequences

中栏现在能直接看出三件事：这段回复思考了多久、这次工具调用花了多久、哪一行明显偏长。代价与边界如下。

**执行段是上界，不是纯执行时间。** 红色的 Read 可能卡在权限确认，红色的 Agent 可能是会话被打断。读者若把红色直接当成工具性能问题，会得出错误结论。尾注已经写明口径，但颜色本身不区分这些成因。

**推理段覆盖率低。** 只有约一半带双时长的请求能算出推理段，纯工具请求完全没有。一个会话里大量行读数为空——槽位仍然占位，视觉上是一段空白而不是缺数据标记。

**颜色分级与降噪规则有张力。** 三档颜色让中栏在正常态也有绿色。这是对「正常态不带装饰性状态」的一次有意例外，用压低饱和度的绿色缓解，右栏仍只在异常时着色。

**联网档绿区偏窄。** 15 s / 60 s 下只有 14.8% 落在绿区，WebFetch 行的橙红偏多。阈值取自中位数附近，若实际阅读中被证明噪音过大，需要重新取分位。

**推理段的假阳性会污染结论。** 缺守卫时约 4% 的超 1 秒差值不是可见推理。守卫依赖 `route_summary` 的尝试数据，若某天该层改变保留策略，守卫要同步迁移；守卫读不出时是留空，不是显示可疑值。

**读数槽挤压正文。** 每行固定保留 78 px（窄屏 64 px），窄栏下正文可用宽度减少。工具参数摘要与结果预览会更多依赖省略号，完整内容仍在悬停与右栏。

**尝试链的 30 s / 60 s 是本机分布的产物。** 换模型族或换网络之后，成功尝试的中位会漂移，这两档需要跟着重新取分位；它不是上游 SLA。

## Testing

- `tests/duration.test.ts`：紧凑时长的量级切换（含 59.95 s 进位到 `1m 00s`）、阈值闭区间、工具类别与等待型无阈值、未登记工具归命令档。
- `tests/trace-view.test.ts`：每条文本行都带同一个推理段；调用行带执行段；User 行与结果行不带；等待型工具的读数不上档；读不出时槽位为空且不出现 `row-reading`。
- `tests/queries.test.ts`：末次尝试带 `firstReasoning` 才算推理段，缺守卫、非法 JSON 与缺摘要都留空；执行段的两笔相减、负值与未结算留空、非 current 时收起；`queued_ms` 不再出现在尝试项里。
- `tests/body-view.test.ts`：尝试链只给异常时长上档，首 token 与首个文本保持正文色，「排队」不再渲染。
- `tests/web.test.ts`：工具概览页尾注改为实际口径；用量折叠行的聚合读数行文随 `secs` 归一。
- `tests/http.test.ts`：静态白名单覆盖新的 `web/duration.js`。

以上全部使用合成数据。真实流量验收另行授权并单独记录；本机浏览器实测（400 px 无横向滚动、最宽读数落在槽内、亮暗两套主题对比度）只用于这个显示层决定的形态检查，不是流量验收。
