# Agent Note: 切片工具配对只写本代结果表，判定逐条复刻同步路径

Status: implemented

## Problem

工具往返是派生结果里唯一跨请求的事实：一笔请求发起的调用，答案在之后某一笔的输入里。同步路径的做法是"先清空重组内旧配对、再把整组的调用与结果装进内存、按 `call_id` 分组、逐条判定、最后把所有关联写回 `tool_call` 表"。三个环节都随组大小增长：整组的调用与结果都在内存里，`tool_call` 是一张跨轮持久表（所以它必须显式处理"正文已回收的行不能被抹掉"），配对结果与旧表混在一起。

切片要解决的是同一件事的规模问题，但不能顺带改掉判定：

- 结果必须晚于调用，同毫秒且顺序未被证据证实时不配对；重复回传的历史不能把已确认的配对降级；增量关系未知时只建立候选，而且只记首次见到的位置。这些规则一条都不能走样，否则"两条路径结果一致"这个等价性判据立刻失效。
- 配对结果也必须有落点，而且不能被旧表的读取口径污染。

## Decision

`sliceToolsStage(store, generation, budget, now)` 一页请求一个写事务，逐 `call_id` 判定，结果写进 **这一代的** `derive_tool_result`，完全不碰 `request`/`tool_call` 旧表。

**候选全集从 work 行数出来，不依赖"调用行是否已经写进结果表"。** 同一 `call_id` 的参与调用多于一笔即 `ambiguous`；判定所需的三个事实（同 `call_id` 的调用数、全部结果、两笔请求的逻辑顺序）都直接查 work 行与结果行。于是不必"先把整组调用插完再配对"，页与页之间也不会因为处理顺序不同而给出不同判定——同步路径靠全局插入顺序实现的那件事，这里靠"查全集"实现。

**筛选按 `purpose_chain`。** 排除用途的请求既不进候选、也不产生工具行。`chain_role='aux'` 在封闭域下等价，但它是角色传播的推论，而 `purpose_chain` 是事实；按事实筛，将来角色传播的规则变了也不会连带改掉配对。

**结果是否算"本轮新增"由角色阶段写回 work 行。** `confirmed` 的判据是"结果的 ord 落在确定增量里"：`first` 整笔都算，`confirmed` 只看增量的 ord，关系未知或分支不算。这个判据只有角色阶段算完 `delta_ordinals` 才知道，所以由它在结算时写进 `derive_result_work.confirmed`，配对阶段只读。

**配对只写本代。** 同步把关联写回 `tool_call` 旧表，因此需要额外规则处理历史行（正文已回收的行不在重建范围内，标 `retained` 而不是覆盖）。切片的工具结果表每代新建，正文不可读的请求根本不产生候选 work 行，所以没有行需要标保留：本代的每一行都是这一代算出来的。读口径的切换由发布指针完成，旧表在切片模式下不再被写。

**收尾校验覆盖。** 走到 `summary` 之前核对"每个参与请求的每一笔候选都有结果行"，缺一行就丢弃整代（`slice_tool_coverage`），不让一套不完整的工具行被发布。`tool_count` 与游标在同一事务里前进，发布时的覆盖校验（`publishGeneration`）拿它与结果表行数比对。

## Alternatives considered

**复用 `pairToolCallsTx`，把结果行换成 `derive_tool_result`。** 那需要把整组的调用与结果装进内存——正是要消除的成本——并且它要求"先插完所有调用再配对"，与分页提交的形态直接冲突。

**让配对阶段自己按 `chain_role` 筛。** 释放了 `derive_request_result` 与角色阶段的耦合，但把"谁算旁路"这件事变成了由角色传播结果反推；角色规则一旦调整，配对会静默跟着变。

**由配对阶段现算 `confirmed`。** 省掉角色阶段的写回，但把一个"已经算过的结论"重算一遍，且重算所需的两列（`prev_relation`、`delta_ordinals`）本来就是角色阶段的产物——判据放在产出它的地方才只有一处。

**把候选也物化进结果表，再按结果表筛。** 等于给每一代写一份"候选的副本"，而 work 行已经是候选的权威。

**把 `retention_state` 也照同步标 `retained`。** 本代没有"上一轮的保留行"这回事：行都是这次算出来的，标保留会声称一件没发生的事。

**按字典序比较结果位置以省一列排序键。** `path` 里的内容下标是字符串（`content[10]` 排在 `content[2]` 前），只在同一条消息里出现重复 `call_id` 这种病态输入上才有差别，且只影响"保留首次位置"这一条；不值得为它加一列排序键。

## Consequences

- 工具阶段的判定不再依赖"所有调用行已插入"这个全局顺序，页边界因此可以任意切；代价是每笔候选都要查一次同 `call_id` 的调用数（走 `derive_call_work` 的 `call_id` 索引）。
- 切片模式下 `tool_call` 旧表不再被写。旧表的读取口径与保留态处理只服务同步路径；切片发布的工具事实一律来自 `derive_tool_result`。
- 本代工具行的 `basis_json` 记代际身份与 `call_id`，`algorithm_version` 是切片算法号：发布出去的工具事实要能说清是哪一代、哪套算法算的。
- 排除用途的请求在 work 表里照旧有候选行（物化阶段不替配对做政策判断），但配对阶段不读它们：work 表是"正文里有什么"，配对才是"谁算数"。
- 覆盖校验今天是不可触发的：它的筛选条件与配对函数自己早期返回的条件是同一套。留着它是阶段边界上的不变量断言，代价是每代一次计数查询。它真正生效的地方在完成阶段，与磁盘预算、逐请求修订一起决定这一代发不发得出去，见[切片完成的闸门、发布与退役代回收](2026-10-22-atc-slice-ready-invalidation.md)。

## Testing

`bun test tests/derive-slice.test.ts` 覆盖 3 条：唯一配对得到 `resolved`、同 `call_id` 多笔候选一律 `ambiguous` 且结果位置仍记下、结果早于调用保持 `pending` 且位置为空——三条来自同一组手工种下的 work 行，并断言 `tool_count` 为 4 且旧表 `tool_call` 保持空白；重复回传的（未确认）结果不能把已 `resolved` 的配对降级；端到端一条（两笔请求、一次工具往返）走完请求、角色、工具三个阶段，结果落在确定增量的 ord 上，因此配成 `resolved`——这一条第一次跑出的正是 `confirmed` 没人写的缺口。
