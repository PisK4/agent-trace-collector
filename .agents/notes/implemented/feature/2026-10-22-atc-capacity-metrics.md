# Agent Note: 容量观测只在进程内保留有界计数

Status: implemented

## Problem

容量基线需要写事务耗时、事件循环延迟、拒绝原因、队列积压与元数据增长。这些值如果落表，会把观测数据混进被观测的库：写统计本身改写 WAL，报告读取又推进页面缓存，测量结果不再可信。被拒请求的原文与错误文本也不能留，否则观测入口会变成第二个正文存储。

## Decision

观测集中在 `src/capacity.ts` 的进程内对象：分位数用最近秩、空样本返回 null；拒绝只按固定 `REJECT_REASONS` 计数；事件循环是 50 ms 定时器的有界环形缓冲（8192 个样本）；队列与存储快照从只读连接现算，不写表。`Store.write` 在包装层计时，成功、失败与回滚都计数，并按[具名提交](../architecture/2026-10-24-named-commit-units.md)归属任务；统计随进程重启归零并在报告里注明起点。

元数据增长只按逻辑载荷计：clean 组队列行、`source_facts_json`、`projection_meta_json` 与已发布代结果字段；同时给 per-clean-group 与 per-request 两个比值，避免只数 dirty 组或只数结果表。

容量配置必须通过 `assertCapacityIsolation`：根目录在 `tmpdir()` 下且以 `atc-capacity-` 开头，三个来源路径与根严格相等，上游端口不是 3425 且与 `magpieUrl` 一致。断言只做路径相等，不解析环境变量。

## Alternatives considered

**把观测写成表。** 写统计会污染自己的测量，报告读取还会触发 WAL 增长；清理与保留期也要另立规则。

**只记平均值。** 容量门槛看 p99 与最大值，平均值会把长尾藏起来。

**记录被拒原因的自由文本。** 其中可能含请求头、来源字符串或正文片段；固定枚举足以分组，且不会把观测变成第二份敏感数据。

**把写计时放在调用点。** 每条写入路径都要重复计时，漏一条就少一类事务；包装层只有一个入口。

**用真实端口做对照。** 隔离断言在建立负载前运行，配置漏项直接失败，不依赖操作者记得改端口。

## Consequences

- 观测不落盘，进程重启后计数归零；报告记录 `started_at_ms` 与 `uptime_ms`，不能跨重启合并。
- 事件循环样本上限 8192，长负载只保留最近一段；分位数不覆盖全程。
- `writeStats` 增加一次 `performance.now()` 调用，所有写事务都付这份成本。
- 隔离断言按字符串路径比较；调用方必须用同一个根字符串构造配置，realpath 只用于判断根是否在临时目录内。
- 一次性脚本手工构造 `Store` 时必须补 `writeStats` 字段，即使不做观测。

## Testing

`bun test tests/capacity.test.ts tests/store.test.ts`：最近秩分位与空样本、固定拒绝原因、容量快照的写计数/队列年龄/存储、元数据按 clean 组与来源 JSON 计长、隔离断言；写事务统计覆盖成功与回滚且回滚不留数据。
