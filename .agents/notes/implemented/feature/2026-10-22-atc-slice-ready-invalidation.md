# Agent Note: 切片完成的闸门、发布与退役代回收，调度按阶段批次轮转

Status: implemented

## Problem

切片派生的前四个阶段（请求、链、角色、工具）把"算得起"解决了，但走完的最后一公里还有四件事没定：

1. **展示结果要不要与同步路径逐字一致。** 标题、输入摘录与回复摘录是用户在折叠行里唯一读到的东西。同步路径的 `writePresentationTx` 有一套顺序敏感的判据（标题请求优先、正文不可读时保留旧值、排除用途不取用户增量……）。切片若另写一套"看起来等价"的分支，等价性判据就失去定义。
2. **发布前该拦什么。** 一代结果可能已经过期（组修订变了、用途重判过、某个请求的输入又动了），可能不完整（有请求没进这一代），也可能装不下（暂存行与 WAL 涨得超过预算）。这些校验必须在切换发布指针之前完成，而且 WAL 检查不能放进写事务——checkpoint 与 writer 事务互相等。
3. **完成与失败之后的回收。** 祖先台账与扫描状态只在构建期有读者；退役代保留却无限堆积会把库撑回去。
4. **调度怎么把两个阶段粒度缝起来。** 同步路径一次调用就是"一批组"，每个组一个完整事务；切片的一次调用只是若干阶段批次，进程每两秒来一次，谁先推进、怎么轮转、模式在哪里切换，都得是确定且公平的。

## Decision

**摘要阶段消费[判定内核](../../implemented/architecture/2026-10-23-derive-decision-kernel.md)的展示判定。** 它接在[工具配对之后](2026-10-22-atc-sliced-tool-pairing.md)：轮次关联只有本代确定下来才能当依据。读的是**当前** `request` 行的用途、旧标题与旧摘录（那些是事实，不是这一代物化那一刻的快照），写的是本代 `derive_request_result`。取值与分支顺序由内核的 `presentationDecision` 与 `previewOf`/`deriveTitle`/`toolResultPreviewOf` 给出，切片与同步两条路径都调这一份：判据一处实现、两处调用，抄一份出来就迟早走样。可读性只看 `fingerprintsOf` 读不读得出正文，不读 `body_state`——骨架损坏时正文同样读不出来，那时旧标题必须原样保留。

**关联按结果所属请求取，不按调用侧取。** 摘录要回答的是"这一笔的输入里回传了哪些工具结果"，所以页查询取的是 `result_req IN (本页请求)` 的行。按调用侧筛（`req_id IN (...)`）在页边界切在调用与回传之间时会漏掉关联，同一份结果就会随批大小给出不同的摘录。

**完成阶段把校验排成固定顺序，一条不过就丢整代。** 组修订 → 暂存与 WAL 预算 → `basis_json` 大小 → 逐请求修订 → 覆盖（每笔候选都有结果行、每笔已知请求都进了这一代、请求数对得上）→ 发布。丢弃与校验同在 ready 的那个事务里提交：它不是"抛错回滚后的补救"，而是校验结论本身。WAL 检查与 checkpoint 在事务之外做，只做 `PASSIVE`，不强迫其它读者退出。

**发布之后立刻回收构建期表与超限的退役代。** 指针的切换规则与"校验不过就不切"见[派生结果按代整体发布](2026-10-22-atc-generation-publish-pointer.md)；这里补的是它留给本阶段的那些校验与回收。祖先后台账与扫描状态发布即删；退役代按发布时间保留最近 `maxRetiredGenerations` 代，更旧的连结果行一起删。当前代与最近几代的原算法结果要留给历史详情与对照，所以删的是最旧的那几代。

**调度一次推进一个组的一个阶段批次。** 选择顺序是"先续跑已有 `compute_generation`，否则取最久没被认领的 dirty 组"，`dirty_since_ms` 打破平局——单个长组不会连续占满事件循环，冷组也不会被热点组饿死。组里还有待判定用途的请求时不认领：切片的组阶段消费的是已经定下来的用途，拿默认值把组算干净等于替那些请求猜了一个用途。

**模式落在 `store.deriveRuntime` 一个字段上。** 没有它就是同步库，`drainDeriveEntry` 走原来的同步入口；有它就是切片，一次调用推进若干阶段步骤。模式标志、预算与库路径合成一个字段，避免出现三者互相不一致的组合。用途阶段两个模式下都走统一入口：切片只把组阶段拆成多批，不改变用途门控。

**认领前把队列行的目标算法号归一到本模式的算法号。** 组变脏时写下的是同步算法号，直接认领会硬失败。只改未完成的 dirty 行：clean 行有已发布产物，改号等于伪造它是另一套算法算出来的。

**`staged_bytes` 由物化阶段按行数估算维护**（结果行 512 字节、候选行 256 字节）。它是给发布前磁盘上界用的粗估，硬闸门是量真实字节的 WAL 检查。

## Alternatives considered

**摘要阶段复用 `writePresentationTx` 本身。** 它写的是 `request` 旧列，且签名绑着同步的 `PresentationInput`（含 `match`、`group`）。改造它去适配两种写目标是让一份实现同时服务两个调用方里最容易出错的那种做法；分支保留、取值复用才是等价性想要的形状。

**把摘要阶段写成"要么全对要么不算"的单页事务。** 已经一页一个事务；问题在于计划原本一次调用只写一页，长组的摘要阶段于是退化成每两秒一页。改成与角色、工具阶段同构的"预算内连续推进"，是为了让阶段时长可控而不是与调用频率绑定。

**关联按调用侧取（`req_id`）以吃到主键索引。** 页边界会改变结果，这与"同一份正文在两条路径上得到同样的摘录"直接冲突。按结果侧取的代价是本代工具行的一次扫描，比正确性便宜。

**给 `derive_tool_result` 加 `result_req` 索引。** 能把这个扫描变成索引查，但上线中的库不会自动获得新索引（v6 的 DDL 只在空库上执行），于是两个库的 schema 悄悄分叉——首版前的 schema 变更要么带可执行 backfill，要么明确拒绝，不靠"以后重建"。

**把所有异常都吞成丢弃。** 计划的包装是"catch 到什么都丢这一代"。那会把真实故障（SQLite 忙、代码 bug）伪装成一个正常的切片决策，进程会一直安静地重试。丢弃只认枚举过的失败，其余照旧冒泡。

**给 store 同时留 `deriveBudget`（模式标志）与 `deriveRuntime`（路径与预算）。** 同一份预算存两处，运行期迟早出现"字段说切片、另一个字段说同步"的组合。

**把 `staged_bytes` 留空、只靠 WAL 检查。** 那 `maxStagedBytes` 就是一个永不触发的闸门配置——比没有更糟，因为它声称有条上界。

**给毒组加尝试上限（用 `attempts`/`last_error` 出列）。** 同步路径今天也是"下个 tick 再试"，切片保持同样行为；到达上限之后的处置（丢弃、暂存、告警）需要一个产品决定，不在这里替它决定。

## Consequences

- 摘要阶段的关联读是本代工具行的一次扫描（`result_req` 无索引）。它是每页一次的量级，与本代行数成正比、与页大小无关。
- 磁盘闸门有两层，触发条件不同：`staged_bytes` 是行数估算（粗，先触发），WAL 增长是真实字节（硬）。估算的两个常量写在物化阶段的一处注释里。
- WAL 是整库的量，不是这一代的量：别处灌进 WAL 时，这一组也拿不到发布资格，会在 dirty 上被反复重建。这是有意把磁盘安全排在进度之前——停在 dirty 是能在 `last_error` 与丢弃计数里看见的状态，比悄悄发布一份超出磁盘预算的结果好。
- `slice_basis_budget` 与 `slice_tool_coverage` 今天是**构造上不可触发**的：结果行的 basis 恒为 `{}` 或代际身份加调用号，远在 4096 字节以下；工具覆盖校验的筛选条件与配对函数自己早期返回的条件是同一套。留着它们是因为它们断言的是阶段边界上的不变量（"发布出去的事实来源有大小上界"、"参与请求的候选都有结果行"），代价是每代两次计数查询。
- 丢弃的一代留下 `derive_generation.state='discarded'` 与队列行上的 `last_error`；`attempts` 由认领累加但暂无消费者。一个反复失败（而非过期）的组会被每个 tick 重新认领、重新构建、再丢弃——同步路径在同样的输入上也是一直重试，代价相同；要停止它需要产品级决定。
- 切片模式的 `processed` 是"阶段步数"，同步模式的 `processed` 是"请求数"，两者不是同一个量；`remaining`（未完成组数）、`discarded`、`purpose_*` 在两边同义。调用方的"没有进展"守卫要按"`processed` 为 0 且 `remaining` 不为 0"来写，不能拿 `groups.length` 当判据（切片一次只推进一个组的一页，也不一定发布）。
- 维护进程（`maintain rebuild`）没有模式配置来源，它的调用点虽然换成了统一入口，但落回同步分支。切片模式目前只由容量实验入口启用；运维入口的模式开关留到切片模式真正上线时补——那时它需要一个库内或配置内的模式事实。
- 摘要复用同步取值的第二个好处：正文可读性、用途门控与展示分支三者的关系只在同步那份实现里定义一次；切片发布的每一行都能追到同一套规则。

## Testing

`bun test tests/derive-slice.test.ts` 覆盖 9 条：摘要阶段与同步入口在同一组输入上的标题、来源与三个摘录列逐行相等（对照值是同一份种子跑同步路径得到的，不手写），且工具往返那一笔的摘录是"工具结果 · 工具名"；排除用途的非标题行在非空增量下不取用户标题（`model_title` 为空时留时间兜底、不为空时保持模型标题来源），输入摘录仍走同一增量分支；组修订在阶段间变化即丢弃整代；暂存超预算丢弃；多了一笔已知请求而这一代没有它时不发布；连续发布四代后最旧一代连同结果行被回收、最近两代留着、指针指向最新；两个 dirty 组按 `last_claimed_ms` 轮转；有待判定用途的组不认领、用途结算后能认领且目标算法号被归一到切片号；统一入口在切片模式下分批推进到发布（同步算法号的队列行被归一、发布后构建期表清零、`published_algorithm` 是切片号），把运行时摘掉后同一入口落回同步分支并写回 `request` 行。
