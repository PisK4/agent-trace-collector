# Agent Note: 读数页上下文窗口三指标

Status: implemented

## Problem

读数页「用量与上下文」折叠行的构成区只有 treemap、图例与内容列表，窗口与占用被放在图下方的 `u-total` 一行，读者要先看图再回到底部找分母；请求级缓存命中在 2026-10-25 已随会话汇总退役，只在会话头合计行表达。2026-10-30 的用户截图把 magpie Routing 页的「上下文窗口」卡作为参照，要求把三个指标提到 treemap 上方：已用上下文 / 总上下文、窗口进度、提示词缓存。

截图是 magpie 的 live 卡：窗口来自回答模型，缓存列在请求未完成时显示「上一个请求的 · 本次请求进行中」。ATC 只记录已完成的请求，本笔的窗口与缓存都已在库，因此照搬 live 文案会写出不存在的状态；三个指标必须按 ATC 的已记录口径重新定义。

## Decision

构成区自上而下改为：三指标行、treemap、图例、内容列表。`u-total` 行删除，不再保留同一批数字的第二处表达。

- **已用上下文**取 `prompt.tokens`，与 treemap 面积同源；分母是 `prompt.window`，同一行写 `/ 总上下文 <窗口>`。窗口缺失时只写「模型的窗口大小未知」，不给分母。
- **窗口进度**取 `prompt.ratio` 的整百分点。比例只在 `state='recomputed'` 且窗口为正时计算；窗口未知写「没有可用分母」，旧结果写「旧结果，不计算进度」，不按旧输入或默认值补分母。
- **提示词缓存**取请求级 `cache_read ÷ (in_tok + cache_read)`，与会话头合计行同口径；下方写「缓读 X · 新入 Y」。缺任一读数写「缓存读数未上报」且不画条；合法的 0 显示 0%，不当作缺失。
- 异常态 pill 跟着对应指标：`counted=false` 的「本地估计」挂已用上下文标签，≥75% / ≥90% 的「接近占满 / 占满」挂窗口进度标签；正常态零标签。
- 保持一个「用量与上下文」折叠行，不拆第二个「上下文窗口」折叠行，不加「实时」pill——ATC 没有在途请求，live 态不可表达。

与[会话信息汇总](../feature/2026-10-25-session-trace-summary.md)的关系：本次部分取代它「请求级命中行与摘要命中已退役，命中率只在会话头表达」的范围界定。退役继续成立的是用量两列的命中行；构成区的请求级命中作为上下文消费读数回归，会话级命中仍留在会话头。两处口径相同（`cache_read ÷ (in_tok + cache_read)`），旧 note 保持活跃并互链。

2026-10-31 起指标行改为四格（已用上下文、固定开销、提示词缓存、耗时），窗口进度不再独立成格，缓存条与「缓读 · 新入」副行撤掉，见[读数页四格上下文指标](2026-10-31-context-metrics-four-cells.md)。本篇仍然成立的是：缓存与会话头同口径、不建模型窗口表、窗口未知不用默认分母、不拆第二个折叠行、不显示 live 态。

## Alternatives considered

**窗口未知时用 magpie Context 页的默认 200k 分母。** 能让进度永远有数，但 200k 是 magpie 评分页的假设，不是本笔路由记录的事实；同一笔请求在 ATC 显示 11%、在 magpie Routing 卡显示未知，会制造第二个分母。落选。重开条件：ATC 自己维护模型窗口表，且表项有可核对来源。

**在 ATC 建模型 → 窗口登记表。** 可以让未知窗口的模型也有进度，但新增一个需要持续维护的事实源，且与路由侧报告可能冲突。本次不做。

**保留 `u-total`，只在上面新增三指标。** 提示总量、窗口、占用会在上下两处各说一遍，违反同一数字一个家。落选。

**拆出第二个「上下文窗口」折叠行。** 更贴近截图的卡片标题，但读数页会多一个折叠行，token 用量与上下文构成被拆成两段阅读；计时与用量两列仍属于同一个「用量与上下文」折叠行，拆开后标题也会失配。落选。

**缓存列显示会话级命中率。** 能复用会话头已有的数字，但它回答的是整个会话，不是这笔请求；放在请求级构成区会被读成本笔的缓存复用。落选。

## Consequences

- 三指标在 treemap 上方，读者先看绝对用量、窗口占比与缓存复用，再看构成；折叠行高度增加约 80px。
- 窗口未知是少数态：决策时生产库 30,780 笔请求里 29,631 笔有 `prompt_window`（96.3%）。未知时进度留白，不用默认值补数。
- 缓存口径与会话头一致；决策时 29,776 笔有账本读数的请求里 `cache_write` 全为 0，`in_tok + cache_read` 与含 `cache_write` 的分母在真实数据上同值，但代码只认会话头那一个公式。
- 右栏宽度 280–640px：三列在 280px 时标签与读数折行，640px 时一行读完；窄栏验收在合成页面做过，不隐藏指标。
- 不改 schema、接口与派生，不 backfill；`prompt_window`、`in_tok`、`cache_read` 都已在读取行里。

## Testing

`tests/web.test.ts` 覆盖三指标的已知/未知窗口、旧结果、缓存缺失与合法 0、`cacheHitOf` 的缺读数与零分母、pill 归属与无正值类别；`bun run typecheck` 通过。合成页面在 280px 与 640px 右栏、亮暗两主题下用浏览器核对三指标与 treemap 的排列，未发现溢出；截图见验收记录。真实数据只做只读计数，用于确认窗口与缓存字段的覆盖率，不读正文、不写生产库。这批用例在 2026-10-31 的四格重构中改写，当前覆盖见[读数页四格上下文指标](2026-10-31-context-metrics-four-cells.md)。
