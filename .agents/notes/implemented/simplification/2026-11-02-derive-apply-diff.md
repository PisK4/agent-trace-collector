# Agent Note: 派生落库只写实际变化的行

Status: implemented

## Problem

派生落库把整组计划原样写回。热组 3,019 笔的实测里，一次落库约一万条语句，真正改变的结果只有几十行：展示列计划 3,003 行、实际变化 11 行；链行 2,991 条、字段变化 8 个；链角色 1,881 行、变化 2 行；工具行计划插入 1,397 条、实际新增调用 9 条。落库单次最长 2,060 ms，同步阻塞 Bun 事件循环，页面在此期间无法响应。

链角色被写两遍：链阶段按初值写 `main` 或 `aux`，角色阶段再把参与链的行逐行改写成最终角色。工具行整组先删后插，最终状态与库里原有行逐列相同。

`derive_version` 也跟着每次展示写入加一。它被文档写成"被重算过几次"，代码却在每一行展示写入时自增，包括内容完全没变的行。跳过无变化行会改变这个计数，所以口径必须先定下来。

## Decision

四段都先比较再写，同一事务、同一 CAS、同一计划，最终状态与改动前逐列等价。

**展示段。** `presentationWrite()` 额外读回当前行的 `summary_algorithm`、`summary_basis`、`summary_state`，把八个展示列与摘要三列一起与计划值比较，结果写进 `changed`；`writePresentationTx()` 在 `changed=false` 时直接返回。

**链与角色。** `planChainRoles()` 返回 `Map<reqId, role>`，不再是一份待执行的写清单。计算段把它与链阶段的关系合成每行最终角色，再与库里现有 `prev_req_id`、`prev_relation`、`delta_ordinals`、`chain_role` 比较，写进 `changed`；落库段只对 `changed` 的行执行那一条 UPDATE，第二遍角色写入整个删掉。

**工具行。** `planToolCalls()` 直接产出本组的最终行（调用位置、结果位置、失败位与状态），并与库里重建范围内的现有行逐列比较，产出 `upserts` 与 `deletes`；落库段按 `(req_id, ord)` 主键做 upsert，再删最终不存在的调用。比较包含 `derive_version`、`algorithm_version`、`basis_json` 与 `retention_state`，所以旧算法行与保留行仍会被重写，不会被误判成"没变化"。正文已回收的请求照旧不在重建范围内，它们的行原样保留，只标 `retention_state='retained'`。

`derive_version` 随之定义为内容实际变化的次数：重算但结果没变不加一，重算后内容变了加一。它依旧不是算法版本，也不表示结果是否最新。三处文档同步改口径：[trace 格式](../../../../docs/trace-format.md#版本字段)、[架构设计的派生算法版本](../../../../docs/architecture-design.md#派生算法版本)、[运维手册的重建报告](../../../../docs/operations.md#rebuild)。

维护 `rebuild` 仍报会话 `MAX(derive_version)`，语义变成"该会话单行最多变过几次"。既有生产库的历史值按旧口径累加，不回填：它是历史计数，没有需要修正的派生结果，回填只会改写历史。

## Alternatives considered

**保留旧计数，无变化行也加一。** 那就必须继续写整组，瘦身等于没做；或者对未变化行单独写一条只涨版本的 UPDATE，省下的语句又加回去。

**把 `derive_version` 改成算法版本号或批量加一。** 那会让"这一行变过几次"这条信息消失，且与 `summary_algorithm` 重复。算法覆盖已经由 `summary_algorithm`、`actual_algorithms` 与 `legacy_requests` 回答。

**保留工具行"先删后插"的重建式语义，只把语句合并成批量。** 删除再插入同样数量的行仍然是整组写入；批量只能省事务开销，省不下语句数。最终状态比较才能把 1,590 条更新降到个位数。

**把落库拆成多条短事务以缩短单次阻塞。** 会破坏组内原子性，中途失败会留下半组。整组一次提交是本仓的一致性底线。

## Consequences

- 生产热组一次整组重算的落库计划从约 10,300 条语句降到 7 条（2026-11-02 只读实测：链 3,440 行变 2、工具 upsert 1、展示 3,440 行变 2）。
- 最终数据与改动前等价；未变化行连 `updated_at` 都不动。
- 每行多一次读回摘要三列，已在原有单行查询里带上；链与工具各多一条组内读查询，不随行数增长。
- 工具行不再每轮删除重建，反向改指与别名迁移不再撞上刚删的行。
- `derive_version` 增长变慢：热组 357 秒内只有 7 行增长，旧值（最大 1,891）停在原地；按它做诊断的读者会看到新旧口径混合的数据。
- 剩下三条组级语句是背景作业清空、工具保留行标记与 CAS，与组内行数无关。

## Testing

`tests/derive-presentation.test.ts` 的「重算不改变内容时 derive_version 不增长」：先排空一次，再排空一次断言版本与内容不变；随后只改第二笔回复正文，断言只有该行版本加一。`tests/derive-apply-plan.test.ts` 的「重算不改内容时链与工具行一条都不写」：排空后再排空，断言计划里没有 `changed` 的链行、没有工具 upsert 或 delete、没有变化的展示行，落库只有三条组级语句，`request` 与 `tool_call` 逐列不变。既有链、工具配对、用途、单元、维护与投影测试全部通过，全量 1,060 例与 `bun run typecheck` 通过。真实流量上的语句数与版本计数见[验收记录](../../../../docs/acceptance.md#展示列差分落库生产部署真实流量2026-11-02)。
