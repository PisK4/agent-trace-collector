# Agent Note: 维护锁与备份的独占探测

Status: implemented

## Problem

离线维护要求采集器已停，但进程停了不等于没有别的连接：只读查询、备份探测、误开的第二个采集器都可能同时存在。备份如果直接拷裸文件，会漏掉 WAL 里已提交的内容；如果先确认再复制，中间又可能被别人打开。陈旧锁如果自动覆盖，会把正在进行的维护踩掉。

## Decision

维护命令 `verify`、`backup`、`rebuild`、`purge-metadata` 统一从 `bun run maintain` 调用。`backup`、`rebuild`、`purge-metadata` 在数据目录下用 `wx` 原子创建 `maintenance.lock`，内容记 pid 与持有者；`verify` 只读，不建锁。采集器启动时看到锁就拒绝启动，陈旧锁不自动覆盖，路径原样报出来由人确认后删除。

备份走 `VACUUM INTO ?`，绑定目标路径。前置检查目标不存在、目录可写、余量不少于源库 1.1 倍；事后对备份再跑一次完整性校验，权限 0600。「源库是否已停」用 `locking_mode=EXCLUSIVE` 探测，探测与复制共用同一个连接，中间不留窗口。

`purge-metadata` 默认只预览，`--apply` 必须带 `--approval-id`。一个事务里按顺序删费用观测、写墓碑、删工具链接、删块引用与孤儿块、删证据与别名、删请求、清无引用的路由摘要；外键是 `NO ACTION`，顺序错了整体回滚。墓碑按证据键记录，同一天只淘汰一部分也能精确处理；来源回放命中墓碑计 `purged_skip`，不复活。

实现见 [src/maintenance.ts](../../../../src/maintenance.ts)，操作步骤与错误码见[运维手册](../../../../docs/operations.md)。

## Alternatives considered

**用 `-wal` 文件大小判断源库是否已停。** 在线库执行 `wal_checkpoint(TRUNCATE)` 之后 `-wal` 同样是 0 字节，看大小会把在线库误判成已停。

**先探测、再另开连接复制。** 探测与复制之间留出窗口，别的进程可以在确认之后打开库；改用同一个连接，探测与 `VACUUM INTO` 不可分割。

**直接拷数据库文件。** 裸拷会漏掉 WAL 里已提交但尚未 checkpoint 的内容；`VACUUM INTO` 生成一致快照，并顺带压缩。

**陈旧锁自动覆盖或按 pid 杀进程。** pid 会复用，自动覆盖会把正在进行的维护踩掉；把锁路径报出来，让人确认后再删，代价是一次人工介入。

**`purge-metadata` 默认执行。** 删除长期元数据不可逆，默认预览、`--apply` 加 `--approval-id`，把不可逆动作留在显式授权之后。

## Consequences

- 维护期间采集器拒绝启动；陈旧锁需要人工删除，换来的是不会误踩正在进行的维护。
- 备份要求额外 1.1 倍源库空间；`VACUUM INTO` 会压缩，实际占用通常低于这个上限。
- 备份与探测共用连接，采集器在线时探测会失败并让备份停在错误上，不会生成半份备份。
- 元数据淘汰是最后一个手段，触发时必须带审批号；墓碑让来源回放不会复活已删证据。
- `rebuild` 只重算正文仍可读的请求，并报告不可用数量与原因；正文已回收的请求保留旧标题与已确认的工具配对。
