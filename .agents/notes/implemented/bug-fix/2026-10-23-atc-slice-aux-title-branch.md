# Agent Note: 排除用途行的标题兜底不挂在增量分支下

Status: implemented

## Problem

摘要阶段转录同步的展示分支时，排除用途（`purpose_chain='exclude'`）的那句标题兜底被写进了"增量非空"这一支里面。同步路径把它放在增量分支**之前**，于是同一笔可读的非标题旁路请求会给出两种结果：

- 关系判得出（增量非空）：两条路径一致，都取 `model_title` 或时间兜底。
- 关系判不出（`delta_ordinals` 为空，旁路请求的常态）——同步写 `title=model_title`、`title_source='model_title'`，切片退到时间兜底 `unknown · 00:00`、`model_time`。

同一笔请求的标题会随它跟上一笔的关系判不判得出而变，这是错的：兜底要说的是"这笔不拿用户增量当标题"，与关系判定无关。

## Decision

把排除用途的标题赋值移到同步路径的同一个位置：可读且非标题的请求先无条件取 `model_title ?? 时间兜底`，只有"增量非空且不是旁路"时才由 `deriveTitle` 覆盖。增量分支里的其余取值（输入摘录、回复摘录）不动。

## Alternatives considered

**在三个增量分支里各写一次兜底。** 三处重复同一条规则，将来加分支很容易再漏一处——正是这次走样的成因。

**让等价性判据容忍这一列。** 标题是折叠行唯一稳定的标识，判据为它让路等于把"两条路径结果一致"降级成"大体一致"。

## Consequences

- 切片摘要阶段的控制流现在与同步路径逐句对应：`isTitle` → 不可读 → 可读（先旁路兜底，再按增量分支）。两处的对应关系是"照抄"而不是"等价重写"，所以下一处走样也会以同样的形状被比对出来。
- 排除用途的可读行在关系判不出来时也保留模型标题，与同步一致；这些行本来就只进旁路队列，改动不影响主链的标题来源。

## Testing

`bun test tests/capacity-slice.test.ts`：固定用例第三笔（排除用途、非标题、关系判不出来、有模型标题）落在这一格；固定种子的模糊组在压缩预算下逐行比对该列——修复前模糊组第一处差异就是这一列（同步 `模型标题 · …`/`model_title`，切片 `unknown · 00:00`/`model_time`），修复后两条路径逐行相等。见[切片派生的等价性判据与容量门槛](2026-10-22-atc-slice-equivalence.md)。
