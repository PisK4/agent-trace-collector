# Agent Note: 派生链前驱匹配的三次方开销与 launchd 后台调度

Status: implemented

## Problem

生产单轮派生最长到 149 s（`jobs.derive.max`），连续两小时里 40 个超过 60 s 的轮次累计 4,622 s，占墙钟 64%。日志只能拆到 compute 段：303 轮 apply 合计 5.83 s，排队为零（`worker.ts` 单飞，第二个请求直接 `busy`），耗时全在 compute 里。

用同一份生产库、同一组（`["session","a6cb4f3b-…"]`，2,325–2,413 请求）、同一份代码在本进程只读复算，耗时 34 s，其中 `matchPredecessor` 占 19.7 s。该组是单链（2,412 条 confirmed），`matchPredecessor` 对每笔请求与**全部**历史祖先逐条算 `commonPrefix`：祖先序列在单链上本身就是本笔的前缀，第 k 条祖先要完整比完 k 段，合计约 n³/3 次比较（n≈2,325 时约 4.2 亿次量级）。

剩下的差距是进程环境而非算法：同一条命令在 `taskpolicy -b`（后台 QoS）下 149.3 s，普通 QoS 下 36.4 s，同一分钟、同一数据、同一二进制。生产由 launchd 托管，plist 写着 `ProcessType=Background`，于是同一份工作被按后台任务调度和限速。

「改前 66 s」不是部署前的基线：旧实例在部署前已经到 87.7 s / 85.0 s，同一实例从 32.5 s 单调涨到 85 s。66 s 是更早、更小规模时的采样，不能当作代码回归的对照。

## Decision

`matchPredecessor` 先找**最早出现的最大长度祖先**，若它整条都是本笔的前缀就直接返回：它是父节点，也是最近祖先。依据是最长祖先的分享长度不可能被更短的祖先超过；并列最长时旧实现保留先遇到的那条，取「最早的并列最长」保持同一取舍。不成立时原样回落到全祖先扫描，分支、增量、零长度祖先、`sawEarlier`/`unreadableEarlier` 的语义都不变。

把启动配置的 `ProcessType` 改为 `Standard`（删除该键等价）。`Background` 不是本服务需要的东西：派生是用户可感知的读模型计算，不该被按后台任务限速。

## Alternatives considered

**只改调度，不动算法。** 那只是把 140 s 压回 36 s，仍有一条 36 s 的同步长组，`chains` 阶段 58% 的 CPU 白烧在重复比较上。

**只改算法，不动调度。** 部署后仍会被后台 QoS 放大 4 倍，19.7 s → 0.07 s 在 140 s 里只是零头，用户看到的仍是百秒级。

**启用切片路径（`deriveBudget` + `capacityExperiment`）。** 它把长组切成小步，不降低总 CPU；工具阶段仍是按 `call_id` 回查全部历史结果再配对。等 QoS 与链匹配都修好、单轮回到十几秒后，再评估是否值得。

**把 `chain_match` 改成维护式增量（只记最长祖先、不扫祖先表）。** 需要改变祖先集合的语义边界（分叉、同毫秒未证实顺序、增量输入），收益与当前短路相同，风险更大。

**本机 plist 之外再放一份仓库模板。** 仓库没有生成 plist 的脚本或模板，`bun run service` 只识别已存在的条目；新增模板会让「本机配置」与「仓库约定」出现两份事实来源。

## Verification

等价性：按 `sync.ts` 链阶段的实际顺序，对请求数最多的 12 个组（含目标组）逐行用新旧两版实现各算一次，比对 `parent`/`relation`/`delta`/`near`，11,935 行 0 处不一致；其中 5,488 行走短路、6,447 行走全扫描，两条路径都被覆盖。单元测试补充了四种边界：单链短路、并列最长只有后一条完整、并列最长两条都完整（保留先到）、最长祖先不完整时回落到更短的完整前缀。

改前后（同组、同一份数据、Bun 1.4.0、只读复算）：`chain_match` 19,705 ms → 69 ms；整轮 34.1 s → 14.4 s。`chain_reads` 5.3 s、`tools_pairing` 5.7 s、`bg_jobs` 3.2 s、`presentation` 55 ms 未变。

门禁：`bun run typecheck`、`bun test`（1,395 项全过）。

调度侧只做了本机配置改动与命令行 A/B，生产重启由用户执行；重启后的实际数字归[验收记录](../../../../docs/acceptance.md)。

## Consequences

短路只覆盖「最长祖先整条是本笔前缀」的形态。分叉多的组仍走全扫描，但那些组的祖先集合本身不大；真正的长链组（本次 2,412 条）几乎全部走短路。

`ProcessType=Standard` 让采集器与派生按普通优先级调度，与用户前台应用争用核心属于预期行为；若将来出现「派生不该抢占交互」的需求，应改回切片的可中断形态，而不是再把整条链路降成后台任务。

`local.tracery-monitor.plist` 仍是 `Background`：它是短周期巡检，不需要同样的优先级，本批不改。

仓库里没有 `ProcessType` 的其他出处，`scripts/service.ts` 只识别与启停已有条目，不生成配置。重装 plist 时必须保留 `ProcessType=Standard`，否则同一份代码会重新慢 4 倍，且日志上看不出区别。
