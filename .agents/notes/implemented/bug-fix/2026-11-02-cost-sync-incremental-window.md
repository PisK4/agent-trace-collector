# Agent Note: 费用扫描改头部增量

Status: implemented

## Problem

`syncCosts` 每 60 秒从 offset 0 重扫当天全部 usage 行。2026-11-02 当天 2,776 行、6 页，每页一个写事务；`writer.by_name.cost` 133 次共 16 秒，`cost` job 的墙钟时间 17 次共 388 秒、单次最长 109 秒——自身写事务不慢，`cost` job 大部分时间在等派生长事务让出事件循环，但每轮全量重扫让它持续抢占写通道，也是尖刺之外可独立消除的周期成本。

usage 行按时间倒序返回（offset 0 是最新），新行插入在开头，因此「从上次进度继续」在时间上并不可行：上一轮的尾部仍是当天最老的行，而新增行出现在头部。

## Decision

已完成的窗口下一轮从头部增量继续：增量轮只处理「行总数增长的部分加固定回看 100 行」，一页以内结束，不再翻到当天尾部。窗口状态记录行总数、定价版本与上次全量时间；每 30 分钟做一次全量校准，定价版本变化时立即退回全量。进度字段与费用观测同事务提交，失败页仍不推进。

## Alternatives considered

**把扫描间隔从 60 秒拉长到 5 分钟。** 只减少轮次，不减少每轮扫描的行数；当天行数越接近全天总量，单轮成本越不变，而且费用显示最多晚 5 分钟。

**按最后一行时间戳做水位。** usage 行是时间倒序，最后一行是最老的行，水位会把自己指向尾部，下一轮仍然从头扫，拿不到增量。

**每轮固定扫头部 500 行。** 比回看窗口省，但定价版本变化或迟到修正落在第一页之外时永远补不上；固定回看加周期全量能覆盖这两类修正。

## Consequences

增量轮通常一页，写事务从每轮六次降到一次；全量轮保留原有分页与进度语义，旧窗口状态（没有行总数与全量时间）在下一轮自动补一次全量。迟到行若插入列表中部，会等下一次周期全量才更新，回看 100 行约覆盖当天 20 分钟的产量。

## Risks

行总数回退（行被删除或上游重置窗口）时增量差为负，按回看下限处理，下一轮的周期全量会收敛。定价版本只在页响应里出现，版本变化要读到第一页才能发现，发现前写入的旧版本页会被全量重扫覆盖；观测按投影去重，重复扫描不产生重复记录。
