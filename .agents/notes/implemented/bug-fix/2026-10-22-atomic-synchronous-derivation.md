# Agent Note: 缺失正文与空消息序列分开判定

Status: implemented

## Problem

正文没有到达的请求与确实没有消息的请求，在库里长得一样：`body_state` 都可能是 `partial`，`request_block` 都可能为空。按"块引用为空即不可读"判定，两者被压成同一种结果。

两个方向的错都在真实数据上发生。真实空消息数组被判成不可比，整组链从第一笔就断——这类请求数量少但位置关键，它们往往是组里的第一笔。反过来，没有骨架的行被当成空序列，而空序列是任何序列的合法前缀，于是它成了任意后续请求的父节点，凭空生成一条没有证据的边；按主链规则，它还会抢走主链根。

## Decision

可比较性由持久化的消息数量判定，不由块引用是否为空判定。`fingerprintsOf` 返回 `null`（不可比较）或指纹数组（可为空数组）：`body_state` 必须是 `available`/`partial`，骨架必须存在，`msg_count` 必须是非负安全整数，且块引用的数量、ordinal 连续性与非空指纹都符合。真实空消息数组因此成为有效证据，占主链根；没有骨架的行保持不可比较，记 `unknown`。

零长度序列不再是合法父节点。`matchPredecessor` 的完整前缀条件要求公共长度大于零：空序列是任何序列的前缀，认它当父节点等于用"这一笔没有消息"证明"本笔续自它"。

`msg_count` 为 NULL 的历史行保守判成不可比较，保留旧摘要；本批不隐式补数。正常写入时 `msg_count` 与骨架的 `has_messages` 一致，损坏骨架的全面校验不在本决策范围内。

## Alternatives considered

**把空块引用一律当不可比较。** 修复前的行为。它保护了缺失正文，却把真实空消息数组一起判死。

**按 `skeleton.has_messages` 判定。** 骨架里的布尔只说明保存时 `messages` 是不是数组，不说明块引用是否完整。库被外部改动、块被误删时它会继续声称"有消息"，读出来的序列比真实上下文短，前缀比较会给出错误的增量。

**让空祖先继续当父节点，但把关系标成 `first`。** 修复前的另一种表现。它把"没有可比对象"伪装成"本组第一笔"，同时给后续请求一条假的父边。

## Consequences

- 合法空请求仍可以是主链根，但不再是任何后续请求的已确认父节点；后继请求落成 `branch`，而不是被接进一条没有证据的边。
- 没有骨架但正文状态为 `available` 的行是防御性判据，生产里对应 `partial` 的降级形态；两者都按不可比较处理。
- 这一改动会改变既有派生结果。部署代码不会自动重算历史会话，历史对齐必须逐会话走维护入口，见[实施计划的离线上线步骤](../../../../docs/superpowers/plans/2026-10-22-atc-derive-correctness.md#上线与历史结果对齐)。
