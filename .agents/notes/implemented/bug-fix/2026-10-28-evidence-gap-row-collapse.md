# Agent Note: 中栏证据缺口记录行的收敛

Status: implemented

## Problem

2026-10-28，本机阅读会话 `7c4d1e83-9a2b-4f57-8e36-0c9a4b1d8f42` 时，中栏一个 30 笔请求的窗口里连续出现四组 Event：每组 3–4 行，全是「正文状态：pending（hook_absent）」「未收到回复」「回调报告失败」「HTTP 状态未知」「新增输入未确认」「会话归属未确认」这类句子，正文内容只有零星几行。点其中任何一行，右栏渲染的是请求级读数页；这些请求恰好正文缺失、结构读不到，右栏只剩「回复还没到」和「结构读取失败」。

读者的反馈是：不知道这些 Event 在说什么，也不知道为什么有这么多。这个反馈指向两个独立的问题——数量与语义——而它们的成因都不在文案本身。

### 现场：五次重试被记成十行

把那个时刻的请求按 `started_ms` 排开，结构立刻显形：

| 请求开始（相对） | 行 | 通道 | 内容 | 状态 |
| --- | --- | --- | --- | --- |
| +0 ms | req 43028 | hook | 请求体完整 | reply=ok |
| +1 ms | req 43034 | 账本 | 无正文 | status=200 |
| +937 ms | req 43030 | hook | 请求体完整 | reply=absent |
| +938 ms | req 43036 | 账本 | 无正文 | status=502 |
| +2190 ms | req 43033 | hook | 请求体完整 | reply=absent |
| +2191 ms | req 43039 | 账本 | 无正文 | status=502 |
| +4769 ms | req 43040 | hook | 请求体完整 | reply=absent |
| +4769 ms | req 43044 | 账本 | 无正文 | status=400 |
| +4967 ms | req 43041 | hook | 请求体完整 | reply=absent |
| +4973 ms | req 43045 | 账本 | 无正文 | status=400 |

**每一对的时间差是 0–6 毫秒**。hook envelope 的 `observed_start_ms` 由插件在 `onRequest` 里取 `Date.now()`（[collector.hooks.ts](../../../../plugins/collector.hooks.ts)），账本的 `started_ms` 是 magpie 记录的请求开始时刻——同一台机器、同一个时钟、同一个瞬间。

也就是说：用户只发了一次输入，客户端因为连续收到 502/400 自动重试了五次，每次重试产生一行 hook 证据和一行账本证据。**5 次真实尝试被记成 10 行。**

全库验证：

| 指标 | 数值 |
| --- | --- |
| `via='hook'` 的孤儿行 | 983 |
| 与某条账本行差 ≤5 ms | 821 |
| 差 ≤50 ms 且候选唯一 | 915 |
| 差 ≤1 s | 978 |
| 找不到对应账本行 | 7 |

两路没能合并的原因写在 [hook 模块的不变量](../../../../src/hook.ts)里：关联只认可核验的 response ID，不按时间近邻猜。而失败请求（502/400/499）两边都没有 response ID——上游没有返回响应体，自然没有 id。`raw_hook` 的 954 条缺失回复记录全部 `success=0` 且 `response_bytes=0`，我们的 `parse_state` 全部 `ok`。这不是解析问题，是失败请求本来就没有共同身份键。

### 每条记录行又各自产出 3–4 条 Event

`projectSteps` 的 `record()` 有十余个调用点，按条件独立判断。一笔请求只要同时缺正文、缺归属、缺 HTTP 状态，就会各出一行；三件事说的是同一个根因。

全库统计（排除辅助请求）：

| Event | 笔数 | 触发条件 |
| --- | --- | --- |
| 正文状态：pending（hook_absent） | 3,453 | `body_state='pending'` |
| 账本报告错误 | 1,003 | `source_facts.selected.error` 非空 |
| 请求失败 · HTTP xxx | 1,002 | `status >= 400` |
| 分支链请求 | 874 | `chain_role='branch'` |
| 新增输入未确认 | 201 | delta 不可算且归属已知 |
| 会话归属未确认 | 341 | `actor_state='unknown'` 且正文可读 |
| HTTP 状态未知 | 341 | `status IS NULL` |
| 未收到回复 | 314 | 回调里 reply 为 null |
| 上下文压缩归档 / 后台作业完成 | 34 | 真实事件 |

重叠关系是决定性的：**341 笔 `actor_state='unknown'` 的请求里，314 笔同时缺回复、缺 HTTP 状态。** 三条行表达的是同一件事。账本错误与 HTTP 失败更彻底：995 笔完全重合，只有 8 笔单独报错、7 笔单独报 HTTP 失败。

一笔请求平均只出 0.38 条记录行，最多 4 条——**数量不是问题，问题是一条请求的同一个缺口被拆成了多行，而重试又把这个数字乘了两倍。**

### 文案是给开发者看的

| 旧文案 | 读者需要知道什么 |
| --- | --- |
| `正文状态：pending（hook_absent）` | `hook_absent` 是存储层的原因码 |
| `回调报告失败 · 未提供失败原因` | 「回调」指 hook 通道，界面从未介绍过这个通道 |
| `新增输入未确认 · retained` | 前缀是 `prev_relation`，后缀是 `derived_state`，两个不同维度的字段拼在一行 |
| `会话归属未确认 · 以下为本次请求的消息` | 「归属」是派生概念 |
| `分支链请求 · 归属来自派生记录，不按时间推断父子` | 纯机制说明。874 笔里 816 笔 delta 本就算得出来，正文照常显示 |

`分支链请求` 归入本表的判断需要单独说明：它记录的是一条派生实现细节，不是请求的内容事实。读者读对话时不需要知道父子关系是推断还是派生的。

### 与既有决策的关系

[单行步骤投影](../../implemented/feature/2026-10-24-trace-step-projection.md)写了「请求级失败、缺正文、未收到回复、截断、未知停止各占一条记录行，已有内容步骤时不省略」，[架构设计](../../../../docs/architecture-design.md#轨迹阅读布局)随后落成「异常作为记录步骤保留」；[孤立请求的正文与来源报告](../../implemented/bug-fix/2026-10-27-unassigned-request-reading.md)定了「标明会话归属未确认，并按请求原文展示消息」；[hook 缺席正文的老化标注](../../implemented/bug-fix/2026-10-25-hook-absent-body-aging.md)定了 `miss_reason='hook_absent'` 的存储语义与文案链路。三份记录的事实判定与存储语义在本篇中全部保留，改变的是**呈现粒度**：缺口不再逐条占据正文轨道，改为每组一行，细节进右栏。本篇部分取代前两份记录中关于「记录行怎么显示」的部分，不取代它们的判定依据。

## Decision

### 中栏：每组至多一条组级状态行

`projectSteps` 不再为每个缺口出一行，改为在步骤列表最前产出至多一条 `kind: 'flag'` 的步骤，稳定键 `reqId:flag`。状态行不带 `Event` 角色标签，标签位是警示标记，整行按缺口强度着色：请求级失败用 bad 软色，其余用 warn 软色。一组没有缺口时不产出该行，正常请求的行数一行不增。

短语按固定槽位拼接，与判定顺序无关：

| 槽位 | 短语 | 条件 |
| --- | --- | --- |
| 正文 | `正文未到` / `正文已回收` / `OTLP 摘要` / `协议暂不支持` | `body_state` 不是 `available`/`partial` |
| 回复 | `无回复` / `回复不完整` / `回复无法解析` / `回复未读到` | 正文可读但回复不可读；正文本身是缺口时不叠 |
| 账本 | `无账本` | `status IS NULL`，即账本里没有匹配到这一笔 |
| 归属 | `归属未确认` / `新增未确认` | delta 不可算；归属可读时说明按请求原文展示 |

处置分四类：

**删除**（纯机制说明或与已有行重复）：

- `分支链请求`
- `会话归属未确认`
- `新增输入未确认`
- `未收到回复`
- `HTTP 状态未知`
- `回调报告失败`

**合并**（说同一件事）：

- `账本报告错误` + `请求失败 · HTTP xxx` → 一行，文案取「上游报错 · 原文」，无原文时取「请求失败 · HTTP 状态码」
- 正文缺口、回复缺口、账本缺口、归属未确认 → 同一条状态行的短语

**保留原样**：

- `上下文压缩归档`
- `后台作业完成`
- 读取进度行（`还有 N 条新增未读取` / `还有 N 条更早的请求消息未读取` / `正文信息未读到 · 点击重试`）——它们带续读或重试入口，是操作入口而非信息
- 回复形状事实（多 choice、截断、停止原因未知）与回调成功/失败报告冲突

**新增**：状态行文案由缺口字段拼装，不再复用存储层原因码。

### 右栏：点状态行打开证据折叠区

`resolveSelectedSource` 对 `kind === 'flag'` 返回 `{side:'evidence'}`（此前 `source === null` 一律落到 `{side:'none'}`，`select-step` 又固定 `railTab: 'facts'`，所以点记录行只能落到请求级读数页）。读数页顶部因此可以渲染「证据」折叠区，四行固定表：

```
证据
────────────────────────────────────────
✓  HTTP 502 · upstream timeout
✗  无关联证据 · 等满 1 小时仍没有回调关联到本笔
✗  正文未到 · hook_absent
?  依赖正文
────────────────────────────────────────
本库没有这笔的回调证据。这不等于上游没有回调过。
```

数据全部来自已加载的 `row`、`read.detail` 与正文首片，不新增接口、不改查询层。正常请求不渲染这一区。整表没有一条到达时给结论句「这一笔只有一条孤立记录」，不留空表。

### 不做的事

- **不合并重试**。读者明确表示重试是真实发生的，需要保留。5 次尝试仍呈现为 5 组。
- **不改关联不变量**。`via='hook'` 与 `via='through'` 的双行问题留在存储层，本轮只做呈现收敛。50 ms 窗口下 51 笔 hook 行同时命中两条账本行，说明时间近邻存在并发歧义，改这条需要独立决策。
- **不改 `TraceStep.status` 的取值**。它是投影层的事实字段，本轮只让渲染层开始消费它（状态行用它定色）。
- **不按 `req_kind` 分流 `source:*` 请求**。107 笔网关旁路请求仍然写「正文未到」；改成「网关旁路请求，无正文」是一个独立的小决策，留待评审。

## Consequences

中栏一组一行状态行；状态行点击进右栏证据折叠区，不落到请求级读数页。`TraceStep` 新增 `flag` 一种 kind；`resolveSelectedSource` 新增 `side:'evidence'`；`railFactsHtml` 新增可选的 `evidenceHtml` 槽位，排在读数页最前。

验证（2026-10-28，worktree `atc-evidence-gap`，分支 `fix/evidence-gap-row-collapse`）：

- `bun test`：923 通过，0 失败。改动覆盖 `tests/trace-view.test.ts`（状态行收口、六种旧文案不再出现、状态行着色与键、证据折叠区四行、无缺口不出行）与 `tests/reader-store.test.ts`（孤立回调的三路缺口合成一行、点状态行解析为证据目标）。
- `bun run typecheck`：通过（`tests/reader-types.ts` 的 kind 联合同步扩展为八值）。
- `bun run verify:notes`：通过。
- 浏览器验收（生产服务 `127.0.0.1:8320`，会话 `7c4d1e83-9a2b-4f57-8e36-0c9a4b1d8f42`，`43028`–`43045`）：结果记在[验收记录](../../../../docs/acceptance.md)。

部分取代的边界：`miss_reason` 的存储值、`hook_absent` 的判定口径、孤立请求按原文展示的判据都没有变。若后续把「正文未到」的文案改动误读成判定变化，应回到 [hook 缺席正文的老化标注](../../implemented/bug-fix/2026-10-25-hook-absent-body-aging.md)核对。

## Alternatives considered

**删除全部记录行，缺口只在右栏出现。** 落选：一笔缺正文的请求在中栏会变成完全空白或只剩一行 loading，读者无法判断是「还没读到」还是「永远读不到」。组级状态行保留了这个区分的最小信息量。

**保留逐行，只给 `failed` / `unknown` 加不同颜色。** 落选：颜色能解决「真失败和不知道长得一样」，解决不了同一根因拆成三行造成的重复。341 笔里 314 笔三件套同时出现，上色只会让三行都变色。

**按 agent 分支处理。** 落选。各 agent 的缺口比例结构性一致（claude 25,595 笔 / 959 条孤儿行，omp 624 / 9，zcode 563 / 8，hermes 429 / 6），因为一笔请求缺 response ID 时两路证据必然各自建行。唯一有差异的 `req_kind='source:*'` 是按请求类别而非按 agent 划分：同一个 `source:vision` claude 与 omp 都会发，按 agent 名排除会同时误伤和漏判。

**在存储层把 `via='hook'` 与 `via='through'` 合并成一行。** 落选：需要放宽 `src/hook.ts` 的关联不变量，从只认 response ID 改成时间近邻。50 ms 窗口下有 51 笔 hook 行同时命中两条账本行，说明并发场景下会错配。这是独立决策，不该混进呈现改动。

**合并同内容块的重试。** 落选：读者明确要求保留，且重试本身是诊断信息。本轮只让每次尝试的呈现从「3–4 行 Event」降到「1 行状态」。

**右栏新建独立的「证据」页签。** 落选：页签是请求作用域，现有四个（读数/正文/工具/路由）已经覆盖阅读维度；证据只在有缺口时有内容，做成默认不出现的折叠区比常驻页签更省注意力。

## Risks

**信息丢失。** 删掉 `会话归属未确认` 后，读者可能不知道下面平铺的是全部历史而非新增。对策是把这条信息压进状态行短语「归属未确认」，并在证据区给出四路事实。若验收发现读者仍误解，需要恢复一行独立说明而不是重新拆开全部 Event。

**右栏空态。** hook 孤儿行没有账本字段，证据表可能三行都为空。此时显示「这一笔只有一条孤立记录」，不留一张空表——那正是旧读数页被批评的问题。

**键稳定性。** 中栏按步骤键做局部提交（[trace-commit](../../../../web/trace-commit.js)）。状态行使用稳定 `reqId:flag` 键，其 HTML 只随缺口字段变化，否则每次重绘都会替换节点，破坏滚动锚点。

**状态行颜色只由缺口强度决定。** 一个 HTTP 500 但正文与回复都完整到达的请求没有缺口，因此不产出状态行，失败只由「上游报错」记录行与请求组边界表达。若读者要求「失败组一定有红色标记」，应改请求组边界而不是把状态行改成常驻。
