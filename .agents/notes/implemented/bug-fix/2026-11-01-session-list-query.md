# Agent Note: 会话列表按页聚合与首屏剩余延迟

Status: implemented

## Problem

后台采集期间打开页面，首个会话行仍需数秒才能显示。[第一轮治理](2026-11-01-collection-interactive-latency.md)已经交付反向索引与列表提前显示，但会话列表查询仍为全部历史会话计算状态，再做排序分页。请求只取 20 个会话，也会访问页外请求的状态字段，当前页之外的历史量继续增加读取成本。

2026-11-01 的独立复核确认剩余问题，观测、候选耗时和覆盖缺口记录在[第二轮复核验收记录](../../../../../docs/acceptance.md#会话列表第二轮复核与候选实验2026-11-01)：生产只读快照里旧列表函数 493–996 ms，两阶段候选 SQL 21–23 ms；合成探针确认旧查询确实读取页外宽字段。

### 与已有记录的关系

Supersession check：本记录细化[第一轮治理的 Deferred](2026-11-01-collection-interactive-latency.md#deferred)中会话候选选择与聚合范围这一项，该项随本记录交付关闭。它不取代已经交付的索引、schema v8 或首屏提交拆分；第一轮记录保持活跃，双方互链。后台任务预算、pending 批次与执行线程仍由第一轮记录持有。

[派生正文重复解压修复](2026-10-26-derive-body-decompression-amplification.md)继续拥有正文复用、读取完整性与完整派生验收。本交付不再以增加同一缓存作为新方案，也不解除生产切片的冻结条件。

## Decision

列表读取分两阶段在同一条只读连接的同一事务里完成，接口、游标编码与返回结构不变，不新增表、索引、缓存、schema 或算法版本。

第一阶段沿 `i_req_session_time` 覆盖索引只读会话键与真实最近请求时间，排序取 `limit + 1` 个候选；游标条件应用在分组之后，首页不带 HAVING。第二阶段以页内会话键的 `IN` 列表复用既有标题、计数、agents 与 flags 聚合；多取的一条只判断 `next_cursor`，空候选直接返回空页。页面顺序按第一阶段候选排列，不依赖第二阶段分组输出次序。页外会话不参与任何宽字段计算，列表读取不触碰正文。

两个阶段放在同一个 `store.read.transaction()`：WAL 快照由阶段一首读固定，采集在两阶段之间提交后，本页排序依据与内容仍来自同一旧快照，下一次调用才可见新会话。事务只覆盖列表需要的同步读取，不跨 `await` 持有。

标题继续按现有优先级与发布代选源，flags 保持失败、待确认、缺正文、旁路、探针的既有顺序；dirty 组不能借提速显示旧标题。跨多次 HTTP 翻页仍采用实时 keyset 语义，不为本次优化增加跨请求快照令牌。

这仍然包含全历史时间索引扫描与会话排序；改法减少的是页外会话的宽字段读取、状态聚合与标题求值，不承诺读取成本只与页大小有关。页面内很长的活跃会话，其页内聚合仍可能较重。

### 旧实现的处置

旧单条聚合查询冻结为 [tests/session-list-oracle.ts](../../../../../tests/session-list-oracle.ts)，供测试与性能脚本做等价对照。它是有意保留的对照快照：列表语义有意变更时，应一并审视这份对照是否仍要成立，而不是无脑跟随改写。

## Alternatives considered

**先缓存整个会话列表或增加物化汇总表。** 能降低重复读取，但要覆盖新增、迟到、合并、删除、标题结算、dirty 与发布代切换等失效路径，还可能带来 schema 与 backfill 成本。两阶段候选的局部收益足够大，不承担这套维护成本；只有覆盖索引扫描或当前页长会话仍不能满足目标时再评估。

**先按请求时间截断，再对剩下的请求分组。** 会把活跃会话的旧请求当作旧页候选，同一会话可能重复出现，计数与 flags 也会缺失。游标必须比较整个会话真实的 `MAX(started_ms)`。

**先取键，再逐个会话查询，或在两个独立快照里查询。** 前者增加往返次数与语句管理，后者允许并发采集混合排序依据与页面内容。一条页面聚合语句加一个只读事务覆盖当前需求。

**只提前绘制或增加 fetch 并发。** 第一轮已经拆掉列表与默认窗口的串行显示等待。服务端列表成本和 HTML 首字节等待仍有独立证据，继续加并发不能保证主线程及时处理请求。

**立即迁移所有后台工作到 Worker。** 可以建立执行隔离，但 writer 归属、协议、队列上限、失败恢复和停机顺序都需单独设计。本交付先落地已验证的小改法；后台采集时尾延迟仍不达标，就按独立方案评审线程边界，不继续靠增加缓存掩盖同步阻塞。

## Consequences

只读事务在读取期间保留 WAL 快照；网络、正文读取与异步等待都不得加入事务，实现是同步函数，结构上不出现这类等待。若仍存在慢查询，需同时观察 WAL 与 reader 持有时间。

页面内超长会话可能占据主要成本：40 万请求合成分布下，首页 20 个会话可聚合上万余条请求，第二阶段耗时随之上升。候选扫描的覆盖索引仍随历史增长；没有测量其分布就不能把合成毫秒数外推到任意数据。

旧查询不是全表字面扫描：计划器用 `i_req_session_time` 免 GROUP BY 排序，外层是会话键区间搜索，差异在「对全部会话键区间做宽聚合」与「只对页内键做宽聚合」。范围断言据此比较 `(conv_key>?)` 与 `(conv_key=?)`，不比较 SCAN/SEARCH 字面。

## Deferred

- 整体卡顿必须按浏览器和 HTTP 实测判断，归[第一轮 Deferred](2026-11-01-collection-interactive-latency.md#deferred)继续定位：HTML 首字节等待与同步长任务不因列表 SQL 达标而消失。列表达标但首屏仍有秒级等待时，保持整体交互问题未关闭。
- `metadataSnapshot` 位于指标快照路径，两秒 TTL 的准入检查调用的是 `measureStorage`，其中包含 `measureBodyBytes`；不得以元数据统计耗时为由认定它每两秒执行，也不得顺带删除准入容量校验。后续统计优化先确认实际调用频率与成本归属。
- 生产部署与浏览器复测、十分钟真实采集负载的列表 p95/p99，交付后另记[验收记录](../../../../../docs/acceptance.md)；合成结果不替代真实响应目标。

## Verification

- 新旧实现等价：冻结快照与两阶段实现各走 limit=3、limit=2 的翻页全序，逐页比较完整返回值（含标题、agents、flags、`next_cursor`），覆盖正式标题、迟到旧请求、同毫秒并列、NULL 会话键与长会话跨页（`tests/queries.test.ts`）。
- 范围断言：捕获真实执行语句做 `EXPLAIN QUERY PLAN`，阶段一两页都在覆盖索引上，阶段二外层是 `(conv_key=?)` 逐键搜索；冻结快照同库计划外层是 `(conv_key>?)` 全范围——断言能失败，通过才有意义。
- 快照一致性：在阶段一首读固定快照之后、宽聚合执行之前，从 writer 连接提交一笔更新会话；当前页仍来自旧快照，下一次调用可见新会话。动态验证，不靠代码含有事务调用判断。
- 翻页边界：空库、仅 NULL 会话键、同毫秒按键倒序、满页与末页游标（`tests/queries.test.ts`）。
- 合成性能对照与等价断言：`scripts/perf-session-list.ts`，4 万与 40 万请求两档，旧、新严格交替计时，首遍单列；数字与覆盖范围见[验收记录](../../../../../docs/acceptance.md)。脚本只验证等价，不设绝对毫秒阈值，不进测试套件。
