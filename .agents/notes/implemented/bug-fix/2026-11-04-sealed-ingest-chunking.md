# Agent Note: 封口会话分块摄入

Status: implemented

## Problem

覆盖护栏上线后的首个 Codex `.jsonl.zst` 回填批次把事件循环压到秒级：滚动最大值 9,036 ms，随后一轮 3,474 ms；到 uptime 1,741 秒时 `writer.codex` 18 次写事务合计 18.58 秒，单次最长 6.17 秒。页面请求在这段时间里只能排队。

原因是封口文件按整份提交：`sealedJsonlRead` 一次返回整份解压文本的全部行，`ingestSessionFile` 把这些行的解析、脱敏、正文与证据写入放进同一个 `store.write`。调度预算在文件之间检查，一个数 MB 的文件已经进入事务后无法中途停下，所以文件越大，单次同步段越长。批次预算按压缩后字节估算，解压后的实际写入量还会超出 2 MiB。

## Decision

封口文件改为按解压后的分块提交，一个文件跨多个写事务完成。

- `sealedJsonlRead` 每次最多返回 256 KiB 或 64 行。`committed_off` 是本块末尾，`observed_off` 是整份解压长度；同代际下 `observed_off <= committed_off` 才算读完，不再重复解压。
- `SessionCursorLookup` 暴露 `observedOff`，发现阶段对封口文件用 `observedOff - committedOff` 算剩余；追加文件仍用文件大小。
- `SessionIngestResult` 增加 `remaining`，`ingestSessionFiles` 在一个批次内连续读取同一文件的多个分块，直到适配器预算用完；物理文件只计一次 `files`。
- 分块之间、live 与 backfill 之间显式让出事件循环。没有推进（坏行阻挡、文件消失）就换下一个文件，避免原地空转。
- 解析状态仍从本代际的 `raw_session_event` 按偏移重放，分块边界不需要在内存里保存状态。

## Alternatives considered

**把解压挪到 worker 或异步 API。** 这只缩短解压本身的同步段，写事务仍然一次处理整份文件；多一套跨线程数据搬运，长尾的主要来源还在。

**只在文件之间让出事件循环。** 首个文件的事务就能压住数秒，让出发生在它结束之后，解决不了单文件长尾。

**每轮只读一个分块。** 事件循环稳了，但数 MB 的归档要按分钟级推进，历史回填会被拖成数小时到数天；分块是为写事务服务，不该同时成为调度粒度。

**跨分块缓存解压文本。** 能省掉重复解压，但要按代际管理内存与失效，单份解压文本仍可能到几十 MB；先把可观测的长尾消掉，CPU 份额留到真实回填数据证明它是瓶颈再处理。

**把 backfill 预算抬到覆盖整份文件。** 等于恢复按文件提交，长尾原样回来。

## Consequences

- 收益：合成样本 1.44 MB 解压文本的最大事件循环延迟从 349 ms 降到 27 ms，总耗时从 359 ms 到 413 ms；9.75 MB 样本从 15,534 ms 降到 406 ms。单次写事务只含一个分块，预算能把大文件切成可中断的工作。
- 代价：每次分块都重新读压缩文件、整份解压并切行，CPU 随分块数放大。9.75 MB 样本总耗时从 15.5 秒升到 22.6 秒，约 45%。分块不降低解压内存峰值。
- 回填吞吐由 backfill 的 2 MiB 解压字节预算决定；封口文件可以在同一轮里连续提交到预算用完，跨轮从 `committed_off` 继续。
- 坏行仍让游标停在行起点，本块 `bytes` 为 0 时循环退出，下一轮从同一位置重试；不会因为分块跳过坏行后的内容。

## Testing

`tests/session-sealed-chunk.test.ts` 覆盖三件事：单块不超过上限且 `observed_off` 大于 `committed_off`；发现阶段用两者之差算剩余；把预算压到 1 字节后每次只提交一个分块，80 轮调用跨多个事务补齐状态，最终游标到整份末尾，请求与证据各 80 条、重复 0、issue 0。合成基准读数见上，真实流量复测见[验收记录](../../../../docs/acceptance.md#封口会话分块摄入合成--生产真实流量2026-11-04)。
