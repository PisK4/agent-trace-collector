# Agent Note: 采集期间交互延迟治理

Status: implemented

## Problem

后台采集与页面读取共享 Bun 事件循环。采集期间打开页面，会话列表和请求窗口都曾等待十多秒。只读连接隔离了 SQLite writer 事务，却没有隔离 JavaScript 执行。后台同步事务未返回时，HTTP 处理同样无法运行。

本轮真实浏览器、生产只读连接和合成 SQL 对照已完成，读数及其覆盖范围归[验收记录](../../../../docs/acceptance.md#采集期间首屏卡顿评估生产只读--合成-sql-对照2026-11-01)。证据指向三个相互放大的问题：pending 合并有无索引反向更新；同步工作单元允许长任务；列表数据到手后还等待请求窗口才画左栏。会话列表全历史聚合也是独立成本，直接读首遍曾达到秒级。

### 与已有记录的关系

[派生正文重复解压修复](../../proposed/bug-fix/2026-10-26-derive-body-decompression-amplification.md)继续拥有正文读取复用、完整性语义和缓存关闭条件。本记录处理 pending 写路径、首屏等待和跨任务响应时间，不取代该记录，不将其缓存视为尚未实现。

[Trace Pair 读模型反向配对索引](../feature/2026-10-24-trace-pair-reverse-index.md)保留详情读取的组内选择与发布代语义。该记录因单条读路径收益不足而暂不增加 `result_req` 索引；本记录新增的依据是 hook 合并的全局写扫描，索引交付时已按约定同步更新其备选依据，配对和失效语义未变。

[性能工作单元计划](../../../../docs/superpowers/plans/2026-10-24-atc-performance-units.md)已经实现具名事务、空闲不写与组间预算。这些措施有效，但动作数和组间预算不限制单动作、单组同步耗时。生产切片继续受[现有容量条件](../../../../docs/operations.md#派生切片与代际)约束，不在本记录中解冻。

## Decision

第一轮交付两件可独立撤回的事：消除已被测到的重复扫描，拆掉首屏的前端串行等待。第二轮候选由剩余延迟决定，见 [Deferred](#deferred)，不把整套候选同时实施。

**两条部分反向索引与 schema v8。** `request(prev_req_id)` 与 `tool_call(result_req)` 各建一条 `WHERE … IS NOT NULL` 部分索引（`i_req_prev`、`i_tool_result_req`），形状来自 hook 合并仅有的两个反向更新——两个更新绑定的参数都非空，NULL 行（链根、未配对调用）从不参与。结构版本升到 v8，v6/v7 存量库在打开事务里原地升级；表结构细节与升级路径归[架构设计](../../../../docs/architecture-design.md#版本与破坏式替换)，启动停顿契约归[运维手册](../../../../docs/operations.md#schema-版本)。

**首屏提交拆分。** `loadSessions` 返回后立即绘制左栏并应用默认选中意图，再独立等待默认会话的请求窗口；统计读取从启动最早点后移到列表之后，不再与 `/api/sessions` 竞争同一时间窗。会话列表不依赖请求正文，页面在窗口请求悬而不决时左栏仍然可用；窗口返回后的 `renderAll` 按既有导航守卫重画全部区块，深链、折叠组与默认落点跳过折叠行的规则不变。

真实库副本上的升级实测约 6.2 s，来源是冷缓存扫描 `request` 全表（骨架 BLOB 使表页散布在 3.1 GB 文件里）。这是一次性成本，之后启动只查 `sqlite_schema` 即短路。接受一次秒级停顿换零新增维护机制。

## Deferred

第二轮候选按剩余延迟取舍，除第一项已交付外其余当前都未实施：

- sessions 的候选会话选择与聚合范围优化已由[按页聚合交付](2026-11-01-session-list-query.md)关闭：两阶段同快照查询，页外会话不再参与宽字段计算。其余候选（pending 批次、重复工作、前端队列、线程隔离）仍按剩余延迟取舍，必要时再比较有正确失效的缓存或物化。
- 缩小 pending 事务批次、在完整动作间让出、给准备扫描加有进度的上限；十个动作上限不是耗时上限，只截前 N 条会让长期无候选记录饿死后排任务。
- 量化并减少派生、存储统计与正文读路径的重复工作；已有缓存省解码，但祖先比较、引用扫描、重配和统计仍同步执行。
- 前端队列清理过期待发任务，再评估 `AbortController` 与目标优先级；浏览器取消不保证中断服务端已运行的同步 SQL。
- 上述仍不能满足响应目标时，把同步采集、写入或派生移出 HTTP 所在线程。触发条件、writer 归属与队列有界要求见[架构设计](../../../../docs/architecture-design.md)的执行线程边界；届时 `main.ts` 继续只做装配，任务协议归持有工作概念的模块。

真实流量复测另写验收记录；合成结果不替代真实响应目标。

## Alternatives considered

**直接开启已有切片。** 旧长链实验排空时间不满足容量门槛，生产读取还有冻结条件。它也不消除 pending 的全表扫描，不能作为本轮首步。

**先加大块缓存或用旧摘要代替正文。** 当前块缓存正在命中；pending 合并仍能长时间阻塞。旧摘要还可能跨输入修订或回收状态失效。先修被测到的 SQL，不改变完整性语义。

**把十动作批次直接改为一动作，或只降低派生预算。** 能缩短一部分同步区间，但无索引时每动作仍可能扫描秒级，单组仍可超预算。先补索引，复测后再定批次。

**先给所有列表和统计建物化表。** 读成本会下降，但需覆盖大量写路径与 dirty 状态失效。现有证据尚不足以承担全部维护成本，先测两阶段查询。

**立即拆服务或换数据库。** 同步线程边界确实需要长期约束，但当前已有低成本的索引与渲染改法。先验证它们能否满足目标；索引不能保证尾延迟时，再按明确触发条件隔离执行。

**先改静态资源缓存和增加 fetch 并发。** 本次模块很快返回；更多并发仍竞争同一服务端线程，还会放大预取。它们不作为十秒级卡顿的首要修复。

**只看平均值或队列最终排空。** 列表可有较快中位数，同时发生十多秒尾延迟；队列清空也不代表 HTTP 可响应。验收同时看尾延迟与吞吐。

**显式维护窗口代替启动迁移。** 需要新增维护命令并处理"用户没跑维护就重启"的情形——启动时照样遇到版本差异，除非再加一条拒绝启动的门，那是第二套机制。升级只发生一次、事务原子、失败回滚后重跑即完成，一次秒级停顿写进运维契约比重读更便宜。

## Consequences

索引增加写维护与存量构建成本；真实非空引用比例（本机 `tool_call` 约 99%、`request.prev_req_id` 约 31%）高于合成稀疏夹具，部分索引在实际数据上接近全索引，空间与写成本以本机实测为准。合并路径的写放大换取的是每次合并从全表扫描降为索引定位。

提前显示左栏会暴露后续窗口仍在读取的状态：中栏加载提示与 pendingSession 语义照旧表达在途导航，导航收尾仍遵守既有 epoch 守卫。统计读取后移不承诺节省其整段 HTTP 等待时间，只移除它与列表的竞争。

升级路径保证：中断即回滚，`user_version` 停在旧版本，库保持可打开状态，重试从头执行；升级前后引用与派生结论不重算。旧二进制遇到 v8 仍按 `schema_version_unsupported` 拒绝。

## Verification

- store 迁移回归：v6 与 v7 库原地升到 v8、空库建到 v8、更低版本拒绝；模拟中断后的半迁移状态（索引缺失、版本停在 v7）重开即完成；升级前后行内容一致（`tests/store.test.ts`）。
- hook 合并回归：前驱引用与工具结果引用随合并改指目标、旧行删除（`tests/hook.test.ts`）。
- 查询计划断言：两条反向 UPDATE 走 `SEARCH … i_req_prev` / `i_tool_result_req`，不再全表扫描（`tests/store.test.ts`）。
- 真实库副本升级计时：3.1 GB、41,186 笔请求、28,755 条工具调用，索引构建 6.2 s、提交 2.4 ms，库文件字节数不变、WAL 增长 0.5 MB，磁盘余量约 423 GB。
- 未验收：浏览器首屏行为（列表到手即画、延迟窗口悬置、深链与竞态）属真实流量复测；十分钟背景采集下的 sessions p95/p99 与 5 s 上限、分项计时增量未跑。目标未达前不用单次最佳值关闭问题。
