# Agent Note: 交互延迟第二轮证据与展示一致性核查

Status: proposed

## Problem

第一轮[采集期间交互延迟治理](../../implemented/bug-fix/2026-11-01-collection-interactive-latency.md)交付了 schema v8 反向索引与首屏提交拆分，但其 Deferred 明确第二轮候选「按剩余延迟取舍」，且真实流量复测当时未跑。2026-11-01 本机完成了一轮真实条件实测：接口基线用 curl（15 场景 × 10 次），前端用 ego-browser 驱动真实页面交互，服务端读 `/api/ingest-metrics` 指标。测试期间会话自身持续产生采集流量，测得的就是采集期间条件。结论是：单步交互全部健康，剩余延迟集中在批量加载与随机尖刺两个形态；同时复合动作下的展示数据一致性尚未验证——「选中 A 显示 B」这类错位无法从单步性能测试中发现。

实测底料：42,673 笔请求，库 3.24 GB（正文 1.05 GB），正文可用 22,129 / 已回收 13,074 / 待定 7,408，pending hooks 1,197。

### 服务端证据：derive 写事务阻塞共享事件循环

`/api/ingest-metrics` 自报的事件循环滞后：p50 1.03 ms，p95 在 22–181 ms 间随窗口波动，p99 242–572 ms，max 2,061–2,417 ms。writer 按名统计给出对齐的画像：derive 事务 1,779 次共 305 秒，**单次最大 2,463 ms**，平均 171 ms；cost 扫描 429 次共 34 秒，单次最大 364 ms。单进程单事件循环意味着 derive 事务运行期间所有 HTTP 响应排队——这解释了 curl 测到的会话列表 p95 尖刺（p1 367 ms、p5 406 ms，p2–p4 仅 8–32 ms，尖刺不随分页深度增长）。第一轮治理针对的是 hook 合并的全局写扫描，derive 本体的长事务尚未动。

### 前端证据：fetch 放大与 DOM 规模

| 操作 | 感知耗时 | 伴随 |
| --- | --- | --- |
| 冷打开到列表渲染 | 512 ms | `/api/sessions` 51 ms、`/api/stats` 129 ms |
| 切换 364 笔大会话 | 161 ms | 65 个 fetch |
| 「加载后续记录」每拍 | 2.7–10.3 s | 每拍 +150~450 行、92–489 个 fetch |

| 滚轮阅读 | 流畅 | 0 fetch、0 longtask：正文在加载时预取，不在滚动时取 |
| 点击行 → 右栏出读数 | 179 ms | 正文页 266 ms 渐进到达 |

1,030 个 fetch 指打开一个 364 笔会话的全过程：每个可见行拉 `/api/requests/:id` 详情、一次 `body?from=0&to=0` 探针与若干追加页。本机 localhost 上单个都 ≤20 ms，但事件循环一旦被 derive 阻塞，在途整批一起 stall，用户感知为一次明显卡顿；这也是 20 秒全量加载的主要构成。

### 复合动作一致性核查结果（2026-11-01）

归属与读数对照全部通过，未发现「选中 A 显示 B」类错位：

- 静置选中行 76511：右栏归属正确，缓存命中 91%（API 91%）、耗时 12.81 s（API 12,808 ms）逐项一致。
- 「加载后续记录」进行中点击已有行 76528：窗口从 141 行涨到 246 行的同时归属不变，缓存 57%、耗时 39.99 s 与 API 一致，0 长任务。
- 120 ms 间隔快速连点 76572→76601：最终右栏显示第二下的 76601。
- 点击加载批次里新到达的行 76647：归属正确，缓存 96%、耗时 19.90 s 与 API 一致。
- 上下文明细弹窗的 `context-item` 请求始终指向当前选中行。

发现一处目录层失真：轮次带只画起点在当前已加载窗口内的轮次（`renderTurnBand` 有意跳过，`web/turn-band.js` 注释「起点不在当前窗口的轮不进带」）。实测大会话 `/turns` 全会话返回 3 轮，窗口外第 3 轮（start_req 77557）在带中没有 chip——目录把部分加载的会话呈现成只有 2 轮。这不是归属错误，是完整性表达的产品取舍：补 chip 需要定义「点窗口外轮次先加载到位」的导航语义，或接受目录按窗口截断并在界面表达还有更多轮。

会话列表 flag 审计（50 个会话、逐会话拉全行重算）：`missing_body` 与 `failed` 与行数据完全一致。17 个会话的 `unknown` flag 无法从行 API 完全复核——列表行不暴露 `prev_relation`，flag 的 SQL 语义是 `actor_state='unknown' OR prev_relation='unknown'`，差异全部可归因于审计盲区而非缺陷。

### 加载时间分解与规模分布（2026-11-02）

对「加载后续记录」逐拍做墙钟分解（在途请求计时 + 长任务观察）后，剩余延迟归为三个因素：前端在途并发上限只有 4（三拍实测 maxInflight 均为 4，295 个 fetch 只形成 5.0 秒的覆盖窗口，管线吃不满）；服务端尖刺叠加（单次 fetch 最长 2,659 ms，与 derive 事务 2.4 s 对齐，命中时四条管线同时停）；随已加载行数增长的渲染残余（零请求零长任务的空窗 1.6→2.4→3.6 秒，是低于 50 ms 阈值的排版与提交成本的累积）。加载慢的主导项是前端管线（fetch 绝对数 × 并发 4），服务端尖刺负责不可预测的恶化。

规模分布把未测风险量化了：全库 936 个会话，最大 2,505 笔请求（实测会话 477 行的 5.3 倍），800 笔以上 12 个；agent 分布 hermes 438、magpie 269、claude 156、omp 38——已测交互全部落在 claude 会话上。按 fetch 绝对数与 DOM 线性外推，最大会话的全程加载约 5,000 个 fetch、DOM 数万节点，这条路径没有任何实测。

### 收尾核查结果（2026-11-02）

规模外推被证实且比线性更糟。2,471 笔的会话全程加载实测：17 拍「加载后续记录」、约 7 分钟点击等待、约 5,000 个 fetch、**1,246 个长任务**、DOM 最终 64,834 节点、**堆内存峰值 2,327 MB**、单次 fetch 最长 7,327 ms。每拍耗时从行数 800 以下的 1.5–3 秒涨到 1,800 行后的 19–50 秒，其中一半以上是渲染长任务——增长是超线性的，卡顿主导。64k 节点下的纯滚动反而流畅（12 次滚轮 0 长任务，键控提交只在加载时付出代价）；但**离开会话后内存不释放**：回主页后堆仍有 846 MB（首次打开基线 95 MB），阅读缓存把整场会话留在堆里。

派生正确性抽查四族全部通过：工具配对取 76460 的回复侧三个 tool_use，按 id 在配对请求 76471 的正文里全部闭合、结果文本在位；增量预览三例（预览文本在本笔正文尾页、confirmed 关系样本的新消息不在父请求正文里）；treemap 归因逐项算术闭合（prompt 1582/2667=59%、billing 36=1%、系统提示其余 1 token=0%）；费用 priced 展示 $0.000500725 与 API 0.00050072469 一致。轮次带截断仍是唯一显示层 finding。

其余收尾：Hermes（951 笔）与 OMP（304 笔）会话打开 615–627 ms、行点击 60–78 ms、归属与读数一致、0 长任务；OMP 会话默认视图只有 2 行可见（探针行折叠所致，304 笔请求几乎全部收进折叠组，目录观感偏空）。深链 `?trace=` 802 ms 落位、back/forward 由缓存重建（0 次取数）；但**深链到不在已加载列表的会话时 h1 显示「这个会话不在已加载列表里」**、document.title 回退——功能可用、身份降级。会话搜索即时。未覆盖（窗口内无对应夹具，如实记录）：summary entries「更多」分页的点击路径、工具结果右栏页签的点击路径、unpriced/zero/absent 三种费用态的展示。

### 与已有记录的关系

第一轮治理拥有 pending 写路径、首屏拆分与线程隔离触发条件的决策权，本文是其 Deferred 第二轮的证据输入与候选排序提案，不取代它。[按页聚合的会话列表查询](../../implemented/bug-fix/2026-11-01-session-list-query.md)拥有两阶段查询语义，本文的会话列表数据不改变它。[派生正文重复解压修复](2026-10-26-derive-body-decompression-amplification.md)继续拥有正文读取复用，本轮正文页实测 1 ms，未观察到解压放大，不推进也不否决该提案。[稳定的渐进式轨迹阅读](../architecture/2026-10-27-stable-progressive-trace-reader.md)处理阅读中的重渲染跳变；本文补充它未覆盖的另一面——右栏数据与选中请求的归属一致性。

## Proposal

第二轮按证据排序取三件，各自独立可撤回，不整套同时实施：

1. **derive 长事务分段让步。** 在完整派生动作之间让出事件循环（或按耗时预算切片），目标把单次同步区间从 2.4 s 量级压到 50 ms 量级。第一轮 Deferred 已列「在完整动作间让出」，本文补充了它的量化依据：平均 171 ms、单次最大 2,463 ms。cost 扫描（max 364 ms）同路径一并处理。
2. **行明细与正文探针合并。** 每行「详情 + 探针 + 追加页」的聊天式取数合并为窗口级批量端点，全会话 1,030 个 fetch 压到十几个量级。语义沿用现有阅读版本守卫（`if_reading`），批量不绕过一致性检查。
3. **展示一致性核查与修复。** 复合动作断言已于 2026-11-01 在真实页面执行（结果见 Problem 的核查结果小节），归属与读数全部通过；待办收敛为两件：对轮次带目录完整性做产品决策并按决策实现，把断言清单固化进 `bun test`。

`/api/stats` 与 `/api/ingest-metrics` 的慢查询不在本轮：都不在用户路径上，第一轮 Deferred 的「重复工作量化」再决定是否做增量统计。

三块研究收尾已于 2026-11-02 完成（结果见 Problem 的「收尾核查结果」），research 阶段到此收敛，转入修复决策：极端会话实测证实超线性恶化，Hermes 与 OMP 走读无新缺陷，剩余交互面除三项如实记录的未覆盖路径外全部通过。派生正确性抽查（工具配对、增量序号、treemap 归因、费用四态之一）与一致性断言同批固化。突发负载回放不属研究，留给修复验收。

### 复合动作一致性断言清单

- 加载后续进行中点击已有行：右栏 req id 等于点击行的 `data-req-id`，四项读数等于 `/api/requests/:id` 独立返回，正文页请求指向同一 id。
- 快速连点 A→B：最终右栏显示 B。
- 加载进行中点击新到的行：归属与读数同样正确。
- 弹窗 `context-item` 请求的 req id 等于当前选中行。
- turn band 边界与 `/turns` 返回的 `start_req`/`reply_req` 一致。
- 会话列表 flag（如 `missing_body`）与该会话请求的 `body_state` 分布一致。

## Alternatives considered

**立即把采集或派生移出 HTTP 线程。** 第一轮已把它列为触发条件明确的最后手段；当前证据显示 derive 让步与批量取数是更低价的第一步，先验证它们能否满足目标。

**给行明细加物化或缓存。** 读成本已经毫秒级，慢的是请求数量与事件循环阻塞；缓存不解决这两者，还引入失效维护。

**前端只减并发或加 AbortController。** 第一轮已否决作为首要修复：浏览器取消不中断服务端已运行的同步 SQL；减并发反而拉长整体加载。批量端点减少的是请求绝对数。

**长会话虚拟滚动。** 能压 DOM 与 longtask，但改动面大，且 fetch 放大与事件循环阻塞不解决；先做前者，DOM 治理在真实数据重新测量后再决定。

**把一致性检查只放自动化测试。** 合成夹具构造不出真实库的复合时序；断言清单以真实页面执行，修复合入后再固化进 `bun test`。

## Acceptance criteria

- 采集期间（本会话持续产生请求的真实条件）：会话列表与请求窗口请求的 p95 尖刺不超过 100 ms；`/api/ingest-metrics` 事件循环 max 不再出现秒级值。
- 打开 364 笔会话到全部加载完成的 fetch 总数 ≤ 30，全程无可感渲染卡顿（longtask 计数为 0 或接近 0）。
- 2,500 笔量级的会话全程加载可用性有界（当前基线：17 拍约 7 分钟、堆内存峰值 2,327 MB、1,246 个长任务）；离开会话后阅读缓存不把整场会话留在堆里。
- 归属一致性断言（静置、加载中点击、快速连点、新增行、弹窗五态）固化进 `bun test` 并保持通过；轮次带按产品决策收敛——要么补全窗口外轮次并定义导航语义，要么保留截断并在界面如实表达「还有更多轮」。
- 会话列表 flag 审计脚本保留为复核工具；`prev_relation` 进入行 API 后 unknown flag 可全量复核。
- 验收按[验收记录](../../../../docs/acceptance.md)惯例分轮记录，合成与真实分开。

## Risks

derive 让步会拉长单场派生的总时长，dirty 组的排空延迟变长；需要与第一轮的组间预算语义合并设计，避免为让步再引入第二套预算机制。批量端点扩大单响应体积，弱窗口下首字时间变长，需要保留渐进渲染。一致性修复若落在选择状态机，触碰[键控提交与视口锚点](../../implemented/architecture/2026-10-27-keyed-trace-main-view.md)已固化的语义，必须在该记录的约束内改动。
