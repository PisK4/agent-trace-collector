# Agent Note: 脏组的会话标题子查询做全量扫描

Status: proposed

## Problem

[长窗口性能验收](../../../../docs/acceptance.md#认领边界长窗口性能验收真实流量2026-11-03)在 2026-11-03 测到：`GET /api/sessions?limit=50` 顺序 20 轮 p50 462 ms、max 514 ms；`limit=1` 也要 0.46–0.88 秒；取第二页（不含热组）只要 14–23 ms。直接调用 `listSessions` 同样是 200–400 ms，成本在查询内部，不在 HTTP 层。

热组 `679ab0be` 当时有 4,357 笔请求，所属组 dirty。两阶段查询的第一阶段 6.8 ms；第二阶段单独执行时，四个标题子查询合计 226 ms，每条 78–82 ms。同期不带标题的标志聚合 81 ms、计数 10 ms。

标题子查询逐行 join `derive_queue`，谓词要求 `groupCurrentSql`（clean、发布修订等于输入修订、算法一致）。组 dirty 时没有一行满足，子查询仍要扫完该会话的全部请求才能证明无结果。实测佐证：

- 同一会话上不带 join 的 `LIMIT 1`，首行命中时只要 0.05 ms。
- 只做谓词计数的 `count(*)` 要 56.7 ms。
- 把整段标题表达式包进 `CASE WHEN EXISTS(clean 队列行) THEN … END`，同一脏组只要 0.4 ms。

标题语义已经规定脏组没有标题：`groupCurrentSql` 让四个候选全部落空。问题在于这个「没有」是用整组扫描换来的。组越活跃、越长，单次列表读取越慢，而 dirty 恰恰是活跃会话的常态。

[会话列表按页聚合](../../implemented/bug-fix/2026-11-01-session-list-query.md)已经交付两阶段读取，并把「页面内很长的活跃会话，其页内聚合仍可能较重」留在 Consequences 里。本提案处理这一项，不改变两阶段形状、游标语义与标题优先级。

## Proposal

第二阶段先按页内会话判一次组当前性，再决定是否求标题。实现上把四个候选的 `COALESCE` 包进同一个 `CASE`，条件用相关 `EXISTS` 或第二阶段聚合里已有的 `MAX(CASE WHEN … THEN 1 ELSE 0 END)`。组不当前时直接返回 `NULL`，四个子查询不执行。

子查询内部逐行的 `q.actor = r.actor` 与 `groupCurrentSql` 谓词保持原样，标题的来源与优先级不变。多 actor 会话如果同时存在 clean 与 dirty 的组，外层判定为真，dirty actor 的行仍会被扫描；标题结果仍然正确，只是省不掉这部分成本。本机会话是单 actor，这一限制先接受并在实现时写进测试。

按实测，脏热组的标题成本从 226 ms 降到不足 1 ms；列表首屏剩下的标志聚合 81 ms 与计数 10 ms 不动。页面首屏不会因此变成本地调用那么快，HTTP 等待还受事件循环其它任务影响。

## Alternatives considered

**给 `conv_key` 加更多索引。** 扫描不是为了排序或等值查找，而是为了证明没有任何一行满足「组当前」。谓词落在 join 后的状态上，索引起点仍然是整组行，收益接近零。

**发布时把标题写进 `derive_queue`。** 组 clean 时列表直接读一列，脏组继续为空，语义吻合。代价是新增派生列、发布事务里要重算标题、多 actor 会话要定归属，还要 backfill 和算法号联动。改动面比一个 `CASE` 大得多，留到本方案收益不足时再评审。

**物化整张会话汇总表。** 标题、计数、agents 与 flags 一起缓存，能压掉剩余 91 ms，但失效路径覆盖新增、迟到、合并、删除、标题结算与发布代切换。[会话列表按页聚合](../../implemented/bug-fix/2026-11-01-session-list-query.md)已经以同样的理由否决过一次，不重复引入。

**客户端懒加载标题。** 首屏先出没有标题的行，再按需取标题。改变接口与页面契约，且侧栏每行都需要标题，请求数会随会话数增长。

**给列表加结果缓存。** 只降低重复读取，不改变单次读取的固定成本；迟到请求、dirty 切换与标题结算仍要失效，收益不稳定。

## Acceptance criteria

1. 行为等价：脏组与前缀组的会话标题仍为空；clean 组标题与冻结快照 `tests/session-list-oracle.ts` 逐页一致；翻页、同毫秒、多 actor、迟到旧请求这些既有用例继续通过。
2. 组在两次读取之间从 dirty 变 clean，第二次读取必须出现标题；反向切换后标题消失。
3. 性能：在合成 4 千行会话上，dirty 组首页标题求值不再触发整组扫描。用 `scripts/perf-session-list.ts` 或等价脚本记录首屏 p50，目标是去掉标题成本的大部分；脏组与 clean 组分开报。生产只读快照复测一次，记录首屏 p50 与调用次数，不把合成数字外推成生产承诺。
4. 查询计划或计时断言能失败：改动前脏组标题耗时随会话行数线性增长，改动后与行数脱钩。只断言「变快」不算数。
5. 测试只用合成数据，真实会话键、标题与正文不进 fixture。

## Risks

`CASE` 的短路依赖 SQLite 的表达式求值顺序。SQLite 文档保证只求值选中的分支，但版本差异与优化器改写仍可能让子查询被提前求值；验收要用执行计划或计时把这一条钉住。

外层判定按会话聚合，多 actor 会话会退化为逐行扫描。标题结果不受影响，成本上界回到现状。

标志聚合的 81 ms 仍在。会话继续增长时，`MAX(CASE …)` 的增长路径与本提案无关，需要另一次测量，不能拿本次结果宣布列表读取已与大小无关。
