# Agent Note: 派生正文重复解压修复

Status: proposed

## Problem

2026-10-26，一次对本机 ATC 高 CPU 与页面停顿的诊断发现，活跃长会话每次输入变化都会触发整组派生，而派生为生成回复摘要还原了请求的全部消息。另一位 Agent 据此提交性能报告。本轮审查通过源码、合成解压计数和真实库只读聚合确认重复读取存在，又发现工具配对与后台作业配对也会重复扫描正文。本文供下一位 Agent 评审并实施，修复尚未交付。

问题影响同一 Bun 事件循环里的摄入、定时任务和查询。长组同步派生没有组内让出点；一次任务占用数秒，即使摊到数小时的耗时占比不高，也会延迟同时到达的请求。存储层的块去重减少磁盘占用，却没有减少读取端对同一压缩块的重复解压和 JSON 解析。

### 最初怎样发现

原报告记录最大会话组有 885 笔请求、73,160 条消息块引用，按引用累计压缩正文约 120.4 MB。报告给出的全量 SELECT 耗时为 8 ms，派生任务单次最大耗时为 10,736 ms，累计耗时 617.8 s，进程运行时间约 30,434 s。同期事件循环 p99 为 215 ms、最大延迟为 9,159 ms，摄入接受 241 次、busy 拒绝 44 次。这些是原报告的现场快照，缺少本轮独立留存的采集时间与原始输出，不能当作本轮重测结果。

原报告已排查 database is locked 循环、用途排空死锁、缺索引、SELECT 本身慢和多进程并发写入：分别报告只有一次锁错误、purpose_pending 峰值为 3、索引走 SEARCH/COVERING、SELECT 约 8 ms，以及只有一个进程持有数据库。本轮没有重复这些现场排查；下一位 Agent 不应把这些历史观察外推为任何时点都不会发生，也不应在没有新证据时沿这些方向代替本次修复。

原报告留了四个问题：`replyInfoOf` 是否只读回复，`interruptCountTx` / `contextEventTx` 是否也解压，`from_sort` 是否已经让组内处理增量化，以及 2.0% 的累计占比是否足以证明稳态问题。最初提出的三个方向是启用增量游标、复用 `reply_preview` 和等待会话安静后再派生。本轮结论支持重复解压这一主张，但不支持直接据此采用任意一种方案。

### 本轮审查确认了什么

源码检查最初以 `f5b5035` 为锚；提案落笔时工作区为 `5ee5f98`，两者之间本文涉及的派生、正文、调度和指标代码无差异。后续实现前需重新核对符号与调用关系，行号只作为本次定位提示。

| 位置 | 当前行为 | 对问题的判断 |
| --- | --- | --- |
| [组读取与循环](../../../../src/derive/sync.ts)，`drainDeriveGroupTx`，约 270–292 行 | 按 `(conv_key, actor)` 取全部已知归属请求，每行读取指纹；指纹可读时调用 `replyInfoOf` | 同步路径没有用 `from_sort` 限定组内请求范围 |
| [共享读取](../../../../src/derive/read.ts)，`fingerprintsOf`，约 99 行 | 查询持久化的 fingerprint 与引用 ord | 不解压消息块；不能把这里的查询成本称为正文解压 |
| 同文件 `replyInfoOf`，约 159 行 | 调 `readBodyTx`，随后仅使用 `body.reply` 算预览与回复形状 | 有消息的有效正文会被完整还原，取回复付出了全部请求消息的成本 |
| [完整正文读取](../../../../src/body.ts)，`readBodyTx`，约 236–268 行 | 先读骨架与引用校验，再对每条消息引用执行同步解压与 JSON 解析 | 无跨引用或跨请求解压缓存；相同 block 被引用多次仍重复解压 |
| [工具配对](../../../../src/derive/sync.ts)，`pairToolCallsTx`，约 421–444 行 | 遍历参与用途请求，再次 `readBodyTx`，提取回复调用和请求结果 | 单轮派生内存在第二次完整读取；没有工具调用也会先读完整正文 |
| [中断与上下文事件](../../../../src/derive/read.ts)，`interruptCountTx` / `contextEventTx` | 中断按 delta 读取；事件在 first/confirmed 时按 delta 读取，branch 时最多扫 20 条 user 消息并可提前结束 | 会解压，但不能一概称为两次全量扫描；不同消费者仍会重复读取相同消息 |
| [后台作业配对](../../../../src/derive/bg-jobs.ts)，`pairBackgroundJobsTx` | 每个参与请求扫描 role=3 的发起痕迹和 role=0 的完成通知 | 额外的整组消息扫描，修复不能只覆盖回复摘要 |
| [摘要判定](../../../../src/derive/decision.ts)，`presentationDecision`，与 `presentationPortsOf` | 按 delta 读消息，必要时读工具结果预览或首尾 user 预览 | 还有按需解压，应计入总成本并复用已读内容 |

完整解压的前提是骨架、引用等校验成功且 `hasMessages=true`；空消息数组不产生消息解压，无骨架、回收或不满足读取条件的行不会走完这条路径。`replyInfoOf` 在同步组循环中也只对 `fingerprintsOf` 返回非 null 的请求调用。

### 合成实验怎样证明重复

审查使用临时 SQLite 夹具，为三笔请求分别保存消息序列 `[A]`、`[A,B]`、`[A,B,C]`，三笔共 6 条引用、3 个共享块。用途冻结为参与链，统计时用 `mock.module('node:zlib', ...)` 包装真实解压函数，按压缩字节识别消息块，按调用栈区分读取路径。用途判定与建库不计入测量阶段，断言以解压次数为主，耗时仅供观察。

| 操作 | 回复摘要消息解压次数 | 工具配对消息解压次数 | 全部消费者消息解压次数 |
| --- | ---: | ---: | ---: |
| 首次派生三笔、6 条引用 | 6 | 6 | 27 |
| 已 clean，无输入变化，再运行 | 0 | 0 | 0 |
| 追加 `[A,B,C,D]`，四笔共 10 条引用 | 10 | 10 | 42 |

单独读取第三笔时，`fingerprintsOf` 解压 0 条消息，`readBodyMetaTx` 解压一个骨架、0 条消息，`replyInfoOf` 解压一个骨架、3 条消息。delta 为 `[2]` 时，中断计数和上下文事件各解压 1 条消息。27 与 42 包含后台作业和展示取数，不是所有协议或会话固定的放大倍数；6→10 则直接证明追加一笔后旧请求仍被完整读取。

最初使用 `spyOn` 未截获已经绑定的模块导入，出现计数为零的失败；改为在动态 import 被测模块之前安装 `mock.module` 后，计数断言才通过。后续应把有效的计数方式写成仓库内回归，不能复制失败的 spy 方式得到虚假的零解压结果。

实验另构造一条引用仍存在、压缩字节损坏的消息：`readBodyMetaTx` 能返回骨架，`readBodyTx` 返回 null。这说明只改一个调用函数虽然能消除解压，却可能改变完整性判定。该差异必须进入实现评审与测试。

临时脚本不属于交付物，也不作为跨会话可用的前提。下一位 Agent 应依据上述构造建立正式合成测试。本轮临时实验最终 1 项通过、13 个断言通过；另执行 `tests/derive-presentation.test.ts` 与 `tests/derive-tool-pairing.test.ts`，30 项通过。这些验证确认问题与现有基线，没有验证任何修复。

### 重启调查与已有反证

后续反馈提出重启可能放大尖峰。本轮只读核实 `~/Library/Logs/agent-trace-collector.log` 有 39 条 `collector_listening`，当前 launchd 服务 `local.agent-trace-collector` 显示 `runs=5`、`last exit code=0`。两项计数的观察窗口尚未统一，没有逐次启动时间及退出原因；它们既不能证明 39 次异常重启，也不能建立重启与慢派生的因果关系。反馈阶段未记录精确采集时点，这些计数只作调查线索。

代码检查与合成重开实验提供了边界：两笔合成链完成派生后，关闭并重开库，再调用 `createDeriveUnit(...).run({budgetMs:400})`，队列仍 clean，输入修订与发布修订不变，请求派生计数不变，返回 `didWork=false`，工作单元没有任务写事务。该实验覆盖开库与在线工作单元，没有启动完整采集器或重放外部来源。因此，重启本身不会使无变化的同步 clean 组重新派生；不能由启动次数直接推导整库重算次数。

重启时遗留 dirty 组、进程内缓存丢失、启动后补到的来源证据，都可能使启动窗口成本上升。实施前需核对启动与部署、手动维护、退出原因的时间关系，并观察启动前后待办组、输入修订与来源游标。确认是否实际存在重复恢复或新增标脏，再决定是否另修生命周期问题。不得为调查主动重启生产服务或隐式重建真实库。

### dirty 与预算的准确含义

[组标脏](../../../../src/derive/state.ts)推进组输入修订，并将状态置 dirty；正常请求输入变化标组时传入空 `fromSort`。同步领取不使用这个字段，完成时通过组世代、输入修订与算法号的比较交换写 clean。无变化的 clean 组不会继续派生，多次输入变化也可能合并到同一次派生。重算发生在后续输入使组再次变脏之后，不能描述为只要组曾 dirty 就永久空转。

[在线工作单元](../../../../src/derive/unit.ts)仅在组间检查预算；生产当前一次调用预算 400 ms，同步单组不可中断。有积压时调度会在让出事件循环后继续，但单次进入长组仍可能阻塞数秒。400 ms 不构成单组最大耗时保证。

### 与已有决策的关系

[容量决策](../../implemented/feature/2026-10-22-atc-capacity-decision.md)已经将整组同步重算认定为容量主因，并保留 `stop-non-long` 与 5 rps 目标未达成的判断。[切片冻结](../../implemented/architecture/2026-10-24-slice-read-freeze.md)记录旧长组合成实验切片 878.7 s、同步 1.96 s，并要求读取完整性与容量验收。本次定位补充重复正文读取的机制证据，不把旧容量实测当成当前版本基准，也不把已知的整组重算本身冒充新发现。

Supersession check：本提案与上述容量、切片冻结、[预算工作单元](../../implemented/architecture/2026-10-24-budgeted-derive-unit.md)、[请求用途与链](../../implemented/architecture/2026-10-22-request-purpose-and-chain.md)部分相关。目前保留其全部现行决策，不归档、不解除冻结。若实施改变正文完整性判定或组内事务边界，需明确部分取代范围并同步反向链接；本提案不以 Proposed 状态宣称已经反转这些决定。

## Proposal

修复目标是减少重复解压与解析，并验证完整组派生及事件循环尾延迟是否改善。实施顺序为先归因、再做无 schema 变更的有界块缓存、最后按剩余瓶颈决定是否扩大方案。保留整组关系结算与原子提交；跨轮复用、持久化提取和增量关系算法都不作为本次修复的预设完成条件。

### 实施前建立归因基线

先调查启动记录与尖峰的时序，区分部署、手动重启、异常退出和已有 dirty 积压；同时在固定输入快照上测量完整组派生。两条调查独立推进，启动原因未查明不妨碍验证重复读取，也不能用日志总数替代生命周期归因。

测量至少包含三组对照：原实现的完整派生、保持结果相同的预解码替身、候选有界块缓存的完整派生。先在全合成的代表性长组建立可重复基线；真实数据需要补充时仅在受控隔离副本上测量，不在运行库执行派生或把正文复制进仓库。记录输入快照、请求与引用规模、共享率、缓存预算、预热方式、重复次数和耗时分布。

预解码替身在计时外准备相同骨架与消息，在计时内保留引用校验、遍历、判定和写入，核对与原实现的派生输出一致。不得以返回空 messages、null、跳过工具或摘要阶段替代解码；这些操作会改变后续工作量。预解码不计准备时间的结果只用于估计解码消除后的剩余成本，准备时间和额外内存另报，不能当作可上线方案的端到端性能。

分项测量骨架与引用读取、消息解压及解析、祖先指纹比较、工具及后台作业结算、展示取数与写入。分项若嵌套需要说明，不能重复相加。比较同样工作量下的单组 elapsed time、写事务耗时、事件循环延迟和 RSS，先确定代表性场景的改善目标与可接受内存预算，再进入实现。不得拿历史最大值与其他样本的微基准相减，也不将局部 12.4 倍加速当成整组收益承诺。

### 首个实现采用有界块级缓存

第一步只改读取复用，不新增表、输入提取结果或 backfill。一次组派生共享一个显式读取上下文，对不可变块执行解压与 JSON 解析后按内容身份缓存，跨同组请求和各消费者复用。作用域先限定在该次组派生，组结束或失败即释放，不依赖跨轮热缓存才能获得收益。即使进程刚启动，第一次处理 dirty 长组也能在本轮内利用块共享。

缓存键必须区分数据库与块内容，不能只依赖可能在删除后复用的数字 block id。原始解码结果与依赖 agent、用途、协议的解释分开；相同消息字节可共享，不同上下文的解释仍按当前输入执行。消费者将共享对象视为只读，不得原地清洗或修改，否则一个请求会污染后续请求。正式接口和缓存预算在实施 review 中确定，优先复用现有模块，不新增通用缓存框架。

容量按解压字节及可核算的对象开销设上限，定义单个超大块不入缓存、淘汰与重读的退化行为。记录命中、未命中、淘汰与实际解码次数，缓存预算足够时成本趋近不同块数，预算不足时按实际重读报告；不能无界保存所有解码对象来复现微基准。正常读取仍先检查当前 body_state、骨架与引用，缓存命中不得绕过回收、缺块和 ord 校验；失败结果不得成为永久成功或永久失败的跨修订结论。

接入范围覆盖 `readBodyTx` 的消息解码、`replyInfoOf`、工具配对、中断、上下文事件、展示 ports 与后台作业扫描。只给其中一个入口加缓存会留下多条解码路径，验收应统计全部消费者。同步与切片继续共用判定和读取规则，切片实验使用与事务或步骤匹配的生命周期，不借接线改动解除生产冻结。共享骨架和请求引用可按收益补充，但不以此预建完整请求事实层。

### 回复读取与完整性保持一致

回复对象已经在骨架中，生成回复预览和形状无需重新从消息数组取值。第一步可以保留完整正文校验，只将消息验证与解码统一复用；不能为少读一次消息而改变坏块时的结果。已有 `reply_preview` 仍是带依据的派生结果，不能因非空就沿用；已存 fingerprint 继续直接查询。

若归因后认为直接读取 `readBodyMetaTx` 的收益仍值得交付，应单列骨架可读、消息损坏时的预期，并决定是否将回复可读性与请求可读性分开。语义改变需要列出摘要、工具与 retained 的影响、提升实际受影响的算法号和给出显式历史重建范围。纯缓存且结果等价时不提升 `PURPOSE_VERSION`，不隐式重判全库。

### 用结果决定是否扩大方案

缓存交付后复测同一基线，区分首次 dirty 派生、持续追加、缓存淘汰与重启后的 dirty 恢复；重启后的 clean 无变化场景应保持无派生。若重复解码已受控，正确性通过，代表性端到端改善达到事前目标且内存可接受，可以关闭本次重复解压缺陷。仍有组大小相关的扫描或下一轮重新解码，不自动意味着必须持久化；需要看它是否仍是目标指标的显著瓶颈。

若跨轮历史解析仍明显拖慢目标，再比较进程内有界块复用、按输入身份复用请求提取结果与持久化结果，优先选择能满足实测目标的较小方案。持久化须证明收益足以承担 schema、磁盘、失效和恢复成本；具体表和列由后续 review 决定，不提前承诺。请求提取身份至少覆盖 input_epoch、input_revision、提取算法及实际依赖的上下文，不能复用前驱、delta、resolved 状态等组关系结论。

只有选择持久化后才要求可执行升级与 backfill 或明确拒绝旧库的路径，并测试中断、重试、正文回收与结果丢弃重建。提取结果仍属于敏感正文派生物，按预算和回收约束保留；禁止启动时无预算扫描真实库、原地改写旧依据或以陈旧结果冒充本次重算。若分项显示剩余瓶颈是祖先比较、SQL 或写入，应直接评审对应方案，不为了兑现预设架构继续增加缓存层。

### 实施边界与关闭条件

重复解压缺陷与整体容量目标分别验收。前者需要全部消费者的解码次数回归、结果等价、代表性完整派生改善及有界内存；后者继续由既有长组和速率门槛回答。若局部修复通过但仍有数秒阻塞，交付时明确剩余瓶颈并继续跟踪容量问题，不宣布已达到 5 rps 或严格 400 ms 上限，也不为关闭容量问题强制扩大本次缺陷修复。

`from_sort` 暂不直接作为最后发布位置。正常失效路径写空值，字段未编码完整的时间与来源顺序证据；真正的增量算法需先证明最早受影响位置与依赖传播，覆盖乱序、迟到正文、归属迁移、不确定顺序、分支、工具歧义与回收，并与全量结果一致。

派生调度归工作单元，`main.ts` 保持 wiring。调查结果若表明存在异常重启或启动重复脏，作为独立原因修复并单独验收，不用改变 launchd 策略掩盖同步长组成本。本提案不新增 worker、采集队列、用途规则或 UI；切片启用继续遵守读取完整性与容量要求。

### 交付现状

首步的有界块级缓存已落在 `src/body-cache.ts`。一次读取作用域内按 `hex(block.hash)` 复用解压与 JSON 解析结果，默认预算 64 MiB、单块上限 8 MiB，超出按 LRU 淘汰；失败结果不入缓存，命中仍先过 `body_state`、骨架、引用数与 ord 校验，共享消息递归冻结为只读。同步路径在 `drainDeriveGroupTx` 建立一个作用域，覆盖回复摘要、中断计数、上下文事件、工具配对、后台作业与展示取数。

`DrainResult.body_read` 汇报命中、未命中、解码、超大、跳过、不可读与淘汰计数。合成测试 `tests/body-cache.test.ts` 覆盖三笔共享链（首轮 6 条引用解码 3 个块、追加后 10 条引用解码 4 个块）、低预算与超大块退化、坏块不缓存、缓存前后结果一致；240 笔、每笔 40 条消息的长组对照中，同一代码路径无缓存解码 33,939 次，有缓存 279 次，派生输出逐列相同。以上都是合成数据。

真实流量与完整组端到端对照尚未执行，事件循环尾延迟与 RSS 未测。提案因此保持 proposed。

## Alternatives considered

**只把 `replyInfoOf` 换成 `readBodyMetaTx`。** 可能减少不必要读取，但损坏消息时的完整性语义不同，其他消费者仍会解码。先在保持语义的块缓存上验证收益，是否单独拆分回复可读性由后续分项测量决定。

**直接沿用已有 `reply_preview`。** 该列可能为空、过期或属于回收前历史结果，还缺少工具和上下文所需事实。复用必须有输入身份与算法依据，不能用非空判断有效。

**首步即引入跨轮持久化提取。** 尚未证明它比单轮块缓存更值得投入，也未知道完整派生剩余瓶颈。暂缓新表、backfill 与失效模型；只有较小方案不足且瓶颈仍指向跨轮解析时再评审。

**无界保存整组解码对象。** 微基准可能获得较高命中，却没有控制 RSS、GC 与极大块成本。首步选择有界块缓存，低预算允许重读且保留正确性；跨轮复用不是关闭缺陷的必选项。

**把解压替身直接改为返回空消息或跳过阶段。** 会一起减少工具抽取、关系和摘要工作，结果无法归因于解码。对照必须提供相同消息并继续执行完整派生，准备成本另报。

**把 39 条监听日志认定为异常重启根因。** 缺少时间分布、原因和尖峰对应关系，合成实验还证明同步 clean 组重开不重算。保留启动调查，不据累计计数修改服务重启策略。

**直接用 `from_sort` 从上次发布位置往后算。** 尚无支持旧依赖变化的正确性模型；乱序和后补证据会改变历史结果，当前正常标脏路径还传空字符串。先减少正文提取成本，真正的增量关系算法另评。

**按 dirty_since_ms 等待安静 N 秒。** 该列表示首次未完成时间，不能直接证明最近 N 秒无新输入。即使另记最后变更时间，持续活跃会话仍可能一直不能发布，单轮数秒阻塞也未消失。延迟只可在明确最大等待时间后作为辅助手段。

**立即开启已有切片。** 旧实验显示切片总耗时大幅增加，生产启用仍有完整读取与容量条件。切片解决让出时机，不自动消除重复解压，保留冻结。

**因为累计只占 2.0% 而不处理。** 平均 elapsed time 会掩盖数秒单组阻塞，且比例随观察窗口明显变化。应以重复工作、任务尾延迟和容量门槛判断，不能用低平均值否定已确认的读取放大。

## Acceptance criteria

### 正确性与读取次数

1. 将上述三笔链、无变化重跑、追加第四笔的合成场景纳入仓库测试，修复前能因重复解码超预算失败。统计真实消息解压与解析，不依赖仅看 SQL 返回行数。mock 在模块导入前生效，测试间恢复，夹具不含真实正文。
2. 首步缓存预算足够容纳三笔链的不同块时，全组各消费者共享命中，首次 6 条引用的消息解码不超过 3 个不同块；另一次独立派生作用域处理追加后的 10 条引用时，不超过 4 个不同块。这里允许每轮重新建立缓存，不强制旧请求跨轮零解压。骨架另计，避免把消息计数与骨架计数混在一起。
3. 低预算、超大单块与淘汰场景正确退化，计数如实包含重读；不会以无界内存实现命中。跨数据库同 id、删除重建、正文替换、相同块被不同 agent 请求引用以及消费者尝试修改共享对象，都不得导致错误复用或相互污染。
4. 用旧全量参考结果或固定的合成预期核对前驱、delta、主链角色、title/input_preview/reply_preview、reply_shape、interrupt_count、context_event、工具关联及参数失败位、bg_job 位置与状态。缓存与未缓存结果相同；预解码对照也满足同一结果断言，不能只比较汇总计数。
5. 覆盖 first/confirmed/branch/unknown/aux、空消息、无 messages、缺骨架、缺块、ord 不连续、压缩损坏、合法压缩但非法 JSON。第一步保留坏块时的可读性、摘要和工具行为。若单独选择语义变化，另写明确预期及算法升级、重建范围。
6. 覆盖回复替换、合并换 epoch、用途重判、归属迁移、乱序请求、同毫秒无可证顺序、重复 call_id、迟到工具结果、后台作业重复通知。关系按当前组重算，缓存成功不能绕过当前引用与状态检查。
7. clean 无变化时零消息解压且不开无效任务写事务；关闭重开后运行工作单元仍无派生。dirty 重开应继续工作，失败或 CAS stale 仍 dirty，下一轮可恢复；缓存作用域结束后释放。回收后 retained 值与原 basis 保留，缺口不得伪造为新结果。

### 端到端收益与容量

实施前提交固定输入下的原实现、预解码对照与分项基线，记录事先确定的端到端改善目标和内存预算；实现后追加有界缓存的相同工作量对照。重复测量并报告分布，注明冷暖状态、缓存预算和准备成本。完整派生仍明显超标时列出剩余阶段，不以局部解码次数达标替代性能结论，也不将预解码替身当上线后的保证。

在全合成数据上构造历史高度共享、每笔少量追加的长链，覆盖约 1,000 笔请求、约 80,000 条引用的量级，另测低共享、大单块和真实形状的工具结果。记录引用与独立块规模、读取字节、解压解析次数、命中淘汰、单组/单事务耗时、事件循环延迟与 RSS。测量首次 dirty 派生、持续追加、低预算淘汰、重开 dirty 恢复和重开 clean 无变化；不能只用热进程或高度可压缩短文本证明全部容量。

首步的预期是同组共享消息的解码成本由不同块与淘汰情况决定，重复调用和引用不会各自重新解码。各轮仍可重新读取这些不同块，组关系仍可随请求数增长；只在其剩余成本显著影响指标时评审跨轮方案。性能改善必须来自受控完整派生对照，不能将 793→64 ms 的反馈微基准直接写成验收通过。

启动调查记录实际采样时间、启动日志覆盖窗口与 launchd 计数范围，尽可能区分部署、手动重启与异常退出。检查启动前后 dirty、输入修订、来源游标和尖峰时序；无对应证据时保留未知结论。不要把合成开库实验描述成完整生产重启验收。

### 条件性扩展与交付检查

只有后续评审选择持久化提取结果时，才要求 schema 升级或明确旧库拒绝路径、backfill 中断重试、缺坏结果重建、失效、回收和重启恢复测试。普通缓存修复不因此新增迁移。完整性或算法变化按实际受影响范围显式重建，禁止隐式全库扫描、伪升级与静默跳过损坏。架构事实更新到架构设计，若新增运维命令或恢复步骤则在运维手册持有。

按实际改动选择窄测试，候选为 `tests/body.test.ts`、`tests/derive-presentation.test.ts`、`tests/derive-tool-pairing.test.ts`、`tests/derive-bg-jobs.test.ts`、`tests/derive-chain.test.ts`、`tests/derive-state.test.ts`、`tests/derive-unit.test.ts`、`tests/derive-rebuild.test.ts` 与同步/切片等价性用例。代码交付执行 `bun run typecheck`，提交前执行 `bun run verify:notes`，未受后续修改影响的通过检查不重复。

文档验证分开报告范围：`verify-agent-note-format` 读取工作树活跃 Note，归档检查验证冻结记录；`verify-change-notes --staged` 只验证暂存区，`--range` 只验证指定提交。尚未暂存的本次修改不能声称已被变更配套门禁验证；提交时对最终暂存内容执行该检查，不为获得通过而擅自暂存用户改动。

真实流量验收只记聚合，不将正文、账号、令牌或用户配置写进 fixture、日志和提交。区分启动积压与持续新增窗口，记录请求速率、组大小、派生耗时差值及事件循环尾延迟。重复解压缺陷可在读取复用、正确性和事先约定的端到端改善目标达标后关闭，持久化不作为前提；整体容量结论仍须通过既有长组与速率门槛，busy 的因果证据不足时保留归因限制。

## Risks

块缓存会让多个消费者持有同一个解码对象。原地修改会污染后续请求，键只用数字 id 会在错误作用域下命中其他内容；当前正文状态与引用的校验也不能因命中而跳过。实现需保持消息只读、内容身份准确、作用域清楚。

骨架读取与完整正文读取对损坏消息的可读性判断不同。首步保留语义，后续拆分可读性需单独评审。低缓存预算、高度低共享或极大块可能使收益下降，缓存之外的引用查询、遍历与对象分配成本也不会消失。

微基准预解码会改变分配、GC 和 CPU 缓存行为，只能估计归因，不能承诺实际收益。有界块缓存的端到端对照才是交付依据。启动计数缺时序，错误归因重启可能导致无效的运维改动。

跨轮持久化若后续确有必要，会引入身份、失效、磁盘与恢复成本。它是条件性扩展；不为尚未证明的收益提前新增 schema，不把完整消息数组复制成长期提取结果。

减少解压后，祖先指纹比较、工具扫描和逐行写入可能成为主要成本。保留整组结算与原子提交意味着本次缓存不提供严格的 400 ms 单组上限；剩余容量问题继续按分项证据处理，生产切片冻结仍有效。
