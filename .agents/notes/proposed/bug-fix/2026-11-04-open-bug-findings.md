### F39 `diskTight` 仍以正文预算 9 GB 作为停止条件（11-04 新发现，系统巡查，第五轮）

### F40 keyset 游标在数据变动下没有一致性保证（11-04 新发现，系统巡查，第五轮）

- **现象**：请求列表按 `(started_ms, req_id)` 做 keyset，但 `started_ms` 会在账本晚到后被 `projection` 原地改写；合并会把 loser 行删掉；会话列表的游标是 `MAX(started_ms)`，活跃会话会因新请求跳到游标之前。另外 forward 游标不携带 `conv_key`，可以静默复用到另一个会话。
- **证据**：
  - [src/queries/requests.ts L121-138](../../../../src/queries/requests.ts#L121-L138)：older 游标校验 `parts[1] === convKey`，forward 游标只校验 `startedMs/reqId`，不绑定会话；[L183-185](../../../../src/queries/requests.ts#L183-L185) 用当前行生成下一页游标。
  - [src/queries/sessions.ts L226-L237](../../../../src/queries/sessions.ts#L226-L237)：会话游标键是 `MAX(started_ms)`；[L263-265](../../../../src/queries/sessions.ts#L263-L265) 的 `HAVING (last_ms, conv_key) < (?,?)`。
  - [src/sources/projection.ts L652](../../../../src/sources/projection.ts#L652)：账本投影完整时 `UPDATE request SET ... started_ms=?, day=?` 原地改写排序键；[src/merge.ts L156](../../../../src/merge.ts#L156) 合并时删除 loser 行。
  - 生产实测：1,626 个 `conv_key`，最大会话 **4,433** 条请求，**94 个会话 >200 条**（必然翻页）；hook + ledger 同时存在的请求 **49,699** 对，这些行的 `started_ms` 至少被账本覆盖过一次；手工复用 forward 游标（会话 A → 会话 B）返回 **200** 并给出 B 的一页，而不是 400。
- **影响**：翻页窗口内被改写/合并的行可能跨过游标 → 后续页重复或漏掉；会话在翻页期间收到新请求会移到游标前 → 本轮不再出现；forward 游标跨会话不会报错，调用方拼错会静默拿到另一会话的数据。刷新首屏即可自愈，但「一次翻到底」不保证完整。
- **严重度**：P3（瞬时漏行/重复，可自愈；不是稳定错误）。
- **建议方向**：游标绑定 `conv_key` + 一个不可变键（`req_id` 或 `created_at`），或引入快照 id；forward/older 两个方向都做同样的 key 校验；会话列表改按不可变的 `conv_key` 排序或接受并在文档中写明「翻页期间有新请求的会话会跳到首屏」。
- **未证实点**：没有历史版本可比，无法统计真正跨页的重写行数；跨会话复用 forward 游标只做了手工构造验证，未确认前端会走到该路径。

### F41 区间上界用 `Number` 而非安全整数，`from > 2^53` 会坍缩为零宽窗口（11-04 新发现，系统巡查，第五轮）

- **现象**：`parseIndex` 只做 `/^\d+$/` 后转 `Number`，`bodyRangeError` 用 `Number.isInteger`（1e20 也返回 true）且只检查 `to - from > PAGE_MAX`（40）；`to` 默认 `from + 40`，当 `from` 是 1e20 时 `from + 40 === from`，差值 0，校验通过，接口返回 200 且 `from=to`。
- **证据**：

  - 实测 `/api/requests/96204/body?from=9007199254740993` → **200**，响应里的 `from` 已被舍入为 **9007199254740992**、`to=9007199254741032`；`from=99999999999999999999` → **200**，`from=to=100000000000000000000`，`messages` 空，`coverage` 报完整。
  - 同一函数对批读 item 的 `id` 要求 `Number.isSafeInteger`，但对 `from/to` 不要求（[src/http.ts L205-230](../../../../src/http.ts#L205-L230)），同一份参数规则内部不自洽。

- **建议方向**：`parseIndex` 与 `bodyRangeError` 一律要求 `Number.isSafeInteger(from)` 和 `Number.isSafeInteger(to)`；`from > total` 按契约返回空页，但绝不允许 `from+page` 被浮点吞掉。
- **未证实点**：没有真实客户端会传这种值；未测大整数在批读端点的完整行为。

### F42 SIGTERM 停止没有上限也没有 `catch`，进程可能不退出；正常退出也不截断 WAL（11-04 新发现，系统巡查，第六轮）

- **现象**：`stop()` 先 `await deriveLanded`，而这个 Promise 没有超时；`onSignal` 只挂了 `.then(() => process.exit(0))`，没有 `.catch`。只要派生轮次一直不落盘（或 `server.stop` / `store.close` 抛错），进程就会停在 `stopped=true`、定时器已清空、HTTP 仍在监听的状态，永远不会自己退出。代码注释里「超出 service stop 的 30 秒轮询就如实报 stop_failed，进程仍会自己退出」只在 Promise 正常 resolve 时成立。
- **证据**：
  - [src/main.ts L356-378](../../../../src/main.ts#L356-L378)：L366 `await deriveLanded;` 无超时；L363-365 的注释承认「等待没有上限」；L377 `void stop().then(() => process.exit(0));` 无 `catch`，L379-380 绑定 SIGTERM/SIGINT。
  - [src/store.ts L407-412](../../../../src/store.ts#L407-L412)：`close()` 只 `read.close()` + `db.close()`，没有 `wal_checkpoint(TRUNCATE)`。
  - 实测（临时数据目录，端口 8391）：空闲实例 SIGTERM 后 **127 ms** 退出；退出后 `trace.db-wal` 仍为 **4,202,432 B**（正好在 `wal_autocheckpoint=1000` 页附近）。重启后 WAL 被回放，`PRAGMA integrity_check` = **ok**，300 条 hook 行 `hook_id` 全不重复。
- **影响**：SIGTERM 可能变成 30 秒后由 launchd SIGKILL；每次正常停止都在数据目录留一份未截断 WAL，下次启动要承担回放成本。数据本身可恢复，未观察到提交丢失。
- **严重度**：P3（停止可靠性；崩溃后的数据完整性已实测正常）。
- **建议方向**：给 `await deriveLanded` 包一个上限（与 service stop 的 30 s 对齐），`stop().catch(...)` 保证异常路径也 `process.exit(1)`；`close()` 前做一次 `wal_checkpoint(TRUNCATE)`，失败不影响退出。
- **未证实点**：没有构造出「派生永不落盘」的真实卡死，只核对了「无超时、无 catch」的代码路径；WAL 未截断是设计如此还是 Bun 的关闭行为，未进一步分辨。
- **状态**：已修复（2026-11-05）。停止等待加上限、异常路径保证退出，`store.close()` 前执行 `wal_checkpoint(TRUNCATE)`；见[有界保留与停止](2026-11-05-bounded-retention-and-shutdown.md)。

### F43 只读数据目录启动即失败，没有只读降级（11-04 新发现，系统巡查，第六轮）

- **现象**：`openStore` 在打开库后固定执行 `BEGIN IMMEDIATE; ROLLBACK`（落 `-wal`/`-shm`）。数据目录只读时这一步抛 `SQLITE_READONLY`，`startCollector` 直接失败，进程 exit 1，HTTP 从未监听；不会退化成「只读服务」。
- **证据**：
  - [src/store.ts L338-343](../../../../src/store.ts#L338-L343)：`PRAGMA journal_mode=WAL` 之后的空写事务；[src/main.ts L102](../../../../src/main.ts#L102) 与 [L389](../../../../src/main.ts#L389) 没有降级分支。

- **建议方向**：先明确「只读挂载」是否属于支持场景。若属于，启动失败要给出可解析的 `storage_readonly` 诊断并以非零退出（不进入 KeepAlive 循环）；若不属于，补一条运维说明即可。
- **未证实点**：未在真实只读挂载（`mount -u -o ro`）上复现，只在文件权限层面等价构造。

### F44 真实 SQLITE_FULL 落到 `503 writer_failed`，507 只覆盖准入闸门的 `disk_full`（11-04 新发现，系统巡查，第六轮）

- **现象**：hook 与 OTLP 的 catch 只把字符串恰好等于 `disk_full` 的错误映射成 `507 insufficient_storage`；真实写失败时 SQLite 返回的是 `code: "SQLITE_FULL"`、`message: "database or disk is full"`，于是走普通分支：`503` + `{"error":"writer_failed","code":"SQLITE_FULL"}`。
- **证据**：
  - [src/http.ts L351-359](../../../../src/http.ts#L351-L359)（hook）与 [L466-474](../../../../src/http.ts#L466-L474)（OTLP）：`if (code === 'disk_full')` → 507，否则 503。
  - 实测（120 MB 镜像内直接写库）：`{"name":"SQLiteError","message":"database or disk is full","code":"SQLITE_FULL","errno":13}`，与字符串 `disk_full` 不相等。
  - 准入闸门通常先挡住：`MIN_WRITE_MARGIN = 256 MiB`（[src/retention.ts L116](../../../../src/retention.ts#L116)）与 `usage.free_bytes < margin → paused`（[L232-233](../../../../src/retention.ts#L232-L233)）。在 120 MB 卷上（剩余 < 256 MiB）实测 **30/30** 条 hook 都是 `507 {"error":"insufficient_storage"}`，同一实例 `/api/stats` 仍 **200**——没有静默丢，读侧不受影响。
- **影响**：只有在「准入检查之后、提交之前」自由空间被外部进程/WAL/temp 吃掉的窄窗口里才会走到 SQLITE_FULL；此时客户端拿到的是可重试的 503，而不是明确的容量错误，重试会把压力继续打回来。语义上不致命，但契约不稳定。
- **严重度**：P3（窄窗口；不是静默丢，也不影响已提交数据）。
- **建议方向**：把 `SQLITE_FULL` / `SQLITE_READONLY` 与 `disk_full` 一起映射到 507（或统一成 `insufficient_storage`），`code` 只回固定枚举；与 F20/F21 同批。
- **未证实点**：生产上未实际触发（盘余 324 GiB，准入线也远未到）；没有在「准入后瞬时被外部写满」的条件下复现，只证明了错误码不匹配。

## Risks

- **F07 的 A 只压单轮成本**：约 30%，不解决 35–39% 占空；若把它宣传成「长派生修好」，会掩盖 D（真增量）仍缺席。每轮多占约 50 MB 原始 blob，共享解码对象必须只读，否则污染后续行。
- **F07 验收容易用错数**：生产单轮 18.6 s 与副本 6,200/9,057 ms 不可直接对比；不先跑一次取热值就会把冷值当回归。
- **F06 会放大派生队列**：队列基数与首轮回填耗时未估，贸然进派生可能长时间占主线程；必须在写窗口做。
- **F05 的 68 条可能只是新流量**：若据此宣布 `turn_ref` 已修，存量仍空的部分会在身份关联验收里制造假阴性。
- **F03/F04 的证据缺口**：没有新证据就不应改代码，也不应为了让清单变短而宣布关闭。
- **F08 只读预检本身有边界**：它只能判断 schema 版本与迁移可行性，不能替代备份；预检通过不等于迁移一定成功。
- **F09 是写操作**：重判脚本必须保留原 `body_state` 与 `miss_reason` 以便回滚；先在副本/只读计数确认 1,386 这个范围，误判会把真正缺正文的行也改成 `partial`，反而掩盖问题。
- **F10 不插桩就改 SQL 可能白改**：副本同函数 162 / 109 ms，SQL 只占 0.11–0.16 s，差距在 HTTP/IO 层；先分段再定修法。
- **F11 首次「循环到空」会清掉大量超期行**：需评估 WAL 增长与 I/O 峰值，不要在高流量时段跑。
- **F16 未确认客户端重试前**：不能把 429 当作「无数据损失」；这条不确认，F16 只能算观察项。
- **F18 的判级依赖威胁模型**：按标题当 P0 直接收紧鉴权，可能破坏同源浏览器导航（前端读 `/api/` 不带令牌）；按 P1 放着不动，则本机任意进程仍可无令牌读统计。两种做法都要先写清威胁模型，不能默默选一边。
- **F19 删旧日志不可逆**：旧日志是排查 `migrate` / `openStore` 栈的唯一线索；删除前先确认不需要回溯。只改权限不删也能满足「0600」这一条。
- **F20/F21 都是契约变更**：把 500 改成 400、把 `code` 换成枚举值，可能影响现有客户端按字段判断的逻辑；先确认没有外部消费者依赖当前形状。
- **F22 「无上限」本身是设计选择**：冒然限制单块大小会让原本可接收的大请求开始失败；先测再定，别把观察项当成必修。
- **F23 没有可复现的失败组**：只能按代码推断；加了 `attempts` 后要观察一段时间才能证明退避有效，不要一次改到「永久失败即丢弃」。
- **F24 的归因未逐行回溯**：29,347 行按 `via='through'` + `redact_version=NULL` 归到 merge 路径，可能还有别的写入路径漏 `body_bytes`；修完要用全表计数验收。
- **F25 收紧弱规则的代价是拆开**：要求模型相等会拒掉模型别名（同一模型不同写法）的合并，把合法调用拆成两条；要求 usage 交集则在「先落调用、后补 usage」的时序下同样拆。加闸门前要先用正反例确认两类样本。
- **F25 的 60 s 窗口本身是经验值**：缩短会拆开正常重试，放宽会放大误并；窗口与「唯一候选」两个条件的相互作用没有独立的现场证据，回归只能靠 5 条已命中样本。
- **F26 改优先级会动存量 `conv_key`**：把弱键提升为 session 键需要回填历史，回填脚本写错会直接改变派生分组；当前 0 实例，说明没有「必须先修」的紧迫性，优先只加不变量测试。
- **F27 修法本身可能引入重复**：把冲突组改成合并，需要完整走 `mergeRequestTx`（含 block 搬运、alias 写入），改错会制造新的 alias 链；先跑一次全库重复扫描作基线，改完复扫。
- **F28 补 canonical 规则依赖上游形态**：如果不同上游确实把 32 hex 当独立会话（而不是同一会话的另一种写法），强行归一会把两个会话合并；未确认前只能锁现状，不能直接改归一函数。
- **F29 改 `moreTargets` 会牵动整个 tool 步骤渲染**：LRU 淘汰或按可见行清理会改变 `+N` 的生命周期，可能让刚渲染的 chip 立刻失效；只在最长会话复现后再改，不要顺手重写渲染层。
- **F30 加 smoke 会改变 `restore` 的语义**：恢复后自动 `openStore` 会触发迁移，也就意味着 `restore` 从「复制」变成「复制 + 首开」，失败点前移；要确认运维流程能接受这一点（恢复失败在 restore 阶段暴露，而不是首次启动）。
- **F30 的旧 schema fixture 成本高**：要真正覆盖 6/8/10/11，需要保留历史 schema 建表脚本或快照；只改版本号的做法看似省事，正是本轮 F30 的成因，不能再用它凑覆盖。
- **F31 改字段名会影响现有消费者**：`ok` 改成 `usable_for_restore` 或让 DB-only 返回 `ok:false`，可能破坏只读 `ok` 的脚本；本轮没有外部消费样本，改之前先确认调用方。
- **F32 改成本地日会改变已有脚本的窗口**：如果外部脚本一直按 UTC 日期调用，改成按本地日会让同一条命令多覆盖/少覆盖 8 小时；要同时给出迁移说明，或在输出里回显解析后的 epoch 区间。
- **F33 只加 TTL 仍会读到混合快照**：TTL 解决「无限期旧值」，不解决 10 条查询跨快照；两者要一起做，否则只是把不一致窗口缩短。
- **F34 把 `pending_derivations` 也算失败会误伤停机场景**：停机前队列有积压是正常的，门禁若把它算红会让每次停服都报错；必须把「完整性/悬空/重复」与「队列积压」分开。
- **F35 加「不得晚于今天」会挡掉合法的未来日预清理**：若确实需要提前清理未来日期（例如导入数据已知），要留显式 `--allow-future`，不能一刀切。
- **F36 加超时可能把慢但正常的组判死**：大组派生本身可能超过 30 s；超时应按「连续无进展轮次」而不是总墙钟，否则会误报。
- **F37 先计数再改采样**：直接停写 `raw_otlp_span` 会把「静默丢」换成「静默少收」，并失去事后判断「规则漏识别」的唯一证据；先有按服务 × span 名的量级，再谈采样率。
- **F38 的 TTL 与「长期归档」冲突**：`cost_observation` 是历史成本回算的主要来源，加 TTL 会让 10-24 的回填数据到期消失；要么明确声明长期归档并计入预算，要么只对「可重算的副本表」设 TTL。
- **F39 调 `ATC_DISK_LIMIT` 会整体放宽现有保护**：把 16 GB 调到真实盘量后，`diskTight` 与 `paused` 的绝对水位一起后移；先确认这条线原本防的是「盘被其他进程占满」还是「tracery 自身失控」，再决定是否对齐。
- **F40 上快照 id 的代价**：快照要额外存储或过期清理，翻页期间的删除仍可能让页不满；先用「绑定 `conv_key` + 不可变键」这个最小修，不要一次上快照。
- **F41 收紧整数校验会拒绝历史客户端**：用 float/字符串传超大 `from` 的调用方会从 200 变 400；与 F20 同批时仍要各一笔提交，避免回归定位变难。
- **F42 给停止加上限会打断「最后一组」**：真卡住时应超时退出，但正常的大组派生可能超过 30 s；上限只包 `deriveLanded` 的等待，不要把 `deriveUnit.run` 的计算预算一起砍掉。
- **F43 把只读启动改成非零退出可能掩盖问题**：如果 KeepAlive 本意是「等磁盘恢复」，明确失败会停止重试；先定运维语义（快速失败 vs 持续重试），再改诊断。
- **F44 把 `SQLITE_READONLY` 也映射 507 会改变重试语义**：只读挂载下客户端会停止重试；`SQLITE_FULL` 与 `SQLITE_READONLY` 是否同一码，要先按「可恢复/不可恢复」分类。
