# Agent Note: 准入量测的百毫秒同步块

Status: proposed

## Problem

[长窗口性能验收](../../../../docs/acceptance.md#认领边界长窗口性能验收真实流量2026-11-03)的重启后窗口（753 秒）里，事件循环 p50 1.0 ms、p95 3.1 ms、p99 271.8 ms、max 620.7 ms。派生计算已经在 [Worker](../../implemented/architecture/2026-11-02-derive-compute-worker.md) 上跑，落库事务单次 max 158 ms，事件循环的尾延迟还有别的来源。

`measureStorage` 在本机 3.85 GB 库上直接调用 5 次，耗时 111–190 ms；其中 `measureBodyBytes` 单独约 107 ms。它由三条全表求和组成：

| 查询 | 行数 | CLI 实测 |
| --- | ---: | ---: |
| `SUM(length(z))`，`block` | 87,900 | 89 ms |
| `SUM(length(skeleton_z))`，`request` | 51,598 | 74 ms |
| `SUM(length(request_z)+length(response_z))`，`raw_hook` | 未单测 | 计入总量 |

[准入闸门](../../../../src/retention.ts)的 TTL 是 2 秒，调用点比这个周期密：ledger tick 每 5 秒在空批判断之前调用 `gate.check`；每个 hook 与 OTLP POST 走 `gate.check(0)`；回收任务每 30 秒直接调用 `measureStorage`。5 秒一次、每次阻塞 110–190 ms，正好是 50 ms 采样里每 100 个样本卡 1 个，位置与 p99 的定义重合；hook 批次还会加次数。

当前指标不记录 `measureStorage` 自身耗时，这条归因只有代价读数与采样位置吻合，没有逐事件证据。正文占用 1.44 GB，预算 10 GB，离阈值很远，闸门并未因接近上限才频繁量测。

`GET /api/ingest-metrics` 也在请求线程上调用同一个函数，实测单次 1.83 秒。它是监控接口，次数少，但同样占住事件循环。

## Proposal

先补归因，再把量测从同步阻塞改成后台分块，闸门改用最近一次完成的值。

第一步在 `createCapacityMetrics` 里加一组 `storage.measure` 计数：次数、合计耗时、最大耗时，随 `/api/ingest-metrics` 输出。这一步只增加观测，不改行为，用于确认 `measureStorage` 在真实窗口里的次数与分布；后续窗口可以拿它做前后对照。

第二步把 `measureBodyBytes` 拆成按 rowid 区间的分块求和，块间让出事件循环，在后台完成一轮后原子替换缓存值。闸门的 `check()` 仍然同步，读最近完成的 `body_bytes`；磁盘空间走 `walk`、`statfs` 与页计数，这部分个位数毫秒，保持同步。`enforceBodyBudget` 与容量脚本继续用精确的同步版本，避免改变容量验收口径。

分块刷新不持有跨 `await` 的读事务：每块各自取快照，总和不保证对应同一时刻。并发摄入或回收会让相邻块的快照略有差异，误差等于刷新期间的变动量，远小于预算余量；实现要在注释里写明这一点，不把它包装成精确快照。

缓存值的初始值在闸门创建时由一次 `measureBodyBytes` 给出，仍有一次同步开销，发生在开始服务之前。`invalidate()` 标记正文值过期并启动下一轮刷新，不阻塞调用方。

## Alternatives considered

**只把正文求和的 TTL 拉长到 60 秒。** 改动最小：闸门每 60 秒才做一次全量求和，阻塞样本从 1% 降到约 0.08%，p99 大概率回到 100 ms 以下。代价是正文预算的判断最多滞后一分钟；按当前摄入速率误差只有 MB 级，接近上限时的超写风险由批上界与回收兜底。若只追求 p99 达标、接受 max 仍为百毫秒级，这条路先走。

**维护三张表的字节计数器。** 精确且 O(1)，但写入点分散：`block` 插入在 `src/body.ts`，删除在回收与维护清理；`request.skeleton_z` 有写入、搬移与置空；`raw_hook` 另有插入与 TTL 删除。漏一条路径就会漂移，需要启动重算与对账测试。语义正确性成本高于分块刷新，留到分块仍不够时再评审。

**给长度表达式建索引。** `SUM(length(z))` 可以走索引只读扫描，可能快几倍；但仍是全量扫描，且每次插入多维护一个索引。收益不确定，schema 变更成本确定，不选。

**把量测放进现有派生 Worker。** Worker 是单飞的计算通道，塞进量测会串行化派生；另起第二个 Worker 又要处理启停、崩溃与库文件替换。闸门最终仍读缓存值，等于在分块方案外多一层生命周期。

**降低事件循环目标或不再按 2 秒量测。** 目标来自容量门槛；放宽目标只会掩盖阻塞，不能回答页面卡顿。

## Acceptance criteria

1. 合成库覆盖三种求和来源：约 88,000 个 block 行、约 52,000 个 request 骨架、若干 raw_hook 残留。分块刷新的结果与一次同步 `measureBodyBytes` 在静默时完全相等；并发摄入与回收时误差不超过刷新窗口内的变动字节量，并在测试里给出上界。
2. 廉价路径在 3.8 GB 级合成库上单次不超过 5 ms；单块耗时不超过 20 ms，事件循环在刷新期间的最大滞后不超过 50 ms。用插桩读数，不用估算。
3. 准入判定表不变：`paused`/`metadata_only`/`normal` 在磁盘预算、磁盘余量、正文预算三个边界上的结果与改动前逐项一致；`batchUpperBytes` 仍计入判定。
4. `invalidate()` 之后的下一次 `check()` 不会读到过期到超出刷新窗口的值；回收完成后正文值最终收敛到新的总量。启动、关闭、维护替换库文件后重新播种。
5. 生产复测：部署后同负载窗口记录 `storage.measure` 的次数与最大耗时，以及事件循环 p99。若 p99 仍高于 100 ms，按其它来源继续归因，不用本次改动宣布目标达成。
6. 测试只用合成库与临时目录，不复制真实正文、会话键或标题。

## Risks

分块求和跨多个读快照，结果不是某一时刻的精确值。它只服务准入判断，误差在预算余量内；但报告与容量实验必须继续使用同步精确版，不能把缓存值当成测量结论。

刷新仍有 100 ms 左右的 CPU，只是被切成小块。整机 CPU 占比不下降，事件循环的单次滞后下降。若分块粒度选得太小，调度开销会上升；太大则单块仍可能越过 50 ms，验收要用实测块时长定粒度。

缓存值可能因刷新被抢占而变旧。闸门用批上界预留余量，回收另有独立触发；但若有人把 `measureStorage` 的精确版本也换成分块版，容量验收就会失真，调用边界要写清楚。

正文预算与磁盘预算共用同一份 `StorageUsage`。拆分后两者刷新节奏不同，报告里要标出正文值的采集时间，避免把旧值当成当前磁盘占用。
