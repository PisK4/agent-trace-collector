# Agent Note: 会话列表按页聚合与首屏剩余延迟

Status: proposed

## Problem

后台采集期间打开页面，首个会话行仍需数秒才能显示。[第一轮治理](../../implemented/bug-fix/2026-11-01-collection-interactive-latency.md)已经交付反向索引与列表提前显示，但会话列表查询仍为全部历史会话计算状态，再做排序分页。请求只取 20 个会话，也会访问页外请求的状态字段，当前页之外的历史量继续增加读取成本。

2026-11-01 的独立复核确认剩余问题，并在同一真实只读快照中验证了较小的候选改法。观测、候选耗时和覆盖缺口统一记录在[本轮验收记录](../../../../docs/acceptance.md#会话列表第二轮复核与候选实验2026-11-01)。候选只验证了顺序与计数，尚未验证完整返回值，也没有交付修复。

### 与已有记录的关系

Supersession check：本提案细化[第一轮治理的 Deferred](../../implemented/bug-fix/2026-11-01-collection-interactive-latency.md#deferred)中会话候选选择与聚合范围这一项。它不取代已经交付的索引、schema v8 或首屏提交拆分；第一轮记录保持活跃，双方互链。后台任务预算、pending 批次与执行线程仍由第一轮记录持有。

[派生正文重复解压修复](2026-10-26-derive-body-decompression-amplification.md)继续拥有正文复用、读取完整性与完整派生验收。当前 64 MiB 块缓存已经交付，本轮不再以增加同一缓存作为新方案，也不解除生产切片的冻结条件。

## Proposal

本会话只交付方向、证据和验收标准，具体代码由实施 Agent 在独立 worktree 完成。首步采用两阶段同快照查询，保持现有 API 与语义，不增加表、索引、缓存、schema 或算法版本。

### 先选页面会话，再计算页面内容

第一阶段只读取会话键与请求时间，沿现有 `i_req_session_time` 覆盖索引计算每个会话真实的最近请求时间，再排序并取 `limit + 1` 个候选。游标条件应用在分组之后；第一页省略 `HAVING` 与对应绑定参数。

```sql
SELECT conv_key, MAX(started_ms) AS last_ms
FROM request
WHERE conv_key IS NOT NULL
GROUP BY conv_key
HAVING (MAX(started_ms), conv_key) < (?, ?)
ORDER BY last_ms DESC, conv_key DESC
LIMIT ?;
```

第二阶段以候选中的前 `limit` 个会话键绑定 `WHERE conv_key IN (...)`，复用现有标题、计数、agents 与 flags 聚合。多取的一条仅用来判断 `next_cursor`，不参与宽字段聚合。空候选直接返回空页。第二阶段仍读取页面内会话的全部请求，保留旧请求贡献的计数、失败与其他状态。

两个阶段放在同一个 `store.read.transaction()` 中，避免采集在阶段之间提交后，页面排序时间与内容来自不同快照。事务仅覆盖列表需要的同步读取，不读取正文，不跨 `await` 持有。沿用现有游标编码、参数校验和返回结构。

这仍然包含全历史时间索引扫描与会话排序。改法减少的是页外会话的宽字段读取、状态聚合与标题求值，不承诺读取成本完全只与页大小有关。页面若包含很长的活跃会话，其详情聚合仍可能较重。

### 保留当前解释规则

标题继续按现有优先级与发布代选源：排除用途的模型标题优先，其后依次取参与链的主链用户标题、其他用户标题和可用回退标题。`purpose_pending` 与组是否 current 的条件保持原样，dirty 组不能借提速显示旧标题。复用 [sessions 查询](../../../../src/queries/sessions.ts)已有 SQL 片段，不重新实现一套标题规则。

flags 仍按整个会话聚合，并保持失败、待确认、缺正文、旁路、探针的既有顺序。agents 继续表示客户端标签。跨多次 HTTP 翻页仍采用当前实时 keyset 语义，不为本次优化增加跨请求快照令牌；单次两阶段读取必须一致。

### 首屏响应另行验收

列表 SQL 优化可以独立交付，但整体卡顿必须按浏览器和 HTTP 实测判断。HTML 首字节尚未返回时，前端无从绘制；降低列表 SQL 成本也不能限制已经占用主线程的长组派生。

测量分别记录 HTML 首字节、列表请求发出与返回、首个 `.sess` 行插入以及随后绘制机会。HTTP 总耗时与查询函数计时分别报告，不能将不同时间窗口的数字相减后写成精确排队时间。列表达标但首屏仍有秒级等待时，保持整体交互问题未关闭，按[第一轮 Deferred](../../implemented/bug-fix/2026-11-01-collection-interactive-latency.md#deferred)继续定位同步任务；用同窗口轻量计时判断是否需要线程隔离。

`metadataSnapshot` 位于指标快照路径，两秒 TTL 的准入检查调用的是 `measureStorage`，其中包含 `measureBodyBytes`。不得以元数据统计耗时为由认定它每两秒执行，也不得顺带删除准入容量校验。后续统计优化先确认实际调用频率与成本归属。

### 实施影响范围

运行代码集中在 [sessions 查询](../../../../src/queries/sessions.ts)。[HTTP 调用方](../../../../src/http.ts)和前端保持接口不变。实施测试覆盖查询范围与分页边界，并复用[已有查询回归](../../../../tests/queries.test.ts)中的标题、dirty、flags 和发布代断言；[HTTP 回归](../../../../tests/http.test.ts)核对游标和非法参数。

实现完成后才将本提案移至 implemented、更新[架构设计](../../../../docs/architecture-design.md)中的查询事实，并在[验收记录](../../../../docs/acceptance.md)追加结果。没有部署与浏览器复测时，保持生产修复未验收。服务操作遵守[运维手册](../../../../docs/operations.md#起停与状态)，不为测量另起生产采集器。

## Alternatives considered

**先缓存整个会话列表或增加物化汇总表。** 能降低重复读取，但要覆盖新增、迟到、合并、删除、标题结算、dirty 与发布代切换等失效路径，还可能带来 schema 与 backfill 成本。两阶段候选已经显示足够大的局部收益，首步不承担这套维护成本；只有覆盖索引扫描或当前页长会话仍不能满足目标时再评估。

**先按请求时间截断，再对剩下的请求分组。** 会把活跃会话的旧请求当作旧页候选，同一会话可能重复出现，计数与 flags 也会缺失。游标必须比较整个会话真实的 `MAX(started_ms)`。

**先取键，再逐个会话查询，或在两个独立快照里查询。** 前者增加往返次数与语句管理，后者允许并发采集混合排序依据与页面内容。选择一条页面聚合语句和一个只读事务即可覆盖当前需求。

**只提前绘制或增加 fetch 并发。** 第一轮已经拆掉列表与默认窗口的串行显示等待。服务端列表成本和 HTML 首字节等待仍有独立证据，继续加并发不能保证主线程及时处理请求。

**本轮立即迁移所有后台工作到 Worker。** 可以建立执行隔离，但 writer 归属、协议、队列上限、失败恢复和停机顺序都需单独设计。首步先交付已验证的小改法；后台采集时尾延迟仍不达标，就按独立方案评审线程边界，不继续靠增加缓存掩盖同步阻塞。

## Acceptance criteria

### 查询正确性与范围

1. 首屏和游标页都只为前 `limit` 个会话读取宽字段并计算标题、agents 与 flags；额外候选不做这些计算。合成回归对页外字段访问设失败断言，旧实现应能失败，新实现应通过。第一阶段 `EXPLAIN QUERY PLAN` 应使用现有 `i_req_session_time` 覆盖索引。
2. 覆盖空库、NULL 会话、同毫秒按键倒序、满页与末页、活跃长会话跨越游标、迟到旧请求、新会话插入与删除。页面内会话全部历史请求参与计数和状态聚合。保留当前 limit 与 cursor 错误处理。
3. 在候选读取后、详情聚合前从另一个连接提交请求，当前页仍来自同一旧快照，下一次调用可见新结果。此项必须动态验证，不能仅凭代码含有事务调用判断通过。
4. 保留模型标题、主链用户标题及回退顺序，覆盖 dirty、用途待判定和发布代数据与同步旧列不一致。flags 顺序与 agents 集合保持现有语义。在同一个只读快照内比较旧、新实现的第一页及后续页，核对完整 `Page<SessionRow>`，不能只比会话键或计数。

### 性能与首屏

5. 使用合成的约四万条和四十万条历史请求，记录会话数、每会话分布、宽字段大小与当前页请求数。交替测量旧、新查询的首屏和游标页，报告首遍与重复样本，不把后测缓存更热当作修复收益。性能脚本做结果等价断言，CI 不设绝对毫秒阈值。
6. 当前规模、每页 20 个会话的直接查询，以同机、生产同版 Bun 的重复样本 p95 不超过 100 ms 为本轮目标，首遍单列。生产只读测量只保存去敏汇总，不把标题、会话键、正文、账号、令牌或用户配置写入仓库与日志。目标未达时先说明成本在候选扫描还是当前页聚合，再决定是否扩大方案。
7. 后台持续采集至少十分钟，记录列表 HTTP p95/p99 与最大值，拟议目标为 p95 不超过 1 s、p99 不超过 2 s、无超过 5 s 的请求；同时记录实际采集速率、队列年龄、busy、RSS 和 WAL，避免以降低吞吐获得表面改善。合成流量与真实流量分别报告。高成本指标快照只在必要时读取，避免测量反过来干扰主线程。
8. 浏览器验证列表返回后能独立显示、默认请求窗口延迟不阻挡左栏，并记录首行时间和 HTML 首字节等待。列表 SQL 达标但首屏或 HTTP 尾延迟不达标时，只关闭列表查询这一项，保持整体交互问题开放，给出后续同步任务定位结果。不能把局部 21–23 ms 写成上线后首屏耗时。

## Risks

覆盖索引仍随历史增长扫描，排序仍需临时结构。页面内超长会话可能占据主要成本；没有测量其分布就不能据候选实验承诺十倍数据也有相同毫秒数。

只读事务保证同次调用一致，但会在读取期间保留 WAL 快照。实现不得把网络、正文读取或异步等待加入事务。若仍存在慢查询，需同时观察 WAL 和 reader 持有时间。

当前候选实验使用 Bun 1.4.4，生产服务运行 Bun 1.4.0；测量顺序为先旧后新，尚未交替，也未比较完整返回值。它支持优先选择两阶段方向，不足以作为实现完成或生产整体收益的证据。

本提案主动限制首步范围，不调整用途规则、发布语义、准入安全、派生算法或线程归属。后台同步长任务依然可能阻塞 HTML 与 API，最终首屏结果必须由部署后验收回答。
