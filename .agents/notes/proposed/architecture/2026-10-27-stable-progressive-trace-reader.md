# Agent Note: 稳定的渐进式轨迹阅读

Status: proposed

## Problem

用户在中栏连续阅读 trace 时，反复看到组级提示 `已更新 · 自动重读换新`，中栏随之重新渲染，难以辨认刚才选中或正在阅读的步骤。用户补充，正在查看的是早已结束的历史对话，没有继续产生消息。阅读稳定性因此不能只按活跃会话的实时更新问题处理。

本提案记录 2026-10-27 的需求讨论与只读调查，交给下一个 Agent 独立 review。用户明确暂不拍板；本文的推荐方向、进入顺序、版本处理和模块归属均未获实施批准。本文不授权修改生产行为、重启采集器、回填真实库或执行部署。

### 讨论背景与需求收敛

最初讨论围绕自动重读功能展开。该功能为解决版本冲突后整组步骤缩成占位、需要逐笔点击重读的问题而引入；自动恢复后逐组提示换新，以保留版本变化的可见性。原始动机与被否决方案见[作废读取的自动重读与快照状态](../../implemented/feature/2026-10-25-reader-invalidation-auto-reread.md)。

Agent 起初把跳变主要解释为活跃会话的组修订变化，随后建议阅读期间固定中栏、主动刷新再应用更新。用户指出历史会话同样跳变，并明确认为暂停刷新只是治标；系统不能把后续加载与刷新责任交给读者。该手动刷新方向不符合本次需求，不作为推荐方案。

用户提出两种可讨论的读取方式：尽快读取全部所需数据并一次显示；或首屏立即显示，后台继续分批自动读取，但不能扰动已经开始阅读的区域。用户还提出，可以考虑默认从会话顶部最初几条信息进入，替代当前从最近窗口底部进入的方式。顶部进入是候选设计，尚未确定为产品默认值。

本次需要同时满足的目标是：

- 首屏尽快提供真实、可阅读的步骤，不等待长会话全部正文下载完成。
- 正常阅读所需的后续数据由系统自动读取和呈现，不依赖点击刷新、加载或续读。自动加载是明确需求；范围是当前窗口、接近视口的区域，还是打开后遍历整场会话，尚未确认，不能把整场后台排空当作既定目标。
- 后续批次到达、点击步骤、读取右栏和恢复版本冲突，不能让中栏正在阅读的位置跳变。
- 对内容未变化的历史会话，加载先后顺序不能决定最终显示哪些步骤，也不能让已有步骤反复消失、重现或改序。
- 保留版本一致性、精确来源定位、失败与缺失的如实表达，不能把新旧证据混用来换取视觉稳定。

用户要求从架构层面讨论；这不等于预先接受新增步骤表、长期保存全部阅读快照或重写派生流水线。候选方案必须证明比局部修复更有必要。

### 已确认的代码机制

以下是对当前实现的静态调查结果，定位使用符号与相对文件链接。后续 review 需核对工作区版本，不能把这些观察直接当作用户现场的网络复现。

| 位置 | 已确认机制 | 对阅读的影响 |
| --- | --- | --- |
| [app.js](../../../../web/app.js) 的 `loadWindowReads` | 按四笔一批读取详情、元信息和最多两片可信增量，每批完成调用 `renderMain` 与 `renderRail` | 初始加载期间，多条步骤逐批替换占位；无需新增对话也会重绘 |
| [app.js](../../../../web/app.js) 的 `renderMain`、`restoreScroll`、`restoreFolds` 与 `structureSelected` | 整体替换 `main.innerHTML`，恢复原 `scrollTop`；折叠开合和结构内消息选择已有稳定键恢复机制 | 部分阅读状态已有保护，但整栏替换仍破坏 DOM 身份与浏览器文本选择；上方行高变化后，相同像素位置不再对应相同步骤 |
| [selection.js](../../../../web/selection.js) 的 `select-step` 与 [app.js](../../../../web/app.js) 的 `ensureRead`、`ensurePair` | 点选先触发中栏重绘；读取完成后再重绘；缓存命中也走完成后的重绘路径 | 点击没有变化的历史步骤仍可能多次重建中栏 |

| [app.js](../../../../web/app.js) 的 `traceHtml` 与 click handler、[app.css](../../../../web/app.css) 的 `.group-flag` | 更新提示在组内占高度；点击带标记组的步骤时，先清标并整栏重绘，再经选择分支整栏重绘，之后还可能执行读取完成的重绘 | 提示出现与消失改变其下步骤的位置，一次点击也可能多次替换整栏 |
| [rail-facts.js](../../../../web/rail-facts.js) 的 `systemContextOf` | System 是否省略依赖浏览器是否已缓存已确认前驱的元信息 | 同一数据的读取先后可以改变步骤数量 |
| [app.js](../../../../web/app.js) 的 `traceHtml.callOf` 与 [trace-view.js](../../../../web/trace-view.js) 的 `toolRowParts` | 工具结果参数摘要依赖调用方是否进入阅读缓存 | 调用方稍后到齐可能改变已显示摘要 |
| [app.js](../../../../web/app.js) 的 `ensureSelectedVisible`、`userScrolled` | 首载批次期间可能多次把选中组居中；只有中栏 wheel、touchmove 置主动滚动标记，键盘、滚动条拖动与焦点滚动不置位 | 系统可能在读者已经移动阅读位置后继续居中；单纯点击阅读也不会停止首载定位 |
| [app.js](../../../../web/app.js) 的 `anchorSnapshot`、`compensateAnchor`、`loadEarlier` | 已有按步骤键的补偿，但只接在加载更早路径；快照取文档第一条步骤而非首条可见步骤，`userScrolled` 为真时不补偿 | 不能直接将现有函数接到每批刷新；需修正锚点选择和用户交互期间的过期判断 |
| [reader-store.js](../../../../web/reader-store.js) 的 `loadTurns`、`loadSummary` 与 [app.js](../../../../web/app.js) 的 store 回调 | 轮次与汇总独立到达后也触发两栏重绘 | 即使轨迹步骤稳定，迟到的会话头部内容仍需处理高度与位置变化 |

[步骤投影](../../../../web/trace-view.js) 的 `projectSteps` 消费详情、已读消息和正文元信息。当前中栏结构直接取决于详情缓存已经装载到哪一步。请求列表的一笔请求可以生成多条步骤，单行请求占位无法预先表达最终高度。

[请求分页](../../../../src/queries/requests.ts) 的 `listRequests` 已支持 `forward` 从最早请求向后读取，返回顺序保持升序；[前端 store](../../../../web/reader-store.js) 的 `selectSession` 固定使用 `older` 进入最近窗口。因此从顶部进入有现成分页基础，但只改方向无法消除占位扩张和整栏重建。`ordinalOf` 返回当前窗口内的位置，prepend 后已有显示号会重编号；它与稳定的请求、步骤身份不同。显示号是否改为会话内序号需要单独取舍；会话全序号也可能受真实历史补入影响，不能承诺永久不变。

[正文读取](../../../../src/protocols.ts) 的 `getBodyPage` 面向正文、解释与能力视图：`from === 0` 携带请求字段和完整回复，每片还读取 System 块并重建能力视图。单条消息和完整回复的字节量不受消息条数分页限制。[请求详情](../../../../src/queries/requests.ts) 的 `getRequest` 还组装读数与路由摘要等右栏事实。逐笔完整响应存在请求扇出与过量读取的评估空间；批量端点若只循环原有调用，未必减少查询、同步解压和解释成本。独立中栏读口若不复用解释结果，还可能让中栏与右栏重复解压骨架；缓存是否值得做、由谁拥有和如何失效都要测量，缓存本身不必然构成第二份真相。

### 现场原因与验证边界

截图中的更新标记表示自动重读路径曾将记录置为 `updatedSinceSeen`，不证明用户对话新增了消息，也不能单独证明正文发生变化。[阅读身份](../../../../src/reading.ts) 的 `identityOf` 同时包含正文相关身份与派生修订。即使最终可见步骤相同，[组标脏](../../../../src/derive/state.ts) 的 `markGroupDirtyTx` 也会增加组修订，使 token 变化。费用不在该身份里；派生状态参与身份是现行一致性选择，不能仅凭两者不对称就判为缺陷。

[同步摘要写入](../../../../src/derive/sync.ts) 的 `writePresentationTx` 会重写 `summary_basis`，但其值由输入身份、组 epoch、算法和上下文事件等字段确定，不含每次执行必变的时间戳或随机数。重写相同内容不会自行换 token；`derive_version` 自增也不在当前身份数组内。因此不采纳每次重写摘要必然使令牌变化的因果表述。常规重派生经过组修订推进时确实可以让正文未变的请求换 token，但换 token 后还需后续读取发现冲突，才会触发作废恢复。当前页面没有用于定时重取整个会话的轮询或实时订阅。正文回收属于可读性真实变化，不归为纯重算。

用户确认对话早已结束；调查没有读取该会话的真实数据库状态或浏览器网络记录，因此不能确定本次自动重读由哪项修订触发。若相关数据库状态始终不变，仍反复出现当前版本 409，需要另行调查一致性或竞态缺陷，不能以组会持续变化解释过去。无版本变化也存在的整栏重建，与自动重读标记的具体触发原因应分别验证。

本轮调查执行过 `bun test tests/reader-store.test.ts tests/reading.test.ts --test-name-pattern '作废即自动重读|只改费用不换阅读版本|409 只在真正作废当前记录时通知页面'`：3 项通过，29 项被过滤，23 次断言。它们证明现有合成语义按测试运行，不证明用户现场复现成功，也不覆盖 DOM 稳定、焦点、文本选择或滚动漂移。

历史性能材料只供估算调查方向：[2026-10-24 合成验收](../../../../docs/acceptance.md#单一轨迹阅读界面合成2026-10-24)记录过 57 次读取、136,161 字节传输；[架构设计的内容复用样本](../../../../docs/architecture-design.md#内容复用)记录过 1,618 笔请求对应约 1,261.6 MB 引用原文、块去重后约 142.7 MB。前者不是当前首屏基准，后者是历史存储样本，均不能直接推算本方案延迟或浏览器内存。

- 版本恢复期间保留旧投影：[版本恢复期间保留旧投影](../../implemented/feature/2026-10-27-trace-version-retention.md)。旧版本标记不占高度，成功换新不再另设提示。

仍未兑现的部分：首屏与小片段提交的成本基准、可见结果比较覆盖 `callOf` 之外的交互坐标、顶部入口与 URL 定点规则、自动加载范围、普通失败与版本冲突的重试政策区分。本文「已确认的代码机制」表记录的是提案撰写时的工作区状态，其中 `loadWindowReads`、`userScrolled`、`anchorSnapshot`、`group-flag`、`traceHtml` 等符号已随上述交付退出代码；该表保留为当时的调查证据，不再作为现行实现描述。

## Proposal

优先评估现有读取接口下的完整组合方案：后台准备可阅读片段，按稳定步骤身份局部提交中栏，选择与右栏补读不重建无变化节点，并修正锚点与版本恢复。服务端独立轨迹读口改为性能证据支持后的候选，不作为实施前提。默认顶部进入、整场会话后台排空与令牌拆分都保留待评审，不与阅读稳定性捆绑接受。

这里的完整片段指中栏显示结构已经准备好的结果，可以由浏览器消费现有接口后生成，不预设服务端投影或新增持久表。用户要求的稳定是已读区域的位置、顺序、选择和交互连续性；内容没有真实变化时，已有行的身份、结构与文本应保持不变。真实修正应自动核对并如实更新，同时保护阅读位置；具体一致性协议尚未确定，不能宣称永久冻结与始终最新已同时成立。

### Review 采纳结论

本次采纳 Deepseek review 对方案规模的纠偏：原提案未证明独立读口必要，也没有完整比较前端局部更新、可见结果比较、锚点补偿和完整片段提交的组合。评审要求继续保持 proposed，不进入实施。记录 review 的结论不代表用户批准候选实现。

采纳补充现有恢复机制、窗口内一次准备完成后显示、序号口径、重试覆盖关系和遗漏 note。自动补齐需求保留，作用范围另定；顶部与最近窗口均为候选，不以排查或回看场景替用户决定默认入口。不采纳中栏只依赖内容版本、现有锚点直接接入批次即足够、局部指纹字段已经完备等技术结论。

### 优先候选：现有接口的组合方案

读取结果与显示提交分开管理。先准备目标阅读区域所需的详情、可信增量及必要的前驱与调用方事实，再提交完整片段；后续片段自动准备。版本恢复期间保留明确版本归属的已显示结果，不把失效占位作为正常恢复过程覆盖当前步骤，也不把未验证的旧结果当作当前事实。

中栏按请求组与稳定步骤键复用节点。选择只更新高亮；补读没有改变可见内容时不改 DOM。组级复用减少无关区域重建，但正在阅读组的变化还需要步骤级比较与更新，不能通过整组内部替换来宣称焦点和文字选择已保留。逐组占行的更新成功标记拟移除；异常反馈与版本归属方式仍须明确。

可见结果比较必须覆盖实际渲染输入，包括工具名、参数摘要、失败位、背景作业说明、调用方依赖和展示序号。不能只比较部分 `projectSteps` 字段；`callOf` 会在投影之外补出显示内容。显示相同也可能发生来源坐标或版本变化，交互定位信息必须独立更新。先设计明确可测的比较规则，不预设必须引入哈希。

既有折叠恢复与消息选择机制继续复用。锚点改为本次提交前首条可见的稳定步骤及其视口偏移；提交期间若用户主动移动，过期补偿应取消或重新取样。现有 `userScrolled` 是会话级标记，不能让滚过一次之后所有批次永久停止补偿。键盘、滚动条拖动、焦点滚动和窄屏文档滚动都要验证。

### 中栏与正文的读取成本

中栏读取应足以确定步骤身份、顺序、显示文本和详情定位。结果不包含全部历史正文或无限长度工具参数；完整内容留给右栏。中栏预览与悬停全文的取舍涉及现有能力变化，需要显式 review，不能在性能优化里静默删掉完整内容入口。

System 与前驱的比较、工具结果到调用方的摘要定位，应依据读取时可确认的事实完成，不能继续依据浏览器缓存是否命中。跨片前驱不在本片时，读取模块应按必要依赖补齐比较事实，或给出明确稳定的表达。不要先绘制一条 System，再因下一次缓存命中将其删除。

步骤解释只有一份权威实现。评审应比较将现有纯投影提取为可共享模块、在服务端生成投影，或返回足够完整的紧凑输入后在前端一次生成。协议解释、路径、输入清洗与派生可信度继续复用现有定义，不能因增加中栏读口另写一套规则。具体文件、类型与端点命名待评审，不在此承诺。

### 首屏与自动加载

首屏比较两条路径：当前窗口所需轨迹一次准备完再显示；或目标附近的小片段准备完即显示，其余自动补齐。前者可能减少首次提交后的结构变化，后者可能更快出现可读内容，选择依赖当前样本基准，不能从历史单次 SQLite 查询耗时推算整窗串联网络、解释和 DOM 布局成本。这里的一次准备只覆盖轨迹所需数据，不要求下载窗口内每笔请求的全部历史正文。

片段准备以请求组为优先边界，沿用现有步骤身份；单笔超大请求若无法在资源预算内准备完成，再评估按稳定步骤位置分片。预取范围暂按目标窗口与接近视口的区域评估，不预设整场排空；自动加载的最终范围待确认。正常路径不依赖手动刷新或逐片续读，后台仍需限制响应字节、同步处理时间、缓存与 DOM 数量。

后台可以并发准备片段，显示应按已确定顺序提交。不能先显示后段，再随响应到达向其中插入同一读取范围的未就绪步骤。片段读取失败的重试次数、退避和异常入口需与持续版本冲突分别设计；有界重试是候选政策，不是已批准决定。禁止将缺口显示为全部完成，异常重试入口也不能变成正常阅读必经操作。

默认顶部与最近窗口均待评审，原默认不因本文而变更。目标附近优先读取有助于最近窗口和 URL 定点的首屏，应与从头顺序读取比较。带 trace 的 URL 不应为读取后段目标先遍历全会话；最新入口保留明确导航语义。prepend 的显示号目前按窗口重排，是否改为会话序号、预留序号槽宽及其代价要一起评审；步骤身份不使用显示号。

### 中栏显示与选择

中栏显示模块按稳定步骤键保留节点；选择变化只更新高亮与必要属性，右栏详情到达不触发中栏内容重建。片段到达追加对应节点，不能再次替换整个 `main.innerHTML`。不引入框架或第三方依赖作为前置条件。

浏览器文字选择、键盘焦点与当前可见步骤相对视口的位置都属于阅读状态。正常向下追加不改当前滚动位置；prepend、真实结构修订、头部高度变化需要按当前可见步骤与视口偏移补偿。先验证原生滚动锚定与显式补偿如何配合，避免双重移动或把已经主动滚动的读者拉回旧锚点。

会话汇总、轮次带与序号槽也纳入稳定性范围。汇总迟到、轮次带出现或序号位数扩展不能悄悄改变正在阅读的位置；可以保留必要布局空间或执行局部位置补偿，但不为未到数据制造常驻装饰。逐组占行的自动换新成功标记拟移除，其可见性替代方式与恢复失败呈现一起评审。

中栏轨迹快照与右栏正文缓存分别有唯一所有者，选择仍是独立 UI 状态。两种读模型不意味着页面再复制三份可写缓存，也不能让渲染函数负责拉取网络或更改选择。

### 版本与自动恢复

正文缓存与派生缓存分别失效是值得验证的候选，不直接接受中栏只使用内容令牌、右栏只使用派生令牌的分法。[步骤投影](../../../../web/trace-view.js) 与 [deltaOrdinals](../../../../web/body-model.js) 消费派生可信状态、增量序号、用途、前驱和工具反向配对。乱序补到前驱时，原请求正文不变，新增步骤仍可能真实变化。若拆分令牌，中栏需要按其实际依赖校验内容与派生版本；工具结果还要核对配对关系和目标正文有效性，不能保留旧来源坐标后只换 token。

先以合成反例验证纯派生修订但结果相同、前驱变化导致增量变化、配对目标变化、正文回收和迟到响应。根据失效造成的实际重读成本，再决定是否修改现有读取协议并拆分令牌。即使拆分无需 schema 变更，也涉及缓存键、端点参数、响应与消费者契约，不视为机械改动。

每个轨迹片段需要在一致的读取视图中生成，并声明它依据的阅读修订。跨片读取期间如何发现修订变化，以及修订后重取哪些片段，应在接口里定义。仅固定时间上界不能阻止历史行修正或乱序补入；仅做每片独立事务也不能自动证明整场会话来自同一版本。

不建议用一个跨全部 GET 的长 SQLite 事务冻结会话，也不预设长期保留每一版轨迹。可先评估修订校验、受影响片段重取和客户端保留已显示投影是否足够；若需要保留旧投影，必须定义版本归属、过期状态、回收和资源上限，不能把旧值冒充当前结论。

右栏补读遇到 409 时自动恢复详情，不清空已显示的中栏步骤。步骤来源必须随版本核对；不能保留旧坐标、用新 token 读出不同内容后当作同一事实。目标消失或发生真实修正时，应如实说明并保持阅读位置，具体交互待 review。

本轮优先评估打开时已有数据在目标读取范围内的自动补齐。是否遍历整场会话、是否自动发现新消息都尚未确认，后续片自动加载不等于已经设计了 live 模式。当前不存在明确的会话结束状态，不能靠会话年龄判定永久不可变。若纳入新消息自动出现，再定义版本检查、增量拉取或订阅方式；读者不在末尾时不自动滚到底部，真实历史修订也不能简单作为末尾追加。

### 实施范围建议

先建立当前路径基准并验证前端组合方案：首屏可读时间、窗口准备耗时、每批布局时间、传输字节与请求数、DOM 数量、内存和后台读取对采集响应的影响。比较整窗准备与小片段提交；只有现有读取路径在同场景下仍成为瓶颈，且可量化地归因于逐笔扇出、完整回复传输或重复能力解释时，再决定紧凑读口及投影位置。`main.ts` 中派生任务的 400 ms 调度预算不等于前端读取可接受延迟或单次 HTTP 同步处理预算，不能直接拿来设性能目标。

有必要时可对指定历史会话的 token 与身份字段做有界只读采样，只记录变化字段名、频率和必要版本元数据，不输出请求正文。30–60 秒轮询可能漏掉瞬时变化，半小时到一小时无变化也不能证明现场从未发生变化；采样是补充证据，不作为所有设计工作的前置等待。本轮不启动采样任务。

只有测量或一致性需求证明有必要时，再评估持久化步骤投影、虚拟列表或会话快照。拓扑调整不顺带启用切片派生、改变采集与回收策略、安装依赖或重建真实库。

若按需生成轨迹仍然昂贵，再独立决定是否在派生阶段预计算。持久化方案必须同时设计版本升级、存量 backfill 或明确拒绝路径，并验证正文回收后的含义；不能通过静默建表和缺省空结果掩盖历史轨迹缺失。

### 交给下个 Agent 的评审问题

1. 现有接口加完整片段准备、步骤级节点复用、完整可见结果比较和正确锚点能否满足需求？若仍不足，请用具体反例或性能证据说明，再评估独立轨迹读口，不预设服务端投影必要。
2. 当前窗口一次准备与目标附近小片段提交各自的首屏、字节和布局成本是多少？中栏最小事实包括前驱比较与调用方定位，如何避免重复能力解释和不必要的完整字段传输？
3. 以请求组分片能否覆盖超大单请求与稀疏增量？步骤身份继续沿用稳定键；显示号保留窗口位置还是改会话序号，真实历史插入与槽宽变化如何处理？
4. 顶部、最近窗口和 URL 定点分别适合什么任务？先读取目标区域能否保留现有导航且不抢滚动？不要把入口方向与解决跳变绑定。
5. 现有 token 的哪些变化要求重读正文，哪些只需重算派生显示？令牌拆分是否值得，如何证明中栏的双重依赖及配对目标有效性、迟到响应和旧坐标处理完整？
6. 自动加载范围是当前窗口、接近视口的区域还是整场会话？新消息发现是否另立范围？明确正常路径自动补齐，不用手动刷新替代。
7. 首屏可读时间、每批布局时间、窗口准备时间、网络、DOM、内存和事件循环的基准是什么？什么可观察瓶颈才足以支持紧凑读口、缓存、虚拟化或持久化？
8. 如何分别复现批次扩张、缓存命中点选、提示消除、首载居中、纯派生修订和真正内容修正？只读采样能补充哪些证据、会遗漏什么？重试次数与现行无限冲突恢复策略如何取舍？

## Alternatives considered

**阅读期间暂停更新、要求手动刷新。** 讨论中曾推荐，用户明确认为只是治标。它把读取恢复与更新责任交给用户，不满足自动加载需求，不作为当前推荐。

**一次读取整场会话的全部正文后再显示。** 用户提出一次渲染的可能性；它可以减少显示阶段的补齐，但延迟受整场最重请求影响，并下载大量重复上下文。短会话的全部紧凑轨迹仍可一次返回；不建议强制全正文作为所有会话的首屏前提。

**保留当前数据路径，仅放大批次或并发。** 可以减少等待批次数，却保留步骤数量取决于缓存进度、右栏补读影响中栏和整栏 DOM 替换的问题。并发增加还可能放大后端同步处理成本，不能在无测量时当作根治。

**只删换新提示、保留 scrollTop，或给整栏重绘增加锚点。** 删除提示可减少噪声与高度变化，锚点可改善视口位置，但仍损失 DOM 身份、焦点与文字选择。两者可作为实现细节，单独交付不足以兑现当前目标。

**只改为从顶部进入。** 后续向下追加更利于阅读，且现有 forward 分页可复用；但首段占位继续膨胀、缓存命中仍整栏重绘时依然会跳。适合作为组合方向，不能代替完整片段与读取分离。

**现有接口的完整组合方案。** 作为优先候选，组合评估完整片段准备、步骤级节点复用、选择局部更新、准确可见结果比较、锚点补偿和后台恢复；不再用单独删除提示或单独加锚点的不足否决整个组合。它仍需证明跨缓存依赖、正在读取组和 409 恢复不会破坏稳定性。

**当前窗口一次准备完成再显示。** 单独保留为中间选项，不与整场全正文下载混为一谈。可能减少后续结构提交，也可能拖慢首屏；本地单次查询历史数据不足以证明整窗延迟，需要同样本测量后取舍。

**独立服务端紧凑轨迹读口。** 保留为现有读取成本成为实测瓶颈后的选项。潜在收益来自减少不必要字段、请求扇出和能力解释，不等于必须把步骤投影移到服务端；重复解压、缓存归属与同步处理预算需一并证明。

**内容与派生令牌直接按中栏、右栏拆分。** 不接受该依赖划分。中栏仍依赖用途、可信增量、前驱和工具配对；仅检查正文版本会遗漏真实步骤变化。可以另评估按数据依赖细化缓存失效与协议，但需要一致性反例和成本证据，不作为已定修复。

**立即新增持久化步骤表或长期保存全部阅读版本。** 能降低重复生成或支持固定版本补读，但增加派生一致性、存量回填、回收与版本维护成本。只有按需轨迹生成的测量或一致性要求证明有必要时再考虑，当前提案不把它当作前置条件。

## Acceptance criteria

以下是方案接受并实施后需要验证的可观察行为，本轮未执行这些验收。

- 构造内容稳定的历史会话，打乱网络响应顺序并延迟各片、前驱、调用方、汇总与轮次数据。首屏已显示步骤不因缓存到齐而增删、改序或重建，背景补齐无需手动操作。
- 首屏不等待整场正文。记录从进入会话到首个可读片段的时间、传输字节与请求数，并与同设备、同合成样本的现行实现对比；数值目标在基准后明确，不以旧验收读数宣称达标。
- 点击已加载步骤、打开工具配对、右栏分页及缓存命中，不替换无变化的中栏节点。选中步骤、键盘焦点和浏览器文字选择在无数据变化时保留。
- 当前可见步骤的视口位置在下方追加时不漂移。prepend、头部变化与真实修订有单独的浏览器验证；记录像素偏差及原因，不以 scrollTop 相同代替阅读位置稳定。
- 在评审确认的自动加载范围内，长会话与超大单请求可自动继续读取，无永久 loading、错误的已是最新或被隐藏的中间缺口。按确认的普通失败与版本冲突重试政策验证，不预先将现行无限冲突恢复改成固定上限；切会话丢弃旧任务结果。
- 固定数据与读取范围，不同响应顺序产生相同语义步骤；System 抑制与工具结果摘要不再受浏览器缓存顺序影响。步骤身份与显示号分开断言；若沿用窗口序号，扩大窗口后的重编号不能误报为步骤身份变化。多协议路径、多个结果块、辅助请求、未知派生与正文回收保持如实表达。
- 当前版本 409、迟到 409、纯派生修订但结果相同、前驱修订导致增量变化、配对目标变化和正文回收分别有合成回归。恢复不清空已读中栏，不混用旧来源坐标和新正文；显示未变时交互定位信息仍可正确更新，失败与目标消失可识别。
- 默认入口、URL 定点、最新入口与历史恢复按评审确认的规则工作。自动新消息发现若纳入本轮，另验证不抢滚动与乱序历史插入；若不纳入，明确其能力范围。
- 测量后台轨迹生成对采集响应和事件循环的影响，验证读取预算、并发、缓存与 DOM 资源上限。只用合成数据做测试；真实流量验收须另行授权并单独记录。

## Risks

**需求中的不动需要精确定义。** 没有真实变化时可以要求结构、文字与节点都不变；真实修正时应保留阅读位置并如实更新。若把两类场景混成永久不可变，可能保留错误配对或过期证据；若只承诺滚动像素不变，则没有解决用户问题。

**服务端生成可能转移而非降低成本。** 将逐笔 HTTP 改为批量响应并不会自动消除逐笔查询与解压。Bun 单进程下过大的同步片段可能影响采集，必须有时间与字节预算，不能用无限并发掩盖。

**独立中栏可能成为第二份真相。** 轨迹与正文必须声明各自版本及所有者，派生规则继续单家。脱离版本的预览、旧来源坐标或双写页面缓存会引入新的误导。

**跨片一致性尚未定案。** 多个 actor、乱序补入、组状态变化和来源修订可能影响已经展示的前后关系。客户端保留旧显示不会让服务端具备旧版本读取能力，需要证明自动恢复策略完整。

**自动补齐可能失去有界性。** 首笔可信增量可能很大，整场轨迹也可能远超当前窗口。预取、已下载缓存和 DOM 必须分别有预算；自动化不能意味着永远下载全部全文，虚拟化也不能损坏选择与文字复制。

**顶部默认改变了产品入口。** 历史回看受益，直接排查最新调用可能多一步。用户只提出这一候选，不能当作已接受；定点与最新入口应在 review 中一并比较。

**稳定行高可能牺牲现有信息入口。** 截断预览、悬停按需读取或工具状态局部更新都涉及能力变化。必须保留可达的完整正文和明确失败反馈，并遵守前端降噪约束。

**实测证据仍不足。** 已确认实现具备多条无数据变化也重绘的路径，但没有用户现场的逐次冲突原因与性能记录。本提案不宣称已经找到该历史会话提示反复出现的唯一原因，也不宣称架构调整必然消除所有布局跳变。

[中栏按承载请求的 delta 分组](../../implemented/feature/2026-10-28-request-delta-trace-groups.md)已实施，部分取代本篇以回复在产出组为前提的行数、身份与提交假设：回复改为下一笔承载组的新增 assistant 消息，没有承载请求时单独成末尾组，末尾组只在会话完整加载时出现。键控提交、锚点补偿与已显示行稳定的要求继续有效；本篇其余部分仍为 proposed。
