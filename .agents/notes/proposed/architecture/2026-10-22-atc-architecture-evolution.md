# Agent Note: 以事实重建统筹 ATC 架构演进

Status: proposed

## Problem

ATC 需要承载更多机器调用，也需要集中处理不同 Agent 的请求语义。已有[类别注册表提案](2026-10-22-agent-request-kind-registry.md)与[字段保真提案](2026-10-22-magpie-parity-and-field-fidelity.md)覆盖了两类缺口，但分别实施会重复触碰版本、回填、正文解释和查询。mapper 修复不能修正全部请求写入路径，会话派生也不能重建来源字段；[联合评审](../../../../docs/agent-request-kind-review.md#与字段保真方案的联合评估)已经给出源码依据。

扩展机制与容量同样需要分开判断。把规则挪进注册表能改善修改位置，却没有减少长会话祖先比较或历史文件解压。若把所有工作都称为 Feature 插件化，后续容易把身份、协议、后台调度与页面交互一起放进 Agent Profile，增加调用者需要理解的 Interface。

## Proposal

采用[架构演进方案 v2](../../../../docs/architecture-evolution-v2.md)作为下一轮讨论入口，用事实重建、请求语义和有界执行组织变更。三个值得加深的 Module 分别集中来源字段与投影规则、Agent 专有解释、派生调度及恢复。在线摄入与离线重建共享事实规则；请求级解释与等待归属确认的会话派生分清触发时机。

统筹的理由是减少一次正确修改需要同步理解的位置。源码中的字段知识、Agent 语义和重算成本分别有主，调用者通过小 Interface 获得完整行为；模块拆分必须改善 Depth、Locality 或 Leverage，不以文件数作为完成条件。具体职责、分阶段推进、容量门槛与迁移约束只在方案中维护。

定向复核支持将请求用途的待处理状态放在请求上，分组队列保留会话依赖。理由是 actor 未定并不妨碍判用途，且直接关联成功后的补正文也需要可靠触发；写入完成后的内存通知不能替代事务内的持久标记。输入解释与技能清单按正文读取执行，不因统一语义规则而变成必须全库执行的后台任务。

来源投影共享规则还必须说明输入完整性。owner 证据收集与完整性判断也由该 Module 承担，调用方只传已关联的身份和事务上下文；只提取字段计算会继续让关键知识散在多个入口。raw 过期后部分重放会缩小长期合计，旧占位符也可能被重复脱敏改变，因此缺失、保留旧结果与按新规则复核要分别表达。来源 kind 的冲突建议保守保留，不用最后到达者隐式裁决；具体规则在[来源投影](../../../../docs/architecture-evolution-v2.md#投影输入完整性与来源冲突)维护，反例见[补充评审](../../../../docs/agent-request-kind-review.md#来源完整性与隐私一致性)。

稳定占位符依赖原盐，可恢复采集的备份必须保留匹配盐及绑定信息。仅恢复数据库后静默生成新盐会破坏跨记录关联；认证 token 可独立恢复或重配。拒绝统计采用固定原因的有界观测，不要求拒绝分支写库，也不借机扩大并发或缓存正文；两项边界见[方案 v2](../../../../docs/architecture-evolution-v2.md)。

正确性回归与容量基线分开推进。字段修复可在对应反例固定后实施，完整负载入口不作为它的前置；来源版本、请求修订和保留状态在其 schema 迁移前确定。计算代际随切片交付，在切片迁移前冻结存储与查询契约，避免同步执行阶段承担尚无测量依据的暂存成本。

[架构演进实施入口](../../../../docs/superpowers/plans/2026-10-22-atc-evolution-implementation.md)与[同步派生正确性计划](../../../../docs/superpowers/plans/2026-10-22-atc-derive-correctness.md)细化可执行工作。完整重建必须先区分证据缺失与真实空输入，并区分稳定身份与顺序依据，才能为后续语义和性能改造提供可信对照。采用时间优先会改变当前运行时结果；代码验证与历史对齐分别报告，避免把保留旧值误称为新规则确认。具体步骤与上线条件只在实施计划维护。

magpie 补充调研围绕未决问题展开，优先借鉴缺失语义、来源归并、尝试解释和缓存失效。每项研究需说明 ATC 中的实际消费者与代价。配置管理和网关执行不属于旁路记录器；direct、正文全文搜索和专有指纹保持独立决策，避免扩大本轮迁移。

## 与现有决策的关系

本提案统筹两份 proposed 的范围，不将它们转为 implemented，也不按未修订的旧验收直接执行。原提案保留问题背景与备选讨论，联合评审保留具体反例；下一轮的统筹职责与次序以方案 v2 为讨论依据。

已检查相关 implemented 记录：[schema 显式回填](../../implemented/architecture/2026-10-20-schema-v3-rejects-in-place-upgrade.md)、[容量三门槛](../../implemented/architecture/2026-10-20-retention-three-gates.md)、[隐私与本地访问](../../implemented/architecture/2026-10-20-privacy-and-local-access-boundary.md)、[任意祖先前驱](../../implemented/architecture/2026-10-20-semantic-fingerprint-and-ancestor-predecessor.md)、[标题与主链](../../implemented/feature/2026-10-21-title-generator-and-main-chain.md)及[不可读请求保持中性](../../implemented/bug-fix/2026-10-21-unreadable-requests-stay-neutral.md)。本轮没有运行时交付，不完整取代其中任何一项，均保持活跃；实施涉及事实或决策改变时再在同一变更中处理。

## Alternatives considered

**按原来的两篇提案分别实施。** 字段保真与类别规则有各自价值，但它们在版本、长期证据和回填处重叠；分别推进而缺少统筹，会留下修 mapper 却没修投影、升结构却没完成重建的空隙。

**继续扩展 RequestKind，容纳所有 Agent Feature。** 用途、输入包装和技能声明可以同时出现，互斥匹配会遮蔽结果；身份、协议和调度的变化原因也不相同。保留三个独立语义操作更接近实际数据。

**先完整对标 magpie，再决定 ATC 架构。** 已有源码研究足以支持已确认的修正。无问题约束的继续调研会把配置写入与网关能力带入范围，推迟可验证的改进；补充研究按阶段问题进行。

**一次替换全部目录与数据模型。** 更难区分字段纠错、语义改变和性能优化，也放大已有正文的迁移风险。分阶段穿过相同 Seam 验证，可以保留恢复入口和差异定位能力。

**仅增加写入完成回调，或让请求用途共用 actor 分组队列。** 前者在崩溃后没有工作依据，后者不能覆盖未知归属。请求行待处理状态与现有分组队列分别管理实际依赖，共用 writer 和调度入口即可。

**链算完即删队列，调用方随后重配工具。** 两步之间退出时没有恢复触发，合成库已经复现。同事务集中执行还必须统一逻辑顺序，并让依赖工具的摘要消费本次关联；单纯合并事务仍会保留排序差异与上一轮摘要依赖，反例见[补充评审](../../../../docs/agent-request-kind-review.md#派生排序与摘要依赖)。

**切片时原地覆盖派生值，只在查询侧屏蔽半成品。** 计算完成前若正文回收，已被覆盖的上一份标题或工具关系无法恢复。跨事务切片需保留已发布结果，将本次派生写入独立代际并短事务发布；不复制正文与请求事实。此成本只在实施切片时承担，初期同事务集中执行即可封闭当前恢复缺口，分批产物、WAL 与清理都需有预算。

## Acceptance criteria

本提案评审完成需明确三个 Module 的责任、在线与离线重建关系、请求语义触发时机、已有决策的保留范围，以及 magpie 采用与延期的依据。每阶段的可观察完成条件在[方案 v2](../../../../docs/architecture-evolution-v2.md#分阶段推进)维护，不在此复制。

代码交付必须分别报告字段正确性、语义一致性和混合负载容量；合成检查、静态读码、真实流量与迁移执行各自说明。完整重建先满足统一逻辑顺序、重复重建及清空可重算派生后的语义一致性，优化再与该基准比较；维护报告须区分当前产出与历史保留。文档通过格式和链接检查只表示提案可审阅，不表示架构已经落地。

## Risks

统筹方案可能演变成一次性大重构。阶段应按可验证行为交付，明确规则迁移与规则改变，维持现有存储、访问和正文回收的不变量。

长期保留过多解释结果会增加元数据和敏感内容成本；只保留必需的短依据与有消费者的事实。后台切片若缺少失效检查，可能发布过期链结果；保留派生代际还会增加暂存空间与清理工作。热组持续失效可能长期无法发布，需以积压和排空验收暴露；增量优化必须与完整重建比较，不能删除任意祖先候选换取速度。

本轮合成容量目标仍需在固定环境建立基线后收敛。没有测量结果前，不能从设计图或注册表规模推导吞吐，也不能假设引入 worker 就会改善单 writer 的工作量。
