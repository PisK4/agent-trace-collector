# Agent Note: 中栏间距、历史边界、用量读数与右栏入口的界面修正

Status: proposed

本提案只覆盖阅读界面的显示与入口修正，不触碰采集、派生与存储。它与工作区里未提交的[工具配对页](../../../docs/superpowers/plans/2026-10-24-trace-pair.md)改动在第三项上相邻但不相交：配对页改的是工具四页的内容组织，本提案改的是用量读数在右栏的组织方式；两边的稳定键都在右栏折叠行空间内，实施时必须先确认没有键名冲突。右栏页签的入口修正与配对页共用 `selectRequest` 的同一段赋值，需要合并裁决，见[待评审的决策点](#待评审的决策点)。

## Problem

四个独立的界面缺陷，共同的根因是同一类错误：**用布局与边界重复表达同一件事，或者让入口态覆盖用户的阅读位置**。它们都不影响账本数据的正确性，但每一个都让阅读成本上升，且都不会被测试捕获。

**中栏标号与标签之间的大段空白。** `.compact-meta` 固定宽 86px（`web/index.html:224`），槽位按「序号 + 时间」双列设计（原型的 `.compact-meta` 是 `gap:8px` 的双列，`prototypes/trace-reader-prototype.html:622`），生产只渲染了前半（`web/trace-view.js:266`）。实测 1507px 视口下：序号文本 `1` 只占约 10px，剩余约 70px 是空槽，`row-label` 因此被推到 x=374，而预览文本起点在 x=445。中栏可用宽度 611px，序号槽吃掉了其中 86px。原型保留双列是因为它有 `compact-metrics` 那一列读数；生产按[中栏只呈现内容](../implemented/simplification/2026-10-24-trace-content-only-and-wide-rail.md)删掉附加信息之后，这个宽度就没有存在理由了。

**「已到会话起点」是一句多余的边界声明。** `web/app.js:819-820` 在 `olderCursor === null` 时渲染这一行。它所在的 `.history-loader` 自带 `border-bottom` 与上下 14/15px 内距，本身就是历史区与步骤列表的视觉边界；边界由结构承担之后，这句文字没有增加任何信息。同一区域的 `history-range`（「序号表示当前窗口内的请求 · 时间从上往下 · 点击行查看详情」）常驻显示，也说明这个区域不依赖状态文字来表明自己的存在。真正需要状态文字的是另外两种：读取中（进行态，必须给反馈）与可加载（操作入口）。

**用量与上下文的读数平铺难读。** `usageFoldHtml`（`web/app.js:970-1001`）把计时与用量各渲染成一行 `.strip-row`，用 `flex-wrap` 加 `·` 分隔平铺。实测 640px 右栏内：

| 元素 | 实测 |
| --- | --- |
| 计时读数行 | 高 20px（单行），文本 `首字 0.42s·总 2.10s·71 tok/s·首个文本 0.48s` |
| 用量读数行 | 高 20px（单行），文本 `入 9,000·出 120·缓读 10,000·缓写 700·命中 51%` |
| 构成图例 | 高 113px，18 个单元格，三列 `507px 32px 34px`，文本把六类全列出（`系统提示 31.9k 95% 对话内容 1.6k 5% 工具定义 0 0% 记忆与技能 0 0% …`） |
| 折叠行总高 | 284px |

三个问题：其一，数字之间没有对齐列，读者做不了纵向比较；`·` 分隔符在窄栏会折行成参差不齐的多行。其二，`首字` 与 `首个文本` 在本次实测里分别是 0.42s 与 0.48s，在另一样本里相等（截图会话 `ttft_ms=7636`、`first_text_ms` 同值），两者并列时读者无法判断它们是两个事实还是一个事实的两种说法。其三，构成图例把 `0` 的类别也列满六行，占用 113px 中的大部分；本次实测里只有两类非零。

**右栏入口覆盖用户位置，且 URL 声明的页签被丢弃。** 三个实测场景（合成场景，无头浏览器）：

1. 首次载入（无 `trace` 参数）：右栏落在「读数」。此时用户尚未选择任何步骤，落在读数是合理的默认。
2. 带 `?tab=body` 载入：右栏仍落在「读数」。`selectSession`（`web/app.js:1512`）无条件执行 `state.railTab = 'facts'`，把启动时从 URL 读到的值（`web/app.js:452`、`web/app.js:1880`）覆盖掉。`?tab=tools`、`?tab=route` 同样被覆盖。
3. 从「正文」页点一条 `record` 步骤：右栏被踢回「读数」。`selectRequest`（`web/app.js:1423-1424`）对非内容类步骤一律落 `facts`。

第 2 项是明确的缺陷：URL 是用户或外部链接的显式声明，被静默丢弃没有任何提示，且 `updateURL` 之后会把 `tab` 参数一并抹掉，刷新也恢复不回来。第 3 项是设计取舍而非缺陷，但它与用户预期「选中某条信息之后看正文」直接冲突，需要裁决。第 1 项不是缺陷，是默认值的取向问题。

## Proposal

四项修正，按代价从低到高排列。前三项互不依赖，可分别实施与分别验收；第四项依赖一次取舍裁决。

### 一、序号槽收到内容实际宽度

`.compact-meta` 宽度按序号实际占用给：序号是 1–3 位数字（窗口上限 100 笔），等宽字体下约 10–22px，给 4px 右内距后定 28px。`title` 保留完整的「请求 N」，鼠标悬停仍可读到语义。既有断点（1300px 的 76px、620px 的 22px）随主值一并归并，620px 那一档本来就是 22px，证明窄屏下 28px 不会溢出。

代价与收益同时落在中栏：序号槽让出约 58px 给预览文本，长预览的截断点后移。这不改变任何语义，但会改变[中栏只呈现内容](../implemented/simplification/2026-10-24-trace-content-only-and-wide-rail.md)里记录的 36px 行高实测之外的宽度数字——那篇的验收只断言行高与附加元素数量，不断言列宽，因此不需要修改该篇的结论。

### 二、删除「已到会话起点」

删掉 `web/app.js:819-821` 的第三个分支。保留另外两种：`正在读取更早记录…`（进行态）与 `加载更早记录` 按钮（操作入口）。删除后 `rows.length > 0` 这个条件连同分支一起消失，`traceHtml` 的历史区只剩两种状态。

保留 `.history-loader` 本身的分隔线与内距。它承担「有加载入口」与「已到顶」两种状态下的同一个边界，删掉会让这两种状态的视觉结构不一致。

### 三、用量读数改成两列对齐，构成图例只列非零类别

`ledgerParts`（`web/app.js:883-928`）输出的两行读数从「平铺加分隔符」改为「标签列 + 数值列」的两列网格，沿用 `.chain-row` 已有的形状（`web/index.html:374-378`：`grid-template-columns:78px minmax(0,1fr)`，标签左、数值右）。这样数字右对齐成列，窄栏折行时也是整行折，不会把一组数字拆散。样式复用 `.chain-row`，不新增类。

具体三处：

1. 计时与用量各成一个 `<div class="chain">`，内部每项一条 `.chain-row`；`·` 分隔符与 `.strip-row` 的 `flex-wrap` 一并删除。
2. `首字` 与 `首个文本` 合并成一个事实。两者同源（`first_text_ms` 与 `ttft_ms` 都是上游报告的时点），差异只在上游口径。合并规则：任一为空则只显示有值的那个并保留 `—`；两者都有且相差超过 100ms 时并列显示（这时它们确实是两个事实，差值是信息）；相差 100ms 以内只显示一个，标签用「首字」，`title` 里给出另一个的值。阈值取 100ms 是因为低于它的差值小于一位小数秒的显示精度（0.1s），显示出来只会造成「两个数不一样」的错觉。
3. 构成图例过滤 `tokens === 0` 的类别。构成条本身已经用 `list.filter(x => x.tokens > 0)` 过滤（`web/app.js:983`），图例没有同步过滤，这是不一致。过滤后本次实测的图例从 18 个单元格降到 6 个（两类），高度从 113px 降到约 40px。被过滤类别的总量仍由 `u-total` 的「提示总量」承载，不丢数字。

`ledgerRowsHtml`（`web/app.js:931-935`，窗口外请求复用）与 `usageFoldHtml` 共用 `ledgerParts`，两处同时受益。`fold-count` 摘要（「总 / 出 / 命中」三项）不变。

**明确不做**：不把读数收进 28px 的 pill 加弹层。Deepseek Harness 的 `TurnUsagePanel`（`packages/client/ui-chat/src/client/chat/TurnUsagePanel.tsx`）用这个组织让用量不占正文宽度，代价是引入 portal 与锚定定位；ATC 的读数页已经把用量放在末位折叠行里，不占首屏，引入弹层只会增加一层交互而不减少占用。搬 DSH 的两列对齐就够。

### 四、右栏入口：保留显式声明，内容类步骤不打断当前页签

一次改动解决第 3 节的两项：

1. `selectSession` 不再无条件写 `state.railTab = 'facts'`。URL 的 `tab` 由启动路径读入（已有），切会话时保留当前页签；只有「新会话且没有任何页签声明」时才落 `facts`。
2. `selectRequest` 的页签分支改成：配对目标与调用进 `tools`（沿用[工具配对页](../../../docs/superpowers/plans/2026-10-24-trace-pair.md)的新增分支），`request`/`reply` 来源进 `body`，其余（`record`/`aux`）**保持当前页签不变**。这样点一条 `Event` 行不会把用户从正文踢回读数，而首次进入仍是读数。

增量续读那条路径（`web/app.js:1399-1414`）显式设 `facts` 不变：点击事件记录行就是要看读数并续读，那是动作入口，不是浏览。

这一项与工作区未提交的配对页改动共用 `selectRequest` 的同一段赋值，必须合并后一起实施，见下节。

## 待评审的决策点

1. **右栏默认落在哪一页。** 首次载入（无 `trace`、无 `tab`）时右栏现在落「读数」。用户表述是「选中某条信息之后，右栏默认跳到读数，而不是正文」，方向是希望看到正文。两种取向：(a) 首次载入落「正文」，与「选中即看内容」一致，但首屏失去这一笔的账目概览；(b) 维持「读数」为首次默认，只在用户显式选择或 URL 声明后跟随。本提案倾向 (b)：读数页的「本次回复」默认展开，首屏已经能看到回复正文，用户点任意步骤立即进对应正文页，不需要先切一次页签。若倾向 (a)，改动只是把 `state.railTab` 的初值从 `facts` 改成 `body`，但 `updateURL` 会开始往 URL 写 `tab=body`，链接语义随之变化。

2. **`record` 步骤是否应该进正文。** 现设计的取向是「保持当前页签」。另一种是让 `record` 步骤也进正文并定位到它 `source` 指向的位置（部分记录有 source，如未知回复块）。前者更保守，后者信息更直达但会把「这是一条事件记录」的语义混同成内容。

3. **与未提交的配对页改动如何合并。** 配对页把工具四页第三页从「结果」改成「配对」，并新增 `state.toolOwner`。本提案第四项改的是同一段页签赋值的另一半。建议配对页先落地（它已在进行中），本提案第四项作为其后的一次独立改动，避免在同一段代码上叠两个未评审的决定。

## Alternatives considered

**只把「已到会话起点」改成更短的字样（如「会话起点」）。** 仍然是一句重复边界的文字，没有解决它不该存在的问题。删除比缩短更彻底，且删除后代码少一个分支。

**序号槽改用 `min-width` 让内容撑开。** 序号是 1–3 位数字，宽度的实际变化来自位数而非设计；固定 28px 让每一行的标签起点一致，扫读时不会左右跳。这与 `.row-label` 固定 62px（`web/index.html:228`）是同一条理由。

**保留「首字」与「首个文本」两个读数。** 它们来自上游两个字段（`ttft_ms` 与 `first_text_ms`），并排显示看起来更完整。但本次实测两者相差 60ms，低于一位小数秒的显示精度，读者只会得到「这两个数为什么不一样」的疑问，得不到任何判断。合并不是丢数据，差值小于阈值时另一个值进 `title`。

**用量读数收进 pill 加弹层（对齐 DSH）。** 见 Proposal 第三节末段：ATC 的用量不占首屏，弹层只增加交互层次。若将来右栏要腾出宽度给别的内容，再重新评估。

**读数条改用表格（`<table>`）。** 表格语义正确，但这一组读数不是关系数据（每一项的标签、口径、缺值处理都不同），用 `<dl>` 或 div 网格更贴近实际结构，也不需要额外的表格样式。

**构成图例全部保留，用颜色区分零值类别。** 六类里通常只有两三类非零，把四类 `0` 列出来占 70px 高度，读者要跳过它们才能看到有用的两行。零值不是「这一类是空的」这个事实的展示需求，`u-total` 的总量已经说明总量构成。

**首次载入落「正文」。** 见待评审决策点 1：首屏会失去账目概示。若用户明确要这个取向，成本只是一行初值。

**右栏页签在每次选中时强制归位到内容页。** 包括 `record` 步骤也进正文。这会让「点事件行看它是什么」这个动作把用户从正在读的正文带走，且事件行的正文定位语义混同于内容步骤。

## Acceptance criteria

- 合成场景 1507px 视口实测：`.compact-meta` 宽 28px，序号文本不被裁剪，`row-label` 起点从 x=374 移到 x=306 附近，预览文本起点相应前移；36px 行高不变；1300px 与 620px 两档无横向溢出，序号仍完整。
- 已到会话起点的会话（`olderCursor === null`）：历史区只剩「序号表示当前窗口内的请求 · 时间从上往下 · 点击行查看详情」一行，无状态文字；有更早记录的会话仍有「加载更早记录」按钮；读取中仍显示「正在读取更早记录…」。
- 用量与上下文折叠行：计时与用量各成一列两列网格，数字右边缘对齐；`首字` 与 `首个文本` 差值小于 100ms 时只显示一个（`title` 含另一个的值），大于 100ms 时并列；构成图例只列 `tokens > 0` 的类别，零值类别不出现；`u-total` 三项与 `fold-count` 摘要不变；全缺时整行仍不渲染。
- 窗口外请求分支（`ledgerRowsHtml`）的读数同样两列对齐。
- 右栏入口：`?tab=body` / `?tab=tools` / `?tab=route` 载入后右栏落在声明页；切会话保留当前页签；无任何声明时落「读数」；点 `record` 步骤不改变当前页签；点增量事件行仍进「读数」并续读。
- `bun test`、`bun run typecheck`、`bun run verify:notes`、`git diff --check` 通过；新增回归先在旧实现失败再随修复通过（序号槽宽度、历史区状态文字、读数两列对齐、图例零值过滤、首字合并阈值、URL 页签保留、record 不切页签）。

## Risks

- **序号槽收窄后与 `title` 的配合。** 28px 只放得下数字，「请求 N」的完整语义进 `title`；不悬停就看不到。这是刻意的取舍：序号在窗口内连续可见，悬停成本低于为它常驻 58px 空白。若将来序号要携带更多信息（如失败标记），宽度需要重新定，届时应连带考虑是否回到双列。
- **首字合并可能隐藏上游口径差异。** `ttft_ms` 与 `first_text_ms` 在上游是两个字段，合并显示后读者看不到它们各自的原始值。缓解：差值超过 100ms 时并列显示，`title` 始终给出另一个的值。若将来要提供「两个字段的原始对比」，应放在工具详情那样的独立视图，不放在读数行里。
- **构成图例过滤零值后，类别缺失与类别为空无法区分。** 一个类别 `tokens=0` 与它没有被这次估计覆盖，在图例上同样是不出现。这是可接受的：`parts_json` 只包含本次估计覆盖的类别，未覆盖的类别本来就不在这份数据里，`u-total` 的总量与「分类是估计分配」的注记已说明口径。
- **`selectSession` 不再重置页签，跨会话的页签可能不适用。** 例如在会话 A 的「路由」页切到会话 B，右栏仍显示路由页（B 的路由按需读取）。这符合「页签是用户的阅读位置，不是会话的属性」；若评审认为页签应随会话重置，退回显式重置，但要同时保留 URL 声明优先。
- **与未提交的配对页改动冲突。** 第四项与配对页共用 `selectRequest` 的页签赋值。若两者同时实施而没有先合并评审，会出现一段代码承载两个未评审决定的情况。缓解：本提案第三、四项之间的依赖只在第四项，评审时可只批准前三项。
- **宽度变化影响此前的实测记录。** [中栏只呈现内容](../implemented/simplification/2026-10-24-trace-content-only-and-wide-rail.md)记录了 36px 行高与「行右侧附加元素为零」，本提案不改变这两条；但它记录的宽度观察值会变。该篇不断言列宽，不需要修改；实施时在新 note 里记录新的实测值即可。
