# Agent Note: 后台性能监控先用外部采样与阈值告警

Status: proposed

## Problem

采集器现在只有拉取式观测，没有历史，也没有告警。`GET /api/ingest-metrics` 给出事件循环、定时任务、具名写事务、正文读取、存储与派生队列；`GET /api/stats` 给出采集游标、缺口、待处理 hook、准入模式与 magpie 探针；`bun run service status` 把 launchd 状态、代码新鲜度、接口探测与日志尾部合在一起。三者都要手动调用。

[容量观测](../../implemented/feature/2026-10-22-atc-capacity-metrics.md)有意只保存在进程内：计数随重启归零，事件循环环形缓冲只覆盖约 6.8 分钟，日志没有时间戳。跨天趋势、回归定位和「夜里出问题第二天才知道」都没有承载。

最近两处性能问题都是人工验收才发现的：[认领边界长窗口验收](../../../../docs/acceptance.md#认领边界长窗口性能验收真实流量2026-11-03)测出事件循环 p99 271.8 ms 与会话名单 462 ms。阈值本身是现成的——容量门槛要求 p99 ≤100 ms，准入模式、派生队列与磁盘余量都有明确状态——缺的是持续采样和触发后的提醒。

需求边界：单机、单用户、一个采集器进程；需要跨天保存少量指标、越界时通知、采样本身不能明显扰动被测进程。不需要多主机聚合、远程告警、历史高分辨率或可视化大盘。

## Proposal

分三步，先小后大，不一步到位。

### 第一步：轻量指标端点

新增 `GET /api/metrics`，返回与 `/api/ingest-metrics` 相同的进程内计数，但跳过 `measureStorage`；存储值改用准入闸门最近一次量测，没有就读空值。两个端点共用现有的 `metrics.snapshot` 组装逻辑，区别只在存储段。同一个改动加上 [准入量测](../../proposed/bug-fix/2026-11-03-admission-storage-measure-block.md)里提出的 `storage.measure` 次数、合计与最大耗时。

`/api/ingest-metrics` 在本机单次 1–2 秒，主要成本是三条全表求和；轻量端点只读内存计数与队列快照，目标个位数毫秒。它是采样器的主入口，也让按分钟级的轮询成为可能。鉴权仍用读令牌，不新增写路径。

### 第二步：外部采样与阈值

仓库内新增 `scripts/monitor.ts`，子命令 `sample`、`check`、`report`：

- `sample` 取轻量指标与 `/api/stats`，向 `~/Library/Application Support/agent-trace-collector/monitor/` 追加一行 JSONL；目录 0700、文件 0600，按日分文件，保留 14 天。没有会话键、正文、账号或令牌，只有计数与状态。
- `check` 跑阈值表，命中时写一条 `alerts.jsonl` 并调用 `osascript` 发系统通知；同一条规则连续命中只在首次与每 30 分钟提醒一次，避免刷屏。命令以 0/1 退出，方便外部再包一层。
- `report` 对最近 24 小时或 7 天的 JSONL 做 min/avg/p95/max，输出到终端。

调度沿用本机已有的 launchd：新增 `local.agent-trace-monitor`，`StartInterval` 300 秒，标准输出与错误进 `~/Library/Logs/`。采样与检查用 `scripts/service-support.ts` 的 `readToken`、`probeStats`、`readServiceState`，不复制读令牌与探测逻辑。

初始阈值：

| 规则 | 条件 | 依据 |
| --- | --- | --- |
| 进程退出 | 作业不是 `running`，或上次退出码不为 0，或接口探测超时 | `service status` 现有字段 |
| 事件循环尾延迟 | p99 连续 2 次 >100 ms | 容量门槛的产品目标 |
| 派生积压 | 最老 dirty 组 >10 分钟 | 在线派生本应每轮推进 |
| 存储模式 | 准入模式连续 2 次不是 `normal` | 正文预算或磁盘预算触顶 |
| 磁盘余量 | 空闲 <100 GB | 当前 421 GB，留出回收余量 |
| 采集缺口 | 未闭合缺口连续 3 次 >0 | 当前为 0 |
| 正文预算 | `body_bytes` 超过预算的 90% | 预算 10 GB，当前 1.44 GB |
| 内存 | RSS 连续 3 次 >4 GB | 当前 2.06 GB，看增长趋势 |

阈值先跑一周再调；告警记录保留命中时的样本，避免只留「超过了」而没有现场。

### 第三步：按需升级

只有在出现第二台机器、需要跨主机看板、或希望手机收到告警时，才把 JSONL 转成 Prometheus textfile 或接 Grafana。升级触发写在上面，平时不引入新守护进程。

## Alternatives considered

**一步到位装 Prometheus、Grafana 与 Alertmanager。** 单机单用户只有一台采集器，288 个样本一天，全套栈要多跑两个守护进程，还要维护配置文件、时序库、面板与升级。它解决的问题（多主机聚合、长期高分辨率、团队看板）当前都不存在。先用 JSONL 与阈值覆盖需求，升级有明确触发条件。

**在采集器进程内定时采样并落表。** 会让观测数据写进被观测的库，和[容量观测](../../implemented/feature/2026-10-22-atc-capacity-metrics.md)「观测不落表」的结论冲突，还要在 trace 库上另立保留期。采样器留在进程外，采集器只多一个轻量只读端点。

**只轮询 `bun run service status`。** 便宜，但只有数据健康与进程状态，没有事件循环、任务与写事务。最近两处问题它一个都发现不了。

**继续只靠人工验收。** 现状就是如此；回归发生在两次验收之间时没有记录，只能事后猜。

**直接高频采 `/api/ingest-metrics`。** 每次阻塞 1–2 秒，既会出现在自己的 `max` 里污染读数，也会让页面每秒级卡一下。先做轻量端点再提高频率。

**用 cron 调度。** 本机进程生命周期已经由 launchd 管；再引入 cron 会有两套启停与日志语义，且 macOS 对 cron 的权限处理更容易出意外。

## Acceptance criteria

1. `GET /api/metrics` 在 3.85 GB 库上 p95 <10 ms，且调用期间 `measureStorage` 计数不增加；返回字段与 `/api/ingest-metrics` 除存储段外一致。
2. `storage.measure` 的次数、合计与最大耗时出现在两个指标端点里，采样器能据此区分「监控自己」与「业务阻塞」。
3. `sample` 单次在冷启动下 <50 ms（不含网络排队），每次恰好追加一行 JSONL；按日分文件，14 天后旧文件被删除；目录与文件权限符合运行数据边界。
4. 阈值规则是纯函数，逐条用合成样本测试：边界值、连续命中、恢复到正常、去重窗口；每条规则都能因对应输入失败，不能只测全绿。
5. 注入一次越界样本，`check` 产生一条 `alerts.jsonl` 与一次通知；连续越界在 30 分钟内不重复提醒；恢复后再次越界会重新提醒。
6. `report 24h` 输出每个字段的 min/avg/p95/max 与样本数，空文件返回空结果而不是报错。
7. launchd 安装与卸载步骤写进[运维手册](../../../../docs/operations.md)，`service status` 的输出不受影响。监控停止时采集器照常运行。
8. 采样器只读令牌与计数，不写采集器的库；JSONL 不含会话键、正文、账号、令牌或用户配置。

## Risks

阈值调得太紧会产生告警疲劳，调得太松等于没有。先用一周的真实样本校准，再决定是否把「连续 2 次」改成更长的窗口。

`osascript` 通知只在本机登录时可见，不能作为远程告警。真要离开本机时，第三步的 textfile 或推送服务才解决问题。

监控自己的存活没有独立看护。launchd 的 `runs` 与上次退出码能看出它停过，但不会主动通知；一个可选做法是把最近一次采样时间写进状态文件，由 `service status` 顺带显示，这属于第二步之后的补充，不提前耦合。

采样仍会占一点事件循环时间。轻量端点把单次成本压到毫秒级，但频率越高总量越大；1 分钟一次、每次个位数毫秒，可以接受。

JSONL 与告警文件属于运行数据，放在仓库外。备份与恢复不在本提案内；它们丢了只会丢历史，不影响采集器。
