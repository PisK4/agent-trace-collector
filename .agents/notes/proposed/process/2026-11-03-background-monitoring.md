# Agent Note: 后台性能监控先用外部采样与阈值告警

Status: proposed

## Problem

> 生命周期说明：本提案的三步已由 `686990d` 落地，实现记录见 [后台监控装成独立 launchd 作业](../../implemented/process/2026-11-03-background-monitoring-rollout.md)。该篇持有已交付决策与部署事实；本篇保留设计依据、阈值来源、备选方案与验收要求，不另立第二份 implemented 记录。两篇描述的是同一决策，交付范围以 rollout 篇为准。

采集器现在只有拉取式观测，没有指标历史与告警。`GET /api/ingest-metrics` 提供事件循环、后台任务、具名写事务、正文读取、存储与派生队列；`GET /api/stats` 提供游标、缺口、待处理 hook、准入模式与 magpie 探针。`bun run service status` 提供进程与接口探测。这些入口都需要人工查看。

[容量观测](../../implemented/feature/2026-10-22-atc-capacity-metrics.md)把计数保存在进程内，重启后归零。任务和写事务的 `max_ms` 是启动以来的最大值，没有发生时间。事件循环环形缓冲最多保存 8,192 个样本，按 50 ms 的目标间隔约覆盖 6.8 分钟，阻塞时实际覆盖时间会更长。现有错误日志缺少时间戳，异常结束后往往无法查到现场。

[长窗口验收](../../../../docs/acceptance.md#认领边界长窗口性能验收真实流量2026-11-03)测出了事件循环与会话列表延迟。持续采样能够发现退化，少量带时间的日志才能帮助确认当时哪个操作变慢、失败发生在哪个阶段。

需求限于单机、单用户、一个采集器。首版保存跨天趋势、异常通知和辅助 debug 的日志；不建设独立 tracing 系统，不持续采集调用栈或每条 SQL。

### 与已有记录的关系

本提案沿用容量观测的进程内计数，外部采样器保存历史，不向 trace 库新增监控表。[Worker 决策](../../implemented/architecture/2026-11-02-derive-compute-worker.md)继续持有执行隔离，[准入量测优化](../bug-fix/2026-11-03-admission-storage-measure-block.md)继续持有求和成本的优化。本提案补充观测与日志，不替代这些决定。

## Proposal

分三步交付，先保证异常被发现、发生时间可查，再按实际需求扩展。

### 第一步：轻量指标端点与辅助日志

新增 `GET /api/metrics`，复用现有进程计数，跳过 `measureStorage` 和 `metadataSnapshot`。完整快照的这两个部分都有全量求和，只移除存储求和不足以保证端点轻量。存储值使用准入闸门最近一次量测，附量测时间；没有值时返回未知。派生队列只取组级待办数与最老 dirty 时间，不扫描历史请求。端点自身处理的目标为 p95 小于 10 ms，HTTP 往返另报。

同时补上 `storage.measure` 次数与耗时，并保留以下四类结构化日志，输出复用 launchd 已有的日志出口，不引入日志依赖：

| 日志 | 何时记录 | 帮助查什么 |
| --- | --- | --- |
| 生命周期 | 采集器启动、停止，Worker 失败或重建 | 异常是否伴随部署、重启或线程故障 |
| 错误 | 后台任务或读取失败、事务回滚 | 哪个操作失败、错误分类与重试背景 |
| 慢操作 | HTTP 读取、具名写事务、容量量测超过各自阈值 | 页面慢时，同期主线程是否有长查询、写入或量测 |
| 派生结果 | 每次实际组计算结束，空闲 tick 不记录 | Worker 计算与主线程落库分别多长，结果是整组发布、前缀发布、丢弃还是失败 |

共同字段只保留时间、进程实例、操作名、关联编号、阶段、耗时和结果码。启动日志记录实际加载的代码版本；异步操作使用单调时钟计耗时，墙钟时间用于对齐记录。同一派生轮的 Worker 计算与主线程落库共用关联编号，不用业务会话键充当编号。

诊断日志写入文件，正常启动、停止和重启均保留已有记录，新进程以新的实例标识继续追加，不在启动时清空。生产当前的 launchd 配置已将 stdout 与 stderr 写到 `~/Library/Logs/agent-trace-collector.log` 和 `~/Library/Logs/agent-trace-collector.err.log`；新增结构化日志沿用这条持久化路径。外部采样保存的指标历史同样跨重启保留；归零的只有尚未采走的进程内计数和事件循环样本。

日志按 14 天归档保留，并设总量上限；达到上限时先清理最老归档，报告可查询的最早时间。正常重启不触发日志清理，服务启动也不以覆盖模式打开日志。突然崩溃或断电仍可能丢失尚未写出的末尾记录，不承诺断电级完整性。

HTTP 日志只用具名操作或路由模板；错误使用固定分类，不直接拼接自由错误文本。日志不记录真实正文、请求参数、令牌、账号、会话标题或 SQL 参数。正常快速调用不逐条输出，不为每个消息块或 SQL 打日志；重复错误与慢调用限流，但保留被抑制的次数。

慢操作阈值区分执行位置：同步读取、写入和量测先以 100 ms 为调查起点，Worker 计算单独配置。`jobs.derive` 包含等待 Worker 的墙钟，不能当成主线程阻塞。`published_revision` 的增量是输入修订推进，也不能当成发布次数；派生结果日志记录真实发生的发布。

### 第二步：外部采样、报告与告警

新增 `scripts/monitor.ts`，子命令为 `sample`、`check`、`report`：

- `sample` 拉取轻量指标与 `/api/stats`，保存允许列表里的计数、状态、时间和进程实例。探测失败也写记录，保留超时或状态码，不把缺数据填成正常。
- `check` 按阈值判断，写告警记录并发 macOS 通知。同一规则首次命中通知，持续异常每 30 分钟提醒，恢复时记恢复事件。
- `report` 输出最近 24 小时或 7 天的趋势，标出异常时段、重启和缺失样本，并指向同一时段的诊断日志。报告不自动宣称根因。

调度沿用 launchd，独立任务 `local.agent-trace-monitor` 每 300 秒运行一次。采样和告警写数据目录下的 `monitor/`，按日分 JSONL，保留 14 天，目录 0700、文件 0600。诊断日志也必须设置保留期和大小上限；沿用 launchd 输出时，归档与轮转由外部任务负责，不能让文件无限增长。令牌与探测逻辑复用 [service-support](../../../../scripts/service-support.ts)。

累计次数与总耗时只在同一进程实例内做差，重启后重新建立基线。启动以来的 `max_ms` 不能相减，也不能据此认定当前五分钟出现了同样的尖刺；查具体发生时间要看慢操作日志。事件循环分位数保留采样时间与样本数，不把多个 p99 平均成全天 p99。

初始告警规则如下，持续条件按时间判断，运行一周后再校准：

| 规则 | 初始条件 | 说明 |
| --- | --- | --- |
| 服务不可读 | 当前作业未运行或接口探测失败 | 历史非零退出码只作为事件，不能永久判坏 |
| 事件循环尾延迟 | 连续观测到 p99 超过 100 ms，跨度达到 10 分钟 | 产品目标，报告注明样本窗口可能重叠 |
| 派生积压 | 最老 dirty 超过 10 分钟，且整组或前缀持续没有进展 | 活跃且仍在推进的组先记观察项 |
| 存储模式 | 准入持续 10 分钟不是 `normal` | 显示具体预算或磁盘原因 |
| 采集缺口 | 未闭合缺口持续 15 分钟未减少 | 联查来源游标与任务错误 |
| 容量提醒 | 正文达到实际预算的 90%、空闲低于 100 GB，或 RSS 持续 15 分钟超过 4 GB | 磁盘与 RSS 是待校准提醒值，过期量测标为未知 |

### 第三步：按需扩展

出现多主机、团队看板或远程通知需求后，再评估 Prometheus、Grafana 或通知后端。需要定位具体 CPU 函数或对象泄漏时，按问题运行 profile；增加看板不能补出没有采集的调用栈。

## Alternatives considered

**只持久化 p99、RSS 和累计最大值。** 能够报警，却不能确认慢操作发生时间、具体操作和结果。首版补上错误、慢操作与实际派生结果日志。

**立即安装完整监控栈。** 可以存储时序数据，但应用仍要先记录操作耗时与错误。当前单机规模先用 JSONL、结构化日志和阈值，避免增加守护进程与维护成本。

**记录全部 HTTP、SQL、消息块和调用栈。** 日志量和内容泄露风险都过高，正常请求也会付出成本。首版只记录异常与关键结果，不新增 tracing 框架。

**只在告警后打开日志。** 暂态问题可能已经结束。首版在运行期间持续保留少量诊断日志，详细 profile 再按需要启动。

**把监控写入 trace 库。** 增加被测库写入与保留工作，违背容量观测的归属选择。外部采样器和日志使用仓库外文件。

**直接定时拉完整指标或只看服务状态。** 完整指标现算存储和元数据，会扰动事件循环；服务状态又缺少操作耗时。两者继续用于人工检查，不替代轻量采样与日志。

## Acceptance criteria

1. 轻量端点在代表性合成库上自身处理 p95 小于 10 ms，不执行存储、元数据全量求和，不扫描历史请求；生产 HTTP 往返单列。
2. 用合成数据注入慢读取、慢写、慢量测和 Worker 失败，日志包含正确的操作、阶段、时间、耗时和结果。Worker 慢但主线程正常时，不标为主线程阻塞。
3. 整组发布、前缀发布、丢弃和失败各记录真实结果，同一轮计算与落库可用关联编号匹配。空闲 tick、正常快速 HTTP 和消息块读取不产生逐条日志。
4. 日志限流保留抑制次数，轮转后保留期与大小上限生效，目录与文件符合运行数据权限。合成敏感字符串检查日志与采样中没有正文、凭据、参数或自由错误文本。
5. 重启、探测超时、空样本、休眠和量测过期都有合成验证；报告标出缺口，不跨进程做差，不用累计最大值差定位异常，不将缺数据判成恢复。
6. 阈值用纯函数验证持续时长、恢复和重复提醒。监控停止或失败不影响采集器，生产起停沿用 service 命令。
7. 交付时把运行机制写入架构设计，安装、卸载、日志位置与轮转步骤写入运维手册，真实流量与合成验证分别写入验收记录。
8. 用合成子进程在同一日志文件中追加重启前后两条记录，验证旧记录仍在且实例标识不同；指标历史不因重启被删除。验证保留期与大小上限触发的清理不会被普通启动路径调用，不为这项测试重启生产服务。

## Risks

指标与日志能缩小到接口、后台任务或执行阶段，不能保证直接指出具体代码行。多个操作可能重叠，时间相近只能作为候选原因；查询计划、CPU profile 或堆分析仍需针对性执行。

单条标题或工具配对错误属于语义正确性，可能不触发性能告警。此类问题要查 ATC 已有的来源证据与派生依据，监控日志不复制真实内容。

进程突然崩溃可能来不及输出结束日志，硬故障也可能丢失尚未写出的数据。调度暂停和机器休眠会造成采样空白，首版要明确记录这些限制。

本机通知不能覆盖离机值守，采样器也没有独立的远程看护。报告需显示最近成功采样时间。阈值、慢操作限流与日志大小上限根据首周实际数量调整。
