# Agent Note: 轮次两端阅读:命令直达最终回复

Status: proposed

## Problem

trace 的一种高频读法是问答式的:这一轮我下了什么命令,agent 最后给了什么答复。agent loop 把一轮撑成很多笔请求,中间全是工具循环。中栏轨迹按请求粒度投影,命令和结论隔着几十行折叠行,想从命令走到最终回复只能沿时间线一段段往下翻,自己认哪一笔是收尾。

工具配对解决过一次同类问题:一次工具调用的两端靠 call_id 硬关联,配对页一屏读完,见[Trace Pair 配对页与右栏就地阅读](../../implemented/feature/2026-10-24-trace-pair-rail-page.md)。轮次没有这种硬 ID。那条 note 的「其他配对候选的边界」否决过「模型请求 / 模型回复」,理由是输入含全部历史、单条 User 与单块 Assistant 不是一对一问答。这个否决只覆盖请求级口径,留下一个真实缺口:轮次级口径,跨多笔请求的「命令 → 收尾回复」。维持现状,这个缺口继续靠人眼翻轨迹来填。

2026-10-25 讨论给出的需求原话:点进一个入口,快速看到这一轮我的命令是什么、最终回复是什么;点第二个,是第二轮的命令和最终回复。逐轮翻阅整个会话。

## Proposal

### 轮的判据(已定:收尾信号,不用命令切分)

- 起点:主链上一笔请求的确定新增里出现用户主动文本,即 `request.input_preview_kind = 'delta'`。包装剥除沿用 input-interpretation 的既有判定。
- 终点:沿主链(`prev_req_id` 前驱链)向后,第一条「reply 不含 tool_use」的回复。收尾笔的整条 reply 全文就是这一轮的最终回复。
- 未收尾的轮不呈现:中断在 tool_use、后面再无收尾笔的轮,不进列表。不显式标注「未收尾」,也不造终点。这比[读数缺口诚实行](../../implemented/bug-fix/2026-10-25-reading-gap-honest-row.md)更进一步,连状态行都不给,是讨论里明确的取舍。
- 新命令不切分旧轮:旧轮若未收尾就永远不出现。追加命令的场景下,旧轮的收尾笔可能落在新命令之后(agent 先总结旧任务再处理新命令),这是机械判据的自然行为,接受。

### 排除范围

subagent 会话组(`subagent`/`parent_agent` 字段)、`req_kind='title'`、`purpose_chain='exclude'`、`chain_role='branch'` 都不参与轮次结算,只认主链。

### 实现方式:三层,不落新表

1. **派生层加回复形状位**。request 表加列(reply 的 tool_use 计数或形状枚举),派生时写入;同步与切片两条路径共用,判定进 `derive-decision.ts`。schema 变更,按仓库立场带可执行 backfill 或明确拒绝路径。正文回收(`body_state` 离开 available)后该位保留派生时的值,不清除不重算,与 presentation 的 retained 待遇一致。
2. **读模型即时结算轮次**。queries 层沿主链扫当前已加载窗口,产出轮次列表(起点 req_id 与消息 ord、收尾 req_id)。终点晚于起点,窗口内的起点其终点必也在窗口内,不需要扫全历史。「加载更早」后更早的轮自然出现,与中栏窗口语义一致。不落表的理由:判据还在定型期,固化进 schema 后改判据就要 backfill 重算;判据稳定后再评估是否落表。
3. **HTTP 与前端**。会话窗口响应带轮次列表,行摘要直接用现有 `input_preview`,不新增摘要来源。

### 前端形态(已定:中栏样式不动,只往上添)

中栏 session-head 与第一条轨迹行之间加一条轮次带:

- 一行高度、横向滚动,高度恒定,轮数多少都只占一行。每轮一块:轮号加 `input_preview` 截断,旧轮在左,与轨迹时间方向一致。
- 点击选中,右栏进入轮次内容态;点下一块就是下一轮,逐轮翻阅靠带内顺序点击。
- 无可结算轮的会话整条带不渲染,不占位、不留空态。
- 块上不加「第 N 轮命令」这类二级标签,位置和顺序自己解释。

右栏轮次内容态:

- 身份行换成「轮 N · 命令 req X · 回复 req Y」,上下文靠请求号手动定位,不做跳转,沿配对页的既有立场。
- 正文区两个面板:命令全文在上、最终回复全文在下,默认同时展开,复用 `body-panel` 组件语言。
- 读数 / 正文 / 工具 / 路由页签行在轮次态隐藏,它们是请求作用域。点轨迹任意行回请求态,轮次带选中清除。右栏短暂离开请求态有先例:窗口外请求详情。
- 命令全文读起点请求正文,回复全文读收尾请求的 reply,跨两笔请求的 owner 协调沿用 tool pair 的机制。

轮次带是轨迹的目录层,不是新视图:轨迹本体一行不动。

### 与既有配对边界的关系

配对页 note 否决的是请求级「模型请求 / 模型回复」,本提案不推翻它,是它边界外的第三种口径。那条 note 断言「窄口径的『本次新增输入 vs 本次回复』就是时间线同一请求组内的 User/Assistant 步骤」,在 agent loop 多笔请求的场景这句不成立。实施本提案时,同一变更更新那条 note 的边界段落并互相链接,它保持活跃。

## Alternatives considered

**定义 B:下一条命令切分。** 终点取下一条用户命令出现前的最后一条 assistant 文本。打断与队列输入场景下与定义 A 结果不同,打断的轮两边都找不到收尾文本。讨论选了收尾信号:回复自身形状是证据,不从相邻命令反推。

**未收尾轮显式呈现「未收尾」状态。** 对齐诚实立场的第一反应,讨论中否决:列表里不出现,被中断的命令回轨迹视图找。轮次视图与轨迹互补,不是替代。

**落表 turn pair(仿 tool_call 表)。** 查询稳、天然带反向索引,但判据未定型就固化 schema,回头改判据要 backfill 重算;新请求到达还要把先前未收尾的轮补结算,增量推进比 tool pair 复杂。读模型先行。

**中栏视图切换(轨迹 ⇄ 轮次)。** 讨论中一度推荐,用户否决:中栏保持当前样式,Trace 的直观简洁优先,可以往上添但必须克制。轮次带由此收敛为一行高度横滚。

**右栏第五个页签。** 页签挂在选中请求下,轮次没有请求上下文,作用域错位。排除。

**轨迹行内「直达终点」入口。** 动线要沿轨迹滚着找命令,逐轮翻阅体验碎。第一刀不做;轮次带用起来后,若「读到一半想看结论」的需求仍真实再补。

**头部按钮加浮层列表。** 仓库没有浮层形态,目录层要求常态可见,且多一次点击。排除。

## Acceptance criteria

- 判据单源:回复形状判定在派生内核一份,轮次结算在读模型一份,同步与切片两条派生路径不各写一套。
- 合成数据测试覆盖:纯对话轮(两端同一笔)、工具循环轮(跨多笔)、中断轮不出现、subagent / title / exclude / branch 不参与、正文回收后形状位保留旧值、窗口边界(起点在窗口内即可结算,加载更早后早轮出现)。
- backfill 可执行:对已有真实库,回复形状位有明确回填路径或拒绝路径。
- 前端:轮次带一行高横滚、无轮不渲染;点选后右栏两端默认展开;点轨迹行回请求态并清选中。
- 真实库只读核验:对生产实例跑轮次结算,抽轮人工核对起点命令与收尾回复的对应;浏览器逐轮点击链路显式验收。合成数据验收与真实流量验收分开写。
- 提交前 `bun run verify:notes` 与 `bun run typecheck`;行为变更只跑能对该回归失败的最窄测试。

## Risks

- 收尾信号是推断,不是硬证据。轮次两端没有 call_id 式关联 ID,靠链结构与回复形状推。追加命令时旧轮收尾可能落在新命令之后;被打断的轮直接消失,不记得的人要回轨迹视图才找得到。这些是既定取舍。
- 回复形状位是 schema 变更。仓库有本机真实数据,backfill 落实不到位会卡在「首版前地基优先于兼容」的立场上,实现者要把回填与拒绝路径写清。
- 轮次带与轨迹信息重复。带是目录层,接受这份重复;若阅读价值不成立,撤掉成本小——读模型即时算,没有落表,没有迁移。
- reply 文本与 tool_use 同存的笔按判据不算收尾,要等下一笔。若真实数据存在「说完就停但带 tool_use」的形态,轮会被判成未收尾而不出现。真实库抽验时重点看这类。
