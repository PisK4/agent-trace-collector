# Agent Note: 会话信息汇总:会话事实与证据回溯

Status: proposed

## Problem

打开一个长会话,「这次 agent 干了什么」没有汇聚点。中栏轨迹按请求粒度投影,320 笔请求的会话里想数出动过哪些文件、用过哪些工具、失败几次、用户打断几次,只能人工翻完整条时间线。右栏读数是单请求作用域;session-head 的合计只有 token 与费用,而且是「已加载窗口」口径,不是会话口径。

2026-10-25 讨论的需求原话:为每一条 Session trace 增加信息汇总,先想到四类——工具调用次数(失败数、各工具次数)、用户中断次数(如会话 `98da290b-7df1-4759-9dd4-d7d6482ea858` 里的 "Request interrupted by user for tool use")、核心修改文件(Edit/Write 统计)与参考文件(Read 统计,默认前三、可展开)、引用的 Skill(默认三个、可展开)。随后的扩展讨论把范围放宽:凡库里已有证据、聚合即可得的会话级信号都进候选。

证据大多已经在库里,缺的是汇聚点与三个尚未持久化的事实。生产库 2026-10-25 实测(31 会话 / 3,775 笔请求 / 3,595 次工具调用):

- `tool_call` 表有全部调用与配对状态,但没有参数、没有失败位。`is_error` 在正文块里,只在展开消息时按需读取——[来源投影与字段保真](../../implemented/architecture/2026-10-22-source-projection-and-field-fidelity.md)当时为此否决了长期列,理由是「首版前没有证据表明需要」。
- 中断标记的形状已确证:真实中断以**用户消息文本块开头**的 `[Request interrupted by user for tool use]` 出现。目标会话 1,053 个去重块里 65 处含这个短语,只有 2 处是真实标记,其余 63 处是压缩摘要的引用;全库 tool_result 里 0 处。全文搜索会误报三十倍,判定必须按消息开头的位置前缀做。
- 参数键全库统一:Edit/Write/Read 用 `file_path`,Skill 用 `skill`(配 `args`)——与 trace 视图 `toolSummary` 已认的键名(`command ?? cmd ?? file_path ?? path ?? pattern`,见[轨迹行工具摘要与着色](../../implemented/feature/2026-10-24-pretty-trace-tool-summary-and-tint.md))同一套词汇。
- 会话结构信号全部现成:`req_kind` 已派生(全库 912 笔安全分类器、17 笔标题生成、2,836 笔主链,旁路占 24%);10/31 个会话有子代理,子代理请求 1,877 笔(占全库一半);`attempt_count>1` 共 16 笔。

需求与社区证据经[独立评审](../../../docs/session-trace-summary-review.md)核实,两条口径警示写进定位:OpenTelemetry GenAI 的 `tool_calls` 指标按单次 agent invocation 计客户端执行的调用、子代理归自己的 invocation,与本提案「模型发出的调用、全会话累计」是不同口径,不混称一致;HITL 语境的人介入包括批准、改参、拒绝、补充回答,中断只是其中一小类,本提案不把中断计数称为人介入率。首批定位是**辅助人工评估的会话事实汇总**:计数回答不了任务是否完成、工具是否选对,验收锚定三项阅读任务——快速盘点操作范围、找到值得复核的异常、回到对应原始证据。

## Proposal

### 范围:第一梯队六项,延后项不因可提取就先做

1. **工具调用**:总数、各工具分布、已判定失败数、未知结果覆盖。
2. **涉及路径**:写入尝试(Edit/Write 的 `arg_path`)与读取请求(Read 的 `arg_path`)按原始路径分组,各默认前三、可展开。
3. **显式 Skill 调用**:`arg_skill`,展开区,默认前三、可展开。
4. **已识别用户中断**:事件计数。
5. **全会话 token、费用与缓存命中**:session-head 既有合计行就地升级为会话口径,不在折叠区另立第二处;缓存命中并入该行尾部(资源故事的一部分),分母口径与缺值进悬停。
6. **结构详情**(展开区):主链/旁路笔数、子代理 actor 数与请求数、网关重试笔数、上下文占用峰值、模型足迹(多于一个模型才显示)。

延后到第二梯队(需要先定义口径,不是反对):stop 原因分布(`tool_use` 不是任务轮次,语义要另定义)、TTFT 分位、时长密度。缓存比例、上下文峰值与模型足迹原在此列,2026-10-25 样张评审时按用户决定并入第一梯队:缓存命中不再是孤立百分比,并入资源合计行且分母进悬停;峰值与模型足迹走结构行,模型设「多于一个才显示」的门槛。第三梯队:Bash 命令统计、会话列表行微缩。自动评分、轨迹匹配、数据集对比是独立选型(AgentEvals、Langfuse 会话评分等已有现成能力),本仓不为此提前引入依赖或兼容层。

### 口径定义

- **会话口径**:按 `conv_key` 全量请求,含子代理,与轨迹视图同一导航范围。token 与费用的唯一表达点是 session-head 既有的合计行,**就地升级为会话口径**(替换「已加载相加」),窗口信息由「已加载 N 笔」承载。facts 行原有的「N 笔失败」与「N 笔未取得费用」后缀移出可见文案:失败读数由折叠区承载(工具级),请求级失败在轨迹行已有红色边界,费用缺口进悬停。折叠区不重复任何已表达的信息——同一数字一个家。
- **工具调用计数**:`tool_call` 行数,一行一次调用(发出方唯一,天然不跨请求重复计)。按 `state` 分列 resolved / pending / ambiguous。**失败数 = 已判定结果里 `is_error=true` 的次数**;ambiguous 与未判定既不算失败也不算成功,进覆盖度字段,沿用「缺失不等于成功」的既有立场。
- **涉及路径**:发出的调用不解释成执行或产物——Edit 发出后可能匹配失败或被权限拒绝,Read 的路径可能不存在,Bash 实际改的文件不在 Edit/Write 参数集合里。所以命名是「写入尝试」「读取请求」,不称修改/参考成果;top N 是**高频路径**,不称核心文件,核心程度需要次数之外的评价依据。分组按原始路径(次数降序、并列路径字典序,保证确定性);显示层 basename 折算与悬停全路径沿用轨迹行惯例,同名 basename 并列时显示更多路径段。两组独立统计,同一文件两边都出现是正常形态。
- **显式 Skill 调用**:按 `arg_skill` 分组。命名「显式调用」:技能可以经 system 声明进入上下文而不发生 `Skill` 调用,该计数不暗示技能使用的全貌(能力视图另有覆盖)。
- **已识别用户中断**:派生解释新增用户消息时,文本块 trim 后以 `[Request interrupted by user for tool use]` 开头计 1,落 request 级 `interrupt_count`,会话 SUM。摘要引用、tool_result 内文、块中段短语都不算。界面文案「已识别用户中断」,来源限定为当前支持的客户端标记;无法判定时如实呈现,不冒充 0,也不外推为人介入率。
- **全会话 token 与费用**:SUM(`in_tok`/`out_tok`/`cost`) over 会话全部请求;费用四态沿用,`absent` 计数进覆盖度;分母缺值时不给比例,不给 0。
- **缓存命中**:SUM(`cache_read`) / SUM(`in_tok` + `cache_read`),并入会话合计行尾部;分母口径与缺值进悬停,分母为空时不给数,不给 0。
- **上下文峰值与模型足迹**:峰值取 max(`prompt_tokens` / `prompt_window`) 的整百分点,悬停给公式;模型足迹数 distinct `model_requested`,多于一个才显示,完整清单进悬停。

### 提取:三个事实进派生,单源双写

- `tool_call`(同步模式)与 `derive_tool_result`(切片模式)各加三列:`arg_path`、`arg_skill`、`is_error`。提取函数一份,两条派生路径共用,与 `tool_name` 同一家族:tools 阶段本来就要解块读 `tool_use` 的 id 与 name,顺带读 input 的 `file_path`/`skill`;配对时本来就要读结果消息块做 preview,顺带读 `is_error`。键缺失落 NULL,不猜近邻键。
- 中断计数进输入解释:interpretMessage 逐条解释新增用户消息,判定结果状态处顺带判前缀,写 `request.interrupt_count`(同步)与 `derive_request_result.interrupt_count`(切片),进整组选源体系,不出现两套取值。
- 正文回收后:已提取的事实随配对行保留(`retention_state='retained'` 照旧),没有提取到的行留 NULL。汇总端点不读正文,回收会话的计数与明细照常返回,覆盖度反映缺口。
- backfill 走既有路径:工具与摘要算法号 bump → 全组标 dirty → `drainDeriveEntry` 重算。提取不到的行不阻塞组完成。

### 结构变更:v7 加列迁移,首版前的一次性例外

新列组成结构版本 v7。v6 生产库已经承载 3,775 笔真实记录,而 hook 通路无保留,按[破坏式替换](../../implemented/architecture/2026-10-23-destructive-schema-replacement.md)整库重建等于永久丢正文。所以 v6→v7 做一次加列迁移:全部是可空 `ADD COLUMN`(request 一列、tool_call 三列、derive_request_result 一列、derive_tool_result 三列),不动既有行,迁移单事务提交,失败拒绝启动、不带半迁移状态。这与「首版发布前不提供跨结构升级」的立场关系:加列迁移是一次性例外,不是常设升级通道;首个 tag 之后回到破坏式替换的总立场。迁移完成即 bump 算法号触发重算,老库事实不丢。

### 端点:查询时聚合与证据回溯

`GET /api/sessions/:key/summary`,只读快照内完成,预期毫秒级、以实测为准。不物化会话级表:单会话最大 378 笔、366 次调用,全库 3,595 次,`GROUP BY` 量级很小;物化表要跨组协调代际发布(汇总横跨一个 conv_key 下全部 actor 组),复杂度买不来收益。

响应方向(字段名实现时定):`tools[]`(name/count/paired/error_known)、`files{written[],read[]}`(path/count)、`skills[]`、`interrupts`、`totals{in_tok,out_tok,cost,cost_absent,cache_hit}`、`structure{main,bypass,subagent_actors,subagent_requests,retries,context_peak_pct,models}`、`coverage{calls_total,calls_paired,calls_error_known,calls_fact_known}`。行存在即计数;组 dirty 时返回已发布代事实加 dirty 标志,不猜未完成的派生。

**证据回溯是首批验收,不是附加项**:汇总条目带稳定身份(所在 `req_id` 与调用 `ord` 的定位元数据);失败数直接给出失败调用集合,工具与路径条目点击后按组查询,首屏不返回全部调用列表;复用工具配对页与窗口外请求详情的既有导航;正文已回收的行展示仍有的定位元数据并注明正文不可读。唯一成功标准:能从任一数字回到支撑它的记录。

### 前端:session-head 折叠区

位置在中栏 session-head,`session-facts` 之后、`view-row` 之前,做成 `rail-fold` 语言的折叠行。前提是去重:token、费用、HTTP 失败已由 facts 行表达,折叠区一个都不重复——facts 行的合计**就地升级为会话口径**是本提案对既有 UI 的唯一改动。收起时 summary 一行核心数(路径用去重条数):`366 次工具 · 13 失败 · 2 次中断 · 写入尝试 44 / 读取请求 24 条路径`。

展开后分区,靠分组与明度差解释结构:

- **工具**:六色 tint 的 chip 行(Read 蓝/Edit 橙/Write 紫/Bash 玫红/Skill 黄/Agent 绿,其余中性青灰),chip 内「工具名 次数」。失败数只在非零时以 warn 色出现在对应 chip——「正常态不带装饰性状态,异常才出现标签」的界面常备立场。点击 chip 定位该工具的调用;未判定数等覆盖缺口进 chip 悬停,不占可见文案。
- **涉及路径**:单行流式 chip,写入=橙、读取=蓝,颜色承担分组语义,不设两列与列头,两色之间只留一条细分隔;各前三加同色 `+N` 二级展开,全部路径两三行排完;chip 内 basename 加次数,悬停给全路径与计数,同名 basename 并列时悬停与展开列表补更多路径段;点击定位该路径的调用。
- **显式 Skill 调用**:排在工具区之后,黄色系 chip,前三加二级展开;**没有显式调用的会话整区不渲染,不留空位**。
- **结构**:一行式文本,只显示非零项——主链/旁路与上下文峰值常驻(旁路解释请求总数与主链的差),子代理、重试非零才出现,模型多于一个才显示。零值不渲染是「异常才出现」原则对结构行的应用;不加括号注释,词义说明进悬停。

展开状态按稳定键记忆(既有约定)。打开会话即拉一次汇总,不懒加载。点击定位的交互形态:汇总条目先开右栏条目列表,逐项跳配对页(配对页已支持调用方在窗口外时按需读取该请求),不新造导航。与[轮次两端阅读](../../proposed/feature/2026-10-25-turn-pair-reading.md)的空间协调:那条提案要在 session-head 与第一条轨迹行之间加一行高的轮次带,本提案的折叠区在 session-head 内部,两者不重叠;两条都未实施,先落地者定稿具体间距,后者对齐。布局样张(生产 token、目标会话真实数据、现状与提案对照)已于 2026-10-25 交人工评估,收起行、两列与空区不渲染以样张评审结论为准。

**随本提案的既有界面精简。** 命中率是现状里唯一两处表达的同类比例:读数页「用量与上下文」每笔给一个请求级「命中 X%」(`rail-facts.js` 的 ledgerParts,行内读数加摘要预览各一处)。会话头合计行落地时,读数页的请求级命中行与摘要命中在**同一次变更**里退役——搬家不出现空窗。保留项与理由:入/出/缓读/缓写/费用是请求级原始读数,构成条与图例回答「这笔的上下文被什么占满」,计时四行是时延诊断,窗口外请求详情复用同一函数自动一致;它们与会话汇总回答的是不同问题,不裁。

## Alternatives considered

**直接用 claude-devtools 或 ccusage。** 两者读客户端本地日志(`~/.claude` 等),与本仓以 magpie 请求为单位、三路证据对账的边界不同;正文回收覆盖度、路由尝试、派生代不在它们的输入里;会话阅读主界面在本仓,汇总离开阅读界面就变成第二个工具。会话成本速查可先用 ccusage 交叉验证需求,实现留在本仓。

**读时解压全部正文聚合,不动 schema。** 打开会话时解压该会话全部消息块、现场提取参数与 `is_error`。否决:本库当前最大会话 378 笔、千余消息块,magpie 账本实测单会话到过 1,825 笔,读时解压的量级只会涨,且每次打开都重算;正文已回收的会话整段算不出,汇总从「有缺口」变成「没有」;中断前缀判定还要重跑消息解释,与「读模型不重解读正文」的既有口径冲突。

**物化会话级汇总表,派生完成时写。** 查询零成本,但要跨组协调:一个 conv_key 下多个 actor 组各自重算、各自发布代,任何一组变化都要重算会话行;单会话聚合本身量级很小,物化买不来收益。轮次提案「不落表」的理由是判据未定型,这里的理由是成本不成立——都指向读时聚合。

**中断用全文搜索(`LIKE '%interrupted%'`)。** 实测误报三十倍(65 处命中里 63 处是压缩摘要引用)。位置前缀判定是唯一可靠口径。

**`is_error` 不落列,汇总端点按需读结果正文。** 即读时解压方案的子集,同样被 evicted 与性能否决。这条同时是对[来源投影与字段保真](../../implemented/architecture/2026-10-22-source-projection-and-field-fidelity.md)否决项的反转:当时的理由是「首版前没有证据表明需要长期列」,会话级聚合就是新证据——不读全部正文就数不出失败数。实施时同一变更更新那条 note 的 is_error 段落并互相链接,它保持活跃(它的其余决策不受影响)。

**arg 提取做成独立回填脚本。** 与既有「派生阶段顺带产出 + 算法号 bump + drain 重算」路径重复,还要自己处理增量与重算触发。否决。

**Bash `command` 提取进第一梯队。** 机制上顺路,但命令的展示口径(规范化、去重、是否分类)没有需求边界,先不做;提取函数留键名位,第三梯队再启用。

**会话列表行加微缩指标。** 左栏会变成仪表盘,违背降噪立场。否决,需要时随第二梯队再评估。

**缓存比例与 stop 分布进第一梯队。** 初稿包含,评审指出:缓存比例的分母要处理混合协议与缺值,单出一个百分比会被读成 Agent 好坏评价;`tool_use` 收尾不是任务轮次,stop 分布的语义没定义就上线是数字堆砌。降级到第二梯队,先给有明确语义的异常停止入口。2026-10-25 样张评审时用户要求第一版范围更宽:缓存命中以并入资源合计行、分母进悬停的形态回到第一梯队,上下文峰值与模型足迹随结构行进第一梯队——「孤立百分比被当评价」的顾虑由呈现语境解决。stop 分布维持延后。

**把中断计数叫人介入率。** 初稿借用了社区指标名,评审纠正:HITL 的 approve/edit/reject/respond 我们一项都观察不到,中断只是取消类事件,同名会误导。改称已识别用户中断。

**称「核心修改文件」。** 初稿沿用需求原话的「核心修改」,评审指出按调用次数排出的只是高频路径,核心程度需要调用之外的评价依据;且发出的调用不证明改动落地。改为写入尝试/读取请求。

## Acceptance criteria

- 提取单源:参数与 `is_error` 提取函数、中断前缀判定各一份,同步与切片两条派生路径共用;键名清单与 trace 视图 `toolSummary` 的回退链不漂移(测试锁定 `file_path`/`skill` 的提取与缺键 NULL)。
- 口径测试(合成数据):anthropic 与 chat 两协议形状的调用各提取正确;ambiguous 不计失败;pending 与未读结果不冒充零失败,coverage 如实;中断只认用户消息开头前缀,摘要引用与 tool_result 内文不算;同一条中断消息跨请求重复出现只计一次(按 delta 归属);retained 行计数保留、明细列保留、coverage 反映;evicted 会话的汇总不返回零,返回已有事实加覆盖缺口;token 与费用缺值进覆盖度,不给 0;缓存分母为空不给数;上下文峰值取 max 比值;模型足迹多于一个才出现;路径按原始路径分组,同名 basename 在显示层可区分。
- 结构迁移:v6 库升级到 v7 后既有行不动、新列全 NULL;迁移失败拒绝启动;空库直接建 v7;bump 后 drain 重算把存量会话的三个事实补齐。
- 端点:聚合数值与手工 SQL 对照一致;coverage 各分母自洽;dirty 组返回 dirty 标志;**每个汇总数字可回溯到 req_id 与 ord 的定位元数据**,失败集合、工具组、路径组三类都成立。
- 前端:收起一行核心数;展开分区;top 三加二级展开;失败数为零时不出现失败元素;无 Skill 调用整区不渲染;结构行零值项不出现、模型多于一个才出现;路径区为单行流式双色 chip、无列头;**折叠区不出现 token 与费用,facts 行不含失败笔数与费用覆盖后缀**(缺口进悬停);facts 合计行为会话口径并带缓存命中;点击条目经右栏列表进配对页,窗口外条目走既有窗口外详情;展开态跨重绘按稳定键恢复;正文转义不变;**读数页无请求级命中行,命中率只出现在会话头合计行**(`rail-facts` 相关断言同步更新)。
- 人工验收三任务(真实库,目标会话 98da290b):定位一个失败调用及其结果;列出写入尝试涉及路径并解释覆盖边界;辨认汇总是否完整或过期。合成数据验收与真实流量验收分开写。
- 交付后观察(不阻塞发布):实际复盘中记录哪些数字触发了检查、是否成功找到证据;只被看总数、没有后续动作的指标列为删除候选。
- 提交前 `bun run verify:notes` 与 `bun run typecheck`;行为变更只跑能对该回归失败的最窄测试。

## Risks

- **反转既有否决。** `is_error` 落列推翻了来源投影 note 的一个 alternatives 结论,依据是聚合需求这个新证据。若 review 不接受反转,本提案退回读时解压方案并接受其代价,或整个失败数项不做——失败数是四类原始需求之一,倾向接受反转。
- **定位边界是这个功能最大的失败方式。** 计数回答不了任务是否完成、工具是否选对、某个 Skill 是否改善结果;首批只服务三项阅读任务,文案与命名不得外推成评价结论。超出的评估诉求走独立选型。
- **前缀判定的脆弱性。** 客户端措辞变化(例如无括号变体、其他 agent 的中断形状)会漏计。实测全库只有带括号的一种形状;漏计不误计,新形状出现时扩展判定并 bump 算法即可。
- **branch 双计。** 同一条中断消息若同时出现在两个 branch 的确定新增里,`interrupt_count` 会加两次。窗口极小(需要上下文重写后分叉),接受为已知边界,测试锁定常规场景;真要做指纹去重要等独立需求。
- **v7 迁移开了一个口子。** 「首版前不跨结构升级」的立场被例外一次,未来每个结构变更都会引用这次先例。边界必须写死:仅可空加列、单事务、失败拒绝启动,任何数据搬动类变更不享受此例外,首版后回到破坏式替换。
- **与轮次带提案的实施顺序耦合。** 两条提案都改 session-head 区域,判据互不依赖但布局互相占位;先落地者定稿间距,后者必须对齐而不是各排各的。
- **数字堆砌的反噬没有完全解除。** 收窄后首屏一行,但展开区仍有四组信息;交付后观察里「没有后续动作的指标删掉」要真执行,否则汇总区自己会变成降噪对象。
