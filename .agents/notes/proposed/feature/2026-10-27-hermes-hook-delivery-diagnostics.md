# Agent Note: Hermes hook 投递诊断

Status: proposed

## Problem

Hermes 流量的钩子缺口需要分层判断，不能直接归因成投递丢失。截至 2026-10-27T05:33:18Z 的只读快照，1,242 笔 Hermes 请求里有 210 笔已有关联账本与路由、没有关联 hook 正文（`have=6`、`body_state='pending'`），其中 205 笔已标 `miss_reason='hook_absent'`；等待队列 605 条里 603 条没有 response ID。

`have=6` 与 `hook_absent` 只能证明本行没有已关联的 hook 证据。失败或被取消的请求可能仍触发完成期 hook，但回复为 null、没有 response ID，ATC 无法按 `response_id_norm` 精确关联；单列未知，不按时间邻近强行配对。

投递丢失仍是假设。[magpie 机制研究](../../../../docs/magpie-mechanisms-research.md)在 `开源源码@magpie-2374ffe` 下区分了 HTTP 失败、回复不可用与回调缺失，该源码结论不替代当前安装版的运行验证。本机 magpie 的插件配置写了 `gatewayTimeoutMs=2000`，高于薄插件自身 1500 ms 的总预算、600 ms 单次 fetch 与最多两次尝试；插件仍有独立截止。调大宿主预算只能验证宿主提前终止这一种路径，`ingest_issue` 没有错误也不能排除未到达、请求超时或 HTTP 拒收。

## Proposal

验证按阶段统计，诊断只记录固定码、计数、大小与耗时，不记录正文、令牌与账号：

- 宿主是否调用完成期 hook，是否因宿主生命周期或预算终止。
- 插件是否开始投递，是否发生单次超时、总截止、网络错误或 HTTP 拒收。
- ATC 是否收到并接受 envelope，收到后是否因缺 response ID 或多候选留为 pending。
- 已有账本、路由的请求中，哪些仍未关联 hook，哪些已有正文但回复不可用。

实验取同一截止条件的前后窗口，按 agent、状态码、请求体积与请求类别分别计数。缺口在等待阈值后统计；null ID 回调单列未知。

诊断分两侧。ATC 侧读现有 `request`、`request_evidence`、`pending_hook`、`ingest_issue` 与 `raw_hook` 做窗口聚合；插件侧把投递码写进 `ctx.state.collector_code`，宿主只保存在插件状态里，ATC 不读取。若证据要求插件持久化结果或调整预算，另提代码与合成验证；不承诺所有问题仅靠配置解决。

提高宿主预算不恢复历史正文，也不提供持久投递保证。ATC 既有缺失标注保持原义，历史无正文不因配置变化宣称已恢复。

## Alternatives considered

**仅调大宿主超时后判断丢因。** 插件自身截止、宿主生命周期、HTTP 拒收与无法关联都会表现为请求缺 hook，单一配置实验不足以区分。

**把 null ID 回调按时间邻近配对。** 时间邻近不是身份证据，强行配对会把失败请求的回复挂到别的请求上。

**先修投递再接用途。** 用途识别与投递诊断的证据互不依赖，可以分开交付；缺正文行继续如实保留缺口。

## Acceptance criteria

1. 诊断覆盖宿主截止与插件截止的区别；模拟接收方晚于插件单次截止返回成功，即使宿主预算更大也记录为失败，延迟值以实施时插件预算为准。
2. 窗口聚合按 agent、状态码、请求体积与请求类别分别计数，null ID 待关联项单列未知。
3. 前后窗口使用同一截止条件；缺口在等待阈值后统计。
4. 诊断不落正文、令牌或账号。

## Risks

- 提高超时不恢复历史正文，也不提供持久投递保证；当前没有稳定关联锚点的失败回调仍可能无法对账。
- 窗口里把“缺 hook 证据”写成“从未收到回调”会夸大结论，聚合口径必须保留这一区分。
- 插件侧投递码只存在宿主插件状态里，ATC 侧窗口统计看不到单次超时与总截止的差别；证据若要求跨进程观测，需要另立持久化通道。
