# Agent Note: 中栏按请求新增消息分组

Status: proposed

## Problem

中栏的组回答的是「这一笔请求发生了什么」，读者点开的却是一行消息。读者想知道「这条消息在哪个请求里、那个请求还新增了什么」，组给的是「这一笔请求的输入 + 这一笔的回复」。两个集合不相等，右栏与中栏就对不上。

本提案把这条不变量放在最前面：**组里的每一条内容行（用户、assistant、调用、结果、消息级 System）都能在承载请求的正文里找到，并且属于该请求的可信 delta；顶层 System 与请求级记录是承载请求自己的事实；没有承载请求的末尾回复组除外。** 承载请求指消息所在的那笔请求；产出请求指这条 assistant 消息由哪一笔请求的回复产生。正常 agent loop 里，回复的产出请求是下一笔承载请求的 `prev_req_id`。

### 现场

会话 a58b0a51-0182-4c08-84b0-3dd808dccb91，用户截图所在的窗口（窗口序号取自页面）：

| 窗口序号 | req_id | 可信 delta 的 ord | delta 里的消息（只记角色与块类型） |
| --- | --- | --- | --- |
| 2 | 40057 | [0,1] | 用户命令；消息级 System；没有工具结果 |
| 4 | 40059 | [2,3] | assistant（文本 + 2 个 tool_use）；user（2 个 tool_result） |
| 5 | 40061 | [4,5] | assistant（文本 + 5 个 tool_use）；user（5 个 tool_result） |
| 6 | 40063 | [6,7] | assistant（文本 + 11 个 tool_use）；user（11 个 tool_result） |

40059 的两个结果属于 40057 的两次调用，40061 的五个结果属于 40059 的五次调用。结果消息物理上在下一笔请求的正文里，调用在上一笔请求的回复里。读者看到的「编号 4 的组里最上面两条结果属于编号 2」就是这个结构；「编号 63 显示编号 61 的请求结构」是同一件事的另一面：右栏显示的是 63 自己的结构，但 63 的结构新增里是 61 的回复和 63 收到的结果，而组又把 63 的回复放了进来。读者把「结构新增是上一笔的回复」读成了「右栏读错了请求」。

### 现行口径

[投影](../../../../web/trace-view.js)的 `projectSteps` 对一笔请求投影两类行：可信 delta 里的输入消息，以及这一笔的回复对象。delta 里的 assistant 消息走 `!entry.isInput` 分支被跳过，理由是同一条消息已经作为上一笔的回复投影过。[组装配](../../../../web/app.js)的 `mainModel` 按 `req_id` 组装组，行上的序号是承载请求的序号；右栏 `railFacts` 固定读这一笔请求的详情与结构。三个后果：

- 一次工具往返的两端被拆开：调用行在上一笔的组里，结果行在这一笔的组里。
- 组里的回复行不在本笔结构里：它是本笔的输出，下一笔请求才会把它作为输入带上。
- 本笔结构的新增部分是上一笔的回复加本笔收到的结果；组的内容是上一笔的回复加本笔的结果再加本笔的回复。组与结构没有一一对应。

所以编号 63 与编号 61 的错位不是 off-by-one，也不是结构读错了请求。右栏一直读的是被点中的请求；错的是组的定义与结构的定义不一致。

### 用户给出的判据

2026-10-28 的讨论里，用户用三个场景定下分组应该服从的直觉：

1. 一笔 assistant 消息带 tool call、结果还没回来：右栏应显示这笔 assistant 消息，不显示空的工具结构。
2. 一笔 assistant 消息没有调用：不应出现它的工具结果。
3. 点击一笔消息：不应看到它的回复。

用户同时否决了「保留现行分组、给行加归属标签」：标签要求读者先判断这是上文还是新结果，违反所见即所得。标签把歧义写出来，不消除歧义。

### 分组的需求

- **组是承载请求结构新增部分的可读投影**：组里的每一条内容行（末尾回复组除外）都能在承载请求的正文里找到，并且属于该请求的可信 delta；顶层 System 与请求级记录是承载请求自己的事实。
- **不跳过 assistant 消息**：承载请求新增的每条消息都要出现；上一笔的回复在这一笔的结构里，就归这一笔。
- **没有就不出现**：没有结果块就没有结果行；没有调用块就没有调用行；不按时间或位置补造另一端。
- **点击打开内容本身**：点击一行打开这一行所在的请求结构；末尾回复打开产出请求的回复。不默认打开由两行推导出来的配对页。
- **序号等于承载请求**：行号是这条消息所在请求的窗口序号；末尾回复没有承载请求，取产出请求的序号。
- **回复不在产出请求的组里**：回复作为下一笔承载请求的新增 assistant 消息出现；没有承载请求的回复单独成末尾组。
- **不靠标签解释**：组边界、角色标签与结构本身承担解释，不加二级说明文字。
- **稳定阅读**：末尾组只在会话已完整加载时计算；历史加载不改已显示行的归属、顺序与内容。
- **证据不新造**：分组只用已有的 delta、反向配对、回复视图与已确认前驱，不新增 schema、端点或派生字段。

### 轮次分组为什么答不了这个问题

用户最初提出按轮次分组。评估确认轮次结算不能直接复用：

- 这个会话的 `GET /api/sessions/:key/turns` 返回空表；2026-10-28 只读看到的最新非辅助请求 43914 的 `reply_shape='final'`，但 `chain_role` 仍是 `unknown`，没有结算成轮。
- 轮次是「用户命令到最终回复」的跨请求配对，一个轮可以包含几十笔请求；轮内的工具循环仍然需要请求粒度的行。
- 轮次判据依赖回复形状与路径纯净，回答的是「这一轮在哪收尾」，不是「这一笔请求结构新增了什么」。

轮次带与轮次两端阅读继续有效，见[轮次两端阅读](../../implemented/feature/2026-10-25-turn-pair-reading.md)；本提案不动轮次结算与轮次带。

用户在同一轮反馈里还提了另外四个点：非配对默认读数、工具往返的显示格式、请求结构从尾片读起、用量与上下文只留 basename。它们与分组同批落地，范围表在 Proposal 开头。

### 另外四个点的现场

同一轮反馈的其余四点，现状与问题各记一句：

- **点击落点。** `select-step` 按来源分页签：`source.side==='pair'` 或回复侧的调用进工具页的配对页，请求侧与回复侧的消息进正文，其余进读数。点一笔 User 或 Assistant 消息会离开读数，读者想先看计量与结构时得再点回来。
- **工具往返的显示。** [renderTools](../../../../web/body-view.js) 渲染 `工具名(截断 90 字的 inputText)`。中栏调用行早已按工具分派摘要（Read 给路径与行区间、Edit 给行数变化、Bash 给 description 或命令、Skill 与 Agent 给名称），右栏却把原始 JSON 截断后塞进括号，多数行读不出这次调用要做什么。
- **请求结构的读取方向。** `structure` 状态是 `{next, total, ords}`，首次展开从 ord 0 读 40 条，按钮「加载下一片」。长请求的读者关心的是新增与尾部，而尾部要翻过整个前缀才到；结构列表与折叠摘要在同一个折叠区，滚动位置由内容决定，从头读等于每次展开都先看最早的上下文。
- **用量与上下文里的路径。** 列表行是 `<b>basename</b> <small>目录前缀</small>`，tile 的可见名与弹窗头、合并成员名单用完整路径。右栏宽度固定，完整路径把名字挤成省略号，读者要读的是文件名。

## Proposal

### 范围

本轮反馈一共五个点，第 4 点是本提案的主体，另外四点同批落地，没有「另案」或「不在范围」的例外。

| # | 最初的要求 | 现状 | 本提案的落法 |
| --- | --- | --- | --- |
| 1 | 选中 Assistant 或 User 的 trace，右栏默认读数 | `select-step` 按来源进正文或配对页 | 非配对一律读数，配对页只由显式按钮打开 |
| 2 | 右栏工具往返太丑（优化建议），参考中栏的 `Command Description` | 工具名加截断 90 字的原始 JSON | 工具名 chip 加中栏同一份动作摘要 |
| 3 | 请求结构默认展示最底部 | 从 ord 0 连续读 40 条 | 首读尾片，按钮向前加载更早 |
| 4 | 选 63 显示 61 的结构 | 组是本笔输入加本笔回复 | 组是承载请求的 delta（本篇主体） |
| 5 | 用量与上下文里的文件只显示 basename | 行带目录前缀，tile、弹窗与成员名单用完整路径 | 可见文件名只留 basename，完整路径进 title 与 aria |

第 4 点展开为「分组规则」到「组装、提交与选择」；第 1、2、3、5 点见「其余四项修改」。

### 一句话

中栏的组 = 承载请求的可信 delta 消息；回复不是产出请求的组内步骤，它作为下一笔承载请求的新增 assistant 消息出现；没有被任何请求承载的回复，单独成末尾组。讨论里把这个方案叫 B；B 只指第 4 点的分组方案，本提案的范围是五项，下文不再重复区分。

### 分组规则

| 内容 | 归属 | 行 |
| --- | --- | --- |
| 用户消息、消息级 System、工具结果 | 第一次包含它的请求（承载请求） | 与现行一致 |
| assistant 文本块、tool_use 调用块 | 第一次包含它的请求（承载请求） | 每段文本一行，每个调用一行；thinking 不常驻 |
| 回复对象 | 只在没有承载请求时进末尾组；读数「本次回复」照旧 | 不在产出请求的组里出行 |
| 末尾回复 | 产出请求的末尾组，紧跟产出请求的组 | 只在会话完整加载且没有后继承载时出现 |
| 顶层 System、请求级事实与记录（HTTP 失败、缺正文、截断、未知停止、未收到回复、回调与账本错误） | 产出请求的组 | 事实属于请求，不属于消息内容 |

**末尾组的判定**：

- 窗口已到会话末尾（`window.newerCursor === null`）。
- 请求不是辅助或排除请求。
- 没有已加载的非辅助请求的 `prev_req_id` 指向它，也就是没有后继承载。
- 它之后的已加载行里没有前驱未知（`prev_req_id` 为 null）的请求；未知前驱可能承载这条回复，排除不了就抑制末尾组，避免同一回复出现两次。
- 回复对象可读且 `replyView` 状态为 `ok`，至少有一个文本或调用块。空回复、缺失、部分、非法与多 choice 的说明留在产出请求的组，不单独成组。

**序号与位置**：末尾组紧跟在产出请求的组后；行号取产出请求；同一请求可以相邻出现「新增组」与「末尾组」两个组。末尾组不挂请求级 `aria-current`，它是同一请求的回复，不是第二笔请求。

### 一个例子

同一段会话在本提案下的中栏：

| 组 | 行 |
| --- | --- |
| 2（40057） | 用户命令；消息级 System |
| 4（40059） | assistant 文本；调用 ×2；Tool result ×2 |
| 5（40061） | assistant 文本；调用 ×5；Tool result ×5 |
| 6（40063） | assistant 文本；调用 ×11；Tool result ×11 |

40063 之后还有请求，它的回复出现在下一笔承载组的开头。末尾组只在窗口到会话末尾、且没有后继承载时出现；2026-10-28 只读核对时，会话最新的非辅助请求是 43914（`reply_shape='final'`），它的回复是末尾组的真实样本。带工具调用、还没收到结果的末尾形态见判据 1：末尾组只有调用行，没有结果行。

组 4 里调用与结果同组，结果行的 `参数 → 结果` 摘要来自同组的调用行；组 2 是 40057 的 delta（用户命令与消息级 System），它的回复在组 4 的开头。点击组 4 的任意一行，右栏打开 40059 的结构，选中的消息在结构里。

### 点击、右栏与配对

- 中栏所有内容行与普通记录行的默认点击都进读数：用户、assistant、调用、结果、System、末尾回复一律如此；续读、重试与加载入口保持动作语义。配对页不再由调用行或已配对结果行默认打开。
- 选中消息行时，读数页的请求结构折叠展开（用户之后仍可收起），列表从尾片读起，选中消息高亮并展开详情。选中请求级行或没有选择时，折叠保持用户自己的开合状态，展开时同样从尾片读起。
- 配对页保留显式入口：读数页「本次回复 → 工具往返」里的「配对两端」、工具页，以及消息详情里针对调用或结果块的「配对两端」按钮。按钮只在 call_id 能确认两端时出现；确认不了就不给按钮，不按块序号猜。
- 「本次回复」面板保持请求作用域：它显示承载请求自己的回复，不是选中消息的回复。本提案不改面板顺序；如果实际阅读中它仍被误读成选中消息的回复，再单独评审面板顺序或折叠，不混进分组变更。
- 正文页签与工具页签的请求作用域不变；消息行打开正文时仍定位到该消息，末尾回复定位到回复块。

### 数据与投影

- 无 schema、无端点、无派生字段变更。投影消费 `delta_ordinals`、`read.entries`（assistant 消息的文本、调用与结果块）、`detail.tool_results`（反向配对，带 `call_id`）、`detail.tool_calls`（产出请求的调用与 `exec_ms`）、`prev_req_id` 与 `replyView`。
- `projectSteps` 去掉两件事：跳过 delta 内的 assistant 消息、投影本笔回复。新增 assistant 文本块行、调用块行，以及独立的末尾回复投影；回复投影不再由普通组调用。
- 调用块的工具名与参数复用现有块解析（`messageBlocks` 与 `ToolCallView` 的同一份提取），不另写协议分叉。
- 调用行的配对坐标与 exec 读数跟随内容的产出请求：用 `prev_req_id` 的已确认前驱元信息按 `call_id` 匹配；前驱不在窗口、调用 ID 不匹配或元信息未读到时留空，不猜归属。assistant 文本行的推理读数只在承载 delta 只有一条 assistant 消息、且 `prev_req_id` 可读时挂到该消息的第一段文本；其余情况留空。
- 结果行的 `参数 → 结果` 摘要优先用同组调用行，找不到再回退现有 `callOf`（产出请求缓存）。结果在 delta 里、调用不在同一 delta 的跨片情况保留反向索引归属，不补造调用行。
- 可信 delta 未知（`deltaOrdinals` 返回 null）时保持现行「会话归属未确认」路径：按请求原文展示所有消息，不推断分组。分支与辅助请求保持现行记录行。

### 组装、提交与选择

- `GroupModel` 的组身份从数字 `reqId` 改为字符串键：`req:<id>` 与 `tail:<id>`。DOM 的 `data-req` 仍是数字，用于定位、URL 与读取；[键控提交](../../../../web/trace-dom.js)的节点复用、锚点与 `scroll-group` 按字符串键工作。
- [组装配](../../../../web/app.js)按行顺序输出「组、末尾组、组、末尾组……」；末尾组的行键沿用 `reqId:reply:*` 与 `reqId:call:*`，与承载组的 `reqId:message:*` 不冲突。
- 末尾组的后继集合由窗口内已准备详情的 `prev_req_id` 构建；列表行不带这个字段，不为此新增接口。
- 新增内容行的稳定键：assistant 文本 `${reqId}:message:${ord}:text:${blockIndex}`，调用 `${reqId}:message:${ord}:call:${blockIndex}`；结果沿用 `${reqId}:message:${ord}:result:${blockIndex}`。块序号取消息内容块位置；调用行的配对坐标（产出请求的 `owner_req` 与 `ord`）单独保存，不拿块序号冒充调用序号。
- 末尾投影单独缓存（按 req_id），不写进 `retainedSteps` 的组投影槽；版本作废时与组一起标 `stale` 或隐藏，不把旧回复冒充当前。
- [选择转换](../../../../web/selection.js)的 `select-step` 不再按来源改页签，固定读数；`resolveSelectedSource` 的 request 侧分支处理 assistant、调用与结果，reply 侧分支只服务末尾组；配对页由 `open-pair` 显式动作触发。
- 读数结构选中的消息取自当前步骤的 `source.messageOrd`（与当前请求同号时），与折叠内点击的 `structureSelected` 合并；展开时读取尾片。
- URL 的 `trace` 仍是请求号，末尾组与产出请求同号；页签默认读数。

### 其余四项修改

#### 非配对一律读数

- `select-step` 的 `railTab` 固定 `facts`，`toolOrd` 与 `toolOwner` 置空；`pair` 的推导和 `resolveSelectedSource` 的 `side:'pair'` 分支删除。承载组里的调用行与结果行按请求消息解析，点击看到消息本身；末尾组的调用行按回复块解析，仍进读数。
- 配对页只从 `open-pair` 进入：读数页工具往返行的「配对两端」、工具页列表、消息详情里调用与结果块的按钮。按钮只在 `call_id` 能确认两端时出现；确认不了不显示，不按块序号猜。
- `select-message`（结构列表与右栏下拉）不改，它不离开右栏。
- URL 页签默认 `facts`；点击不再写 `tab=body` 或 `tab=tools`，显式配对仍写 `tools`。
- 测试：中栏每种行（用户、assistant 文本、调用、结果、System、末尾回复）点击后 `railTab==='facts'`，且 `select-step` 不产生 `ensure-pair`；只有「配对两端」按钮或工具页列表才进配对页。

#### 工具往返改用中栏摘要

- 现状：`renderTools` 把每次调用渲染成 `工具名(截断 90 字的 inputText)`；中栏的调用行用 `summaryParts` 按工具分派（Read 的路径与行区间、Edit 的行数、Bash 的命令、Skill 与 Agent 的名称等）。两处格式不一致，右栏截断后的原始 JSON 多数不可读。
- 改成中栏的同一份摘要：工具名 chip 保留，参数段用 `summaryParts(name, inputText).args`；行内不出现原始 JSON，完整 `inputText` 进 chip 的 `title`，完整参数仍在配对页。未命名工具沿用「未命名工具」。
- 摘要分派在 `trace-view.js`，`body-view.js` 不能反向 import（`trace-view.js` 已 import `body-view.js` 的 `toolTint`）。把 `summaryParts` 及其分派与回退链移到叶子模块 `web/tool-summary.js`，中栏与工具往返共用同一份；摘要用到的 `clipChars`、`baseName`、`nonEmpty`、`firstNonEmptyLine` 一并迁到叶子，`clipChars` 仍服务步骤标题，所以 `trace-view.js` 也从叶子取它，不能留在原处让摘要反向依赖。`trace-view.js` 继续导出 `toolSummary` 作为转发，现有测试与消费者不必同时改。具体文件边界在实现时按依赖方向定，约束只有两条：分派只有一份，`body-view.js` 不 import `trace-view.js`。
- 工具往返行仍是调用列表，结果不搬进来；「配对两端」按钮、多候选警告与折叠键不变。
- 测试：`tests/body-view.test.ts` 断言 Read、Edit、Bash、Skill 的行文本与 `toolSummary` 的参数段一致，已知工具的行内没有原始 JSON，`title` 含完整参数；`tests/trace-view.test.ts` 的现有摘要语义不变。

#### 请求结构尾片优先

- 现状：`structure` 状态是 `{next, total, ords}`，`loadStructure` 从 0 读到 40，按钮「加载下一片（已读 next / total）」；长请求要翻很多片才看到新增消息。
- 改成已读区间：状态加 `back`，`[back, next)` 是连续已读窗口；首读取 `back=max(0,total-40)`、`next=total`，读尾片；「加载更早」读 `[max(0,back-40),back)`，成功后 `back` 前移。`ords` 仍是结构读到的序号并集；`entries` 仍是全部缓存消息的并集，delta 定点读与空洞标记不混进游标。
- `total` 从已读元信息取；为空时先读 `0/0` 元信息（`readRequest` 已有这一步），仍为空才读第一页拿 `total`，再读尾片。读取仍走 `GET /api/requests/:id/body?from=&to=`，不加端点。
- `structureMoreParts` 的按钮改为「加载更早（已读 back–next / total）」，显示条件是 `back > 0` 且正文可读；按钮放在消息列表上方（紧接折叠摘要），与向前加载的方向一致，错误说明也在上方。空态文案从「展开后从开头读取前 40 条」改为「展开后从末尾读取最近 40 条」。
- 正文页签的「请求消息」段现在也按 `structure.next` 判断未读和按钮；同一游标改动要覆盖 `app.js` 的这段，不能只改读数页。两处按钮与文案同源，避免一个说「加载更早」、一个说「加载下一片」。
- 尾片到达后，结构列表的滚动位置落到 `scrollHeight`，最新一条可见；「加载更早」前插时按首条可见消息的序号与偏移恢复，不把读者拉回顶部。选中的消息详情替换列表，不涉及这段滚动。
- 选中消息的详情仍由 delta 缓存提供，不依赖尾片包含它；列表是缓存并集，选中的消息在尾部之外时带空洞标记显示，详情照常展开。
- 测试：首读尾片区间、向前分页、`back` 到 0 后按钮消失、空洞不推进 `back`、`total` 未知的两次读取；`structureFoldHtml` 与正文页签的按钮文案、位置与 `unread` 条件。

#### 用量与上下文只留 basename

- 现状：`context-map.js` 的列表行渲染 `<b>basename</b> <small>目录前缀</small>`；tile 的 `name` 用 `itemLabel(it)`，文件是完整路径；`context-detail.js` 的弹窗头 `s.label` 与合并成员名单也用完整名字。
- 改成显示层折算：文件与记忆类条目的可见名字取 basename；`turn`、`turns`、`more` 的固定叫法不变；工具、结果、对话等非路径名字原样。完整名字只进 `title` 与 `aria-label`。列表行的目录前缀 `<small>` 删除，`itemDir` 退役。
- `itemLabel` 继续返回完整名字或固定叫法，作为 title 与 aria 的来源；新增显示名折算给可见文本，不把 `itemLabel` 改成 basename，否则 title 会丢掉完整路径。
- 身份键 `iidOf` 继续用完整名字；点击、选择与明细查询的匹配不变。`context-detail` 的 `entry.path` 是协议路径（`messages[N]` 等），不是文件路径，不改；条目里的工具名与角色原样。
- 弹窗头与成员名单的文件名同样取 basename，完整名字进 `title`；弹窗的 token、类别色与关闭行为不变。
- 测试：`tests/context-map.test.ts` 断言 tile、列表行、title 与 aria 的三份名字，并断言 `turn`、`turns`、`more` 的固定叫法不变；`tests/context-detail.test.ts` 断言弹窗头与成员名单；`iidOf` 与点击键的断言不变。

## Alternatives considered

**A：保留请求加回复的分组，给行加归属标签。** 用户否决：标签要求读者先判断这是上文还是新结果，违反所见即所得；组的内容仍来自两笔请求，右栏仍无法一一对应。标签只是把歧义写出来，不消除歧义。

**A′：保留分组，右栏按回复的产出请求打开结构。** 点击回复行会打开上一笔的结构，与行上的承载序号不一致；同一组里，结果行与回复行会打开两笔不同的请求；结果行仍然没有同组的调用行。否决。

**C：按调用方分组，把 assistant、调用与结果归到发起调用的请求。** 与 B 的消息集合相同，组号取调用方。代价是组的内容跨两笔请求结构：assistant 与调用在调用方结构里，结果在下一笔结构里；右栏只能显示一笔结构，组无法与结构对齐，需要第三个「步骤视图」才能同时看两端。用户判据 3 在 C 下仍要跨请求，否决。B 与 C 的差别只在组号归属与右栏能否对齐一笔结构；B 选承载方，是为了让组号、结构、点击三者同源。

**轮次或链段分组。** 轮次在本会话结算不出任何轮；链段需要新的读模型与窗口语义，段的内容仍不等于一笔请求的结构，对「本次请求结构新增了什么」答非所问。链段可以作为后续的目录层，不替代请求组。否决作为本次分组。

**服务端投影出组，前端只渲染。** 现有数据已经足够；新增读口会复制一份投影规则与缓存失效逻辑，还要证明比前端投影快。否决。

**跨分支去重承载的 assistant 消息。** 分叉与重试会让同一条 assistant 消息出现在多条分支的 delta 里；去重需要消息身份，并隐藏「这条消息被两笔请求发送过」的事实。B 接受重复：组是请求的结构，不是消息的档案。否决去重。

**末尾回复在每个窗口都显示，作为下一条承载请求的预览。** 加载更多会让末尾组消失、同样的内容在下一组重现，已显示的行改归属。改为只在会话完整加载时计算末尾组；历史加载不会让已显示的末尾组消失。否决每窗预览。

**用回复对象把回复放进下一组。** 回复对象与下一笔请求里回显的 assistant 消息通常相同，但来源不同：回复对象有停止原因、用量与耗时，回显消息可能剥掉 thinking、加 cache_control、被客户端改写。B 以请求结构为准，回复对象只服务末尾组、读数与请求级事实；混用两个来源会在不一致时无法解释。否决。

**默认点击配对页保留给已配对结果。** 用户判据要求点击消息看到消息本身；配对页改为显式入口。否决默认配对。

**工具往返：右栏复制一份摘要分派，或把格式化函数作为参数传进 `renderTools`。** 复制会让两份规则漂移，新增工具时只改中栏不改右栏；传参要把函数穿过 `renderReply` 与每次调用，签名变宽，测试多一个注入点。改为把分派移到叶子模块，两侧 import 同一份。否决前两种。

**结构：保留从头读，加「跳到末尾」按钮。** 首次展开仍先读 40 条前缀，读者每次都要多点一次；结构折叠的首屏仍是最早的消息，与「默认看新增」相反。否决。

**结构：列表倒序渲染，尾部在上。** 不换读取方向，只换显示顺序；消息序号在列表中从大到小，与轨迹、正文和读取的升序惯例相反，读者要在两种序里切换。否决。

**上下文路径：保留完整路径，靠列宽省略号与悬停。** 现状就是这样；右栏宽度下省略号从路径中段截断，文件名常被截掉，读者看到的不是名字。否决。

**上下文路径：固定显示末两段（父目录/文件名），像中栏的工具摘要。** 能区分一部分同名文件，但右栏比中栏窄，两段更早触发省略；用户明确要 basename。否决，同名混淆留作重开条件。

## Acceptance criteria

- 合成投影：delta 内的 assistant 文本与调用各出行；同一 delta 的结果与调用同组；调用没有结果时不出现结果行；assistant 没有调用时不出现调用行；结果没有同组调用时不补造调用行；未归属与分支路径不变。
- 组与结构一致：对每个普通组，组内所有 request 侧行的 `source.messageOrd` 都在该承载请求的 delta 中；普通组不出现 reply 侧行；末尾组是唯一例外。
- 末尾组：会话完整加载时，每个没有后继承载的非辅助链末请求各有一个末尾组；未完整加载时没有末尾组；加载更早历史不改已显示末尾组；辅助请求不出末尾组；前驱未知的后续行存在时抑制对应末尾组。
- 点击：中栏所有内容行与普通记录行的默认点击进读数；选中消息行时结构折叠展开并选中该消息；`select-step` 不产生 `ensure-pair`；配对页只在显式入口（「配对两端」或工具页）后打开。
- 工具往返：每行的可见文本与中栏同一工具的摘要参数段一致；已知工具的行内没有原始 JSON，`title` 保留完整参数；结果不搬进列表；配对按钮与多候选警告照旧。
- 请求结构尾片：首次展开读 `[max(0,total-40), total)`；「加载更早」读前一片并前移 `back`；`back` 到 0 后按钮消失；空洞不推进 `back`；`total` 未知时先取元信息再读尾片；按钮在列表上方；尾片到达后列表落在底部，加载更早保持阅读位置；空态文案说从末尾读取；读数页与正文页签的按钮文案一致。
- 用量与上下文：文件与记忆条目的 tile、列表行、弹窗头与成员名单只显示 basename；完整名字在 `title` 与 `aria-label`；列表行没有目录前缀；`iidOf`、点击与明细查询不变；`entry.path` 仍是协议路径。
- 真实会话只读核对（a58b0a51-0182-4c08-84b0-3dd808dccb91，不把正文写进 fixture）：组 4 含 assistant 文本、2 个调用与 2 个结果；组 2 是 40057 的 delta（用户命令与消息级 System），没有回复行；点击组 4 的调用行，右栏是 40059 的结构且选中 `messages[2]`，页签是读数；工具往返行的 Read 摘要与中栏一致；编号 63 与编号 61 的错位不再出现。尾片读取的区间与分页由合成用例覆盖；真实会话若存在消息数超过 40 的请求，再补一次只读核对。
- 命令：`bun test tests/trace-view.test.ts tests/selection.test.ts tests/trace-commit.test.ts tests/trace-anchor.test.ts tests/web.test.ts tests/reader-store.test.ts tests/trace-pair.test.ts tests/body-view.test.ts tests/context-map.test.ts tests/context-detail.test.ts` 与 `bun run typecheck`。
- 无 schema、端点、依赖与派生版本变化；真实库只读，测试只用合成数据。
- 文档：[架构设计](../../../../docs/architecture-design.md)的轨迹阅读布局、工具往返、结构分页与上下文标签按新口径重写；覆盖关系表里的部分取代逐条落成互链与句子更新；验收结果另记 [acceptance](../../../../docs/acceptance.md)。

## Risks

- **末尾组在完整加载时插入。** 开始锚定的窗口加载到会话末尾后，先前未显示的链末回复会以末尾组插入对应组之后，下面的行位移。按键控提交与锚点补偿处理；这是新增内容，不是已有行改归属。
- **同号两组相邻。** 末尾组与产出请求的新增组同号相邻，读者可能以为是编号重复。组边界与回复行区分它们；如果真实阅读中仍误读，再评审末尾组的序号槽（留空或换标记），不在本提案先加标签。
- **分支重复。** 同一条 assistant 消息在多条分支的承载组里各出现一次，读者可能觉得重复。接受：组是请求的结构，不是消息的档案。
- **产出请求查找降级。** 窗口从会话中间开始、前驱不在窗口或 call_id 不匹配时，调用行没有 exec 读数与配对状态，结果行回退现有 `callOf`。这是诚实降级，不猜归属。
- **回显消息与回复对象不一致。** 中栏显示请求里的消息，读数「本次回复」显示回复对象；两者不同时按各自来源标注，不合并、不互相覆盖。
- **回复形状记录与回复正文分属两组。** 截断、未收到回复等记录留在产出请求的组，回复正文在下一组或末尾组；文案按「本笔请求的回复」写，读数完整性面板保留同一事实，避免读者漏读。
- **读数「本次回复」的误读。** 选中消息时它仍显示承载请求的回复；本提案不动面板顺序。实际使用中若仍被误读，另案评审。
- **默认读数让正文页签多一步。** 点消息不再直接进正文；正文仍在读数页的消息详情、正文页签与工具页签的既有入口。用户已选择「非配对一律读数」，本提案不保留按来源自动切正文的旧行为。
- **组键从数字改为字符串。** `trace-dom` 的节点复用、锚点与 `scroll-group` 都依赖组键；键错会让选择丢失或节点重复。测试覆盖 `req:<id>`、`tail:<id>` 与只有一笔请求的会话（承载组与末尾组同号）。
- **工具往返与中栏的路径折算不同。** 中栏的工具摘要按[路径显示末两段](../../implemented/feature/2026-10-27-trace-path-two-segments.md)显示 `父目录/文件名`；第 5 点的 basename 只作用于用量与上下文。工具往返复用中栏摘要，因此也显示末两段，这是刻意的；实现时不要把 `baseName` 统一成 basename，否则中栏的行会退化。
- **上下文同名 basename。** 只留 basename 后，不同目录的同名文件在列表与 tile 上无法区分；完整路径在 `title` 与 `aria-label`，点击明细仍按完整名字查。真实阅读里如果同名混淆明显，再评审「仅冲突时补一段父目录」（`session-view.js` 的 `pathLabel` 已有按需补段的先例），不在本批先加。
- **尾片读取的 total 未知。** 元信息未到时多一次 `0/0` 或第一页读取；首屏在尾片到达前只显示「正在读取消息结构…」。读取失败保留重试，不退回从头读。
- **结构按钮上移与列表落底。** 「加载更早」从列表下方移到上方，折叠区高度与右栏滚动位置会变；列表首次落到底部、向前加载保持首条可见消息的位置，两个滚动容器（右栏与 `.msg-list`）都要测，别让重绘把读者拉回顶部。
- **尾片读取与分组同批。** 结构游标从连续前缀改为已读区间加空洞，`structure.next` 的旧语义退役；如果拆开落地，选中消息的详情仍可由 delta 缓存提供，但结构列表暂时看不到它的位置。第 1、2、5 点可以独立提交，第 3 点与第 4 点同批、分开验收。
- **轮次带为空的会话。** 末尾组仍可能显示工具调用回复；读者可能把末尾组的调用当成「这一轮的收尾」。角色与配对状态说明它是调用，不是最终答复。
- **文档旧句。** 现行文档里的「中栏样式不动」「调用进入工具四页」「结构从开头读取」「工具往返显示工具名与截断参数」等句子在实施前仍成立，实施时必须同批更新并互链，否则新旧口径并存。
