# Agent Note: schema v3 拒绝原地升级，回填走独立脚本

Status: implemented
Archived: 2026-10-24

## Problem

语义指纹、折叠摘要、新的前驱判定与链角色改变的都是派生结果，不是正文。旧库里的派生结果按旧口径算错，就地改写只会把错误固化下来：补列能让新代码读得下去，但 `request` 的增量、标题、工具配对、前驱关系与链角色仍然是错的。另一条路是删库重来，可正文块只在本库里，`raw_hook` 的原文早已按保留期清掉，删库等于永久丢掉这些请求的正文。

## Decision

这条策略在 schema 升到 v3 时确立；当前版本为 v6。`openStore` 遇到低版本直接报 `schema_rebuild_required`，不提供启动时自动升级；遇到更高版本报 `schema_version_unsupported`；空库首次打开时建到当前版本。v5 起没有跨结构迁移：旧库由运维删除后重建，见[旧库删除重建](2026-10-23-destructive-schema-replacement.md)。[scripts/backfill-fingerprint.ts](../../../../scripts/backfill-fingerprint.ts) 只覆盖 v3/v4 时代的列补齐与派生重跑，不会把旧库带到 v6；它自己开 SQLite 连接，绕过版本检查，补齐块指纹与预览列、链角色相关列与索引，再整库重跑派生与工具配对。脚本可重复执行，只处理还没有指纹的块；解不开的块指纹留空，派生把它当成不可比。

版本常量与拒绝逻辑见 [src/store.ts](../../../../src/store.ts)，表结构见 [src/schema.sql](../../../../src/schema.sql)。

## Alternatives considered

**原地迁移并保留旧派生结果。** 旧结果是错的，保留它等于把错误当成基线。补列只能让新代码读得下去，不能让增量、标题与工具配对变对。

**删库重来。** 正文块只在本库，`raw_hook` 原文已按保留期清理，删库会永久丢掉这些请求的正文。错的只是派生结果，正文本身仍然有价值。

**读时重算，不提升 schema 版本。** 每次查询都要重算全库，查询延迟不可控；而且旧库缺少指纹列与预览列，读时重算仍要先补结构。

**让 `openStore` 自动升级。** 自动升级会把结构升级与派生重算混在一次启动里，失败时既没有明确错误，也没有可重跑的回填入口。把升级留成显式脚本，失败可见、可重跑。

## Consequences

- 旧库不能直接启动，必须先停采集器再跑回填。这是有意的摩擦，避免错误派生被继续使用。
- 回填脚本绕开 `openStore` 的版本检查，因为它的职责就是升级旧库；它自己开连接、自己设 WAL 与 `auto_vacuum`。
- 回填脚本在补列后写版本号，派生重算在其后执行；中断时库已经标成当前版本，直接启动会使用未完成的派生，必须重跑脚本。v5 起没有这条路径：旧库直接拒绝打开，不存在由回填脚本带过来的 v5 库。
- v3 与 v4 的旧库在回填脚本的时代可以保住已有正文；v5 起按破坏式替换处理，正文与派生结果一起丢弃。
- 回填按块是否已有指纹判断是否重算，重复执行不会重复计算；派生全量重跑，耗时随库大小增长。
- 回填后的关系分布与标题来源会打印出来，用来核对这次修复改变了多少；它不是验收门槛，只是变更前后的对照。
