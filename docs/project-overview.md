# agent-trace-collector 是什么

> 实施范围更新（2026-10-21）：本文仍保留早期方案中的三处旧约定：版本越界拒绝启动、第一版摄入 direct、实时 trace 作为补充。这三项已由[当前架构](architecture-design.md)调整为 `>=0.1.1294 <0.2.0` 外降级启动、direct 默认关闭、只使用 hook/账本文件/路由文件三路证据；through 费用另由 API 补齐。开工以架构和[实施总入口](superpowers/plans/2026-10-20-collector-implementation.md)为准，下文对应旧表述不作为实现要求。其余产品定位继续有效。

## 一句话

一个只服务 magpie 的本机 LLM 请求记录器：每经过 magpie 网关的一笔请求，在这里留一条记录，详情页展示的就是那笔请求本身。

## 它挂在什么位置

```text
agent ──> magpie gateway ──> provider
               │
               ├── gateway hook ──────> 本项目（请求体与回复）
               ├── usage ledger ──────> 本项目（状态、用量、路由 id）
               └── routing/*.jsonl ───> 本项目（路由决策）
```

它挂在数据面的旁边。没在运行时，Agent 的请求照常走完，只是这一段时间没有新记录，查询页停在最后一次写入的位置。名字里的 collector 指汇聚，不指代理。

## 为什么重新做一个

两个前身，问题不一样。

AVA（agent-visualization-analysis）已经做成了一套完整的可视化系统，采集、存储、前端都有。它的问题有两处：承担的范围太大，同时对流量的把控不如 magpie。会话归属一直要 AVA 自己判定，判不准，这是当初最痛的地方。

ATA 是另一个未完成的轨迹项目，定位接近，卡在展示格式上。它是事件账本，一轮对话由 `turn.started`、`message.upserted`、`tool.upserted`、`turn.ended` 等多个事件拼出来，看的时候要先还原成一次请求，才能知道模型当时看到了什么（`ata/schema.py:4-29`，路径相对 ATA 仓库）。

新项目算 ATA 的重写版本。不继承它的 schema，不背兼容包袱，重叠的功能按新显示单元重新设计。AVA 的存量数据不导入，切换后历史从零开始。

## 记录单位是请求，阅读入口是对话

主实体是 LLM request，顶层一条记录对应一笔客户端发给 magpie 的请求，带上请求体、回复、agent、会话、模型、状态、用量、耗时、路由去向。magpie 内部可能多次尝试 provider；这些尝试作为请求的明细保存，不额外增加顶层请求数。账本中的 `handed_on` 行也是尝试明细，不能每行算一笔请求，或按 `route_id` 去重时丢掉费用。源码依据见 [机制与复用边界](magpie-mechanisms-research.md) 的多次尝试一节。

会话、Agent、模型、日期都是查询出来的视图，不存聚合行。界面左侧选择一段对话，主区默认按对话顺序展示整段会话：每一笔新增的用户消息，紧跟该笔的 assistant 回复，工具调用与结果各自收成一行，点击回到对应请求。切换「请求账本」后，每笔请求收成一行，展开可读该笔的完整请求结构、本次回复、路由与尝试。右侧固定显示当前选中的 Request 的 Response 读数：首字、总时长、输出速度、用量与缓存、上下文组成、路由去向与三条通道的完整性。页面标明当前第几笔及共记录几笔 Request。未确认会话归属的请求独立列出，不因字段都为空而合并。

请求是保存与检查的单位，对话是默认导航入口。最新请求可能包含重发的历史，但压缩、裁剪或上游前序响应引用会使它缺少完整对话原文，不能将其称为完整会话。更早请求的失败、重试与用量仍保留在各自记录中。最新 Trace 缺正文时显示缺失原因，不自动用旧请求替代。要看某个 Agent 一天的用量，把它当天的请求加起来。

这条选择带来三个后果。

**存储必须做内容复用。** Anthropic 与 OpenAI 都是全上下文重发，第 N 轮请求的 messages 数组包含前 N-1 轮的全部内容。按请求存全文，一段 N 轮的对话要占 O(N²) 字节，其中真正新增的内容只有 O(N)。轮数越多，重复占比越高。做法是按内容哈希去重：请求表存行的身份与元数据，块表存去重后的文本片段，两者多对多。AVA 的 blocks 与 record_blocks 两级表做的正是这件事，这个结构值得保留，它和 AVA 范围过大的问题无关。

**不拆工具调用。** 工具调用是请求体里的一个元素，不独立成实体。详情页保留脱敏后的客户端协议结构，避免展示时重新拼接。hook 的观察位置在后续 middleware、脱敏和协议转换之前，不能保证它与每次 provider 尝试的最终输入逐字节一致。

**汇总放在查询时。** 不预存总量、平均值、按天合计这类聚合值。用量逐笔记录，需要汇总时相加。

## 数据从哪来

三条通道，各自补别人的缺失。

| 通道 | 拿到什么 | 拿不到什么 |
| --- | --- | --- |
| magpie gateway hook | 客户端协议请求体、合并后的回复、success、agent、session、model、stream、cwd；失败时回复可能为 null | 请求头、流内事件、每次 provider 尝试、route_id、conv、subagent；回调也可能缺失 |
| 用量账本 `/v1/magpie/usage/requests` | 状态、用量、route_id、response_id、provider、账户 | 请求与回复正文 |
| 路由历史 `~/.config/magpie/routing/` | 已记录的候选顺序、尝试、规则、亲和性与 prompt 结构 | 窗口过滤并非全部留痕；只能读盘，30 天滚动 |

当前方案由 hook 拿客户端协议的请求对象与合并回复，账本补权威元数据，路由历史补决策与上下文分析。实时 `/v1/magpie/trace` 也有路由结构，但环形缓冲很短。magpie 另有可选的归一化会话录制、OTLP 正文导出与 S3 归档，各有内容、保留和部署限制，不能把当前三路方案解释成 magpie 只有这三种能力。详见 [机制与复用边界](magpie-mechanisms-research.md)。

连接靠两个键：

- `response_id` 把 hook 记录接到账本行。实测一千六百余条带 response_id 的 hook 记录全部命中，其中约 2.4% 要去掉一侧的 `chatcmpl-` 前缀才算同一个值。
- `route_id` 把账本行接到路由历史。实测一万七千余个全部命中。

两组数字的精确值、采集时间与统计口径见 [magpie-integration-research.md](magpie-integration-research.md)。它们随使用增长，不在本文重复。

账本里的 direct 行是 magpie 从 Codex、Pi、ZCode 等 Agent 自己的会话文件里读出来的调用，本机约占账本的三分之二。这类行照样建记录，但没有正文、没有 route_id，只有约两成带 response_id。界面上要标出这一类，不能当成采集失败。

本项目不读 Agent 自己的会话文件。direct 行是 magpie 读完之后写进账本的，本项目读的是账本。这顺带满足了 AVA 那条禁止扫描 `~/.claude` 与 `~/.codex` 的约束：确实没有扫，扫的是 magpie。

## 与 magpie 的绑定有多深

深到可以把 magpie 的接口面当成这个项目的输入规格。

身份判定采用 magpie 已经输出的结果。agent、session、conv、subagent 从实际提供它们的通道补入；hook 的上下文不含 conv 和 subagent，不能把空字段当作没有会话或没有子代理。本项目不解析 User-Agent，不实现 conv 哈希，不维护 Agent 名单。magpie 的 agent 归属来自字符串匹配，任何客户端都能用自定义 token 把自己命名成一个新名字，所以这个字段按标签用，不当身份凭证。字段接入面的源码依据见 [机制与复用边界](magpie-mechanisms-research.md)。

hook 的九个上下文字段、请求体、合并回复与 success 是正文通道的输入；账本与路由结构提供关联、用量和决策。不设计通用的 trace 摄入协议，不预留接别的网关的适配层。

代价是 magpie 升级可能改载荷形状、改账本字段、改路由历史格式。应对办法有三条：

- 启动时探测 magpie 版本，超出已验证区间就拒绝启动。已验证的版本目前是一个点：0.1.1294。
- 每条记录存下采集时的 magpie 版本，事后能区分数据由哪个版本采得。
- 接口形状的假设集中在一处，版本变了只改那一处。

## 第一版做什么

做：

- 常驻进程，只监听 `127.0.0.1`。
- 接收 magpie hook 落脱敏后的协议对象，轮询账本落元数据，及时摄入路由历史并保留上下文分析；实时 trace 作为补充。上游历史会滚动，不能等用户打开详情时才首次读取。具体取舍见 [机制与复用边界](magpie-mechanisms-research.md)。
- SQLite 存储，正文按内容哈希去重。
- 一个网页：请求列表、请求详情、会话视图。详情页展示请求体与回复原文，结构化解析只做辅助。

不做：

- 不做代理，不转发、不改写、不拦截任何 LLM 流量。
- 不做 magpie 之外的任何数据源。
- 不做 AVA 数据导入。
- 不做告警、指标看板、多机聚合。
- 第一版保持独立进程加薄 hook。Bun hook 技术上能做 I/O 与持久化；独立运行的理由是保存、补齐和查询需要自己的生命周期，不能把可靠性寄托在有界回调上。完整 UI 嵌入插件页的取舍见 [机制与复用边界](magpie-mechanisms-research.md)。

## 已知边界

- hook 是 best-effort。账本或路由可能证明某笔请求已发生，但正文缺失；三路都没有观察到的请求则无法计数。请求统计应以已保存的观测范围为限，缺正文单独标明，不能把 hook 覆盖率当作总请求量。
- 历史从零开始。账本能回补的元数据止步于 magpie 开始记账的那天（本机是 2026-10-12），正文一条都补不回来。第一版的时间轴会有一段只有骨架、没有内容的区间。
- direct 行只有元数据，没有正文与路由决策。
- conv 是内容指纹，会随首条消息变化，也会随 magpie 的脱敏设置变化。它只用来聚合同一段对话的开头，不当去重键。
- 浏览器直连 magpie 网关不可用：localhost 来源拿不到 CORS 响应头，预检返回 404。网页前端必须走本项目自己的后端。

## 名词

- **请求**：主实体，一笔客户端提交给 magpie 的请求，可包含多次上游尝试；direct/reported 记录按其来源另外标识。
- **session**：客户端自己声明的会话 id，magpie 原样记录。
- **conv**：magpie 根据首条用户消息生成的会话指纹，只在没有 session 时使用。哈希输入的字节处理仍有源码与旧实测解释待复核，见 [机制与复用边界](magpie-mechanisms-research.md)；本项目直接采用输出值。
- **trace**：本项目的展示单位，等价于一笔请求。
