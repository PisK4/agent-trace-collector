# 插件系统必要性评估

评估日期：2026-11-05。代码基准：`732d281`，Bun 1.4.4、macOS arm64。本文是评估意见，尚未改变项目决策、实现或生产配置；[插件指引](plugin-guide.md)中的 v2 仍是提案。评估时仓库另有未提交改动，本轮没有触碰。此后 master 前进到 `74acfa4`：`732d281..74acfa4` 里 `src/plugins`、`src/queries`、`src/body.ts`、`src/main.ts`、`src/read-contract.ts`、`web/reader-store.js`、`web/todo-tab.js` 没有差异，新增提交是 Hermes 会话适配器、owner 起始窗口判据、会话来源标签与容量验收记录。本文仍以测量时的 `732d281` 为基准。

## 结论

Tracery 现在适合保留仓内模块、静态登记和按 Agent 区分的 Parser，暂缓把它们发展成通用的外部 Feature 插件系统。当前社区 Parser 运行时建议从默认交付中撤出；若仍希望支持本机实验，可以作为显式启用的实验能力保留，但需要先处理下文的队列、预算和输出上限。没有必要为了支持未来社区市场继续实现 v2，也不应为了证明机制有用而新增搜索页签。

Todo 的需求已由用户在 2026-11-05 的补充讨论中明确：用户下达命令后，Agent 主动创建任务列表，并随着 trace 推进更新任务，经历待开始、进行中和完成状态。列表创建后需要持续可读，没有更新的请求不应让列表消失。按这个标准，当前实现没有完整运行正确：它能折叠同一已结算轮内的更新，却不支持运行中的状态读取，也不能在没有更新的新轮次继承列表。优先事项是修正这项持续状态阅读能力；单次工具参数展示不能替代需求。暂不据当前轮次覆盖直接建议移除或降级 Todo 页签，布局应在正确的生命周期能力上评估。

性能判断也需要分开：静态登记本身开销很小，没有社区包时也没有新增周期任务。当前 Todo 读取则有明确的重复工作，在合成场景中从不足 1 ms 增长到约 146 ms p95。此前秒级后台尖刺有独立的容量扫描、封口摄入与派生证据，不能归咎于插件；这不影响 Todo 自身仍需控制读取成本的结论。

## 先从产品需求判断

[README](../README.md#why)把 Tracery 的用途写得很具体：保存实际请求、查看消息与系统提示、定位失败或重试、比较不同 Harness。现行实现还要处理多来源认领、正文回收、派生修订和持续采集。这些事实能否保存正确、页面能否及时读到，是系统的首要价值。

插件系统解决的是另一组问题：外部作者需要独立发布能力；用户需要按本机环境安装或卸载；维护者不愿把每种可选解释都纳入核心发布。仓内模块化已经可以支持分工、测试、静态选择与普通 PR。只有独立分发带来的收益超过清单、执行生命周期、失败恢复、版本与安装维护成本时，才需要运行时加载。

原始[插件提案](../.agents/notes/proposed/architecture/2026-11-04-plugin-system-and-todo-feature.md#alternatives-considered)明确记录了首版双轨和日后社区市场的意愿，这个目标有出处。但本轮能找到的交付证据仍只有一个内置 Feature 和四个 Parser；[已有生产验收](acceptance.md#真实流量验收2026-11-05)记录社区目录不存在。没有查到独立外部贡献被发布流程卡住的实例，也没有安装量、使用频率或持续维护者证据。不能把没有查到写成永远不会有需求；它足以支持暂缓承诺通用协议。

删除测试能说明哪些抽象已经有用。拿掉四家 Parser 的适配入口，形状分支会重新散进读取代码，复杂度还在，因此 Parser 有价值。拿掉通用 Plugin 登记外壳，当前只需保留一份 Todo Parser 数组；拿掉外部包运行时，内置 Todo、第五页签、轮次与其他四栏仍可工作，只失去免改仓库安装第三方 Parser 及其线程超时保护。两者的必要性不同。

## 四种机制如何选择

| 形式 | 信任与失败处理 | 发现、安装与性能 | 维护成本与适用时机 |
| --- | --- | --- | --- |
| 仓内普通模块 | 审查过的源码；异常可捕获，同线程同步死循环无法靠计时器中断 | import 明确，无清单与跨线程复制 | 最低；当前一个阅读 Feature 首选 |
| 仓内静态登记 | 与普通模块相同；通过统一 Interface 选择不同 Adapter | 登记数组可发现，可静态开关，运行成本很小 | 低；多个真实实现需要相同分派时使用，四家 Todo Parser 已满足 |
| 本地外部包 + Bun Worker | 当前与宿主同权限；可以终止超时线程，仍共用进程资源 | 清单发现，改清单后重启；首次加载和 IPC 有成本 | 中高；确有独立安装、发布需求后再引入 |
| 进程外插件 / 权限沙箱 | 独立进程改善崩溃和资源隔离；文件、网络权限还需要操作系统限制或受限运行时 | 协议、序列化、进程监督与分发更重 | 最高；确有运行不可信代码或更强隔离需求时评估 |

进程外执行本身不会自动限制文件和网络权限。当前 Bun Worker 也不能称作权限沙箱。Parser 不拿数据库句柄、只返回 DTO 是好的 Interface 约束；外部代码仍可主动使用宿主权限，文档已经承认这一点。

静态登记与普通模块可以并用：把差异留在小 Interface 后，把数据库、身份、读取与展示规则留在拥有它们的模块中。没有必要因为一个目录名叫 `plugins`，就同时承诺动态加载、通用视图模型和兼容周期。

## 什么时候重新引入外部插件

不要把达到三个插件或五个插件当作硬门槛。至少两个独立、实际使用的可选能力，可以检验共享 Interface 是否成立，但数量本身不能证明独立分发有价值。相反，即使只有一个企业内部 Parser，确实需要独立安装和维护，也可能足以支持一个很窄的外部接口。

建议以后每个外部插件提案都回答下列问题，前四项缺证据时先做仓内模块：

1. 具体解决哪个阅读问题，现有工具详情、条目列表或搜索能否解决？提供合成输入和预期结果。
2. 谁需要独立发布和安装，为什么普通 PR 或静态登记不能满足？社区愿景不能代替一个具体受阻案例。
3. 哪些内容确实跨实现变化？Interface 应先由实际差异验证，不能先规定所有能力都输出 list、tree 或 facts 再找例子填满。
4. 可读覆盖如何计算？以真正能取得所需事实并生成有用结果的请求或会话为分子，不能只数工具名命中次数。
5. 宿主提供哪些事实、身份与修订，插件是否需要重扫正文、改派生或取得额外权限？缺事实时先补所属核心模块。
6. 输入、输出、单项同步耗时、总执行时间、排队、内存与取消如何有界？超时按完整读取算，不能只限制一个内部步骤。
7. 关闭后是否不再取数、不再执行、不再展示槽位？异常、部分缺失、回收和重建是否能被明确区分？
8. 安装、诊断、恢复和版本变化由谁维护？对外承诺前要有真实安装及失败恢复验收。

这些是本报告的建议，尚未替换[插件指引的七条判据](plugin-guide.md#21-七条准入判据)。

## 现行准入规则需要怎样收紧

| 现行判据 | 评估意见 |
| --- | --- |
| 只读 | 适合作为当前阅读扩展的范围；只读查询仍可能长时间阻塞或复制大量正文，必须同时证明工作量有界 |
| 独立读取契约 | 输入、身份和结果应清楚；能复用已有读取时不新增 HTTP 路由，独立函数也无需自动升级成 Feature |
| 独立槽位 | 不能把占一个页签当成价值证明；扩展也可以放在已有工具视图，页签数量不应由插件数量决定 |
| 可整体关闭 | 当前不成立得足够完整：服务端禁用只得到空 Parser，前端页签和读路径仍在，社区认领也未与 enabled 联动 |
| 核心持有信任 | 取数、转义、身份与调度由核心持有合理；对外部包的文件和网络限制只是可信代码约定，运行时没有强制 |
| 不改核心语义 | 保留；需要改变身份、轮次、actor 或保留策略时，应由对应核心模块处理，再重新评估可选展示 |
| 可合成测试 | 必要但不足；还要覆盖跨轮状态、部分失败、切会话、禁用和大正文，当前窄测试未覆盖这些反例 |

指引中的七条全过并不能推出现在就应建立动态插件机制；缺一条也不意味着功能应自动放进核心。没有阅读价值的功能可以放弃，需要 HTML 执行或额外权限的提案可以拒绝，不能把核心当作插件准入失败后的默认去处。

## 当前各项能力的处理建议

| 内容 | 建议 | 依据与重新评估条件 |
| --- | --- | --- |
| Todo 的四家 Parser | 保留仓内适配 | 数组快照、编号文本、按主题增量、按索引增量确实有差异；共享折叠入口有实际用途 |
| Todo 独立页签 | 先按完整生命周期修正能力，再评估布局 | 持续查看任务状态有明确用途；当前已结算轮覆盖不足不能直接证明独立位置没有价值 |
| 社区 Todo Parser 包 | 推迟默认支持 | 当前只扩展已知 Todo，未证明独立安装需求；若继续保留，先补运行预算与恢复能力 |
| Web 搜索聚合 | 先做阅读用例，暂不实现外部 Feature | 已有搜索卡；需证明查询历史、重复搜索或证据对照提供新增价值，425 次调用不能证明应多一个页签 |
| Skill / Plan | 继续使用现有工具阅读 | 未证明现有入口无法满足；不用为了增加第二个插件迁移它们 |
| Subagent、归属与轮次 | 核心负责事实与关系 | 它们影响可读身份和可信状态；未来可选展示可以消费这些事实 |
| 数据源适配器 | 保留自身静态 Adapter Interface | 来源形状确实变化，但摄入失败、游标、版本与回填由摄入模块负责，不并入页面插件运行时 |
| 正文、路由、计费、回收、鉴权、读取调度 | 核心能力 | 直接承担事实与运行可靠性，不交给当前阅读 Parser 包 |

Todo 应展示所选 trace 位置对应的任务列表：创建之前没有列表；创建后继承上次状态；有更新时替换全量快照或应用增量；明确完成后保留完成状态，不能因没有新调用而清空。历史位置不能显示未来更新，当前执行位置也不能强制等到最终回复才显示。列表按会话与 actor 隔离，生命周期可以跨请求和用户轮次；只有来源明确重置、清空或替换时才改变相应内容。工具详情可以作为更新来源入口，但不能替代持续任务状态。

不建议为尽快扩大覆盖而放宽 `final`、actor 或前驱判据。若主要需求是实时任务状态，可以另选当前请求的读取时点，不必强依赖已经结算的轮次。选择请求时点仍需正确处理历史快照、增量和失效，不能直接把查询参数从 turn 换成 reqId 就视为完成。

## Todo 的可用覆盖与正确性

本轮没有重新读取生产库。以下覆盖数字引用[2026-11-05 02:08 的验收快照](acceptance.md#真实流量验收2026-11-05)：915 次 Todo 调用、131 个会话、139 个 `(conv_key, actor)` 组；其中只有 3 个会话结算出轮次，只有 1 个 zcode 会话的已结算轮内读到了 Todo。3/131 约为 2.3%，实际读到 Todo 的 1/131 约为 0.8%。这些是当时的样本覆盖，不是当前生产覆盖率，也不是用户点击率。

这组数据证明当前页签把读取前置条件限制在了少量已结算轮，不能用它衡量完整 Todo 需求的价值。pi 和 droid 当时没有 `final`，在 Parser 之前就无法进入可读轮次。增加 Parser 数量没有消除这个限制；按持续生命周期要求，应先纠正这一读取范围，再测真实可用覆盖与使用收益。

本轮用真实读取函数、合成 SQLite 和客户端 store 复现了下列问题；未修改实现：

| 场景 | 当前结果 | 阅读后果与代码位置 |
| --- | --- | --- |
| 第 1 轮 pi create，或 omp init；第 2 轮 update / done | 第 1 轮 ready，第 2 轮 absent | 每轮从 `latest=null` 开始，缺少上一轮列表；不能表示第 2 轮结束时的完整状态。[读取编排](../src/queries/todo-by-turn.ts#L127)、[pi](../src/plugins/todo/parsers/pi.ts#L18)、[omp](../src/plugins/todo/parsers/omp.ts#L24) |
| 同轮先得到快照，下一笔外部 fold 抛错 | ready，保留早先快照 | `latest` 非空优先于 failed，过时中间态被当成轮末结果。[返回优先级](../src/queries/todo-by-turn.ts#L145) |
| 同轮先得到快照，下一笔正文回收 | ready，保留早先快照 | 同样隐藏后续证据缺失；不能证明列表完整。[返回优先级](../src/queries/todo-by-turn.ts#L145) |
| A 会话读取完成，再切到 B；保持待办页签且没有选轮 | store 仍持有 A，渲染输出包含 A 的任务 | 代次只拦迟到回写，没有清除完成值；`hasTurn` 只在 idle 分支检查。[切会话](../web/reader-store.js#L470)、[渲染](../web/todo-tab.js#L11) |
| 同一身份连续读两次 | 两次实际 transport 调用 | 身份字符串用于阻止不同身份的迟到结果，不是完成缓存，也没有同身份在途合并。[loadTodoByTurn](../web/reader-store.js#L382) |

前两个增量 Parser 在同一轮 create 后 update 的现有测试可以通过，不能据此推断跨轮状态正确。用户补充的生命周期定义已经确定这里应展示某个 trace 位置的持续任务状态。全量快照型在没有更新的下一轮也会显示 absent，这不符合已创建列表应延续的要求。

## 按完整生命周期补测

补测基准为 `472d5c3`。脚本使用合成累积消息前缀，经正式 `persistBody`、`drainDerive`、`listTurns` 与 `getTodoByTurn` 读取，没有手工指定轮次、tool_call 或派生状态。zcode、droid 和 omp 的输入都通过 Anthropic 合成载荷进入统一工具调用解释；这次验证状态重放，不声称重新校准了各家真实来源协议。与首轮合成读模型测量分开记录。

| 检查 | zcode | droid | omp |
| --- | --- | --- | --- |
| 同一用户命令内，多笔请求依次创建、普通工具、进行中、完成，最终回复后读取 | completed，符合 | completed，符合 | completed，符合 |
| 尚未创建列表的已结算轮 | absent，符合 | absent，符合 | absent，符合 |
| 创建列表后的已结算轮 | pending，符合 | pending，符合 | pending，符合 |
| 下一轮只有普通工具调用，没有 Todo 更新 | absent，不符合应继承 pending | absent，不符合应继承 pending | absent，不符合应继承 pending |
| 后续轮更新为进行中 | 全量快照读出 in_progress，符合 | 全量快照读出 in_progress，符合 | absent，跨轮缺少初始化列表 |
| 后续轮更新为完成 | 全量快照读出 completed，符合 | 全量快照读出 completed，符合 | absent，跨轮缺少初始化列表 |
| 完成之后的下一轮没有 Todo 更新 | absent，不符合应继承 completed | absent，不符合应继承 completed | absent，不符合应继承 completed |
| 完成后回看创建时的历史轮 | pending，未混入未来状态 | pending，未混入未来状态 | pending，未混入未来状态 |
| 创建、推进后仍在执行，尚无最终回复 | 无已结算轮，读取 absent，持续状态需求未满足 | 同左 | 同左 |

这 27 个生命周期检查中，16 个结果符合预期，11 个未满足。它们是评估脚本记录的行为检查，脚本正常退出只表示收集完成，不代表全部通过。跨请求不等于跨用户轮次：当前一轮内的多笔请求折叠已经成立，不能笼统地称它不会随 trace 更新；缺失的是运行中读取、无更新延续和跨轮增量重放。

Pi Parser 还缺少完成语义：当前代码只认 create 和 update，create 写 pending，update 固定写 in_progress。补充合成探针在 update 中加入 `status: completed`，结果仍为 in_progress；这只验证实现忽略该字段，不声称字段是 Pi 的真实完成协议。无论这个探针的实际协议含义如何，现有两个分支都无法从空状态生成 completed。修复前仍需按真实工具契约核对完成动作、状态字段与任务身份，不能自行发明动作名称。

原始脚本与结果在 `/tmp/atc-plugin-evaluation-20261105/lifecycle.ts`、同目录 `lifecycle-results.json`。本次没有读取生产库、打开真实页面或修改实现。报告对单次工具展示与移除默认页签的建议已按用户明确的生命周期需求修正；关于是否需要动态外部插件运行时的评估仍应单独判断。

## 读取路径与查询计划

一次 Todo HTTP 读取会进入 `getTodoByTurn`，解析主 actor，调用 `listTurns` 重新结算整个会话，再选择轮号、查起止时间和区间请求，读取这些请求的 `tool_call`，最后按请求读取正文与折叠。没有先按 Todo 工具名筛选；即使全部是 Read 等无关工具，也会读取对应请求正文。`foldRequest` 为了取得回复里的工具参数，还调用完整正文读取，连历史消息块一起解压。[读取编排](../src/queries/todo-by-turn.ts#L59)与[正文读取](../src/body.ts#L250)可核对。

`listTurns` 的查询属于既有机制，插件合并只把 `mainActorOf` 改成导出。但 Todo 每次显式读取都重新调用它：扫描本会话主 actor 的请求、建立前驱关系、结算全部轮次，并为全部已结算命令取 ordinals。本轮的命令形状走 `delta`，每个命令又完整读正文。不能把这个成本全算成新写的算法，也不能因为算法已存在而忽略新增调用造成的重复成本。[轮次结算](../src/queries/turns.ts#L92)不接收 Todo 目标轮作为提前停止条件。

合成单轮两笔请求的生产入口观测到 14 次 SELECT；100、500、1,000 轮且目标轮两笔时分别为 311、1,511、3,011 次。后者对应这组数据的 `3 × 轮数 + 11`，不是适用于所有输入形状的固定公式。主 actor 被选择两次，其中一次来自 `listTurns` 内部。

对实际执行 SQL 跑 `EXPLAIN QUERY PLAN`，结果如下。没有发现这些查询对全库的无条件全表扫描；瓶颈是有索引的会话范围读取、逐轮正文读取与重复解压。

## 合成性能实测

数据库均由测试 fixture 新建，测试结束关闭并清理。性能种子直接构造已发布的读模型，先断言可结算轮数；不把写入和派生成本计入读取。正文历史是重复字符组成的共享块，容易压缩，不能代表高熵文本、冷盘或生产并发。首次读取也不是操作系统冷盘；每场景预热 3 次后顺序采样。SQL 计数和计划另取一次，计时不带代理插桩。

表中的 p95 是单次函数墙钟耗时，包含同步查询、解压与 Parser，未计 HTTP、网络、JSON 响应和浏览器布局。不同场景分别采样，不能用两列中位数相减推导精确增量。

| 合成场景 | 样本数 | Todo p50 / p95 / max（ms） | 既有 listTurns p50（ms） | 空 Parser p50（ms） |
| --- | ---: | ---: | ---: | ---: |
| 1 轮、2 笔、1 KiB 历史 | 60 | 0.080 / 0.474 / 1.107 | 0.025 | 0.056 |
| 100 轮、每轮 2 笔、1 KiB 历史 | 40 | 1.948 / 2.334 / 2.471 | 1.957 | 1.800 |
| 500 轮、每轮 2 笔、1 KiB 历史 | 25 | 9.253 / 11.188 / 12.800 | 9.141 | 8.729 |
| 1,000 轮、每轮 2 笔、1 KiB 历史 | 20 | 18.069 / 19.698 / 20.230 | 17.008 | 17.792 |
| 1 轮、32 笔工具请求 + 1 笔 final、1 MiB 历史 | 20 | 8.176 / 8.801 / 8.825 | 0.214 | 8.133 |
| 1 轮、128 笔 Read + 1 笔 final、1 MiB 历史，无 Todo | 15 | 31.568 / 33.859 / 33.859 | 0.318 | 34.402 |
| 500 轮、每轮 2 笔、1 MiB 历史 | 15 | 119.898 / 146.284 / 146.284 | 128.688 | 128.471 |
| 1 轮、128 笔 Read + 1 笔 final、4 MiB 历史，无 Todo | 12 | 86.885 / 90.595 / 90.595 | 0.660 | 89.017 |

空 Parser 使用 `todoByTurnWithParsers(..., [])`，不含生产入口额外解析 actor 的一步，因此不适合比较微秒级差异；它证明移除 Parser 后仍然执行轮次和正文读取。500 轮大正文的 `listTurns` 本身是同步函数，max 132.104 ms，这是本轮直接测到的单次同步工作量。外层 `async` 或 Worker Parser 都不能中断这段同步计算。

与历史使用的 15 秒响应验收尺度相比，Todo 的 19.7、90.6、146.3 ms p95 约占 0.13%、0.60%、0.98%。这只说明本轮没有测到秒级 Todo 请求，不意味着交互成本可以忽略：146 ms 已超过常用的 100 ms 即时反馈目标，而且主线程同步工作会延迟同期采集与其他 HTTP。15 秒是历史服务探针与验收使用的尺度，本轮没有在 Todo 客户端或服务端发现一个强制的 15 秒总 deadline，不能把它当作实际保护。

小样本和最坏输入要分开。当前实现没有总工作上限，不能从表中最大 146 ms 推导最坏情况也是 146 ms；会话长度、历史正文、工具请求数继续增加时成本仍会增长。

## 客户端与关闭行为

未选中 Todo 时，`select-turn` 不产生 `read-todo`；选中 Todo 后才产生。`select-tab` 只有在已选轮次时才发 Todo 读取。没有新增 Todo 轮询、预取或每次渲染取数。第五个按钮仍会随右栏头部一起生成，两个前端模块静态加载；所以无交互取数成本为零，不代表安装了这部分代码后的全部成本严格为零。

Todo 使用现有 `reader-store` 和 `read-scheduler`，没有直接 Fetch 旁路。调度默认活动 4、待发 64，会话取消可以中止网络，但切轮次或切页签没有独立取消旧 Todo 任务；旧读仍可能继续消耗服务器资源。每次显式读取都先 loading、再通知完成，两次通知各触发 `renderRail`；即使期间切到其他页签，当前回调仍会重绘右栏。它没有完成缓存或同身份请求合并，重复点选会重读。

关闭机制还有两个缺口。服务端 `enabled=false` 或移除内置登记，只能让 `parsersOf` 返回空数组，不能阻止核心查询；前端的 `RAIL_TABS` 是独立登记，也不会消失。社区清单装配使用登记 id 而不检查 enabled，外部认领也可以继续提供 Todo。因而指引所说的整路关闭目前只覆盖部分内置计算，不是完整开关。

纯 HTML 生成测量中，500 条待办生成 63,457 B 字符串，p50 0.028 ms、p95 0.036 ms、max 0.277 ms；这个数字不包含 HTML 解析和 DOM 布局。按模板可数出约 1,502 个元素（section、ul、500 个 li 和 1,000 个 span），当前 DTO 没有限制条数。实际 DOM 增量、浏览器布局、焦点保持和滚动体验本轮未测。代码复用了右栏同身份滚动恢复，但仍会整体重建内容与头部；不能把已有滚动代码写成 Todo 的真实页面验收通过。

## 社区运行时的收益与成本

当前能力仅是 `api: 1` 的本地 Parser 包，必须认领已经登记的 Feature，今天只有 Todo。新页签、新 Feature 的事实信封、通用视图、`pluginRead` 和 `/api/plugins` 都未实现。给已有 Todo 增加 Agent 适配与独立发布一种新阅读功能，收益规模不同。

启动阶段读取一次清单并建管理对象；首次相关 fold 才起 Worker 和 import。没有社区包时不启动 Worker，没有每 tick 工作；默认仍有一次清单探测、少量对象，以及相关读取里对空数组的查找。显式 `communityPlugins:false` 可以跳过这层装配。生产没有包的历史状态下，把持续后台尖刺归因于社区 Worker 没有证据。

独立运行时审查用合成包取得以下读数。它们来自审查脚本 stdout，未另存结构化原始结果，不与前文有 JSON 留存的 Todo 测量混为同一数据集：

| 场景 | 实测 |
| --- | --- |
| 无包 load + create + close | 单次约 0.088 ms |
| 首次小包 fold，含起线程与 import | 约 4.56 ms |
| 热 fold | p50 约 0.01 ms，p95 约 0.04 ms |
| 完整合成 Todo 读取 | 内置 p50 约 0.07 ms；社区热读约 0.09 ms，首次约 1.70 ms |
| 40 个并发 fold，各自忙等 5 ms | 总计约 200 ms，串行执行 |
| 配置 120 ms 超时 | 首次约 123 ms 超时，同包后续约 0.01 ms 直接失败，其他包继续 |
| 返回 200,000 条待办 | fold 约 104.2 ms、主线程校验约 1.4 ms，全部被接受 |

Worker 有实际收益：能够终止外部 Parser 同步死循环，同线程普通模块做不到；本地包也能绕开源码合入与重新发布。但当前一个 Worker、一个 FIFO 队列共用全部包，没有队列上限或取消；1.5 秒超时从任务出队后计算，按每笔请求的一次 fold 计算，不包含队列等待，也不是整轮读取预算。N 个均在期限内完成的慢 fold 可以累计接近 `N × 1.5 秒`，排队另计。四个浏览器活动槽不能限制其他客户端或服务端全局任务数。

DTO 校验只检查类型，没有条数、字符串或总字节上限。跨线程复制、主线程校验、JSON 响应和 DOM 生成都可能承受大输出。Worker 没有文件、网络、子进程或内存权限限制，包共享进程资源；因此只能说隔离了部分抛错与超时，不能保证任意包的失败不影响其他页签和采集器。入口路径校验也不是权限沙箱。

这些问题不要求现在就建设更复杂的插件平台。推迟外部运行时，可以同时避免公开承诺一个尚需补全的协议。若继续保留实验入口，最低完成条件应包括全局有界队列、完整读取 deadline、取消、输入输出大小上限、失败身份和可恢复性、禁用后不执行，以及与前文部分失败和状态生命周期一致的测试。

## 建议的收缩与撤退路径

以下是后续实施建议，本轮没有执行：

1. 暂停 v2 Feature 包、通用渲染器与新增默认插件页签。将其视为待验证方向，不继续承诺兼容周期或计划自动推进搜索 Feature。
2. 先修 Todo 生命周期和结果诚实性：切会话/离开/刷新清空完成值；显示前匹配当前身份；后续失败或缺失不能返回无提示的完整 ready。
3. 按用户已明确的完整生命周期读取 Todo：以 trace 中选定位置为时点，按会话与 actor 从可信快照重放增量；没有新更新时延续旧状态，完成状态保留。运行中的列表不以最终回复为前提，历史位置不混入未来更新，缺失与重置分别处理。
4. 收缩外部运行时：先确认实际安装者；目前证据只证明曾经没有社区目录，不能保证现在仍然没有。可默认关闭并对配置存在的包明确提示实验状态，或在确认无使用者后移除清单加载与 Worker 装配。不要直接在主线程动态 import 外部代码替代 Worker。
5. 如果保留默认 Todo 入口，先让查询跳过无关工具，避免为回复参数解压整份历史，复用已有轮次结果或按修订共享计算，并给完整读取工作量设上限。单纯关 Parser 或重命名目录都不会消除这些成本。
6. 保留四家 Parser、合成样本与独立页签登记中已经有用途的部分。通用 PluginRegistration 可以缩回具体的 Parser 数组；无需为了撤退重搬 magpie hook，现有 integrations 路径有独立用途。

当前 Todo 和 Parser 没有新增持久化表或算法版本，撤出运行时与页签不需要数据迁移、backfill 或删除真实正文。代价主要是客户端路由/选择、读取契约、HTTP 和静态文件、测试与文档的同步修改；外部包使用者则会失去免改仓库安装能力，需要保留实验通道或明确退出说明。旧 `tab=todo` 链接也要有清晰回退，不能留永久加载态。历史验收保留原记录，新决策另写 Agent Note 并与既有插件 note 互相链接，不改写过去的决定。

后续工作的先后顺序应是核心事实和持续采集可靠性、读取成本与 Todo 正确性、再到外部扩展。当前最需要的证据是可用状态和阅读收益；补齐通用协议无法替代这两项验证。
