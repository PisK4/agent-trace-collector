# 架构落地前评审

评审日期：2026-10-20。评审对象为 [收敛型技术架构设计](architecture-design.md)，基准提交 `85fa684`。本轮只读核对设计、既有原型和固定提交的 magpie 源码，并运行合成数据验证；没有读取真实请求正文、账号或凭证，没有调用模型、修改 magpie 或停用 AVA。

结论是保留 TypeScript + Bun、独立 collector、SQLite WAL、三路证据和按需读取正文这些选择，修正数据身份、持久化和保留契约后再施工。现有性能回放可以支持技术选型，但不能证明崩溃恢复、乱序收敛与容量回收正确。本文不重测原方案的线上数字，也不以源码推翻那些运行观察。

P1 表示实施前必须解决，否则会丢失已采集数据、产生错误账目或破坏安全边界；P2 表示相关功能验收前必须解决，否则读模型、缺失状态或接口结果不可信。以下修法均为设计建议，不代表已有实现。

## 1. P1：账本唯一键与尝试语义错误

位置：`architecture-design.md:206–208`、`:251`。

`handed_on` 和 `kind` 是两件事。固定源码的 `usage.Record` 将前者定义为某次失败后转交后续候选的计费行，与最终行共用 `route_id`；后者表示调用用途，真实 Agent 的 compact、review 等调用也可能设置。源码依据为 `internal/usage/usage.go:163–176`、`internal/gateway/gateway.go:2953–2969`、`:2997–3013`、`:3549–3564`，以及 `internal/gateway/codex_backend.go:1541–1567`，来源等级为 `版本锁定`，物证为 `开源源码@magpie-2374ffe`。

例如候选 A 拒绝并产生用量，候选 B 随后成功，两行的 `route_id` 相同、`kind` 都为空。按当前规则，两行都要写入 `raw_ledger` 的 `r:<route_id>`：忽略冲突可能留下失败状态，覆盖可能丢掉前一次尝试的用量。按 `kind` 非空过滤，还会丢掉真实调用。项目定位和既有机制研究已经要求保留这类计费明细。

最小修正是让原始账本按物理记录身份入库，例如 `(source_id, file_generation, byte_offset)`，将 `route_id` 改为非唯一关联索引。`request` 仍是一笔客户端请求，结果取最终非 `handed_on` 行；计费用量按尝试保留，明确区分最终回复用量与整笔请求的尝试总量。`kind` 用于分类，不能充当删除条件。路由 usage 与账本明细不能再重复相加。

验收：同 route 的失败计费行和最终成功行都在，请求数为 1，最终状态成功，费用包含该计入的尝试；再验证非空 `kind` 的真实调用没有丢失。原始账本重复回放不得增加请求数或费用。

## 2. P1：回收步骤删除了承诺永久保留的元数据

位置：`architecture-design.md:297`、`:502`、`:510–518`、`:616`。

方案要求元数据保留全部历史，却在回收第 4 步删除 `request` 行。按这组步骤实现，超过正文预算后，历史请求的读数、会话导航和标题也会消失，直接违反第 3 步验收条件。合成 SQLite 验证确认，执行该删除后请求行数为 0。

还有一项保留缺口：原始层建议只留 7 天，长期 `request` 表却没有完整 `tries/order/affinity` 的承载字段。`/api/requests/:id/route` 目前依赖 `raw_route.payload_json`；清理原始层后，即使正文尚在，也无法再解释历史路由。

最小修正是只删除正文引用和骨架，保留 `request`。增加与 `have` 独立的正文状态，例如 `pending / available / partial / evicted / unsupported`，并记录回收时间和原因。`have` 表示是否收到证据，回收不能把已收到改写成未收到。需要长期展示的路由详情应独立保留，或明确宣布它也有保留期，并让接口返回可区分的过期状态。

验收：强制回收最旧一天后，历史请求仍可分页查询，读数和会话请求数不变；正文返回已回收原因。超过原始层保留期后，路由详情仍按约定可查或明确标记已过期。

## 3. P1：10 GB 预算没有覆盖实际正文副本与物理磁盘占用

位置：`architecture-design.md:186`、`:284–294`、`:322`、`:488–518`。

容量估算主要按去重后的内容库和骨架计算，但 DDL 还在 `raw_hook.request_z/response_z` 保存整份正文，spool 也保留一份。方案没有规定它们何时删除，以及它们与 10 GB 的关系。保留 raw hook 整份副本会重新引入跨请求重复正文；已消费 spool 若持续追加也会一直增长。

物理回收同样缺少前提。Bun 本轮验证的 SQLite 默认 `auto_vacuum=0`，在 WAL 库删除约 2 MiB 合成数据、执行 checkpoint 和 `incremental_vacuum` 后，页数仍为 522，其中 520 页空闲。空页可供后续写入复用，但文件不会因此缩小。若预算按文件字节判断，删除循环可能持续运行到没有正文可删。

最小修正是把正文预算与总磁盘上限分别定义：正文计入所有存活副本；总磁盘计入数据库、WAL、spool、隔离记录和临时文件。raw hook 在规范正文成功提交后删除正文副本，或作为有独立上限的短期重放层。spool 按段轮转，消费检查点提交后删除完整旧段。新库建表前设置并验证 `auto_vacuum=INCREMENTAL`；已有库需要单独迁移。明确 WAL checkpoint、回收批次、低水位和磁盘余量，不能等凌晨才处理已满的磁盘。

引用计数按被删引用行的数量递减，同一块在同一请求出现两次要减两次；引用删除、计数修改和孤儿清理必须处于同一事务。保留可运行的 `refs` 对账与孤儿检查。当前规模下也可以选择直接从引用表判断孤儿，减少维护一份计数的负担。

验收：灌入可重复正文、唯一正文和 raw hook 副本，持续观测 DB/WAL/spool 的实际字节；强制低预算后停止增长并满足磁盘策略，幸存请求可完整重建。注入回收中断后，引用计数无负值、悬空引用或误删共享块。

## 4. P1：spool 尚未定义可兑现的持久化确认与重放协议

位置：`architecture-design.md:173`、`:180–186`、`:284–286`。

追加 JSONL 与记录消费偏移不足以证明崩溃恢复。当前方案未确定 200 返回前是否已同步到磁盘、偏移存在哪里、偏移与数据库提交的顺序、半行如何恢复，以及消费失败如何处理。若先推进偏移再提交数据，崩溃会丢记录；若先提交再推进偏移，重启会重放，`block.refs` 等副作用必须幂等。

magpie 的 hook context 没有暴露稳定投递 ID，宿主也没有自动重试 HTTP 投递的契约。宿主只调用一次 `onResponse`，异常记录告警后结束；向 collector 发 HTTP、检查状态和重试都由薄 hook 负责。依据为 `internal/plugin/host.js:1293`、`:1315`、`:1357–1380`，来源等级为 `版本锁定`，物证为 `开源源码@magpie-2374ffe`。

若保留 spool，最小协议应写清：薄 hook 在请求期生成并保存稳定 delivery ID；collector 在脱敏后的完整记录持久化成功后才确认。worker 在一个 SQLite 事务中完成证据写入、读模型修改和 spool 消费检查点；重放同一 ID 不重复建请求或递增引用。尾部半行保留或隔离后继续追加，坏记录不会永久挡住后续记录，磁盘满时不得返回持久化成功。非 2xx 的处理和有界重试须由薄 hook 明确实现；超过上游回调预算仍可能丢失，不能承诺可靠补投。

可以先用带实际提交成本的端到端测量比较直接写 SQLite 与 spool。单 writer 已消除了进程内的竞争写者；同步 GC 或查询仍会占用同一个事件循环，spool 不能消除这类等待。若直接事务提交稳定满足预算，少维护一套日志更简单；若保留 spool，就必须完成上述协议。

验收：分别在追加中途、确认后未消费、数据库提交前、提交后未清理 spool 时终止进程，再重启；所有已确认完整记录至少保留一次，最终只产生一份逻辑数据。另测磁盘满、坏行、重复投递和停机排空。

## 5. P1：tailer 没有处理路由压缩、文件代际与事务游标

位置：`architecture-design.md:174`、`:186`、`:192`。

当前只规定按字节偏移读两个文件。路由实际上是日期文件集合：过期日期被压成 `.jsonl.gz`，跨午夜完成的请求还会在旧日期重新创建 `.jsonl`，以后再并入 gzip；`.gz` 通过临时文件加 rename 整体替换。只追当前日期或只记路径和偏移会漏掉这些记录。依据为 `internal/gateway/history.go:73–95`、`:99–154`、`:198–205`，来源等级为 `版本锁定`，物证为 `开源源码@magpie-2374ffe`。

最小修正是持久化来源身份、文件代际和完整行的提交偏移；原始证据与游标在同一事务提交。半行不推进已消费偏移。持续发现保留窗内的 `.jsonl` 和 `.gz`，忽略临时文件；gzip 可以按文件指纹重读并幂等入库，不需要实现可随机定位的压缩流游标。文件替换、缩短与重建应触发重新识别，而不是沿用旧偏移。

验收：冷启动读压缩历史、跨午夜迟到记录、`.jsonl/.gz` 并存、gzip 被替换、读到半行后续补全，以及事务中断后重启，最终证据集合一致。上游历史已过期的停机缺口应单独报告，不能声称可以补齐。

## 6. P2：集合差无法正确识别重复消息

位置：`architecture-design.md:390`、`:396–405`。

上一笔为 `[user:A, assistant:B]`，本笔为 `[user:A, assistant:B, user:A]` 时，用户确实新增了一条 A，但集合差输出空数组。消息哈希相同不代表同一个消息位置；集合丢掉了顺序和出现次数。这会同时影响对话视图与第一条新增用户消息生成的标题。本轮合成验证复现了空数组，正确新增下标应为 `[2]`。

最小修正是比较消息哈希序列的共同前缀，确认上一笔输入序列完整保留后取新增后缀。压缩、裁剪、分支、前序响应引用或缺正文使关系不确定时，保存未知状态，不把全部差异写成确定新增。首笔与无法判断也应使用不同状态。

验收：连续相同用户输入、同一消息重复多次、重排、裁剪、历史被重写，以及没有上一笔正文的情况。

## 7. P2：一次性派生与实际的乱序、迟到和工具往返冲突

位置：`architecture-design.md:131`、`:325–327`、`:386`、`:409–411`。

逻辑请求顺序 A→B→C，实际证据按 A→C→B 摄入时，C 已按 A 计算前驱和增量。B 到位后没有失效重算规则，结果会长期与全量重建不同。账本先到、正文后到以及待关联 hook 合并，都有同样问题。

工具配对的矛盾更直接：A 回复里发出调用 x，摄入 A 时携带结果的 B 尚未发生。只做一次配对会永久留下空结果；后续真实结果到达也不会改变 A。

最小修正是定义稳定前驱排序，以及局部重算规则：插入、关联、补正文或更改会话时，重算当前请求和受影响后继；待配对调用在后续结果到达时更新，并处理反向到达与重复投递。稳定顺序不能直接依赖摄入时才分配的 `req_id`，同毫秒时仍需固定的来源键。派生结果记录算法版本与未知原因，便于重建。

验收：同一证据集以 A→B→C、A→C→B、正文迟到等顺序回放，最终读模型一致；工具调用/结果两种到达顺序和重复投递均得到同一配对。

## 8. P2：同 session 不等于同一条消息历史

位置：`architecture-design.md:220`、`:307`、`:325`、`:409`。

magpie 的子代理可以保留父会话的 `session`，另用 `subagent` 区分。方案原始表保存了子代理字段，`request` 读模型和派生规则却只按同会话取前驱、配工具。依据为 `internal/usage/usage.go:153–159`、`internal/gateway/trace.go:73–83`，来源等级为 `版本锁定`，物证为 `开源源码@magpie-2374ffe`。

父代理 P1、子代理 S1、父代理 P2 交错时，P2 会把 S1 当上一笔。不同代理使用相同局部工具 ID 时，也可能错误配对。

最小修正是保留 `subagent/parent` 等实际可得身份。会话可统一导航，增量与工具配对按会话内的 actor 和可确认分支计算。身份不足时明确不确定，不按名称或时间猜。会话键本身也要区分来源和键类型，避免客户端 session 与合成 conv 键碰撞。

验收：父代理及两个子代理交错请求，消息历史独立，并故意使用相同工具 ID，确保前驱和结果均不串联。

## 9. P1：8 MiB 的上游常量不是 hook POST 接收上限

位置：`architecture-design.md:188`。

`conversationBodyMax` 在 hook 路径中限制的是捕获的响应原始字节，包含 SSE 封装。请求则通过 `json.RawMessage(body)` 送给插件，该路径没有用这个常量截断请求。因此不能从它推出 collector 整个 POST 应按 8 MiB 收。依据为 `internal/gateway/gateway_hooks.go:15–28`、`internal/plugin/gateway.go:149–188`，来源等级为 `版本锁定`，物证为 `开源源码@magpie-2374ffe`。

例如请求约 6 MiB、回复约 3 MiB 时，两个对象均可合法存在，collector 的 8 MiB envelope 限制却仍会拒绝整笔回调。反过来，上游原始 SSE 已超限而回复退化成 null 时，放大 collector 限额也无法补回。

最小修正是分别规定 envelope、请求对象、回复对象和解析内存预算，禁止截取整个 JSON 文本后继续按完整对象处理。大小保护保留，但必须由观测与接收行为决定。薄 hook 对过大正文可以只发送有稳定 ID、原大小和缺失原因的完整元数据；collector 对不合法或超限 envelope 返回明确错误。收到 `reply=null` 与没收到 hook 必须分开，无法区分的上游失败原因保持未知。

验收：请求和回复合计超过 8 MiB、原始 SSE 超限、合法大 JSON、坏 JSON 和客户端中断。即使正文不可用，成功收到的元数据仍有准确状态。

## 10. P2：协议适配只描述了两种形状

位置：`architecture-design.md:413–426`。

表中的 OpenAI 实际只覆盖 Chat Completions。固定源码支持 `chat / responses / anthropic / gemini`，hook 保留客户端协议形状。Responses 使用 `input/output/instructions`，工具通过 `function_call / function_call_output` 和 `call_id` 关联；Gemini 使用 `contents[].parts` 与 `systemInstruction`。按现有表读取 messages 会生成空消息。依据为 `internal/provider/provider.go:35–41`、`internal/gateway/gateway_hooks.go:39–93`、`internal/gateway/responses.go:328–408`，来源等级为 `版本锁定`，物证为 `开源源码@magpie-2374ffe`。

最小修正是按实际 `protocol` 分派，并将保存能力与解析能力分别记状态。第一版可以先实现两种适配器，其他协议仍保存脱敏原对象，明确标记暂不支持解析。Responses 的前序响应引用不能被解释为本笔包含全会话历史。

验收：四种协议的最小合成对象、Responses 字符串和数组 input、工具往返、前序响应引用以及未知类型内容块，不能把未支持解析显示为零消息或完整正文。

## 11. P2：through 的费用没有输入来源

位置：`architecture-design.md:238`、`:265`、`:315–316`、`:446`。

普通 through 文件行没有 `cost/priced`：文件直接序列化 `usage.Record`，其中可选的 `OwnCost` 是上报客户端自报费用；接口返回的 `Row` 才有按有效定价算出的费用。方案指定费用取账本，同时把 API 只用于 direct，会让 through 费用长期为空。依据为 `internal/usage/usage.go:195–198`、`:227–247`、`:374–378`、`internal/usage/request_page.go:464–473`、`internal/usage/ledger.go:521–547`，来源等级为 `版本锁定`，物证为 `开源源码@magpie-2374ffe`。

最小路径是允许 API 按稳定关联键补费用派生值，继续以文件保留原始 token 和字段存在性；费用附来源、定价时点和状态。没有取得费用、模型未定价和已定价为零必须分开。不建议为此立即复制 magpie 的价格解析；若以后确需离线计价，再引入有版本的定价快照，并包含 1 小时缓存写入等完整输入。

验收：文件没有费用但 API 可计价、已定价为零、未知价格、API 暂不可用和价格变更；每种状态可解释，尝试计费不重复。

## 12. P1：只绑定回环地址不足以保护正文接口

位置：`architecture-design.md:153`、`:547–556`。

任意网页同样运行在本机浏览器中。方案只规定监听 `127.0.0.1`，没有规定 Host、Origin 和 hook 身份校验。DNS rebinding 可以使网页域名解析到回环接口；单凭监听地址和不开放 CORS 无法构成完整的浏览器访问边界。hook 载荷里的 `origin=local` 也只是正文来源字段，不能认证是谁向 collector 发了 POST。此处为设计边界检查，不是对尚未实现服务的漏洞实测。

最小修正是统一检查 HTTP Host 的确切允许值，页面 API 限同源，拒绝异常或 `null` Origin；对无 Origin 的非浏览器访问明确规则。薄 hook 用独立的本地随机凭证认证，凭证不暴露给前端；`origin` 过滤在认证之后执行。正文与路由内容保持转义渲染，并用合成载荷验收现有 Markdown 渲染边界。

验收：合法本机页面和合法 hook 可访问；错误 Host、跨站及 null Origin、无 hook 凭证和伪造 `origin=local` 被拒绝。不要把用户真实正文放入测试或日志。

## 维护契约还需补三处

这些项目与上面的修正一起写进方案即可，不需要新增服务或通用框架。

- **证据可追溯与可重建。** 保存 `request` 到各来源记录的关联，以及原始 ID、规范化规则版本、歧义状态。合并重复请求时，迁移正文引用、前驱与工具链接须在同一事务完成。定义 schema 迁移版本、派生算法版本和重建入口；原始数据过期后，明确哪些字段仍能重算。版本/形状探测应持续覆盖新记录，不能只在启动时探一次就把后续数据都视为已验证；本地升级和按类型合法缺字段应分别处理。
- **原对象和规范哈希的关系。** 去掉 `cache_control` 后做哈希可以减少规范键，但不能因此失去各笔请求的原字段。若相同规范哈希复用一个块，必须保留每笔字段差异以恢复脱敏后的协议对象；更简单的第一版是先按完整脱敏消息做哈希，接受已测得的小幅空间差异。脱敏规则同样需要版本：按字段路径区分凭证和 token 用量，避免宽泛匹配 token/key 破坏数字、工具 schema 与关联 ID。字符串中的 JSON 工具参数也要纳入脱敏验证，不能只遍历外层对象。
- **缺失与健康状态分开。** 记录各来源已处理位置、最后成功时间、解析失败数、spool 积压与磁盘状态。区分上游未提供、collector 未追上、解析失败、关联歧义、收到但无回复、正文已回收。新进程回放期间不要立即报告通道永久缺失。沿用 `/api/stats` 即可，不新增指标平台。

## 实施顺序与准入条件

建议在原四步之前增加一个小范围的持久化验证阶段，然后沿用原有顺序。

| 阶段 | 进入下一步前必须证明 |
| --- | --- |
| 持久化验证 | R1 的多账本行身份、R4 的确认与重放、R5 的完整行和文件代际成立；明确迁移版本与磁盘策略 |
| 第 1 步：账本、路由与页面 | 尝试不增顶层请求数，最终状态正确；回放中断后不丢不重；费用状态有来源；Host/Origin 校验生效 |
| 第 2 步：正文与派生 | 大 envelope、不支持协议、重复消息、父子代理、迟到正文和工具结果均有合成验收；脱敏在所有落盘之前完成 |
| 第 3 步：回收与停 AVA | 元数据不删，真实 DB/WAL/spool 字节受控，共享块不误删；恢复测试通过后，再以并行样本验证正文覆盖率 |
| 第 4 步：可选 direct | 单独确定稳定身份；相同 `(t, session, agent, model, in, out)` 只能视为候选重复，不能未经证明就把两笔合法调用合成一条 |

关联率 100% 和提示量等式 99% 是某次样本的观察，不能单独充当通用正确性判据。还应核对输入记录数、唯一请求数、尝试行数、待关联与缺失数的守恒关系。正常故障场景允许降级，但不能误合并、静默丢弃或伪造完整状态。

AVA 停用前应将回收和恢复能力完成，明确回滚方式，并按同一时间窗、相同筛选范围、原始及规范化 response ID 集合比对。历史快照中的 98 条不能当成未来并行窗口必须多出的固定数量。预算、磁盘满和停机行为也应进入下线判据。

## 本轮验证与证据边界

本轮执行了两类合成检查，所有临时数据库都已删除。

1. 提取评审基准文档中的三个 SQL 代码块，在临时 SQLite 数据库建表。相同 route 的两条账本行触发 `UNIQUE constraint failed: raw_ledger.row_key`；按文档回收删除请求后，历史行数为 0。重复消息的集合差返回 `[]`，正确后缀为 `[2]`。
2. 使用本机 Bun 的 `bun:sqlite` 创建临时 WAL 库，写入 64 个 32 KiB blob，删除后执行 `wal_checkpoint(TRUNCATE)` 和 `incremental_vacuum`。`auto_vacuum=0`，页数维持 `522 → 522`，空闲页 520。该实验只验证默认回收配置，不是 10 GB 压测，也未测真实 hook 提交延迟。

没有运行 magpie 的 Go/GUI 测试，没有启动 collector 后端，因为仓库中尚无生产实现。原方案的吞吐、线上正文覆盖率与磁盘估算均未在本轮重测。R4、R5 和 R12 是缺失契约与威胁场景分析，不写成已经运行复现的服务缺陷。

引用的来源等级为：`版本锁定` 指针对特定客户端版本或特定源码快照逆向得到的实现事实，包括本地文件布局、落盘结构与源码控制流；`实测` 指受控采集下可复现的行为，未被任何官方文档承诺；`推断` 指从以上事实外推的解析或判定规则，不是事实。本文建议和验收条件均为 `推断`，本轮合成检查为 `实测`。
