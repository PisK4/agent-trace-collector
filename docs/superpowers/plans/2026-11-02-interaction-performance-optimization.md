# ATC 交互性能优化评估

> 本文用于方案评审。当前授权只涵盖评估和文档，不授权实现、提交、部署、重启、生产回填或解除切片冻结。源码定位基于 master `92288b5`；2026-11-02 只读核对，未重新执行性能实验。

**Goal:** 缩短会话阅读与后续加载等待，使 2,500 笔量级会话的计算、DOM 和缓存成本可以测量并受控。

**Architecture:** 服务端按小批次提供同快照阅读结果，浏览器复用 reader-store 的版本守卫与缓存所有权。准备通知合并提交，投影按实际变化更新。后台调度保留单组原子事务，超出响应目标的单组另走切片或线程边界评审。

**Tech Stack:** TypeScript、Bun、bun:sqlite、原生 JavaScript；不增加第三方运行依赖。

**Spec:** [第二轮调研证据](../../../.agents/notes/proposed/bug-fix/2026-11-01-interaction-latency-round2-and-rail-consistency.md)、[第一轮治理](../../../.agents/notes/implemented/bug-fix/2026-11-01-collection-interactive-latency.md)、[稳定阅读提案](../../../.agents/notes/proposed/architecture/2026-10-27-stable-progressive-trace-reader.md)。

后续架构演进归[读取架构实施计划](2026-11-02-read-architecture.md)。本文保留性能证据、局部候选与条件分支；读取契约和阶段顺序以该计划及其架构提案为准。

## 推荐判断

多个 Fetch 可以合并，推荐按一批请求合并详情、正文元信息，并批量读取必要的正文区间。整场会话一次取完不适合当前数据形状。它会扩大同步处理、JSON 解析与临时内存，还让首个可读结果等待最重请求。

优先交付前端提交成本治理和有界批量读取，随后按同一组响应目标处理后台同步阻塞。缓存退出清理与取消旧任务属于前端交付的一部分。2,500 笔会话必须进入每阶段复测，不能只优化 364 笔样本后宣布完成。

完整方案包含 DOM 与内存的条件分支：先消除重复模型生成，再复测 64,834 节点规模。仍然超出资源目标时，进入离屏布局或虚拟化的独立交付。该分支属于完成标准，不能无限延后。

## 证据与结论的边界

| 证据 | 支持的判断 | 不能据此承诺 |
| --- | --- | --- |
| 364 笔会话全过程约 1,030 个 Fetch、约 20 秒 | 逐行读取存在明显放大 | HTTP 数量下降多少就等比例提速多少 |
| 2,471 笔约 5,000 个 Fetch；1,246 个长任务；后期每拍 19–50 秒 | 渲染计算已是独立瓶颈 | 合并 Fetch 就能解决极端规模 |
| DOM 64,834 节点、堆峰值 2,327 MB | 必须验证模型、字符串、正文和 DOM 各自占用 | 所有内存都来自 DOM |
| 离开会话后堆仍 846 MB，基线 95 MB | 存在需要复核的高内存现象 | 已经证明正常切会话没有清缓存 |
| derive 具名写事务最大 2,463 ms | 存在单次同步阻塞，HTTP 会排队 | 在组间让步就能把它缩到 50 ms |
| 单条详情、正文页通常毫秒级 | 先治理请求数与重复计算有依据 | 一次读 200 条也必然毫秒级 |

调研数据属于历史实测，本轮只做源码核对。原调研将离开后的内存直接归因于缓存未释放，证据强度过高。正常 `selectSession` 已执行 `reads.clear()`，见 [reader-store.js](../../../web/reader-store.js)。需区分同页切换、回到无 session URL、整页导航、bfcache 与 GC 时机后再归因。

报告对 derive、cost 的按名统计属于明确事实；没有同一时间轴的逐次关联，不能把每次 7.3 秒 Fetch 都归因于 derive。`/api/ingest-metrics` 自身调用重型存储统计，也可能扰动被测服务。

## Fetch 应当怎样合并

### 当前路径

[readRequest](../../../web/reader-store.js) 先取详情，再取 `body?from=0&to=0`。准备阶段补窗口内前驱与工具调用方，然后消费至多 20 片可信增量。[trace-preparation.js](../../../web/trace-preparation.js) 先准备目标，再按四笔一批处理其余请求；网络共享队列另有并发 4 上限。

以 2,471 笔为例，每笔两次基础读取就是 `2 × 2471 = 4942` 次，已接近报告约 5,000 次总数。这支持先合并详情与探针。364 笔样本包含更多追加页，区间批量也要覆盖，不能只优化固定两次。

探针并非只查消息总数。[getBodyPage](../../../src/protocols.ts) 会解压骨架、扫描 System 块、提取能力信息；`from=0` 还返回请求字段与完整回复。[getRequest](../../../src/queries/requests.ts) 会读取配对与路由摘要并解压摘要。一个端点里机械调用这两个函数可以减少 HTTP，却保留逐笔查询和解码；必须同时观察 CPU 与字节。

### 推荐采用两个有界读操作

**详情与元信息批。** 候选路径 `GET /api/sessions/:key/readings?ids=...`。复用当前 GET 读访问控制，不增加通用 POST 分派器。返回每项 canonical 请求身份、详情、元信息与 reading token。一次小批在同一个同步只读事务内生成，单项详情与元信息共用一次身份读取。初次读取给出当前版本；客户端用发起时的 epoch、记录归属与本地修订核验响应是否仍可接收。

**正文区间批。** 候选路径 `GET /api/sessions/:key/reading-ranges?items=...`。每项明确 `{req_id, if_reading, from, to}`。客户端复用现有增量区间打包，服务端继续按 `bodyRangeError` 校验每片最多 40 条消息。稀疏可信增量、结构连续上界和定点读取仍是不同游标，不因批量合并而互相推进。

两个操作分开，可以让客户端继续拥有现成的增量选择规则，不在服务端复制投影或 delta 规则。若后续证明确有必要把增量选择移到服务端，需提取共享纯规则后替换消费端，不能保留两份判定。

以下为候选响应形状，仅用于明确一致性和错误粒度，尚非发布接口：

```ts
type ItemResult<T> =
  | { state: 'ok'; requested_id: number; req_id: number; reading_token: string; value: T }
  | { state: 'reading_changed' | 'not_found' | 'failed'; requested_id: number; reason: string };

type BatchResponse<T> = {
  items: ItemResult<T>[];
  next_index: number | null;
};
```

详情项 `value` 为 `{detail, meta}`；区间项同时返回 `from`、`to`。结果按输入位置对应；区间键包含请求、token、from、to，同一请求的不同区间不能被误去重。跨会话请求拒绝，不借批量放宽原访问边界。参数无效整体 400；合法批次内的 404、409 和读取失败按项返回，不能让一项冲突废掉整批。

`next_index` 表示预算下只完成了输入前缀，客户端在下一次请求发送未完成后缀。续请求重新取得快照，不保留跨 HTTP 长事务。批内一致不代表整场会话冻结；跨批仍以各请求 reading token 校验补读，真实修订沿用自动恢复与旧投影保留机制。

### 批大小与失败策略

建议从每批最多 32 个详情项、64 个区间项开始校准；请求 URL 最长 16 KiB。条数与 URL 上限是候选协议限制，实施前在合成边界用例中锁定。响应约 1 MiB、同步读取约 20 ms 作为起始软预算，完成当前项后停止并返回未完成位置。两个预算均需测量校准，不能冒充已经达成的硬实时保证。

单项也可能很大：消息条数限制并不限制单条消息字节，0/0 元信息仍带完整回复。超大单项不能截断后宣称完整；用明确的 oversized 项状态转回已有单项读取，保留完整内容入口并单独计入验收。实施时必须把解压、对象生成、JSON 序列化和客户端解析都计入成本。软预算不能中断正在运行的单次解压或 SQL。

普通网络失败、503 或鉴权失败不自动展开成几十个单项请求，避免失败时重新放大负载。仅在接口明确不支持，或明确的超大单项路径下使用既有单项读取；版本冲突按项恢复。成功项留存，失败项按既有失败入口重试，禁止无限紧循环。

`reader-store` 注册每项在途任务，批量与并行点击共享任务。详情与元信息在同一个同步段写入；回写前核对 epoch、记录归属、本地修订，区间另核对捕获 token。迟到 409 不能清掉已经重建的新记录。应用层只读 `peek*`，不另存正文副本。

### 合并范围与请求数估算

| 读取 | 建议 | 原因 |
| --- | --- | --- |
| 多行详情 + 0/0 元信息 | 首批合并 | 固定两次读取是主要放大器 |
| 多行可信增量区间 | 同一阶段交付 | 覆盖 364 笔样本的追加页放大 |
| 前驱、调用方元信息 | 同批去重，缺失再补有界依赖批 | 不扩大到全历史依赖 |
| turns、bg-jobs、summary | 保持独立 | 各一次，不拖目标片段首屏 |
| route、工具结果、上下文明细、汇总条目 | 保持按需 | 合并会引入无必要预取 |
| sessions 与默认会话窗口 | 保持拆分 | 左栏不等待中栏，这是首轮已定行为 |

32 项批次下，364 笔的基础读取从约 728 次降为 `ceil(364/32)=12` 批；2,471 笔从约 4,942 次降为 `ceil(2471/32)=78` 批。这里只计算基础读取，不含目标优先单项、请求列表分页、会话信息、依赖、增量、预算提前截断与失败恢复。实际总数必须复测。364 笔全过程不超过 30 次可保留为争取目标，不能为了该数字扩大到危险响应。

## 渲染与缓存需要同批治理

### 合并提交通知并减少重复生成

[准备完成回调](../../../web/app.js) 每笔调用 `renderMain()`，而 `mainModel()` 遍历所有已加载请求，重新投影并生成每行 HTML。已有键控提交省 DOM 替换，模型生成与字符串比较仍是全量。这与[键控提交 note](../../../.agents/notes/implemented/architecture/2026-10-27-keyed-trace-main-view.md)记录的代价一致。

先合并同一小批的准备完成通知，目标请求保持优先。一次通知触发一次提交，不按每个结果项各画一次；需要跨帧合并时只调度一次待执行任务，换会话取消。选择高亮保留即时路径，不能等后台批次完成才响应。

随后按请求记录变化重用投影和 HTML。失效依据必须覆盖正文消息、delta 进度、结构展开、用途和派生状态、前驱 System 比较、工具调用方、背景作业及序号。依赖改变时一起标记受影响组，不能仅以 reading token 作为模型缓存键，因为同一 token 下消息还会继续到达。投影缓存由既有显示层持有，只留当前版本，不增加第二份正文缓存。

窗口变动时一次建立 `req_id → ordinal`、行集合及尾部资格索引，替代每行 `findIndex`、`some` 和重复后缀扫描。消息排序结果只在消息变动时重建。会话头统计只在对应输入变动时重算。提交层复用一次比较结果，只有结构变化才执行折叠恢复、头部高度测量与锚点补偿。

性能测试首先断言工作量：为窗口追加 K 笔，不应再次投影 N 笔未变化请求。DOM 复用、焦点、文字选择和视口锚点仍按现有语义验证；不以 HTML 相同掩盖来源坐标或 token 需要更新。

### 退出与内存回收

正常切会话已有 `reads.clear()`。[popstate](../../../web/app.js) 恢复到无 session URL 时没有对应的 store 与视图退出动作，是一条可核验的清理缺口。统一退出路径清理会话阅读记录、窗口行、在途登记、自动重读 timer、准备状态、保留投影、视图模型及会话专属 UI 状态。

网络队列在发起前检查导航代次，删除已过期的待发任务。对已经发出的旧会话读取使用 AbortController，避免继续下载与解析；最终是否写入仍由原来的 epoch/token 守卫决定，取消不能替代一致性校验，也不保证中断服务端同步 SQL。

内存验收分别记录同页切换、URL 回到无 session、整页回主页和 back/forward。记录是否 bfcache 恢复，在可控浏览器环境区分 GC 前后堆与实际引用。不能以一次 usedJSHeapSize 不下降认定泄漏，也不能以执行了 clear 认定没有其他持有。

本轮不直接降低每组 20 片准备预算，不把未完成内容静默省掉；也不引入整场自动排空。按视口自动读取、正文缓存淘汰需要改变范围及依赖保留方式，归稳定阅读提案单独决定。

### DOM 后续分支

先实施重复生成治理，再观察长任务归属。若剩余成本主要是离屏布局，可试请求组级 `content-visibility`；它不减少 DOM 或 JS 堆，且会影响高度测量，必须验证锚点、折叠和跳转。

若 2,500 笔样本仍存在超过 100 ms 的重复渲染任务、页面操作无法在 100 ms 内响应，或 DOM/投影内存继续越过资源预算，则评审组级虚拟化。保留轻量会话顺序与目录，只挂载视口附近组；不能直接裁掉窗口数组，改变序号和轮次累计下界。

虚拟化需要覆盖离屏定位、深链、轮次跳转、工具配对、焦点和浏览器查找。跨离屏文字选择与浏览器全文查找可能改变，这是需要 Pis 决定的能力取舍。当前不以虚拟化作为第一步，也不将它排除出最终完成路径。

## 后台同步阻塞怎样处理

[在线工作单元](../../../src/derive/unit.ts) 按十笔用途批与独立组事务执行，在组间检查 400 ms 调度预算。[主进程](../../../src/main.ts) 通过 setTimeout 安排后继 tick，已经有组间让步。`drainDeriveGroupTx` 将链、角色、工具、摘要与完成 CAS 放在一个原子事务内，单组不可中断。

因此，减少每个 tick 连跑的组数可以降低连续占用，却无法缩短那笔最大 2,463 ms 的事务。写事务内插 await 会破坏当前契约，不采纳。直接启用现有实验切片也不采纳，生产仍受 `slice_read_unmigrated` 与长组容量门槛约束。

推荐先增加或复用有界分项计时，区分用途批、候选读取、完整组、正文解码、链匹配、工具配对、展示写回与序列化。按已有调度预算机制，在完整事务之间更及时交还事件循环，记录积压最老年龄和排空时间。不能为前台更快而让后台长期不追平。

cost 当前每页 500 行，费用观测与页进度原子提交；跨页已有网络 await。若该页 364 ms 事务在新采样中仍可复现，优先减少上游分页大小并同步调整 done 判定，保留整页冲突回滚。不能拆成若干已提交半页后仍声称整页原子。

单组剖析后先消除有证据的重复工作；如果仍不能满足响应目标，停止继续微调组间预算，启动独立线程边界方案。可比较解冻既有代际切片与隔离 writer 执行：前者必须通过长组容量及发布读模型验收，后者必须定义唯一 writer、跨线程有界队列、hook 提交后应答、故障恢复和停机顺序。不能只把 derive 挪到第二个 writer；也不能只挪查询而保留 HTTP 分派所在主线程长时间阻塞。

原第一轮 note 指向架构文档的执行线程边界，但当前架构文件没有该同名章节。本文不虚构已存在的队列协议；线程分支实施前补完整设计。现行约束仍以[进程模型](../../architecture-design.md#系统边界与进程模型)和[组完成语义](../../architecture-design.md#组完成与输入修订)为准。

`measureStorage` 同时被指标快照和准入容量检查调用。即便前端不用 `/api/ingest-metrics`，统计成本也不能全归为无用户影响。先分别记录调用次数、耗时与任务名；容量检查不可删。验收采样用已有进程计时与低频快照，或将轻量时延读取与重型存储统计分开；禁止高频扫描 1 GB BLOB 后把新增阻塞全部记到 derive。

## 验收标准与失败分支

以下新增数值是建议验收目标，未经过本轮实验验证；历史事实只引用调研 note。实施首项前冻结同设备、同页面版本的基准。每阶段完成后只复测受影响路径与极端样本，最终再做整体验收。

| 维度 | 建议判据 | 失败后的行动 |
| --- | --- | --- |
| 首屏与点选 | 目标组先可读；固定样本首片段 p95 不劣于基准 10%；已加载点选到高亮 p95 不超过 100 ms | 缩小首批、移除无关等待，保留目标优先 |
| 364 笔完整读取 | 争取 Fetch 总数不超过 30；同步记录字节、解析、重试与完成时间；建议整体不超过 5 秒 | 按基础读取/依赖/增量拆数，不通过无限增大批次过关 |
| 2,500 笔完整读取 | 建议自动化执行原有加载动作累计完成时间不超过 30 秒，不计测试器人为停顿；后期每拍不应随累计行数持续恶化 | 分解模型/布局/网络，进入 DOM 或读口后续分支 |
| 主线程 | 正常准备提交不超过 50 ms，超过 100 ms 的渲染/解析任务为 0；区分 GC 与应用长任务 | 优先变更组复用，再按归因启用离屏布局或虚拟化 |
| 缓存与堆 | 会话退出后 store/保留投影/视图持有的旧请求与旧任务为 0；建议 GC 后堆回到基线加 50 MB，连续切换 5 次无递增残留 | 以 retaining path 定位；bfcache 单列，不伪装成应用释放 |
| HTTP 与后台 | 沿用 query p95 不超过 100 ms、event loop p99 不超过 100 ms；p99/max 必须另报，秒级尖刺保持未关闭 | 大事务仍超时则评审切片或线程边界，不再只减 tick 预算 |
| 采集正确性 | 受控合成负载没有新增丢失、错误 2xx、永久积压；沿用现有容量门禁，不降低 offered rate 掩盖退化 | 回退调度策略；比较积压年龄和排空时间 |
| 一致性 | 批内同快照、逐项 409/404、迟到成功/失败、切会话、别名合并、正文回收均不混版本；工具来源路径与费用状态不变 | 修正共享读取与回写守卫，不移除 token |
| 阅读稳定 | 加载中点选、快速 A→B、前驱/调用方迟到、右栏分页、折叠、文本选择和窄屏锚点保持正确 | 归现有键控提交与稳定阅读约束修复 |

建议 2,500 笔完整阅读时峰值堆先以不超过 512 MB 为评审目标，并同时记录旧版同样本峰值。该目标若受超大正文刚性开销影响，需要明确数据尺寸，再决定紧凑输入或按视口缓存；不能只将目标调高，也不能悄悄省略内容。批量和模型缓存可能同时增加临时对象，必须同测峰值。

合成矩阵覆盖 30、364、2,500 笔、单笔超大回复、稀疏增量、缺正文、多 actor、折叠旁路、版本冲突。对服务端用受控负载分别测试空闲读取与后台同步运行，区分排队、SQL、解压、序列化和客户端等待。保存测量窗口增量，不从进程累计最大值宣称本阶段已经达标。

真实浏览器验收复用原报告的 Claude、Hermes、OMP 场景及深链，另补 summary entries 分页、工具结果页签、unpriced/zero/absent 展示。真实库只读，不在当前评审阶段执行生产测试。合成通过与真实复测分别记录在[验收记录](../../acceptance.md)。每项仅运行其最窄回归；最终执行 `bun run typecheck` 与 `bun run verify:notes`，不重复已通过且输入未变的检查。

## 与现行决策的关系

本计划细化第二轮提案，保留其历史证据，建议调整其排序与两项归因：前端计算优先级提高；单组让步与内存泄漏不作过强承诺。原 proposed note 继续作为调研事实入口；方案被接受后再同步其 Proposal，不在评估阶段反写历史测量。

第一轮的两阶段列表、首屏拆分、单 writer、组原子性和切片冻结继续有效。准备流水线、生产阅读缓存、键控提交、自动重读及版本保留将被部分调整；实施时在各自 note 添加双向引用，只更新被实际交付的部分。不得整篇归档仍有效的稳定性规则。

性能优化不改变 PURPOSE/GROUP/DERIVE 判定语义，按此边界不需要 schema 或派生版本升级、不需要存量回填。若后续线程或切片方案改变发布算法、存储或读取依据，另行设计版本及 backfill/拒绝路径，不混进纯传输优化。

## 备选方案的取舍

**整场全量一次返回。** Fetch 最少，但首屏、响应字节、解析与内存没有边界；不推荐。

**只放大并发 4。** 不改变总工作量，也不隔离服务端同步阻塞；批量与计算治理后才根据队列利用率校准。

**把 turns、summary、stats 都放进一个入口。** 它们不构成主要扇出，合并会让目标片段等待无关数据；保持独立。

**只加后端缓存或持久化步骤表。** 尚无证据证明毫秒级单读值得增加失效、schema 与 backfill 维护；先用请求作用域复用和现有缓存。

**直接上流式 NDJSON。** 能逐项交付，但要处理断流、逐项边界、取消和重试。先以小批 JSON 验证首片段与解析预算；单项字节仍不可控时再决定。

**只加虚拟滚动。** 保留 Fetch 和服务端阻塞，且影响查找、定位与选择；作为实测触发的后续交付，不作为第一步。

**批量失败自动回退所有单项。** 错误时放大负载，掩盖接口问题；只对明确不支持或超大单项回退。
