# ATC 架构演进方案 v2

本文是下一轮架构改造的统筹提案，尚未实施。它组织字段保真、证据重建、Agent 语义与机器流量容量之间的依赖，作为本轮方案讨论入口；现行设计仍见[收敛型技术架构设计](architecture-design.md)，运行操作仍见[运维手册](operations.md)。采纳某一阶段后，在对应代码变更中更新现行设计与所属 note。

## 目标与完成条件

ATC 要持续记录机器调用，并让读者区分请求事实、上游报告、ATC 解释与尚缺证据。兼容新的 Agent 时，专有规则应集中在少量位置；请求增长时，采集、后台派生和阅读应有明确的工作量限制。

下一版同时追求三项结果：字段与多次尝试的解释正确；新增已知 Agent 语义不再要求前后端分别识别；混合负载下的采集与查询能够满足明确的延迟预算。三项分别验收。新增一个注册表不能证明容量改善，字段数量增加也不能证明事实更准确。

技术约束沿用现有设计：单进程 TypeScript + Bun、SQLite WAL 与单 writer、独立只读连接、原生 JavaScript 页面、不增加第三方运行依赖。ATC 继续作为 magpie 的旁路记录器，保留请求为主实体、会话为派生阅读视图的定位。采集范围受上游可观察面限制，不承诺覆盖每一笔内部辅助调用。hook 保存的是客户端交给网关的脱敏协议对象，后续仍可能发生转换和逐 provider 改写；不能标成每个实际模型收到的逐字节输入，依据见[现有接入约定](magpie-mechanisms-research.md#开始实现前要落实的输入约定)。

## 为什么需要统筹重构

现有两份提案分别指出了来源读错与用途解释缺位，但它们共同依赖的重建、版本、隐私和调度尚未形成完整路径。以下事实属于 `版本锁定`，基准见文末；具体反例和字段核对保留在[联合评审](agent-request-kind-review.md#与字段保真方案的联合评估)，本文只列决定架构切口的依据。

| 当前路径 | 已核对的问题 | 对下一版的要求 |
| --- | --- | --- |
| `src/sources/magpie.ts:145` → `src/reconcile.ts:143`、`:174`、`:237` | mapper 读错 req/cost/counting；三个请求写入路径又各自解释模型，修一处仍会失真 | 来源读取与请求事实投影各有一个归属，在线摄入与离线修复共享规则 |
| `src/reconcile.ts:461`、`:467`、`:556`、`:564` | 结构化字段先取原值，payload 另行脱敏；路由摘要也保留脱敏前提取的数组 | 将身份提取与可保存内容分清，结构化列、payload 和摘要遵守同一隐私政策 |
| `src/derive.ts:613`、`:718`，`src/hook.ts:272` | 整组派生混合用途、摘要和链计算；derive_version 实际累加；hook 归属未定时不会进入既有组队列 | 请求语义的失效与会话派生的失效分别管理，算法版本与执行次数分开 |
| `src/derive.ts:484`、`web/app.js:563`、`:592`，`web/body-view.js:585` | title、包装、技能在不同消费者重复解释 | 规则集中，前端消费解释结果并保留原始脱敏内容入口 |
| `src/derive.ts:617`、`:622` | limit 限制组数，组内工作仍可很大；from_sort 未参与截断 | 以实际工作量限制后台任务，增量结果要与完整重建一致 |

推荐优先加深三个 Module：来源解释与请求投影、请求语义解释、派生执行。它们分别集中上游字段知识、客户端语义知识和重算成本。新增文件必须承载这些知识的实际迁移；只增加转发层不提高 Depth。

采用 improve-codebase-architecture 的删除检验审视这些切口：若删掉来源投影 Module，模型与尝试选择会重新散入多个写入点；删掉请求语义 Module，title、包装与技能规则会回到多个消费者；删掉派生执行 Module，实时 tick 与维护命令又需各自安排重算和工具配对。这些复杂度都有实际调用者，值得集中。单纯包装 Store、为每个 Agent 建空壳或为每个字段建专用 Module，没有同样的收益。

| 候选 | 当前改动路径 → 目标改动路径 | 推荐程度与先后 |
| --- | --- | --- |
| 来源解释与请求投影 | mapper + 多个请求写入点 + 回填各自解释 → 来源 Adapter 确认字段，请求投影集中选择，在线与离线共用 | 强：先解决会持续写错的数据，作为语义与阅读的前提 |
| 请求语义解释 | derive 与 web 各自猜用途、清洗、解析 → 三个独立语义操作，派生和正文阅读消费同一规则 | 强：已有重复及不同真实形状，迁移能直接删除分散规则 |
| 派生执行 | tick 调全组 derive，再自行工具配对 → 一个执行入口管理受影响范围、预算、提交与恢复 | 值得推进：先测量并集中现有调用，再按瓶颈增加切片或增量 |


## 目标组织与职责

下面是数据经过各 Module 的逻辑顺序，不要求每行新建目录、进程或独立表。

```text
账本 / 路由 / hook
        ↓
来源读取 + 来源 Adapter + 统一隐私处理
        ↓
证据身份与 owner 关联 → 请求事实投影 + 长期路由摘要
        ↓                         ↓
请求语义解释                  独立只读查询
        ↓                         ↑
会话前驱 / 链角色 / 工具关联 ──────┘
                                  ↓
                      正文分页解释与阅读页面
```

协议 Adapter 为请求语义和通用派生提供消息、文本、工具定义、调用与结果的协议解释。正文读取与解压仍属于调用上下文；Agent 规则不取得数据库、网络或写库能力。后台调度限制上述任务的单批工作量，容量准入继续由统一磁盘策略控制。

| Module | 调用者应知道的 Interface | 内部集中承担的 Implementation | 预期收益 |
| --- | --- | --- | --- |
| 来源解释与请求投影 | 输入来源、证据身份、已脱敏事实及可用状态；输出确定的请求更新或未决原因 | 真实键名、类型、缺失、来源优先级、多次尝试选择、可重建性 | 在线和回填穿过同一 Seam，修一次字段规则覆盖全部写入路径，改善 Locality |
| 请求语义解释 | 已知 Agent 标签、协议视图与证据状态；输出用途、链参与策略、输入解释或技能声明 | 固定规则顺序、命中依据、规则版本、缺证据处理；三个操作各自独立 | 删除页面的重复识别；相同规则服务派生和正文阅读，形成 Leverage |
| 派生执行 | 受影响范围、目标算法、单批预算；返回进度和未完成工作 | 合并触发、数据复用、分批计算、过期结果防护、提交和恢复 | 调用者不再自行组织全组扫描与工具配对，成本与正确性从同一 Seam 验收 |
| 读模型与正文阅读 | 稳定 ID、keyset 游标、正文区间、明确状态 | 摘要读取、消息级解释、能力覆盖状态、路由结构的安全投影 | 列表不解压正文，页面只组织阅读与交互 |

这是职责提案，函数名和 TypeScript 类型在对应阶段结合调用者确定。保留现有 Store 事务方式，不引入通用 Repository、可插拔数据库或全局事件总线。协议已有 anthropic/chat 两个真实 Adapter；Agent 专有规则也已有不同解析形状，因此这些 Seam 有实际变化依据。其它位置没有第二种实际变化时，先用具体函数。

### 来源解释与请求投影

来源 Adapter 读取上游真实结构，保存未知字段，报告可选字段缺失与非法类型。稳定的物理证据身份仍按现有机制生成，不由 Profile 或显示文本生成。请求投影负责从属于同一请求的证据集选择事实，不能让每个写入点各自补默认值。

版本在区间内不能证明字段解释正确。`src/sources/magpie.ts:286` 的现有 probeMagpie 检查版本与可达性；[现行设计](architecture-design.md#版本与形状漂移)还要求持续检查来源形状。下一版将必要键、合法省略、非法类型和未知键的检查放进来源解释路径，按来源记录不含正文的计数与短原因，不为一次可选缺失降级整批。先覆盖本轮读错的键与类型，不另建通用 schema 框架。

隐私处理先于内容落盘与摘要提取。关联需要的 route_id、物理偏移与响应 ID 应在专用提取路径保持其既有语义，合成测试确认没有被泛化脱敏误伤；account、错误文本、候选和尝试数组从统一处理后的对象形成列与摘要。来源键 account 与 providerAccount 是否别名，由来源 Adapter 明确，脱敏政策对两个入口一致生效。历史已保存的稳定占位符保持原样，不能在回填中重新散列。未知原始字段也只保留脱敏后的版本。默认查询响应继续遵守[既有账号与 host 披露限制](architecture-design.md#安全边界)。

投影需要集中回答以下问题，不把答案留给页面或 Feature：

| 事实族 | 下一版处理原则 |
| --- | --- |
| 请求模型、provider 模型、回复声明模型 | req、model、served 分别保留含义；req 缺失保持未知。显示层需要备用值时说明其来源 |
| hook 模型暂存 | `src/hook.ts:135` 目前把同一个 envelope.model 写入 requested/served；投影重构也要覆盖该路径。hook 报告值保留其来源，不因此显示为 vendor 回复已确认；补齐账本后按确定规则收敛 |
| 最终尝试与其它尝试 | provider、host、account、effort、tier_sent、tier_served、err 跟随同一选定尝试；无最终证据时保留 pending_final 或失败状态，不跨尝试拼接非空字段 |
| 请求层身份与声明 | session、native_session、Agent 标签及原始 kind 保留来源；native_session 不替换请求唯一身份或现有 conv_key/actor |
| 上游 kind | ledger 与 route 分开保留报告值和来源；有冲突时按确定规则选择并留下冲突信息。不要让最后到达者覆盖。选择规则在来源投影实施前与合成冲突用例一起确定 |
| Prompt 计数 | 合法、受支持 Prompt 中 true 表示已校准，false/合法省略表示未校准；Prompt 缺失或非法保持未知。总量校准不证明各 part 精确；held 表示上游持有历史，不得把当前 body 当完整会话 |
| 费用 | 账本 cost 是客户端自报 OwnCost，API cost/priced 是定价观测；两者不能互相覆盖或混合汇总 |

这些规则不要求所有字段进入 request。长期存储按消费者和恢复需求选择：来源 kind、语义判定依据与版本为本轮共同必需；effort、tier 和错误摘要按详情消费确定；account、host 的上浮与公开需要另行说明用途；没有长期消费者的字段继续留在短期脱敏证据中。索引仅随查询需要增加。

路由尝试已经有 order/tries 可读，不先建立新的 attempt 专表。先验证长期摘要是否足以保留实际需要的尝试事实；如证实账本尝试无法用现有结构表达，再在该阶段选择存储形状。`开源源码@magpie-2374ffe` 中 routeUsage 可包含 Deferred 计费条目，用量条目与尝试并非严格一一对应，不能按数组位置强行配对，依据见[已有机制研究](magpie-mechanisms-research.md#估计值与报告值)。route_summary.z 不是完整 raw_route，不能将其视为恢复任意字段的来源，也不新增第三份重复摘要。

### 请求语义独立于会话归属

请求用途、输入解释和技能声明都描述当前请求，不必等待 actor 确认。现有 derive_queue 按 conv_key/actor 工作，不能直接成为这些结果唯一的触发路径。下一版要在请求证据变化后安排请求级解释，actor 未定时保留归属未定状态；只把前驱、链角色和跨请求工具关系留到归属确认后计算。

不必立即新增一套常驻队列。先检查现有写入完成路径能否可靠触发有界解释，失败是否可由持久化的待处理状态恢复；如不能，再扩展现有队列的表达。Interface 必须保证 hook-only、账本后到、Agent 标签后到和正文后到都不会永久漏判。证据归属发生迁移时，旧组与新组都标记受影响。

Agent 语义保持三个独立操作：用途分类、输入解释、技能提取。同一 chat 请求可以同时有 harness 包装与技能声明。Profile 只选择确有依据的规则，不建立全能 Feature Interface，也不为仅使用通用规则的标签建空 Profile。工具定义归协议 Adapter，用户首句备用标题及会话最终标题选择归通用派生与读模型。

用途分类保存 ATC 稳定类别，同时保留上游报告。固定优先级先处理适用 Agent 下的强请求指纹，再用共享启发式；title 保持现有识别兼容及其误判边界。classifier 的保守门槛与反例见[分类器门槛评审](agent-request-kind-review.md#分类器门槛会把普通请求移出主链)。无匹配表示尚未识别特殊用途，不能同时宣称证据已确认属于 chat。存储可以保留兼容的 chat 值，但必须能从判定状态区分默认值、已识别类别和无法复核的旧结论。

链参与策略与最终 chain_role 独立。已确认 title/classifier 退出祖先与工具配对候选；未知类别不自动成为 aux。正文不可比时沿用中性处理，不能改成 branch。普通未知用途是否参与既有链算法，应在兼容用例中显式固定，避免以类别命名推导策略。会话标题候选、列表轮次与工具配对都需消费同一参与政策；`src/queries.ts:102` 的标题 SQL 也属于贯通范围，不能只替换 derive 中的判断。

规则 ID、规则版本、短信号代码、判定状态就地保存到请求，不复制 system 或 transcript 全文，不建立独立证据台账。正文存在时允许新规则重新判断；正文已回收时保留旧结论与旧版本，并标无法复核。算法升级不能把保留旧结果写成新规则已确认。

### 派生执行与调度

先区分请求事实、请求语义、会话派生的依赖变化，再讨论增量。schema 版本表达结构；来源映射版本表达字段解释；语义规则版本表达用途或包装解释；会话算法版本表达前驱、角色和工具关联。复用已有 adapter_version、redact_version 等版本概念，不给每个小函数加版本列。derive_version 不再用累加次数比较算法新旧；历史值需要明确重置或迁移，执行次数如有诊断需求另记。

初期保留完整组重建作为正确性基准。逐步合并同组触发、复用已读取的指纹与解码对象、避免不变数据重复写入，再把后台工作按请求数、候选比较或实际耗时切片。仅在两个组之间 yield 不能限制一个超长组；耗时预算也不能中断一次同步解压，需要在处理大小上有界，并保留既有单对象尺寸限制。

切片不能逐块发布自相矛盾的链。实现需选择一种可验证办法：在可恢复的进度中计算，完成后提交受影响结果；或使用明确的重建状态，使查询知道当前派生未完成。计算期间收到新证据、发生合并或回收时，应使过期计算失效并重新入队，不能覆盖较新的结果。`src/store.ts:92` 的 writer 仅允许同步事务，yield 必须发生在事务之外；不能在持有事务时 await。具体保存方式在派生阶段选择，不提前引入并行 writer 或 worker。

from_sort 只用于识别受影响起点，不能据此删除更早祖先候选。迟到请求、旧请求用途变化或归属变化可能改变后继和主链选择；优化必须保留[任意祖先前驱规则](../.agents/notes/implemented/architecture/2026-10-20-semantic-fingerprint-and-ancestor-predecessor.md)。

### 正文与阅读

服务端用同一语义 Module 解释列表摘要与正文分页消息，按 ord 返回显示解释及状态，原始脱敏消息保持可读。输入解释不修改内容哈希或共享 block.fingerprint，不把显示清洗当成内容等价。已有指纹设计与实现的差距留在[联合评审](agent-request-kind-review.md#包装迁移不能同时改写指纹)，Agent 专有指纹另案处理。

能力视图区分协议工具定义与 Agent 技能声明，区分为空、未识别、缺失和分页覆盖不完整。首片没有读到某段 system 文本不能解释成零技能。按需解释不默认长期复制技能描述或工具 schema；以后如需正文回收后继续阅读能力，需要纳入正文预算与保留政策。

页面先完成会误导读者的纠错：未知 req_kind/chain_role 原样保留、中性显示；part 采用 magpie 已知类别并给未知值有效颜色；分页文案与实际方向一致；flags 从确定状态聚合。随后再做尝试链结构化阅读、上下文占用提示、滚动保持和复制。未知 fail 保留原值，无时间证据时不补造重试间隔；75%/90% 仅作阅读提示。

## 历史修复与迁移

历史修复要穿过与在线路径相同的规则，按三步执行：脱敏后重映射可用来源，按现有证据 owner 重建请求事实与长期路由摘要，再重建请求语义、会话关系及工具配对。不能只改 mapper 或只跑 derive，不能删除 request_evidence 绕过幂等保护。

结构版本与迁移完成状态分开。沿用[启动拒绝自动升级、显式脚本保住正文](../.agents/notes/implemented/architecture/2026-10-20-schema-v3-rejects-in-place-upgrade.md)的策略，补上迁移中断后的启动检查：列已添加不代表数据已重建。离线入口应有范围预览、分阶段检查点和恢复报告，配合维护锁；第一轮只在合成库验证，真实库操作另行授权。

迁移按可恢复性报告：有脱敏 raw 的可重映射；raw 过期但长期摘要足够的仅恢复对应字段；两者都没有的保持未知；历史错误备用值不继续作为可信请求模型。保留 req_id、alias、证据 owner、正文引用、cost_observation、游标与主动淘汰墓碑。重复运行结果收敛，中断后续跑不增加请求或费用。

同一批必要字段可以共用一次 schema 升版，但不能借此塞入所有候选字段。先确定消费者、增长预算和缺失语义，再冻结列集合；表结构与脚本在实施时一起交付，本文不提前写出 v5 的既定列定义。

## 容量目标与验证方法

容量工作从第一阶段采集基线，贯穿每个改动。已有存储回放数字不能代替常驻进程的混合负载；本轮没有性能测量，以下负载是 `推断` 的合成验收起点，阈值是拟议门槛。

| 合成场景 | 初始负载 | 需要观察的结果 |
| --- | --- | --- |
| 连续采集与阅读 | 1 请求/秒持续 10 分钟；另跑 5 请求/秒持续 10 分钟；请求正文以 0.35 MiB 与 2 MiB 混合 | hook 延迟、接受/拒绝、队列年龄与追平时间；同时翻页与读正文 |
| 突发 | 10 个并发 hook，包含 4 MiB 请求及不同回复大小；重复发送同一 hook_id | 有界内存、明确背压、重试后不重计；不以返回 200 代表正文一定存在 |
| 长会话 | 2,000 笔；再用 10,000 笔检验增长；共享历史与独有正文分别构造 | 候选比较次数、解码次数、单批最长占用、完整与增量结果一致 |
| 历史目录 | 同一批不变路由文件重复轮询，再追加、替换 gzip、跨午夜 | 不变文件的解压次数下降；替换仍可检出，证据集合不漏不重 |
| 混合维护 | 采集和查询期间触发正文回收、raw 清理、费用同步 | 写事务时长、事件循环延迟、库/WAL/临时文件总量、准入状态与查询延迟 |

先沿用现有会话列表 100 ms 的验收目标；hook 200 响应以数据库提交为前提，拟以 2 秒预算检验重试在内的端到端行为，具体应与实施时插件超时配置一致。合成测试目标为接受率和重试结果可核对，正常持续负载不出现 503；429、507 必须有明确原因和统计，不能通过丢弃未记录工作换取低延迟。正文尺寸超限或磁盘降级单列，不混入正常接收率。

固定机器环境、Bun 版本、数据种子和配置后记录 p50/p95/p99、最大事务时长、事件循环延迟、峰值 RSS、派生积压最老年龄与停止输入后的排空时间。先记录基线，再为派生积压和排空设可复现阈值；没有这些阈值与前后对照，不宣布容量目标完成。10,000 笔是扩大规模的压力点，不是默认支持上限或已验证能力。

吞吐之外还要验算长期元数据。按合成库实测的每请求新增字节、路由/尝试数量和索引成本，计算日请求量下的年增长与到达磁盘门槛的时间；持续秒级吞吐不能直接等同于全年平均流量。正文回收不会缩减长期请求元数据，[现有容量门槛](../.agents/notes/implemented/architecture/2026-10-20-retention-three-gates.md)也不保证无限期保存。若目标日量与保留年限超出上限，需要单独提出元数据保留或扩容决策，不能通过暗中清理请求满足验收。

优先尝试的优化是路由文件变化确认后再解压、同组派生触发合并、单次任务内解码复用与后台切片。费用重扫和预算 SUM 若在基线中占用显著，再采用有失效规则的缓存或增量计数。worker、spool、更换数据库和多进程要有上述测量证明，才进入下一次方案决策。

## magpie 的补充调研

继续调研有价值，但范围应由本轮未决问题限制。既有研究已覆盖配置适配、用途归并、prompt 分解、路由与 direct，不能重新列一轮 Feature 清单作为架构依据。对标的对象是解决问题的机制及其适用条件。

现有可吸纳项包括原始 kind 与归并结果分开、按实际能力和形状门控、Prompt 总量校准与分项估计分开、尝试失败码保留未知。读取缓存的失效机制需要结合具体路径复核，不能笼统当作现成解法。源码不能证明本机安装版已经启用相同路径；对 ATC 的采用判断属于 `推断`。

补充研究随各阶段进行：来源阶段核对字段省略/类型/漂移；投影阶段核对 attempt 与最终行的关系；阅读阶段核对 fail 与 prompt 的真实语义；容量阶段研究缓存的失效条件。每项必须给出固定源码、ATC 对应切口、采用代价和可失败的合成用例。不能以 magpie 有该能力作为采用理由，也不把其网关控制策略搬入 ATC。

| 仍值得调查的问题 | 对应产出与停止条件 |
| --- | --- |
| 来源升级后，如何区分合法省略与解析失败 | 完成本轮字段的固定源码形状、合成正反例与降级理由即可；不枚举全量 Agent 配置 |
| 多次尝试、计费用量与最终状态如何对应 | 找到明确生产者与消费逻辑，保留不能一一配对的情况；不从展示顺序发明关联 |
| 读取缓存何时失效，旧快照如何停止发布 | 说明来源代际、内容变化、配置变化或过期的触发；ATC 仅采用与自身数据身份一致的部分 |
| 尝试链与上下文有哪些误读风险 | 固定失败码、未知兜底、计数和窗口的来源；读者所需信息足够后停止，不移植整套界面 |

## 分阶段推进

| 阶段 | 具体产出 | 进入下一阶段的条件 |
| --- | --- | --- |
| 0：冻结基线与目标 | 固定代码与文档基准；合成字段/乱序/混合负载场景；明确请求、尝试、来源与派生的归属 | 缺陷可复现，性能基线可重复；逐项列出待确认的选择，不读取真实正文 |
| 1：来源与在线投影 | 修真实键名/类型及全部模型写入路径；统一结构化字段脱敏；part/分页等独立纠错 | 新证据值和来源准确，多尝试不拼接，已有身份与费用不回归；修复覆盖范围明确，不以新数据正确宣称历史已修复 |
| 2：长期事实与重建 | 选择必要字段；显式算法版本；可恢复离线迁移；请求语义与会话派生各自的失效触发 | 合成旧库、raw 过期、中断续跑与守恒通过；迁移未完成时启动有明确行为 |
| 3：用途语义 | 迁 title、增加 classifier、保存依据，贯通链参与、工具配对和读模型；覆盖 actor 未知 | 缺回复、乱序、未知类别、规则冲突与正文回收结果明确；页面删除重复用途判断 |
| 4：输入与能力阅读 | 统一包装解释、消息级结果；技能解析与协议工具组合；结构化尝试链 | 多条增量用户消息不丢、原文可查、解析覆盖可见，页面不再维护另一套同义规则 |
| 5：容量收敛 | 按阶段 0 基线完成路由读取与派生工作量优化，修复测出的其它瓶颈 | 混合负载达到明确门槛，优化与完整重建等价，资源上限与积压恢复均有结果 |

阶段 5 的测量与低风险优化可与 1—4 并行，不等功能迁完才关注容量。阶段 1 的新摄入正确与阶段 2 的历史修复分别交付；classifier 不等待账号展示、搜索或 direct。每阶段按可回退的行为范围交付，拆清纯迁移、识别规则改变和性能优化，避免一次大替换让差异无法定位。

## 验收与回退

字段和重建检查使用合成数据，覆盖三模型各异、req 缺失、cost 为零、err 与 err_type 不同、Prompt true/false/省略/非法、最终尝试缺失及全部失败。相同证据集以不同顺序到达，最终的语义投影必须一致；接收时间、执行次数等运行元信息不参与这项一致性断言。请求数量、证据唯一 owner、正文引用和费用观测守恒。复用现有 [magpie 测试](../tests/magpie.test.ts)、[收敛测试](../tests/reconcile.test.ts)、[派生测试](../tests/derive.test.ts)等入口补回归，新增测试以实际共享 Interface 为表面，不为一层转发单独复制整套测试。

语义检查穿过实际解释与派生 Interface，覆盖普通 `<block>no` 反例、Agent 不符、缺回复、迟到 Agent、hook-only、规则优先级、保留旧判定与新规则复核的区别。输入解释测试覆盖合法相似标签、包装里真实文本、插话、畸形和分页；HTML 转义断言继续留在页面测试。

性能优化用同一合成数据分别运行完整重建与优化路径，比对类别、前驱、增量 ord、链角色、标题和工具关联，穿插迟到、合并、回收与重启。保留完整算法作为恢复工具，直至优化路径的等价性有足够覆盖。

上线选择以来源事实修正、历史重建、用途迁移、输入/能力解释和容量优化为独立改动单元。title 迁移先按原有合成结果保持行为；classifier、Agent 门控收紧和包装规则调整分别说明新增行为。每次只保留实际需要的恢复方式，不为这一轮先建永久双管线。

回退围绕代码版本与迁移前备份进行。schema 升级后不能假定旧程序可打开；新增语义也不能通过清空证据或删正文回退。具体命令随实施更新运维文档。本轮不执行真实库回填、服务切换或外部发布。
